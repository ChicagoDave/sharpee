## Decision

### D1 — The language provider is the one word table, and every reader asks it

A language's words — articles, determiners, the actor's possessive, pronouns, self words, all and except words, list separators, name stopwords, number and ordinal words, directions with their abbreviations and opposites, and the manner adverbs — are declared once, in that language's data (`packages/lang-en-us/src/data/words.ts` for English), and reach every reader through `ParserLanguageProvider`. The contract gains the getters it lacks (`getSelfWords`, `getListSeparators`, `getNameStopwords`, `getMannerAdverbs`; `getDeterminers` says whose each possessive is, D6; the all and except words move from literals in the provider into `englishWords`), and loses what nothing calls (`expandAbbreviation`, `getDirectionMappings`, the optional `getArticles`/`getPronouns`/`getAllWords`/`getExceptWords` alternates). The adapter's literal fallbacks are deleted: a provider implements the whole contract or does not compile. No file in `packages/parser-en-us` imports `@sharpee/lang-en-us` as data; the parser reads words from the provider it was constructed with. A structural test pins it: each named list appears in exactly one source file under `packages/*/src`, and `grep` over parser-en-us finds no `from '@sharpee/lang-en-us'` outside its tests. *(Rejected: a new table type in if-domain beside the provider. The plan review's tension and Phase 1 agree: the contract is not missing, it is bypassed, and a second seam for the same words is the duplication this record removes.)*

### D2 — World-model reads the words from the world, which learned them at install

World-model may not import a language package (ADR-385 D1 put the matcher there for that reason). The matcher's self words and `deriveNameVocabulary`'s stopwords are **language words carried by the world**: `WorldModel` gains a `languageWords` value typed in if-domain (`LanguageWords { selfWords, nameStopwords }`, the subset world-model reads; if-domain is already world-model's dependency) which `installStory` sets from the engine's language provider at the seam where it settles the role holder (ADR-344 D6). `namingSurfaceOf(world, entity, observerId)` reads them from the world and `matchNoun` reads them from the surface; `deriveNameVocabulary(name, stopwords)` takes them as a parameter, and world-index passes the compiler's locale words (`STDLIB_MANIFEST.locales[locale]` grows the same two lists). `SELF_WORDS` and `NAME_VOCABULARY_STOPWORDS` are deleted from world-model; `PLAYER_ROLE_ALIASES` is deleted and the player's self aliases come from the same words at install. A world that has not been given its words refuses to derive a name (a thrown error naming `installStory`), never silently matches with an empty list. The words are install-time configuration, not world state: they are not part of a save, and a restore reaches them through the same `installStory` that rebuilt the world, so no save-format field, version or migration is involved (the save format is dormant in any case, ADR-293 as ruled 2026-09-11). *(Q-1 resolved by David, 2026-10-25, session 57820e: "a", put as "design those words language-agnostic and then they get assigned when the engine loads the language model". World-model declares the roles with no words in them — `LanguageWords { selfWords, nameStopwords }` in if-domain — the language fills the shape from its own table, and the engine assigns it to the world when it loads the language, at the install seam. The matcher never knows which language it reads. Rejected: the words on `NounQuery` from every caller, since the validator and the list expander in stdlib hold no language provider today and each site would need one threaded in; a module-level setter in world-model, the process-global state D4 removes.)*

### D3 — The seat questions and parse-failure sentences are the language's

`buildParseError` builds no English. A `CoreParseError` carries `messageId` and `params` (`verb`, `noun`, `slot`) and no `message`. The clarification query renderer (`client-query.ts`) and the command-failed path render the id through the language provider like every other message; lang-en-us owns the twelve sentences as `parser.error.*` templates (the three scope-violation ids already there; `noInput`, `unknownVerb`, `unknownVerb.noVerb`, `missingObject`, `missingObject.noVerb`, `missingIndirect`, `missingIndirect.noVerb`, `entityNotFound`, `entityNotFound.noNoun`, `notUnderstood`). The dead `parserErrors` table and `getParserErrorMessage` are deleted rather than revived; the live templates join the provider's message table. A test pins that `packages/parser-en-us/src` contains no sentence a player reads (a grep for a quote-delimited string ending in `.` or `?`, outside tests and the generated grammar). Wording is kept byte-identical in this record so no Dungeo line moves; a wording change ("Unlock it where?" is odd for a missing indirect) is a content decision David takes separately, not this record's.

### D4 — The pronoun manager and the vocabulary registry belong to the parser instance

`setPronounContextManager`/`getPronounContextManager` and the module-level `let` are deleted. `EnglishParser` owns its `PronounContextManager` and its `VocabularyRegistry` as instance fields constructed in its constructor; the consumers reach both through `SlotConsumerContext` (which gains `pronouns` and `vocabulary`), never through a module. `export const vocabularyRegistry` is deleted from if-domain; the class stays. **The engine's entity registration is deleted, not moved** *(Q-5 resolved by David, 2026-10-25, session 57820e: "delete it")*: no parser logic reads the NOUN tag that `VocabularyManager.updateEntityVocabulary` produced (Phase 1 grep: its only effect is `parseWithErrors`'s unknown-word list, which `allowPartial` already tolerates; entity resolution has been the matcher's since ADR-385), so `engine/src/ports/vocabulary-manager.ts`, the engine's per-turn `updateScopeVocabulary` and the registry's `registerEntity`/`updateEntityScope`/`getInScopeEntities` and their `EntityVocabulary` entries are deleted, and `EngineParser` gains no method. The engine stops importing a registry from stdlib. Phase 6 re-verifies there is no other reader of entity NOUN entries before the deletion lands; if one is found it is reported to David before anything is moved. stdlib's `src/vocabulary/standard-english.ts` and the re-export `src/parser/index.ts` are deleted (the registry was stdlib's only reason to re-export if-domain's parser contracts). Two parsers in one process share nothing: the Phase 1 script becomes a test, and it fails at HEAD and passes after. The parser-en-us tests that `vocabularyRegistry.clear()` in `beforeEach` stop doing so: a fresh parser is a fresh registry.

### D5 — One direction table per language

`getDirections()` is the one direction table: each direction's canonical id (world-model's `Direction` constant), its words and its abbreviations; opposites stay in world-model's `DirectionOpposites` (`src/constants/directions.ts:28`; a world fact, not a word). `directionMap`, `abbreviations`, `englishWords.directions`, `direction-mappings.ts`, stdlib's `standardDirections` and the engine's `extractDirectionValue` copy are deleted; the typed DIRECTION slot, going's direction and the tokenizer's tag all read the provider's table, so **the tokenizer and the slot agree by construction**: a word is a direction everywhere or nowhere. The table's words are what the standard grammar's `directions` blocks accept today (the twelve directions, their abbreviations, `inside`, `outside`), so `upward`, `upwards`, `downward` and `downwards` leave the table rather than join the grammar *(Q-3 resolved by David, 2026-10-25, session 57820e: narrow — "upward and downward are not standard IF direction commands"; a player typing them keeps today's "I don't understand that.")*. The standard grammar's compass list stays written three times (F5 carried, D8); a repokit check that the three blocks are identical is added so they cannot drift meanwhile.

### D6 — The list separators, the possessive and the manner adverbs come from the table

`LIST_CONJUNCTION`, `LIST_COMMA`, `ACTOR_POSSESSIVE` and `MANNER_ADVERBS` are read from the provider (`getListSeparators`, `getMannerAdverbs`, and the determiner table) at parser construction and handed to the consumers through the context. **The possessive is not one word: the determiner table says whose each possessive determiner is** *(Q-4 resolved by David, 2026-10-25, session 57820e: "any 2nd person support would be considered a requirement")*. `getDeterminers()` returns, for each determiner, the person it refers to when it does (`my` first person, `your` second person, `his`/`her`/`its`/`their` third; `this`, `some`, `all` none), and the split marks a phrase `ownedByActor` when its possessive refers to the person the story addresses the actor in — second person being Sharpee's default voice, `your lantern` reads as the actor's own exactly as `my lantern` does. The actor's person comes from `LanguageProvider.getNarrativePerson()` (`if-domain/src/language-provider.ts:97`, today optional and derived from the provider's narrative settings, ADR-089), which the formatter chain already reads for `{You}` and `{your}`; the parser constructed with that provider asks the same method, so the story's voice and the parser's agree by construction, and this record makes the method required on the contract. A third-person possessive (`her key`) stays a determiner that narrows nothing, as ADR-385 D2 pinned. `splitAtSeparators`, `spanText` and the split's structure stay language-neutral. A test pins that a provider with another conjunction changes list parsing with no code edit.

### D7 — "One home" is a structural test, not a convention

A world-model-style readers test (`traversal-readers.test.ts`'s pattern) enumerates, per word list, the one file that declares it and the files allowed to read the provider getter, and fails on any other declaration (a `grep` over `packages/*/src` for each list's words as a literal array or set). It is the floor that keeps the next step from putting a word back.

### D8 — What this record does not change

The matcher's tiers, the gate and its refusals, the validator's resolution, the search, the noun rank and the one ordering (ADR-384, 385, 386) are read, not changed. **F4 and F5 are carried, not taken in** *(Q-2 resolved by David, 2026-10-25, session 57820e: "carry F4, carry F5")*: `EnglishGrammarEngine` and `EnglishPatternCompiler` stay in parser-en-us, word-free after D1 and D6, and Chord's six hard-coded `locales['en-US']` reads wait for a second locale; no Chord construct, diagnostic, EBNF line or `chord-grammar-changes.md` row changes, the typed slot kinds keep no Chord spelling, and a `directions` block keeps lowering to a rule per alias with the compass list written three times and held equal by D5's check. The plan's Phase 7 is abandoned. The Chord parser's and analyzer's author-side word tables (`ARTICLES`, `DIRECTIONS`, `COMPASS_BEARINGS`, `OPPOSITE_DIRECTION`, `ACT_DIRECTION_CANONICAL`) stay where they are, since they read story source, not player input. `parseCardinal` and the number words already live in the language and stay. The IDE and the wire are untouched (D4 adds no port method). Section H items not language or state (`getBestMatch`, `getRulesForAction`, `resolvedText`, the gate's `uniqueIds`) are carried, not this record's.

## Consequences

- One contract answers "what are this language's words" and one world answers "what are my language's words"; no package but a `lang-*` package spells an English word a player types. A second language is a second provider and nothing else.
- **A `lang-*` provider that lacks a getter no longer falls back silently to English literals; it fails to compile.** That is the intended effect. The adapter shrinks to a shape conversion.
- **Rendered text is predicted not to move.** D3 keeps every sentence byte-identical; D5's table holds exactly the words the grammar accepts today and the census found no corpus input using a word that leaves; D4 changes who holds state, not what any single-parser game parses. The implementation measures this on the chain, every tree and Dungeo's unit transcripts at every phase; a line that moves is a defect, and stops for David.
- `SlotConsumerContext` and `EngineParser` change shape; `WorldModel` gains a field; `CoreParseError` loses `message`. Every consumer, the engine's ports, `bridge`, `runtime` and any fixture that builds these by hand fail to compile until updated. No backward compatibility.
- A world constructed outside `installStory` (a bare `new WorldModel()` in a test) must be given its words before it derives a name; the world-model tests that build worlds by hand gain one line. The matcher's own tests pass the words directly.
- The engine's port does not change: entity registration is deleted (D4), so the sidecar's generated protocol is untouched and `./repokit protocol --check` stays fresh with nothing regenerated.
- The multi-user host (the retired Zifmia line's successor, when it comes) gets independent parsers for free; nothing here is built for it beyond the test.
- ADR-385's Consequences ("the world-model module's English words are an interim home") and ADR-386 D9 ("stay where they are until step 7") are fulfilled, not superseded. **Flip ownership:** the close-out phase of the plan that implements this record writes a one-line amendment note under each, pointing here, and the trigger is that plan's implementation landing; neither Status line moves.
- Step 7 closes the parser review. The review, the seven step plans and ADR-383 through this record stay in `docs/work/parser-review/` until David says otherwise.
