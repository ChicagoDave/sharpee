ADR-120 (the plugin tick: after-action phases as an ordered, prioritized list — the one part of the turn whose order is already data), ADR-332 (the `TURN_BANDS` constants and the placement test that pins plugin order — the precedent this ADR extends from the plugin loop to the whole turn), ADR-328 D5 as amended 2026-08-27 (the engine owns the per-turn actor tick). **Related**: ADR-137 (input modes), ADR-172 (sound dispatch), ADR-224 (death detection), ADR-225 (the held command), ADR-293 (determinism at a pinned seed — the regression net every phase of this work relies on), ADR-296 (transaction stamping), ADR-327 D9 (the player-switch drain). ## Context — verified, not assumed

Every line reference below was read this session against `packages/engine/src/game-engine.ts` at `6ad2faeba`.

- **The file is 3015 lines, and the number itself is not the finding.** Four repo files are larger (`chord/analyzer.ts` 8500, `chord/parser.ts` 8434, `story-loader/runtime.ts` 5177, `story-loader/loader.ts` 3091), and a recursive-descent compiler in one file is an ordinary shape. A *coordinator* at this size is a different signal: it grows by absorbing responsibilities, not by covering more grammar. The next-largest engine module is `command-executor.ts` at 722 lines.
- **`executeTurn` is one method of 426 lines** (`1082-1508`) running roughly twenty-five sequential phases: command chaining, the held-command splice (ADR-225, GH #318), the exchange offer (GH #346), the undo snapshot, debug events, the input-mode branch (ADR-137), the meta-command early exit, execution, transaction stamping (ADR-296 D1), enrichment and perception, event storage, command history, pronoun context (ADR-089), the refusal referent (GH #97), emission, the victory check, the plugin tick (ADR-120), sound fan-out (ADR-172 Phase 6), context and statistics, the player-switch drain (ADR-327 D9), platform operations, the prose pipeline, the prompt block, the channel packet (ADR-163), death detection (ADR-224), clearing, completion, and loss routing. **The ordering is the contract and it is carried entirely by comments**: "before text service", "after the plugin tick so…", "*before* the turn's events are cleared below" (`1426-1431`, `1447-1450`). Adding a phase means reading the whole method to find its slot; ADR-327 D9's drain (`1413-1420`) is the most recent instance.
- **Seven ADRs are cited inside that one method.** Under DevArch rule 7 (one reason to change) the file has one reason per turn-cycle ADR. Since June 2026 it has taken 35 commits.
- **The turn has three copies of the platform-operation dispatch and a fourth that is dead.** `processMetaPlatformOperation` (`1691-1806`, the switch at `1694`) switches on `PlatformEventType` for six operations; `processPlatformOperations` (`2656-2897`) switches on the same six, twice (the operation at `2673`, the error mapping at `2860`). Its own header says so: *"This is similar to processPlatformOperations but handles one operation at a time"* (`1687-1688`). Meanwhile `PlatformOperationHandler` — extracted from this class on 2026-01-16 (`2d0468c1d`, "Phase 4 extract services from GameEngine", 2010 → 1583 lines) — is imported (`88`) and declared as the field `platformOpHandler?` (`238`) and is **never constructed and never called**. It also lacks the `AGAIN` case the inline switches carry, so it has drifted as well as died.
- **The same happened to `TurnEventProcessor`.** It is constructed at `352` ("Initialize extracted services (Phase 4 remediation)") and never called; only its standalone `processEvent` function is live, in two separate enrichment funnels (`1240-1252` for the player's events, `2419-2428` for plugin events). Two tests import `processEvent` directly (`adr-296-transaction-stamping.test.ts`, `presence-tagging.test.ts`); `scene-evaluation-plugin.ts` names the module only in a comment (`:43`) and imports nothing from it. The class is exported from `index.ts:49` and has no consumer.
- **So the January extraction did not hold.** The services were written, exported, and left beside the inline paths, which stayed live and kept growing: the file has since nearly doubled (1583 → 3015). An extraction that leaves the original path in place is not a boundary (DevArch rule 8); it is a second copy. Any decision here has to say what stops that from recurring, or it is the January decision again.
- **What is already right and stays.** `command-executor.ts` owns the four-phase run for player and actor alike (ADR-328 D1/D2); `save-restore-service.ts` owns snapshots and serialization and is genuinely used (`2351-2482`); `engine-random-service.ts` owns the seed (ADR-293); the plugin tick (`1330-1367`) is already an ordered list. ADR-332 made that list's order explicit as `TURN_BANDS` with a placement test. The engine is already a facade over services where the extraction was completed; the turn body is where it was not.
- **The two-sided obligation.** Core-concepts says a `packages/` change that serves only "the platform's own internal tidiness while the seam stays where it was" is "a change to question." The seam this touches is the one between the story runtime and the turn: ADR-332 was an argument about *where in the turn* the story's reactions run, ADR-327 D9 about *where* the player switch lands, ADR-325's timers about *when* their prose is spoken. Today those questions are answered by reading 426 lines of prose comments. A named, ordered stage list is something an ADR, a plan, and the loader can point at by name. That is the seam becoming simpler; it is not tidiness alone.
- **The regression net is unusually strong.** The Dungeo walkthrough chain (952 assertions) and the Secret Letter test tree (1468 cards, 2642 assertions) are byte-deterministic at their pinned seeds: `CLAUDE.md` records the check ("verified 3× byte-identical 2026-08-02", under ADR-293 Phase D's retirement of the run-twice habit) — recorded there, not re-run for this ADR; AC-4's before/after comparison is the check that re-establishes it at each phase, and the first phase's comparison is where a false premise would surface. A behavior-preserving refactor that changes one character of output is caught on the first run. The engine unit suite is 708 passing, 7 skipped, 73 files (`pnpm --filter '@sharpee/engine' test`, 2026-09-07); 23 of its test files drive `executeTurn` (`grep -rl executeTurn packages/engine/tests`).

## Decision

- **D1 — The turn is an ordered list of named stages, and `executeTurn` is the runner.** `packages/engine/src/turn/` holds one module per stage, each with one reason to change and its own header. A single exported constant, `TURN_STAGES`, names them in order; `executeTurn` builds the stage context for the input and runs the list. The context is a typed `TurnStageContext` carrying what the phases share today as locals and fields: the input, the turn number, the `TurnResult` under construction, the enriched events, the sound buffer, the engine's services. A stage is `{ readonly name: string; run(context: TurnStageContext): Promise<StageOutcome> }` where `StageOutcome` is `'continue' | 'stop'`. `'stop'` ends the list with the result as it stands (the input-mode branch, a failed statement in a chain); no stage `return`s from the middle of a 400-line method. The parse stage is the one exception to a plain outcome: it sets `context.route` to `'turn' | 'meta'` from the `MetaCommandRegistry` verdict, and the runner selects `TURN_STAGES` or `META_STAGES` on it before continuing (D1a). No other stage reads or writes `route` (folded from `adr-review` 2026-09-07, David: "yes"). The ordering comments become the stage list itself, and the prose that explained *why* an order holds moves into the stage headers, where it stays next to what it constrains.
- **D1a — Two lists, shared stages (resolved Q-1, David, 2026-09-07: "b").** A meta command (VERSION, SCORE, SAVE, UNDO — the `MetaCommandRegistry` set) runs `META_STAGES`, a shorter list that shares stage modules with `TURN_STAGES` (parse, platform operations, prose rendering, the channel packet) and omits the turn counter, the plugin tick, the actor phase, sound dispatch, and death detection. The parse stage is where the two paths part: it is the first stage of both lists, and the runner picks the list from the `route` it sets (D1). "A meta command never touches turn machinery" is therefore readable as the absence of those stages from `META_STAGES`, and D2's test pins both lists. `executeMetaCommand` (`1508-1662`) dissolves into that second list.
- **D2 — The order is pinned by a test, in the shape ADR-332 already uses.** `packages/engine/tests/unit/turn-stage-order.test.ts` asserts the stage names in `TURN_STAGES` and in `META_STAGES` in order, drives one regular turn and one meta command, and asserts every stage of the chosen list ran exactly once and no stage of the other list's exclusive set ran at all. Reordering, removing, or bypassing a stage fails by name. This is the invariant (DevArch rule 6) that January lacked: a phase re-inlined into the runner around the list would not run the stage, and the test would say which one. **It is the whole guard (resolved Q-3, David, 2026-09-07: "a")**: no line-count assertion on `game-engine.ts`, local or otherwise. The January failure was logic living in two places with nothing asserting which was live, not a size problem; a line budget would flag the symptom without naming the cause and invite moving lines to satisfy a number. Size is reviewed by eye, which is how this ADR came to be written.
- **D3 — One platform-operation dispatcher.** The three inline `PlatformEventType` switches and the dead `PlatformOperationHandler` collapse into a single module owning all six operations (`AGAIN` included), with one completion-event mapping and one error mapping. The meta-command path and the turn path call the same dispatcher with the same contract; the difference between "one operation, return its completion events" and "drain the pending list" is a parameter, not a second copy. Whether that module is the existing `platform-operations.ts` brought up to date or a fresh one that replaces it is an implementation choice; what is decided is that afterward exactly one `switch` on `PlatformEventType` exists under `packages/engine/src`. **As built (2026-09-09, session a76673)**: `platform-operations.ts` was rewritten in place. `dispatchPlatformOperations(operations, host, deliver)` runs the one switch (`runPlatformOperation`) per request and hands every completion event to `deliver` at the point the inline paths emitted it — the restart acknowledgment before `stop('restart')`, the quit confirmation after `stop('quit')` — so a turn's event order is unchanged; the meta path passes `[op]` and collects into its result, the turn path passes the drained pending list and delivers to the event source, the turn's list, and the emitter. The list is the parameter. The engine's two private methods keep their names as the two callers (the existing platform test reaches them by name). `PlatformOperationHost` is what an operation needs (hooks read through a getter, so a dispatch sees the hooks registered when each request runs — the dead handler had captured them at construction), and `platformOperationFailure` is the one error mapping as a lookup table keyed by request type, so no second `switch` exists. Three paths' behavior converged on the turn path's, which was the fuller one: a quit, restart, or undo hook that throws on the meta path now yields that operation's failure event instead of escaping to `command.failed`; the meta path's save/restore failures now also log the error; and the restore-without-data message is the meta path's `'No save data available'` on both (the turn path's longer variant retired). None of the six is reachable from any gate transcript, and the paired test pins both paths equal per operation.
- **D4 — One enrichment funnel; the dead class goes.** The two `processEvent` funnels (`1240-1252`, `2419-2428`) become one stage-level function taking the source (player action or plugin) as a parameter. The unused `TurnEventProcessor` class and its factory are removed from `turn-event-processor.ts` and from `index.ts`; the standalone `processEvent` the two tests import stays. No backward compatibility is owed to an export nothing consumes. **As built (2026-09-09, session a76673)**: `enrichTurnEvents(events, source, enrichment)` in `turn-event-processor.ts` is the funnel; `TurnEventSource` is `{ kind: 'action' } | { kind: 'plugin'; pluginId }` and `transactionIdFor` derives the stamp from it. The engine's private `enrichTurnEvents(events, turn, locationId, source)` assembles the turn's context (player, location, presence resolver, perception) once for both callers; the plugin funnel keeps passing the location the tick computed before the loop, the action funnel reads it live, as before. The class, its factory, and the `EnrichmentContext`/`ProcessedEventsResult`/callback types only it used are gone; `EventProcessingContext` and `processEvent` stay. One consumer the Context missed: `packages/sharpee/src/runtime-surface.ts` re-exported `TurnEventProcessor` to the `runtime` and `bridge` transports (never constructed there either) — the one edit outside this ADR's scope, the re-export line removed.
- **D5 — The facade does not move.** `GameEngine` remains the public class; every public method, every constructor option, and every `register*`/`get*` accessor keeps its name and signature. The seventeen files that construct `new GameEngine` compile without edit, and the generated API reference (`packages/sharpee/docs/genai-api/engine.md`) shows no removed public member. Lifecycle (`constructor` `256-404`, `setStory` `404-585`, `start` `742-849`, `stop`, `resume`) is *not* decomposed by this ADR (resolved Q-2, David, 2026-09-07: "a"): assembly and story installation have one reason to change, run once, and are not where the turn-cycle ADRs have been landing. They stay in the facade. If that later proves wrong, it is an amendment to this ADR, not a reason to widen a refactor whose safety argument is small byte-identical steps.
- **D6 — Every phase lands byte-identical.** The work is cut into phases each of which ends with the Dungeo chain and the Secret Letter tree byte-identical to the run before it (one run each, ADR-293 Phase D) and the engine suite at 708 passing or higher. A phase that changes one byte of rendered output has either found a bug or made a content decision; either way it stops and is its own conversation (a platform default that changes a story's text is never buried in a refactor). Order of phases: D3 and D4 first (they delete duplicates and are the smallest diffs), then D1 stage by stage from the ends of the method inward, D2 landing with the first extracted stage.
- **D7 — Not on this branch, not now.** This is discuss-first `packages/` work (CLAUDE.md) with its own plan on `main`, after the Secret Letter port's plan closes (Phase 9 of `docs/work/secret-letter-port-platform-defects/plan.md`). The port branch carries forty-odd uncommitted files and a CURRENT phase; a structural refactor of the turn runner does not ride beside it.

## Consequences

- A future turn-cycle ADR names the stage it adds and the stage it follows, and the plan phase that lands it edits one module plus one line in `TURN_STAGES`. The 426-line read to find a slot ends.
- `game-engine.ts` shrinks to the facade and the lifecycle — the constructor, `setStory`, `start`/`stop`/`resume`, the accessors and registrations, and a runner-shaped `executeTurn` — and stays the largest engine module by design (D5). No line budget exists (D2); the expected size is the consequence, not the goal.
- The plugin tick stays a plugin tick. ADR-120's priorities and ADR-332's bands are untouched; the loop becomes one stage among the others, and plugins remain plugins rather than becoming stages.
- `turn-event-processor.ts` and `platform-operations.ts` stop being the repository's example of an extraction that was never wired. If a later reader finds a field on `GameEngine` that is assigned and never read, D2's test is the place to look for what should have been consuming it.
- The story runtime (`story-loader`) is unaffected in code and gains a vocabulary: "before the actor stage", "after platform operations" become names it can cite. Nothing in this ADR obliges it to.

## Acceptance

- **AC-1 (order pinned)**: `TURN_STAGES` and `META_STAGES` exist and `turn-stage-order.test.ts` names every stage of each in order; moving one entry makes the test fail naming that stage; a regular turn (`take lamp` in a two-room fixture story) runs every `TURN_STAGES` stage exactly once, and `score` runs every `META_STAGES` stage exactly once and none of the turn-only stages (turn counter, plugin tick, actor phase, sound dispatch, death detection).
- **AC-2 (one dispatcher)**: `grep -rn 'switch (.*PlatformEventType\|case PlatformEventType' packages/engine/src` reports one module. `save`, `restore`, `quit`, `restart`, `undo`, and `again` each produce the same completion or failure event from the meta path and from the turn path (six paired assertions).
- **AC-3 (no dead twins)**: `GameEngine` has no `platformOpHandler` and no `turnEventProcessor` field; `TurnEventProcessor` and `createTurnEventProcessor` are not exported from `@sharpee/engine`; `processEvent` still is and the two tests that import it still pass.
- **AC-4 (byte-identical)**: after each phase, `node dist/cli/sharpee.js --test --chain stories/dungeo/walkthroughs/wt-*.transcript` and `./sharpee test branch-stories/secret-letter --tree` report the same pass counts and byte-identical captured output as the run before the phase (evidence inline in the plan: command, count, date).
- **AC-5 (facade unchanged)**: `./repokit build dungeo` regenerates `packages/sharpee/docs/genai-api/engine.md` with no removed or renamed public member of `GameEngine`; the seventeen `new GameEngine` call sites are untouched in the diff.
- **AC-6 (runner-shaped)**: `executeTurn` contains no phase logic — it constructs the context, runs `TURN_STAGES`, and returns the result; every ordering comment it carried today is either gone or lives in a stage header.
