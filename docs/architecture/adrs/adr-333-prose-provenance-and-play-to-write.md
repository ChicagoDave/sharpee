# ADR-333: Prose provenance — every rendered block names the message that wrote it, and Play edits the phrase in place

**Status**: ACCEPTED (David, 2026-09-05, session e0ba74 — "Yes" after the open questions interview resolved Q-1/Q-2/Q-3 (a, a, a) and `adr-review` returned 19/19 with four corrections folded: the ADR-106 citation, the ADR-255 file, the scope header, and D1a's mechanism rewritten against `room.ts:101-110` and `identityTrait.ts:35`. Written the same day from David's direction: "a web client that plays normal, but allows the author to plug in text as you step through a complete walkthrough that includes examine and non-movement commands"; the standalone web client was declined — "I don't need the mobile version (yet)" — so the consumer is Chord Writer's Play panel and nothing else. Not implemented.)

**Scope**: `packages/text-blocks` (the block field); `packages/engine` (the stamp in `prose-pipeline/phrase-render.ts`, and the description handlers' stamp under D1a); `packages/story-loader` (sets `descriptionId`, D1a); `packages/stdlib` (the examining data builder carries the id, D1a); `packages/channel-service` and `packages/platform-browser` (carry and expose it); `tools/ide/SharpeeIDE/Play` (the consumer). No Chord change.

## Parent

ADR-174 (the engine-internal prose pipeline and the `ITextBlock` wire), ADR-106 (domain events carry `messageId` and `params` for rendering — `adr-106-domain-events-and-event-sourcing.md:125-136`), ADR-163 (channels are the one story→UI surface), ADR-210 (the direction rule: the engine never learns Chord's IR shapes), ADR-293 (determinism at a pinned seed) and ADR-305 D1 (the IDE's fixed play seed), ADR-294 D13–D16 (testing intelligence as an author-facing surface). ## Context — verified, not assumed

- **A Chord `phrase` statement reaches the pipeline as a `chord.phrase` event whose `messageId` is the phrase key** (`packages/story-loader/src/runtime.ts:4833`, `rawEvent('chord.phrase', { messageId, params })`). The loader registers every phrase key in the IR with the language provider through `addMessage(key, template)` (`loader.ts:1005-1017`). The pipeline routes on `messageId` first (ADR-106; `pipeline.ts:291-315` — the code comment there says "ADR-097", which is the React client ADR; the messageId contract is ADR-106's), and `renderViaPhrase(context, messageId, params, blockKey)` realizes the blocks and re-keys them to the channel (`phrase-render.ts:88-150`). **At the moment a block is made, the pipeline knows the message id; it drops it.**
- **The wire block has no provenance.** `ITextBlock` is `key`, `content`, `tight?`, `className?` (`packages/text-blocks/src/types.ts:117-147`). The only `phraseId` anywhere in the loader is the banded-scalar rung lookup for scoring and hunger (`loader.ts:1178`, `1296`), which never reaches a block. The IDE's `Play/SourceMap.swift` maps JavaScript stack frames to story source for error symbolication; it knows nothing about prose.
- **The IR keeps spans, with the fragment file.** `IRPhrase.span` (`packages/chord/src/ir.ts:965-990`) is a `Span` whose `file` names the imported fragment relative to the main file and is absent for the main file (`span.ts:14-31`, ADR-251 D6 as amended 2026-08-22). The IDE already indexes the IR's phrases (`tools/ide/SharpeeIDE/Compose/StoryIndex.swift`, `World/WorldIndexDocument.swift`). So a message id is enough for the IDE to find the line an author has to edit; the engine never needs the span.
- **Replay is free.** Every play boot in the IDE is deterministic at a fixed seed (ADR-305 D1, `PlayViewController.swift:29-31`, injected as `__SHARPEE_PLAY_SEED__`), and runs are byte-identical at a pinned seed (ADR-293 Phase D). "Edit a line and be back at this turn" is restart plus re-sending the command history.
- **The browser prose renderer reads block fields by name** (`packages/platform-browser/src/channels/prose.ts:164-169`, `243-256`): `tight` and `className` become classes on the `<p class="main-entry">`; an unknown field is dropped at the entry parse, not passed through. So the renderer is a two-line change, not a free ride.
- **Descriptions already have an id mode the loader never uses.** ADR-107 lets an entity carry literal text OR a message id; `IdentityTrait.descriptionId` exists (`packages/world-model/src/traits/identity/identityTrait.ts:35`), the looking data builder carries it (`stdlib/src/actions/standard/looking/looking-data.ts:65`), and the room handler resolves it through the language provider before falling back to the literal text (`engine/src/prose-pipeline/handlers/room.ts:101-110`). The loader never sets it (`grep descriptionId loader.ts` → nothing): it writes the literal text and registers the same phrase under the entity's key. The examining handler has no id path at all (only `room.ts` references `descriptionId` under `handlers/`). ADR-209 snippets are already resolved at render time by id (`room.ts:117-131`, `resolveSnippetDescription`), so a spliced snippet's key is in hand when the block is made.
- **What today's stand-in does.** The session's missing-lines page finds where a stub prints by string-matching its `(TODO during play-testing — …)` body against captured tree output (`./sharpee test … --json --capture-output`; 96 of 126 stubs reached). That works only because stubs print their own name. Finished text cannot be matched that way, so "click this paragraph and edit it" is impossible without the stamp.
- **The two-sided obligation** (core-concepts, "Where the work is"): the language can already say everything here; the platform is what cannot say where its own prose came from. The fix is platform-side, and it makes the seam simpler for the IDE, the branch-tester, and any future client alike.

## Decision

- **D1 — Every block the phrase path realizes carries its message id.** `ITextBlock` gains an optional, additive `source?: { messageId: string }`. `renderViaPhrase` stamps it on every block it returns (`phrase-render.ts:150`, the re-key map), whether the template came from the registry or from a phrasebook resolution (ADR-250 D4 — the book wins the text; the id is still the key the event named). Blocks made by `createBlocks` from inline fallback text (`data.message` / `data.text`, no registered id) carry no `source`: absence means "not a message", never "unknown".
- **D1a — Descriptions are stamped with the entity's key, through ADR-107's id mode (resolved Q-1, David, 2026-09-05: "A").** The loader sets `IdentityTrait.descriptionId` (and the room trait's initial-description id) to the entity's registered description key instead of copying the literal text onto the trait; the room handler already resolves that id (`room.ts:101-110`) and the examining handler gains the same id path, with the data builder carrying `descriptionId` as looking's does. Each description handler sets `source.messageId` on the block it realizes to that key — overriding the platform message id `renderViaPhrase` would otherwise stamp (D1), because the author's phrase is the thing a click should open. `detail` and `first time` texts ride the same rule under their own registered keys. A snippet spliced at a marker (`{commerce-street-by-night}`) is resolved by id at render already (`room.ts:117-131`); its key is not carried in v1 — `source.contributors[]` is a later, additive extension if Play-to-write needs to open the snippet rather than its host. In the Secret Letter port today this brings the seven entity-text stubs (five descriptions, one `detail`, one `first time`) under D4 alongside the 119 phrase and timer stubs.
- **D2 — The id is the whole stamp; spans are the consumer's.** The wire carries `messageId` and nothing else. A consumer that holds the IR (Chord Writer) resolves it to `IRPhrase.span` — file, line, column; one that holds only a language pack (a stdlib message such as `if.action.taken.success`) resolves it to that pack, or to the story's ADR-255 `messageOverrides` entry (`adr-255-message-override-acl.md`; the same-numbered `adr-255-alias-catalog.md` is its appendix) when one exists. This keeps ADR-210's direction rule intact (the engine registers templates, never spans) and keeps the wire data-only (ADR-163; no paths, no line numbers, nothing a client could mistake for a link).
- **D3 — Channels carry it unchanged; the browser renderer exposes it.** `channel-service` passes `ITextBlock[]` through as-is (`channel-service.ts:63`, `140`), so the packet needs no change. `platform-browser`'s prose channel keeps `source` at the entry parse (`prose.ts:243-256`) and the renderer sets `data-message-id` on the paragraph (`prose.ts:164-169`). This is a DOM attribute, not a wire decoration; ADR-174's decoration model (span + class, `sharpee-` prefix) is untouched.
- **D4 — Play-to-write in Chord Writer's Play panel.** With D3 in place, every paragraph in Play is addressable. Clicking one opens the phrase it came from in the editor at its span (D2), with the block it lives in and its firing clause beside it — the same context the missing-lines page shows. Saving reconciles the file (ADR-309's write path), recompiles, restarts at the fixed seed (ADR-305 D1), replays the command history, and re-renders the turn with the new text in place. Variations are arms of the same phrase; the editor offers `randomly` / `cycling` when a second arm is added, in Chord's own words, and the author decides.
- **D4a — A platform line is editable too, through an override (resolved Q-2, David, 2026-09-05: "a").** When the clicked block's `source.messageId` is a platform id (`if.action.*` and the rest of the language pack) that the story has not overridden, Play opens a new ADR-255 (`adr-255-message-override-acl.md`) `messageOverrides` entry in the story, pre-filled with the pack's current text for that id, and saving it is the same reconcile → recompile → replay as D4. If the story already overrides it, the click opens that entry. Every paragraph in Play is therefore addressable, story's or platform's; the story-side artifact is the one ADR-255 already defines, and nothing new is invented for it.
- **D4b — The replay history is session-only (resolved Q-3, David, 2026-09-05: "a").** Play keeps the command history for as long as the IDE is open; a relaunch starts fresh. The durable record of a walkthrough is the test tree (D5), which the Testing tab re-enters at any card, and a free-play session worth keeping is blessed into a transcript by ADR-300's existing path. Play writes no history sidecar.
- **D5 — The walkthrough is the test tree.** Stepping "through a complete walkthrough that includes examine and non-movement commands" is stepping through a root-to-leaf path of `<story>.tests.json` (ADR-307): the Testing tab already owns those paths, and the same replay drives them. Play-to-write adds no second walkthrough format. Free play off the path stays free play; blessing a turn is ADR-300's, not this ADR's.
- **D6 — Stubs are a special case only in the IDE's eyes.** A `(TODO during play-testing — …)` body is ordinary phrase text to the platform; the IDE may recognise the marker and list every stub the current path has printed so the author can work through them in play order. The marker's spelling is not a platform contract and is not stamped.

## Consequences

- D1a is the one non-trivial platform change: the loader writes ids where it wrote text, the examining handler and its data builder gain the id path the room already has, and both handlers stamp the block. ADR-107 is used, not superseded — its id mode was always the intended shape and the loader simply never took it. Discuss-first `packages/` work (CLAUDE.md) with its own plan phase; D1's stamp can land ahead of it.
- The stamp is one additive field and one line in the pipeline; every existing golden recording and assertion transcript is unaffected because `--capture-output` and the canonical serializer (ADR-300) read block text, not block fields — to be confirmed under AC-3 rather than assumed.
- `branch-tester` and the Testing tab gain provenance for free: a failing assertion can name the phrase that printed the offending line, which is ADR-294 D18's "drop you at the divergence" one step sharper.
- The session's missing-lines artifact remains a phone-side capture until D4 ships; its entries are folded into the `.chord` files by hand. It is not a second client and does not become one.
- The IDE decoder follows IR fields (project memory): the IDE's phrase index reads `IRPhrase.span`; a rename there breaks D2 silently, so the Play-to-write test in AC-4 must fail loudly on it.

## Acceptance

- **AC-1 (stamp)**: after `eat apple` in the Secret Letter test tree at its pinned seed, the block whose text begins `(TODO during play-testing — The first bite` carries `source.messageId === 'apple-first-bite'` (or the loader's registered key for that phrase — the test reads the key the loader registered, not a guess). A block produced from inline fallback text carries no `source`.
- **AC-2 (wire and DOM)**: the same turn rendered by `platform-browser` yields `<p class="main-entry" data-message-id="…">` for that paragraph and no attribute for a fallback block.
- **AC-2a (descriptions)**: the block that prints Commerce Street's first-time text carries the room's registered first-time key, and `x dress` in the silk tent yields a block carrying the dress's description key (both keys read from the loader's registration at test time); `IdentityTrait.descriptionId` is set and the literal `description` string is absent for a Chord-loaded entity.
- **AC-2b (platform line)**: clicking the `Taken.` paragraph after `take apple` in a story with no override opens a new `messageOverrides` entry for `if.action.taking.success` (the id the pack registers, read at test time) pre-filled with the pack's text; saving it changes the paragraph on replay.
- **AC-3 (no drift)**: `./sharpee test branch-stories/secret-letter` and the Dungeo walkthrough chain are byte-identical before and after the stamp (one run each; ADR-293 Phase D).
- **AC-4 (play-to-write)**: in Chord Writer, click that paragraph → the editor opens `grubbers-market.chord` at the phrase's span; change the text, save → Play shows the same turn with the new text, the command history replayed, the seed unchanged. Delete the `span` field from the IDE's phrase index → the test fails by name.
- **AC-5 (walkthrough)**: from the Testing tab, "play this path" on a root-to-leaf path steps Play through every card, examines included, and each printed stub is listed with its message id.
