## Context — verified, not assumed

Every line reference below was read this session against `packages/chord/src/` and `packages/story-loader/src/` at `6ad2faeba`.

- **Two files are the compiler.** `analyzer.ts` is 8500 lines, of which class `Analyzer` (`744-8500`) is 7503 lines across 124 methods, with 27 top-level helpers; `parser.ts` is 8434, of which class `Parser` (`377-8434`) is 8068 lines across 152 methods. Since January 2026 the analyzer grew from 740 lines to 8500 and the parser from 1375 to 8434; since June they took 80 and 67 commits. Both are already sectioned by rulers — eleven in the analyzer (`2725` Phase B declarations, `3094` pass 1, `3635` state-set gates, `4196` entities, `6070` statements, `6623` acting statements, `6965` values, `7461` timers, `7820` conditions, `8233` phrases, `8382` suggestions), thirteen in the parser (`393` file … `8013` conditions). The suite is 78 files, 1158 passing (`pnpm --filter '@sharpee/chord' test`, 2026-09-07).
- **What stays.** A recursive-descent parser in one class, proportional to a 29-statement grammar, is a conventional shape, and its methods genuinely share the cursor and position state; `parseStatement` (`6954`, 515 lines) dispatches on the leading keyword (`switch (word)`, `6972`) with an error default, which is correct for a keyword dispatcher. The stdlib and character manifests are generated by `repokit manifest` with a freshness gate (`stdlib-manifest.ts:1-5`, ADR-276 D2). The EBNF is mirrored to the website by `website/scripts/sync-chord-ebnf.mjs` and byte-identical today. The AST (171 exported types) and IR (89) are two families by design: one carries spans, the other is data. The 629 distinct diagnostic codes (353 parser, 276 analyzer) live as inline strings with no catalog, but the IDE never switches on a code (`grep` of `tools/ide/SharpeeIDE` for `"parse.`/`"analysis.` → 0) and tests pin them by name, so they are not a wire contract and are not a target here.
- **Six switches on `stmt.kind`, none exhaustive.** The AST `Statement` union has 29 members (`ast.ts:1883-1913`); `IRStatement` has 23 (`ir.ts`). Every kind is handled by six switches on `stmt.kind`: `checkConversationTargets` (`analyzer.ts:2451`, `default: break`), `collectInlineTexts` (`3595`, `default: break`), `checkPhaseOrder` (`5974`, a default that records the statement as "ended"), `resolveStatement` (`6187`, **no default**), the runtime's `execStatements` (`runtime.ts:4168`, **no default**), and the select-id collector (`select-ids.ts:43`, `default: break`). There is no `never` assertion in the analyzer, the parser, or the runtime (`grep -c 'assertNever\|: never'` → 0, 0, 0). So a statement kind added to the union and missed in one switch is silently ignored at that stage: the analyzer's phase-order check would not see it, the runtime would not execute it, the select collector would not count it. Last night's `WearStmt` (ADR-325 W1, session 0e7d6f) was added to this union and threaded through by hand; nothing but the author's care checked that every switch learned about it.
- **`buildEntity` is the analyzer's `executeTurn`.** One method, `4900-5819` (920 lines), with 103 `if` branches and 26 loops, handles every line kind an entity block can carry. Its internal comments are a list of the ADRs that added branches: ADR-327 D10 `playable` (`4904`), ADR-231 D5a `starts` pairing (`5012`), ADR-242 D1 `proper` (`5033`), ADR-242 D5 `pronouns` (`5050`), ADR-310 D3/D14 `mood`/`feels`/`knows`/`thinks` (`5079`), ADR-327 D10 player-block composition (`5603`), ADR-234 D3 door location (`5609`), ADR-236 D1/D2 region membership (`5620`, `5640`), ADR-325 D5 `landing` (`5631`), `first time` prose (`5650`), ADR-289 D6 exits (`5661`). Each entity-block feature lands as a branch in the same method, and finding where a new line kind belongs means reading the whole method — the ADR-334 Context finding, in the compiler.
- **Pass order is carried by prose.** `Analyzer.run` (`904-1244`, 340 lines) calls 45 distinct passes in code order, with their dependencies stated as comments: "fact-value sets and named profiles build before entities" (`968-970`), "claims tags check against the built fact table" (`975`), "timers resolve their owners against the entity table" (`979`), "gates resolve once timers are known" (`981-982`), "chapters resolve their triggers against entities, timers, and states" (`984`). GH #359 (closed 2026-09-07, session 0e7d6f) was a pass-order defect of exactly this kind: `phrase detail while <timer read>` gates were resolved inside `collect()` in pass 1, before `buildTimers()`, and failed as `analysis.unknown-timer`; the fix added `resolveOverrideGates()` after `buildTimers()` (`981-983`) — one more line in the prose-ordered list. The ordering is real and load-bearing; it is stated nowhere a test can read.
- **The analyzer's sections share a real core.** Unlike `ChordRuntime` (ADR-335: near-zero fan-in between sections), the analyzer's internal call graph has genuine hubs: `suggestText` (29 internal callers), `resolveEntityId` (17), `resolveStatement` (13), `resolveCondition` (13), `checkPhaseOrder` (8), `resolveValue` (7). A split of the analyzer into section modules is therefore a core-plus-sections design with a designed core, not a mechanical move — which is why it is deferred (D4), not decided.
- **The regression net.** The chord suite (1158 passing) and the story-loader suite (1118 passing, 2026-09-07) both compile the Chord test corpus; the three Chord test trees (`secret-letter`, `fernhill`, `ides-of-march`) are byte-deterministic at their pinned seeds (recorded in `CLAUDE.md` under ADR-293 Phase D; re-established by AC-4 at each phase). The IR is pure JSON (`analyzer.ts` header invariant), so a phase can also assert the compiled IR of every corpus story is byte-identical before and after — a sharper net than rendered output, and free.

## Decision

- **D1 — Every `stmt.kind` switch is exhaustive.** Each of the six switches gains a `default` that assigns the narrowed statement to a `never`-typed binding (`const unhandled: never = stmt; throw new Error(...)` — the standard TypeScript exhaustiveness idiom; the throw is unreachable at runtime and exists so the compiler proves it). Where a switch today deliberately ignores kinds (`default: break` in `checkConversationTargets`, `collectInlineTexts`, `select-ids`), the ignored kinds are listed as explicit `case` labels falling through to `break`, so "ignored" is a decision the reader can see rather than an omission. Adding a kind to `Statement` or `IRStatement` then fails to compile until every switch has decided what to do with it. The parser's keyword switch is untouched (it dispatches on words, not kinds, and its error default is correct). This lands first: it is the smallest change in the survey, changes no output, and turns a class of silent omission into a compile error.
- **D2 — `buildEntity` becomes one builder per entity-block line kind.** `packages/chord/src/analyzer/entity/` holds one module per line kind the block accepts (the keyword families the parser already produces: role and player lines, `starts`, `proper`/`pronouns`, the ADR-310 character lines, placement — door pair, region membership, `landing`, `containing` — `first time`, exits, and the rest), each a function `(decl, entity, context) => void` that reads the parsed lines it owns and writes its slice of the `IREntity`. `buildEntity` becomes the runner: it creates the `IREntity`, calls the builders in a declared order (`ENTITY_LINE_BUILDERS`), and returns it. **Builders are keyed by keyword family (resolved Q-1, David, 2026-09-07: "a")** — placement, character lines, role lines, prose lines, exits, and the rest as the parser already groups them — because the parser produces lines by keyword, so that is the seam the data has; the ADR that added each line kind stays in the builder's header comment, not in the module boundary. The gates that span line kinds (ADR-327 D10's player-block composition, ADR-231 D5a's `starts` pairing) are builders too, placed after the lines they read. The order is pinned by a test as in D3.
  - **As built (2026-09-08, session 56bc75, survey Phase 10)**: fourteen builders under `analyzer/entity/`, in the order the method reported its diagnostics — `playable`, `compositions`, `starts`, `identity` (`proper`/`pronouns`), `character-host` (the person-only gate over all fourteen character line kinds), `character-lines` (ADR-310), `normative-lines` (ADR-318), `host-gates` (which lines a block's kind admits: door/region placement, `landing`, `containing`, `first time`, exits), `placement`, `exits`, `states`, `counters`, `prose`, `clauses`. Builders write to an `EntityDraft`, and `assembleEntity` produces the wire entity — the one place the IR entity's key order is written, which is what keeps the compiled JSON byte-identical while builders run in diagnostic order. `buildEntity` is four lines: create the draft, run `ENTITY_LINE_BUILDERS`, assemble. Builders resolve through an `EntityBuildContext` of delegations the analyzer builds once, so its helpers stay private. `requires` and a traced corpus compile pin the order as in D3.
- **D3 — The pass list is data.** `Analyzer.run`'s 45 calls become an exported ordered constant, `ANALYSIS_PASSES`, each entry a name and the method it runs; `run` iterates it. The dependency comments move onto the entries as a `requires` list naming earlier passes (`resolveOverrideGates` requires `buildTimers`; `buildChapters` requires `buildEntity`, `buildTimers`; …), and a test asserts (a) the list order satisfies every `requires`, and (b) one compile of the corpus runs every pass exactly once in list order. GH #359's class of defect — a pass that reads a table before the pass that builds it — becomes a failing test naming both passes. Passes that run conditionally today (`reportScoringGate` when `scoreDecls` is non-empty, `buildHunger` spread in only when present) keep their condition inside the pass; the list is unconditional.
  - **As built (2026-09-08, session 56bc75, survey Phase 10)**: `ANALYSIS_PASSES` carries a `requires` list per entry, checked two ways — `analysisPassOrderViolations` (pure, so the test also checks a reordered copy) and a traced corpus compile asserting every pass runs once in list order. Thirty-six entries rather than 45: the per-declaration builders (`buildEntity`, `buildTrait`, …) are one pass, `buildDeclarations`, and the IR literal is its own pass, `createIR` — the passes before it fill the tables it reads, the passes after it write into the object it built. `resolveOverrideGates` is not on the survey branch (GH #359's fix landed on `feat/secret-letter-port`), so the AC-3 scratch check moves `buildChapters` above `buildTimers`; it fails naming both.
- **D4 — The section split is deferred, and recorded as such.** Splitting `Analyzer` into section modules around a resolver core (`suggestText`, `resolveEntityId`, `resolveStatement`, `resolveCondition`, `resolveValue`, `checkPhaseOrder`) is the same shape as ADR-335 D1 but with a core that must be designed, not measured. It is not decided here. If, after D1–D3 land, the analyzer's growth still lands in the same method families, a later ADR takes it up. **This ADR's plan carries no measurement phase for it (resolved Q-2, David, 2026-09-07: "b")**: the deferral stands on the measurements in Context, and whoever writes that ADR re-measures at the moment they decide to — the script is twenty minutes, and a note produced on speculation is a phase the plan would carry for nobody.
- **D5 — The facade does not move.** `analyze()`, `parseStory()`, `DiagnosticBag`, the AST and IR types, every diagnostic code and message, and `index.ts`'s exports keep their names and shapes. `story-loader`, `devkit`, `world-index`, `branch-tester`, and the IDE's IR decoder (`ComposeDiagnostics.swift`, which reads IR fields) compile and behave without edit.
- **D6 — Every phase lands byte-identical, in the IR and in play.** Each phase ends with (a) the compiled IR of every story under `packages/chord/tests`, `packages/story-loader/tests`, and `branch-stories/` byte-identical (JSON) to the run before it, (b) the three Chord test trees byte-identical (one run each), and (c) the chord suite at 1158 passing or higher. Order: D1 (compile-time only), then D3 (the list, with the test), then D2 builder by builder from the last branch of `buildEntity` upward, so the runner grows from the bottom and the byte-identical check runs after each builder moves.
- **D7 — Not on this branch, not now.** Discuss-first `packages/` work with its own plan on `main`, sequenced with ADR-334's and ADR-335's plans at David's call; the Secret Letter port's plan closes first. D1 is small enough to be its own one-phase plan ahead of the rest if David wants it sooner.

## Consequences

- A new statement kind is a compile error at every stage that has not decided what to do with it. The hand-threading that `WearStmt` needed last night becomes a list of red squiggles that goes green as each switch is taught the kind.
- A new entity-block line kind is one module under `analyzer/entity/` and one entry in the builder order; the 920-line read to find its slot ends.
- A pass that reads a table before it is built fails a test naming both passes, at the moment the pass is added, instead of surfacing as a story author's `analysis.unknown-timer`.
- `parser.ts` is untouched by this ADR, and stays the largest file in the repository. That is the decision, not an oversight: the survey found no duplicated or comment-ordered logic in it, only size proportional to grammar.
- The analyzer's fan-in measurements (Context, "a real core") are the starting point for any later section split; they are recorded here so that ADR does not have to re-derive them.

## Acceptance

- **AC-1 (exhaustive)**: adding a member to `Statement` (in a scratch branch) fails `tsc` in every one of the six switches, naming the file and line; removing the member restores a clean build; `pnpm --filter '@sharpee/chord' test` and the story-loader suite are unchanged in count and outcome.
- **AC-2 (builders)**: `buildEntity` contains no line-kind logic — it creates the entity, runs `ENTITY_LINE_BUILDERS` in order, returns; each builder module has a rule-9 header; the builder-order test names every builder and fails by name when one is moved before a builder it reads from.
- **AC-3 (pass list)**: `ANALYSIS_PASSES` exists; the order test fails when `resolveOverrideGates` is moved above `buildTimers` (the GH #359 shape), naming both; a corpus compile runs every pass exactly once in list order.
- **AC-4 (byte-identical)**: after each phase, the compiled IR of every corpus story is byte-identical to the run before the phase, and `./sharpee test branch-stories/<story> --tree` for `secret-letter`, `fernhill`, and `ides-of-march` reports the same counts and byte-identical captured output (evidence inline in the plan: command, count, date).
- **AC-5 (facade unchanged)**: `story-loader`, `devkit`, `world-index`, `branch-tester` build with no source change; the IDE suite passes with no Swift change; `packages/sharpee/docs/genai-api/` shows no removed public member of `@sharpee/chord`.
- **AC-6 (no diagnostic drift)**: the set of distinct diagnostic codes emitted across the corpus compile is identical before and after each phase (a `grep`-derived list, checked in the plan).
