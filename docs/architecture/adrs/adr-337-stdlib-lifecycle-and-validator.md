## Context — verified, not assumed

Every line reference below was read this session against `packages/stdlib/src/` and `packages/engine/src/` at `6ad2faeba`.

- **The package is large and mostly well-shaped.** 36,938 source lines across 301 files; 58 standard-action directories totalling 21,629 lines; the largest file is `validation/command-validator.ts` at 1679. The suite is 130 files, 1720 passing, 27 skipped (`pnpm --filter '@sharpee/stdlib' test`, 2026-09-07). Capability dispatch (ADR-090) is used where `packages/stdlib/CLAUDE.md` says to use it (two dispatch actions, five capability-aware ones). `going.ts` (768 lines, twelve ADRs cited, a 214-line `report`) and `attacking.ts` (601, a 221-line `report`) are per-action accretion, not a systemic shape, and are not targets here.
- **The interceptor lifecycle is applied by hand in 42 actions.** ADR-228's preamble (`adr-228-interceptor-lifecycle-engine.md:6-11`): ADR-118 *"left the lifecycle's execution a **convention** hand-copied into each action … 14 hand-rolled copies drifted into two guard semantics, two onBlocked semantics, three multi-object behaviors, and per-path skips."* ADR-228 gave the *rulings* one engine (`lifecycle/lifecycle-engine.ts`, "the engine owns the rulings exactly once") and one descriptor table (`lifecycle/registry.ts:76`, `actionLifecycleDescriptors`, "the table IS the source of truth"). The *call sites* are still the convention: every wired action imports six engine functions and calls them at its own phase boundaries — `resolveLifecycle` + `runPreValidate` + `runPostValidate` in `validate`, `getLifecycleState` + `runPostExecute` in `execute`, `runPostReport` in `report`, `runOnBlocked` in `blocked` (`taking.ts:35-40`, `381-389`, `409-410`, `437-438`, `461`). Measured this session: **605 lifecycle-plumbing lines across 42 action files**; a six-line import block identical in 38 of them is the most-shared code window in the package. `command-executor.ts` — the one path every action runs through (`runPhases`, `425`; ADR-328 D1/D2) — makes no lifecycle call.
- **The convention has drifted again, as ADR-228 said conventions do.** Measured this session over the 42 wired actions: the pre-validate veto is placed anywhere from 1 to 41 code lines into `validate` (going 39, removing 41, putting 35, taking 23; opening, telling, turning 5), because each action decides how much to resolve before consulting — and in at least one case refuses on its own before consulting at all (`answering.ts:78-82`: `no_question` returns before `resolveLifecycle` at `85`). One action, `answering`, never calls `runPostValidate` (the only wired action without it). ADR-228's scope was "**100% coverage — every action, every path, every entity**" (`:26-27`); a hand-placed convention cannot promise "every path", and nothing today checks it.
- **The validator's pipeline exists twice, and the second copy has no caller.** `CommandValidator.validate` (`command-validator.ts:164-379`) and `resolveWithSelection` (`385-660`) walk the same numbered steps — "1. Validate action exists … 2. Resolve direct object … 3. Resolve indirect object … 3b. instrument … 3c. topic … 4. Check scope constraints … 5. Check action-specific preconditions … Success — build validated command" — in both bodies, about 500 lines between them, differing by "use selection if provided". `grep -rn resolveWithSelection packages tools stories` (2026-09-07) finds two files: the validator itself and `tests/unit/validation/command-validator-golden.test.ts`. The engine calls `validate` only (`command-executor.ts:323`). Disambiguation in play goes through the held-command path (ADR-225, GH #318), not through this method.
- **Dead files that still cost work.** `actions/standard/pushing/pushing-original.ts` (398 lines, a pre-lifecycle pushing action by its header) is imported by nothing (`grep -rn pushing-original packages/stdlib` → 0) and was last modified by `593945a80` (2026-08-28, "ADR-328 Phase 4 — actor threading across the standard-action library") — so it is being maintained. `actions/removed/` holds four `.removed` files (663 lines, `8a7a46722`, 2025-07-28) referenced by nothing.
- **The documented six-file layout is not what the code does.** `docs/core-concepts/README.md:307-313` and `packages/stdlib/CLAUDE.md:5,11` describe each action as a directory of six files (`<name>.ts`, `-events`, `-data`, `-messages`, `-types`, `index.ts`). Across 58 actions there are 47 `-events`, 21 `-messages`, 12 `-data`, and 7 `-types` files; seven actions are exactly `<name>.ts` + `-events` + `index.ts`; fewer than five have all six. Two directories carry extra modules (`looking/snippet-resolver.ts`, `snippet-gate-registry.ts`; `hiding/revealing.ts`, `concealment-break.ts`) and `closing/` uses two non-convention names (`closing-event-data.ts`, `closing-error-prevents-closing.ts`).
- **27 skipped tests.** All in the golden suites and the witness-system test: `entering-golden` 4, `exiting-golden` 5, `opening-golden` 3, `dropping-golden` 2, `inventory-golden` 2, `throwing-golden` 2, `taking-golden` 1, `wearing-golden` 1, `witness-system` 3, `command-validator-golden` 1 (the `resolveWithSelection` case D2 removes), `integration/meta-commands` 3. Their titles name features never built ("should fail when too heavy", "should emit movement witness event", "pattern: weight calculation"). A skipped test asserts nothing and documents nothing a reader can trust.
- **The regression net.** The stdlib suite (1720 passing); the Dungeo walkthrough chain (952 passing, recorded session 0e7d6f) — Dungeo is the TypeScript story that exercises the standard actions and interceptors most heavily (the troll axe, the trophy case, the coal machine), so it IS the net for this package; and the three Chord test trees (`secret-letter`, `fernhill`, `ides-of-march`), whose `on <gerund>` clauses ride the same lifecycle. All byte-deterministic at their pinned seeds (recorded in `CLAUDE.md` under ADR-293 Phase D; re-established by AC-4 at each phase).

## Decision

- **D1 — The lifecycle has one call site: the executor (resolved Q-1, David, 2026-09-07: "a").** `CommandExecutor.runPhases` (`command-executor.ts:425`) looks up the action's descriptor in `actionLifecycleDescriptors` and runs the four hooks around the action's phases — `runPreValidate` before `action.validate`, `runPostValidate` after it, `runPostExecute` after `action.execute`, `runPostReport` after `action.report`, `runOnBlocked` around `action.blocked` — using the descriptor's own slot resolvers, exactly as the actions do today. The 605 plumbing lines and the six-function import block leave all 42 actions; "wired" becomes "has a descriptor", which is what the registry already claims to mean. The invariant is asserted, not documented: **every action whose descriptor is in the registry is consulted at all four phase boundaries on every path**, proved by construction and by a test that asserts the hook sequence for one wired action (`take lamp`) and none for one exempt action (`score`). The `answering` gap closes because there is no longer a place for it to exist. An action that must refuse ahead of the hooks (a refusal the interceptors should not be able to pre-empt) declares it on its descriptor as `earlyRefusal?(context: ActionContext): ValidationResult | undefined`, which the executor runs before `runPreValidate`; a returned `{ valid: false }` takes the action's `blocked` path with `runOnBlocked` still consulted (the interceptors see the block and may override its wording under ADR-228 D2, but cannot pre-empt it); the first D1 run's output diff (D6) is the list of candidates, and each is either accepted as the uniform order or given the declaration — decided per line in the plan, never by default. **Multi-object commands are the declared remainder.** Five actions (`taking`, `dropping`, `putting`, `inserting`, `removing`) run one lifecycle per item through ADR-228 D4's separate primitives (`multi-object-lifecycle.ts`: `runMultiObjectValidate`/`Execute`/`Report`) from inside their own item loops; the executor cannot wrap a loop it does not own without the action exposing its items, which is an action-structure change this ADR does not make. Those per-item calls stay in the five actions, and the structural test that AC-1 names covers them: each of the five calls all three per-item primitives, and no other action imports them. ADR-228 named the hand-copied convention as the defect and fixed the rulings; this finishes the single-object call sites and pins the multi-object ones (folded from `adr-review` 2026-09-07 — the first draft did not mention the D4 path).
- **D2 — One validation pipeline.** `resolveWithSelection` is removed with its golden test; if a caller for "re-validate with explicit entity selections" is ever wanted, it is `validate(command, selections?)` — one pipeline with an optional selections map consulted at steps 2, 3, and 3b — not a second copy. The five numbered steps stay exactly as `validate` orders them today.
- **D3 — The dead files go.** `pushing-original.ts` and the four `actions/removed/*.removed` files are deleted, in a plan phase whose sole content is that list, confirmed by David before the phase runs (CLAUDE.md: never delete files without confirmation). Nothing else in the package is deleted by this ADR.
- **D4 — The layout the docs describe is the layout the code has.** `docs/core-concepts/README.md` and `packages/stdlib/CLAUDE.md` are corrected to state the real convention: `<name>.ts` and `index.ts` always; `-events.ts` when the action emits its own event types; `-messages.ts`, `-data.ts`, `-types.ts` only when the action has enough of each to warrant a file. No action directory is restructured to match the old text. The two directories with extra modules and `closing/`'s non-convention names are left as they are; the doc says extra modules are allowed.
- **D5 — The facade does not move.** `Action`, `ActionContext`, `ValidationResult`, `CommandValidator.validate`'s signature (D2 adds an optional parameter only if a caller appears), every action id, every message id, and every emitted event type keep their names and shapes. `ActionLifecycleDescriptor` gains the optional `earlyRefusal` field (D1) and nothing else. Stories (`stories/dungeo`, the branch stories) compile without edit; the executor's change is D1's own.
- **D6 — Every phase lands byte-identical, with one declared exception.** As the sibling ADRs: each phase ends with the Dungeo chain and the three Chord test trees byte-identical to the run before it and the stdlib suite at 1720 passing or higher. **The exception**: D1 moves the pre-validate veto ahead of every action's own validation, which changes which refusal speaks first for the actions that refuse before consulting today (`answering`'s `no_question`, `going`'s exit resolution, and whichever others the first run reveals). That phase is expected to change output, the diff is the finding, and each changed line is either accepted as the intended uniform order or handled by the action's descriptor declaring a named early refusal ahead of the hooks (D1) — decided per line, recorded in the plan, never buried. Order: D3 (deletion, after confirmation), D2 (removal), D4 (docs), then D1 last, because it is the only phase that can move text.
- **D7 — The skipped tests are resolved, not carried.** Each of the 27 is either implemented (the feature exists and the test was never un-skipped), deleted (the feature was never built and is not planned), or replaced by a one-line note in the golden file naming the gap and the ADR or issue that owns it. "Skipped" is not a resting state. This is a plan phase with a 27-row table, each row one of the three verbs.
- **D8 — Not on this branch, not now.** Discuss-first `packages/` work with its own plan on `main`, sequenced with the other survey ADRs at David's call; the Secret Letter port's plan closes first.

**Amendment A1 (2026-09-08, session 4a2d5f — D2 and D4 applied with the code, `refactor/survey-adr-334-340`; D1's refusal-order dispositions, D3's deletions, and D7's skip table are held for David).** D2 as built: `CommandValidator.resolveWithSelection` (the class method, its interface member, and its parameter type `EntitySelections`, which nothing else used and the validation barrel never exported) removed with its six golden cases; `validate` is unchanged; no `selections?` parameter was added, since no caller exists. stdlib 1660 → 1654 passing (the six removed cases). D4 as built: both documents now state the measured convention — of 57 standard actions, `<name>.ts` and `index.ts` always, `-events.ts` in 46, `-messages.ts` in 21, `-data.ts` in 12, `-types.ts` in 7 — and say that a two-file action is complete.

**Amendment A2 (2026-09-08, session 71ed1a — D1 applied with the code, `refactor/survey-adr-334-340`; David approved the descriptor fields the same day).** D1 as built, with four departures from the text, each forced by a call site the ADR did not name. **(1) The descriptor carries two more fields, so D5's "and nothing else" is withdrawn.** `runPostReport` targets the action's primary event and `runOnBlocked` its blocked event, and both were literals at each of the 40 call sites; the executor cannot know them, so `ActionLifecycleDescriptor` gains `reportEventType` (a string, or a function of the context for putting's `put_in`/`put_on`) and `blockedEventType`, both required, beside the optional `earlyRefusal` D1 named. **(2) The call site is a stdlib module the executor calls, not code inside the executor.** `lifecycle/phase-runner.ts` exports `runValidatePhase`, `runExecutePhase`, `runReportPhase`, `runBlockedPhase`; `CommandExecutor.runPhases` calls the four and nothing else about the lifecycle. The reason is the tests: 31 stdlib, 26 story-loader, and 1 character test file drive an action's phases directly and assert on interceptor effects, and they now call the same four functions — one implementation, exercised by the executor on a real turn and by the tests on a built context, rather than a copy in each. **(3) Two contracts name the actions that keep a hook call.** `contracts.runsOwnHooks` lists hooks the action runs itself because the executor cannot place them: attacking runs postExecute mid-execute (the combatant hook IS the combat resolution its later logic reads) and postReport before it appends death and knockout events; asking, telling, talking, and answering run postValidate, postExecute, and postReport only when no open exchange or active thread has gripped the input (ADR-320 D16 — a gripped input must never reach the topic table, whose occurrence bump lives in postValidate; answering declares postValidate and never calls it, since a valid answer is always gripped). `contracts.handlesMultiObject` marks taking, dropping, putting, and removing: for a multi-object command the executor runs none of the single-object hooks and the action's D4 per-item loop runs them all; their `blocked` keeps the all-fail branch that notifies the first failed item's consultations. Inserting is the fifth name the ADR gave the multi-object remainder; it has no per-item loop — it delegates into putting's phases, and now runs putting's hooks around that delegation itself, because the executor never sees the delegated call. AC-1's `grep → 0` is therefore a named list of ten files, pinned by `tests/unit/actions/lifecycle-call-site.test.ts`, which also pins that only those four import the D4 primitives and that every descriptor names both event types. **(4) The refusal-order diff was empty.** With every action's early refusals (the "no target" checks that ran before `resolveLifecycle`) now behind the interceptors' preValidate, and onBlocked now consulted for refusals it never saw, the Dungeo chain, the seeded unit suite, and the three Chord trees were byte-identical to the baseline. No line needed `earlyRefusal`; the field is declared on the type and no descriptor uses it, and the criterion question stays open until a line needs it. `answering`'s "gap" (no postValidate) turned out to be ADR-320 D16's grip by design, not an omission. The engine test `tests/lifecycle-call-site.test.ts` asserts the four hooks fire once each in order for `take lamp`, that a preValidate veto reaches onBlocked, and that `score` consults nothing.

## Consequences

- A story author's `on <gerund>` clause is consulted on every path of every wired action, and the claim is a test rather than a convention. ADR-228's "every path" becomes true.
- The single-object plumbing leaves 42 actions (the five multi-object actions keep their per-item calls, 40 of the 605 lines, measured 2026-09-07), the six-function import block disappears, and a new action is wired by its descriptor alone — the registry entry becomes the whole of "wired". The cost is one phase whose output diff must be read line by line; the placement variance the actions carry today, which was where each author happened to put the call rather than a set of decisions, is replaced by one order plus explicit, named exceptions.
- The validator loses ~280 lines and its second pipeline; the golden test for the removed method goes with it.
- Two docs stop describing a layout that fewer than five actions follow.
- 27 tests stop being skipped; the golden suites either assert the features or say plainly that they do not exist.

## Acceptance

- **AC-1 (one call site)**: `grep -rl 'resolveLifecycle\|getLifecycleState\|runPreValidate\|runPostValidate\|runPostExecute\|runPostReport\|runOnBlocked' packages/stdlib/src/actions/standard` → 0; `command-executor.ts` runs the hook sequence, with a test asserting pre-validate, post-validate, post-execute, post-report fire once each for `take lamp` and none fire for `score`; a Dungeo `on taking` interceptor on the troll's axe still blocks the take with its own message (`stories/dungeo/src/traits/troll-axe-behaviors.test.ts:30`); the five multi-object actions each still call `runMultiObjectValidate`, `runMultiObjectExecute`, and `runMultiObjectReport`, and a structural test fails by name if one drops a call or a sixth action imports them.
- **AC-2 (one pipeline)**: `resolveWithSelection` does not exist; `validate` still walks steps 1–5 in the same order (the existing validator golden tests other than the removed method's pass unchanged).
- **AC-3 (deletions)**: the five files are absent; `pnpm --filter '@sharpee/stdlib' build` and the suite are clean; the plan records David's confirmation of the list.
- **AC-4 (byte-identical, with the declared exception)**: after each phase except D1, the Dungeo chain and the three Chord trees report the same counts and byte-identical captured output as the run before the phase; after D1, every differing line is listed in the plan with its disposition (evidence inline: command, count, date).
- **AC-5 (docs)**: the two documents describe the layout as D4 states it; a count of `-events`/`-messages`/`-data`/`-types` files matches the text's "when …" clauses for a sample of five actions named in the plan.
- **AC-6 (no skips)**: `grep -rn 'test.skip\|it.skip\|describe.skip' packages/stdlib/tests` → 0; the plan's 27-row table records each verb.
