# ADR-341: Chord Writer for Windows — a native mirror of the macOS app

**Status**: **ACCEPTED** (David, 2026-09-08, session 4a2d5f — "yes, mark it accepted" after the rule-11a interview resolved Q-1 to Q-5 and `adr-review` returned 18/18 with folds: the pane inventory corrected, the host contract given a home, three assumptions named with the spike phase as their check, the ADR-154 note owner named. Filed as GitHub issue #386. Written 2026-09-08, session 4a2d5f, on `main`. David, 2026-09-08: "let's circle back to the ADR for the Windows IDE", then, on the first draft's Electron position taken from the 2026-08-13 brainstorm: "I'd change a lot of that from the original brainstorm. The Windows version needs to be a mirror and I'd build it in WPF or the latest Windows client platform." This ADR records that ruling; the brainstorm's §12 (a TypeScript everywhere-else shell, no parity) is superseded on the desktop question and stays the record for the browser tier only. All five open questions resolved through the rule-11a interview 2026-09-08 (Q-1 spike every suspect control in both toolkits; Q-2 x64 only; Q-3 Azure Trusted Signing under David's account; Q-4 installer and updates decided in the plan after the spike phase; Q-5 the Swift mirror moves to the generator first). Acceptance authorizes no implementation by itself (D8).)

**Scope**: a new Windows application directory under `tools/` (named by the plan; no abbreviations), the three web panes under `tools/ide/web/` and the Play pane's host seam, a protocol-type generator for `@sharpee/ide-protocol` consumers (D5), and `tools/ide/SharpeeIDE` only where a pane's host contract is extracted from it or its mirrored types move to the generator. No Chord change, no `packages/` change beyond the generator's read of `ide-protocol`, no change to the macOS app's product surface. Linux is out of scope.

## Context — verified, not assumed

Every measurement below was read this session on `main` at `c95bdb535` unless dated otherwise.

- **Chord Writer is macOS-only, and interactive fiction authors mostly are not.** A macOS-only IDE for a new language is an adoption ceiling; Inform 7 has been cross-platform for its whole life (brainstorm §7). Chord Writer 1.4.0 is shipped and live (`tools/ide/project.yml:203`).
- **The macOS app is a native shell around three web panes, and that pattern is proven.** `tools/ide/SharpeeIDE` is 106 Swift files, 18,921 lines: a native AppKit editor (`Editor/ChordLexer.swift`, `SyntaxHighlighter.swift`, `AutoIndenter.swift`, `BracketMatcher.swift`), a native project tree and window chrome, seven subprocess sites that shell out to `sharpee <verb> --json` (`Build/BuildRunner`, `Build/ShellEnvironment`, `Compose/ChordVersionCheck`, `Compose/ComposeRunner`, `Project/IntrospectionRunner`, `Test/TestRunner`, `World/WorldIndexRunner`), and three panes hosted in a `WKWebView`: two IDE-owned web applications under `tools/ide/web/` (`docs-tab` and `testing-surface`, each with its own build and vitest suite; the `testing-tab` directory beside them is an untracked leftover holding only `node_modules`, not a pane) and the Play pane, which is the story's own built web bundle at `<project>/dist/web/<id>/` (`Play/WebBundle.swift:3`, ADR-252 D2). `Play/PlayURLSchemeHandler.swift` serves the Play bundle and the testing surface (`:29-36`); `Docs/DocsTabSchemeHandler.swift` serves the docs. David, 2026-08-13 (brainstorm §12.7): the Swift app was the fastest path to proving the model, it succeeded, and ADRs 277, 280, 281, 284, 285, and 297 are proven product design. A mirror inherits that design whole.
- **The wire types are hand-mirrored today, once.** Swift cannot import `@sharpee/ide-protocol`, so the app carries `Codable` copies (`Project/ProjectManifest.swift:14`). One hand copy is a live drift risk; a second native shell written the same way doubles it. Rule 8b's answer across a language boundary is codegen, and the repository already runs generated artifacts under a freshness gate (the standard grammar, ADR-269 D7; the ADR-276 manifests) in `./repokit verify`.
- **The compile, load, run, and test chain is browser-clean by design**, measured 2026-08-13 (brainstorm §2): `@sharpee/chord`, `@sharpee/engine`, `@sharpee/story-loader`, and `@sharpee/platform-browser` import no Node builtin. That is why the three panes can be shared between two native hosts without a second copy: the host provides files and processes, the pane provides everything else.
- **The vendored toolchain is the packaging cost, and a native mirror pays it again.** The shipped macOS app carries a full Node runtime plus a per-arch `@esbuild/darwin-*` (`tools/ide/vendor-toolchain.sh:94-98`, `:180`): 171M of the installed 187M (`du -sh` on `/Applications/Chord Writer.app`, 2026-09-08). The brainstorm's Electron position existed largely to escape that cost. A native Windows mirror does not escape it; it vendors `node-v22.x-win-x64` plus the matching `@esbuild/win32-x64` by the same method, on a Windows host, since Node and esbuild are not cross-compiled here.
- **The one real fork is the editor, and one grammar is already decided and unbuilt.** ADR-182 accepted tree-sitter on 2026-06-19 and nothing has implemented it: the highlighter's own header says "no parse tree, no tree-sitter" (`Editor/SyntaxHighlighter.swift:3`) and the project file records tree-sitter as left with the TypeScript author path (`tools/ide/project.yml:31`). Tree-sitter is a C library with a Swift binding; a .NET binding exists as an assumption here and is verified in the D2 spike phase. Without it a Windows mirror would carry a second hand-written Chord lexer, and Chord's syntax would be defined in three places: the Swift lexer, the C# lexer, and the compiler.
- **Windows client platforms, as of this writing.** WPF is mature, open source, on current .NET, and has a mature third-party code-editor control ecosystem; WinUI 3 on the Windows App SDK is Microsoft's stated current desktop direction and hosts the same `WebView2` control. Both host `WebView2`, which is the Windows counterpart of `WKWebView` and the reason D3 holds on either. Health checked 2026-09-08: WPF ships with .NET 10 LTS, is open source, and Microsoft has said it will not be removed, with maintenance-grade investment and the Fluent theme as its one recent feature; WinUI 3 is Microsoft's stated primary native direction, recommitted at Build 2026, on Windows App SDK 1.8 stable with 2.0 in preview on .NET 10 and carrying breaking changes. The editor-control ecosystems differ most: WPF's is mature; WinUI 3's is a Scintilla port that calls itself early work in progress, a Win2D control, and Monaco hosted in `WebView2`.

## Decision

- **D1 — Chord Writer for Windows is a mirror.** The same product, feature for feature: editor, project tree, compose, build, test, play, publish, docs, world index, settings, and updates, as the macOS app ships them, under the same product ADRs. Parity is the acceptance bar, not a goal: a feature ships on both platforms or is recorded in a parity table with an owner and a reason. The macOS app remains the reference implementation; a feature is designed once and lands twice.
- **D2 — Native Windows, in C# on .NET; the toolkit is decided by spikes, not by argument (resolved Q-1, David, 2026-09-08: "we need to spike any control we think might be problematic").** WPF or WinUI 3, per David. Not Electron, not Tauri, not a web application in a window: the macOS app proved that a native shell around web panes is the right shape, and the mirror keeps the shape. The choice between WPF and WinUI 3 is made by the plan's first phase, a spike phase that builds, in both toolkits, every control the parity table (AC-1) marks as possibly problematic, the editor first and then whatever else the table flags (the project tree, `WebView2` hosting of the panes, the window chrome and appearance mirror of ADR-297, and any control the Swift app implements custom). Each spike records inline what was built, what failed, and how it felt; the toolkit whose spikes pass is the toolkit, and the record is the reason, so the choice is never re-litigated from toolkit marketing. The brainstorm's Electron ranking (§12.5) is superseded for the desktop; its reasoning about TypeScript shells stands only for the browser tier.
- **D3 — The three web panes are shared, behind one host contract.** The docs tab and the testing surface are built once from `tools/ide/web/`; the Play pane is the story's own web bundle, which both hosts serve unchanged; all three are hosted by `WKWebView` on macOS and `WebView2` on Windows. What a host provides (serving the pane's files, the story bundle, and the docs; answering the pane's requests for files and subprocess results) is written down as one contract: a TypeScript module under `tools/ide/web/` (named by the plan) that the two IDE-owned panes import and that replaces the two `WKURLSchemeHandler`s as the only thing a pane knows about its host. Each host implements it natively; that `WebView2`'s resource-request hook can satisfy it is an assumption verified in the D2 spike phase. The extraction is done in the Swift app first and each step must leave that app working. A pane that can only be served on Windows by a second copy is the failure this decision exists to prevent.
- **D4 — Two native editors, one grammar.** The Windows editor is native to its toolkit, mirroring the AppKit editor's behavior (highlighting, auto-indent, bracket matching, the line-number ruler). Both editors consume ADR-182's tree-sitter grammar, and ADR-182 is implemented in the Swift app first, so the Windows editor consumes a grammar that already exists rather than adding a third definition of Chord's syntax. The editor control (a third-party component or a custom one) is the first spike D2 orders, and the spike's record is the choice.
- **D5 — Protocol types are generated, not hand-mirrored.** The Windows app's C# types for `@sharpee/ide-protocol` are emitted by a generator that reads the TypeScript source, under `./repokit verify`'s freshness gate beside the grammar and the ADR-276 manifests. **The Swift app's existing `Codable` mirror moves to the same generator first, before any Windows code exists (resolved Q-5, David, 2026-09-08: "now, the generator needs a real consumer first")**: the generator's first emitted target is Swift, its first consumer is `tools/ide/SharpeeIDE`, and the existing `SharpeeIDETests` suite is what proves the generated types are the ones the app was hand-writing; C# is the second target, added when the Windows shell needs it. Both native shells then drift from the protocol only when the gate is red. One hand-written copy was a risk; two is a defect, and rule 8b names the fix.
- **D6 — The project model does not change.** ADR-280's real folders are the project, at `Documents\<Story Title>\` on Windows; cloud sync is the author's own sync client; publishing (ADR-284) and assets (ADR-285) keep their filesystem assumptions; hatched stories build natively. The toolchain is vendored by a Windows counterpart of `vendor-toolchain.sh`, accepted as the price of a native mirror. **x64 only (resolved Q-2, David, 2026-09-08: "arm64 is literally a rounding error")**: one toolchain, one installer, one signing run; Windows on ARM runs the x64 build under emulation (that the vendored x64 Node runs acceptably there is an assumption checked once in the D2 spike phase, not a gate), and an arm64 build is not a parity-table gap, since the macOS app's two architectures are a fact about Apple's transition, not a product commitment the mirror inherits.
- **D7 — Release is Windows-native.** Built on a Windows host (no cross-compile; the publishing workflow is the one CI exception this project makes), signed through **Azure Trusted Signing under David's own account (resolved Q-3, David, 2026-09-08)**: identity validated once against him, keys held by the service, the signing step run by the publishing workflow on its Windows runner with no certificate file or hardware token in the repository or on any machine, which is the posture the npm release already takes with OIDC trusted publishing (no credential in the repository or on the runner); delivered as an installer with an update channel that mirrors Sparkle's role on macOS. **The installer format and update mechanism are decided in the plan after the D2 spike phase (resolved Q-4, David, 2026-09-08: "decide in the plan after the spike phase")**: the two candidates are MSIX with its hosted appinstaller update path, and a conventional installer plus an appcast-style update library; the spike phase must include the vendored Node toolchain and ADR-280's real project folders running under MSIX's packaged filesystem, because that result is what decides between them, and the plan records the choice with the spike's evidence inline. None of this touches the macOS app's release scripts.
- **D8 — Not now, and in this order.** Discuss-first work with its own plan on `main`, sequenced: the D2 spike phase (toolkit decided on evidence before anything is built on it), ADR-182 in the Swift app (the grammar must exist before a second editor consumes it), then D5's generator with the Swift mirror as its first consumer (resolved Q-5: before any Windows code), then D3's host contract extracted pane by pane with the Swift app as the proving host, then the Windows shell. Each step before the shell is useful to the macOS app whether or not the shell ships on schedule.

## Consequences

- Chord's IDE reaches Windows as the same product, not a lesser tier, and every future feature is designed once for two native shells.
- The macOS app gains three things it keeps regardless: a tree-sitter editor it was already promised, generated protocol types in place of a hand copy, and a written host contract for its panes.
- The cost is a second native codebase for the shell, editor, project tree, and subprocess plumbing, held to parity by a table and by tests, plus a second toolchain vendoring and a second release train with its own signing.
- Linux is not addressed. The brainstorm's everywhere-else shell was the route to it; under this ADR, Linux waits for its own decision.
- ADR-154's deferred technology choice is closed as native for both desktop platforms. The plan phase that records the D2 spike result writes a one-line note beside ADR-154's deferral bullet (`adr-154-sharpee-ide.md:150`) pointing here; the brainstorm's supersession note is already written (2026-09-08). No other ADR's Status changes.

## Acceptance

- **AC-1 (parity table)**: the plan carries a table of the macOS app's product surface (one row per feature under ADRs 277, 280, 281, 284, 285, 297, and the Play, Test, Docs, and World Index panes) with the Windows status of each; a release ships only with every row at "shipped" or an owned, dated gap.
- **AC-2 (no hand-mirrored types)**: `grep -rn 'ide-protocol' <windows directory>` resolves to generated files only; `grep -rn 'Codable' tools/ide/SharpeeIDE/Project/ProjectManifest.swift` finds only generated declarations or none; `./repokit verify` fails when `@sharpee/ide-protocol` changes and the generated Swift or C# is stale.
- **AC-3 (panes built once)**: the docs tab and the testing surface each have one source under `tools/ide/web/` and one build that both native shells load; the Play pane in both shells is the story's `dist/web/<id>/` bundle served unchanged; both IDE-owned panes import the D3 host-contract module and nothing host-specific; no pane source exists under the Windows directory.
- **AC-4 (one project model)**: a story created in Chord Writer for macOS opens in the Windows app unchanged, composes, plays, and runs its test tree with the same results; the reverse holds.
- **AC-5 (one grammar)**: both editors load the ADR-182 tree-sitter artifact; no hand-written Chord lexer exists in the Windows directory.
- **AC-6 (the macOS app is untouched in product)**: `SharpeeIDETests` passes after each D3 extraction and after the D5 migration with no test change beyond the host seam and the type source.
- **AC-7 (Windows release)**: a signed installer built by the publishing workflow on a Windows runner installs on a clean Windows machine and passes AC-4 there; evidence inline in the plan with the command, the installer size, and the date.
