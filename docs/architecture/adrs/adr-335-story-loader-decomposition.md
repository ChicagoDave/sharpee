## Context — verified, not assumed

Every line reference below was read this session against `packages/story-loader/src/` at `6ad2faeba`.

- **Two classes hold the package.** `runtime.ts` is 5177 lines, of which `ChordRuntime` is 4914 (`265-5178`, 88 methods); `loader.ts` is 3091, of which `ChordStory` is 2621 (`243-2864`, 36 methods). `evaluator.ts` (924) is a separate module and is fine. The runtime grew from 539 lines in March 2026 to 5177 today; since June the runtime took 65 commits and the loader 81.
- **The runtime is already divided into modules — by comment.** Fifteen ruler comments partition the class by section: bind (`306`), D5 fail-fast (`693`), event clauses (`734`), move clauses (`813`), on-clauses (`872`), topic tables (`1149`), dialogue registration (`1186`), conversation threads (`1887`), dispatch verbs (`2942`), scheduler constructs (`3423`), timers (`3778`), derived (`4036`), statements (`4095`), phrases (`4911`), helpers (`5164`). Private fields are declared *at the section that uses them*, not at the top of the class: `books` at `502`, `phraseClaims` at `1152`, `irEntityIndex` at `1189`, `inStartBlock` at `4117`, `moveArrivalDepth`/`moveArrivalChain` at `4704-4706`, `pendingChannelEvents` at `4914`. Each section carries its own state.
- **The sections barely call each other.** Measured this session over the 88 methods: the internal call graph (`this.<method>(` within the class) gives almost every method zero or one internal caller. The most-shared helper, `dialogueTurn` (`1171`), has six callers and nine lines; the next four are `rawEvent` (`5154`, five callers), `placeOf` (`3692`, four), `narrated` (`3602`, four), `sourced` (`3750`, three). The three largest methods are self-contained or nearly so: `buildTopicArm` (`2586`, 359 lines, no internal calls), `buildDispatchAction` (`3156`, 220 lines, none), `buildDialogueRegistration` (`1579`, 311 lines, four). `runStartBlock` (`4127`, 384 lines) and `bind` (`309`, 228 lines) are the two fan-out points at thirteen calls each. So the rulers are not decoration: they mark modules that happen to share a `this`.
- **The header promises an invariant the code does not keep.** `runtime.ts:15-17`: *"Occurrence and RNG state live in world state only — the runtime holds no turn-scoped mutable fields, so save/restore needs no runtime hooks."* The class declares nine mutable fields: `eventSeq` (`266`), `pendingActEvents` (`278`), `actDepth` (`279`), `actChain` (`281`), `lastTickTurn` (`283`), `inStartBlock` (`4117`), `moveArrivalDepth` (`4704`), `moveArrivalChain` (`4706`), `pendingChannelEvents` (`4914`). Seven are re-entrancy guards or buffers drained within a turn. Two survive across turns and are never reset on restore: `eventSeq` numbers every runtime-raised event id (`4420`, `4652`, `4741`, `5156`), and `lastTickTurn` (`3952`) is returned as the turn whenever no turn provider is set (`3894`). No observable consequence was found this session; the invariant is false as written, and the next reader will trust it.
- **The loader keeps IR-shaped extension construction on its own side of the ADR-215 boundary.** `extension-registry.ts` is "the MAPPINGS half" of ADR-215: each `use` name resolves to an entry carrying its world-side registration and field routes (`extension-registry.ts:1-17`); the loader resolves `use` through it (`loader.ts:457`) and calls each entry's `registerPlugin` slot at engine-ready (`1167`, ADR-260 D6). But the *config-dependent* construction for four extensions lives in the loader as five methods importing the extension packages directly (`@sharpee/ext-hunger` at `79`, `@sharpee/ext-chapters` at `85`, `@sharpee/plugin-state-machine` at `97`): `buildPromotionNarrator` (`1290`, 41 lines), `buildHungerDaemon` (`1331`, 43), `applyNpcAdjective` (`2309`, 102), `buildMachineDefinition` (`2411`, 88), `applyCombatAdjective` (`2499`, 56), plus the inline `if (this.ir.hunger)` block (`1183`) and the state-machine block (`1149-1158`). The loader's own comment at `1180` records the split as deliberate ("installed via `EXTENSION_REGISTRY.registerWorld`; the config-dependent…"). Deliberate or not, the effect is that adding an extension edits the generic loader in five places, which is the engine's disease (ADR-334 Context) in miniature: a registry that exists, and a live path around it.
- **The alias contract is two hand-maintained tables.** `message-alias-map.ts` (834 lines, the loader's alias → `if.action.*` map) and `@sharpee/chord`'s `message-alias-catalog.ts` (830 lines, the names-only set) both say they are *"generated from the built `lang-en-us` action modules"* by the ADR-255 D2 rule (`message-alias-catalog.ts:15-19`, `message-alias-map.ts:15-16`). **No generator exists in the repository** (`grep -rln 'message-alias\|MESSAGE_OVERRIDE_ALIASES' scripts tools/repokit/src` → nothing, 2026-09-07); "regenerate the baseline by re-applying the rule" is a hand step. `message-alias-map.test.ts` pins both tables to the live message-id set and to each other (six cases, `29-55`), so drift fails the build — which is why session 0e7d6f (2026-09-07) recorded, as a trap, that every new message id must be added on both sides. The gate is right; the maintenance is manual on purpose only because nobody wrote the generator. The repository already generates a source file from a declarative source in the build: `packages/parser-en-us/src/grammar.ts` from `grammar/standard-en-us.story` via `./repokit grammar` (`tools/repokit/src/commands/grammar.ts`).
- **What is already right and stays.** ADR-210's direction rule holds (the platform does not import this package); registration is per-world and keyed (ADR-207/208); `evaluator.ts`, `decisions.ts`, `state-keys.ts`, `select-ids.ts`, `hatch-context.ts` are the right size and shape and are the model for what the runtime's sections become.
- **The regression net.** `pnpm --filter '@sharpee/story-loader' test`: 130 files, 1118 passing (2026-09-07). The Secret Letter test tree is recorded at 1468 cards / 2642 assertions passing and byte-deterministic at its pinned seed (session 0e7d6f; ADR-293 Phase D as recorded in `CLAUDE.md`) — recorded, not re-run for this ADR; AC-4's before/after comparison re-establishes it at each phase.

## Decision

- **D1 — One module per runtime section, and a small shared core.** `packages/story-loader/src/runtime/` holds one module per ruler-marked section of `ChordRuntime` — `bind`, `event-clauses`, `move-clauses`, `on-clauses`, `topic-tables`, `dialogue`, `conversation-threads`, `dispatch-verbs`, `scheduler-constructs`, `timers`, `derived`, `statements`, `phrases` — each taking its section's fields with it (the field declared at `1152` moves with the dialogue section, the one at `4704` with the move clauses). **Thirteen modules, one per ruler (resolved Q-1, David, 2026-09-07: "a")**: the rulers are the author's own partition, drawn as the code was written, and the call-graph measurement says they are real seams; grouping them into families would add judgment to a move whose safety argument is that it makes none. Two modules that later prove to belong together are merged then; a family is never split later. The five shared helpers (`dialogueTurn`, `rawEvent`, `placeOf`, `narrated`, `sourced`) and the truly shared state (the IR, the evaluator, the turn provider, the execution entry) form `RuntimeCore`, the one thing every section module receives. `ChordRuntime` remains as the facade the loader constructs and holds (`loader.ts:252`); it delegates. Each section module exports one registration function, `bind<Section>(core: RuntimeCore, ir: StoryIR, world: WorldModel): void`, and `bind` calls the thirteen in the order the sections register today; a section that also serves the turn (timers, statements, phrases) exports its per-turn entry points beside it, taking the core as their first argument. This is a mechanical move of already-partitioned code, not a redesign: no method changes body, and the order of registration in `bind` (`309`) is preserved verbatim.
  **As built (2026-09-09, session 4e5843)**: each section is a class (`<Section>Section` under `packages/story-loader/src/runtime/`) holding its own fields and a `core: RuntimeCore` reference; `ChordRuntime extends RuntimeCore`, constructs the thirteen, and delegates its public surface (D5 unchanged: the loader's twenty-one call sites and the tests' entry points compile without edit). Bodies moved verbatim by script; the only change inside a body is the re-targeting of `this.X` (and the `const runtime = this` alias) to `this.core.X` for core state or `this.core.<section>.X` for another section — the cross-section call graph the Context measured. The core holds the shared state and the five helpers, and also the five re-entrancy guards and both buffers (D2's assertion lives there, so `moveArrivalDepth`/`moveArrivalChain` and `inStartBlock` did not travel with their sections as D1 said; the section fields that did travel are `books`, `phraseClaims`, `irEntityIndex`, `assignedPlayerId`). Two rulers the Context did not count folded in: the three "D5 fail-fast" gerund checks into `bind`, the one "helpers" method into `statements`. **The bind order carries `requires`**: `bind` was partitioned into six steps — on-clauses (with topic arms and event clauses), move clauses, trait clauses, derived evaluators, phrasebook evaluators, message-override evaluators — listed as data in `RUNTIME_BIND_STEPS` (`runtime.ts`) with a `requires` per entry; every `requires` is empty because no step reads another's registrations today, and `tests/runtime-sections.test.ts` pins the order, a reordered copy's fault by name, one call per step per load, the thirteen modules, and that a section's sibling imports name only `core` (`core.ts` type-imports the sections to declare its fields, the one `./` cross-reference AC-1's grep shows). The facade is 244 lines; the thirteen sections total 4,934 and the core 410.
- **D2 — The core states its mutable fields and what restore does to them.** The header invariant is rewritten to what the code does: the runtime holds *re-entrancy guards and per-turn buffers* (named), which are empty between turns and are asserted empty at the top of `bind`'s per-turn entry points; and two cross-turn counters (`eventSeq`, `lastTickTurn`), **which a restore resets (resolved Q-2, David, 2026-09-07: "a")**: `ChordStory.onWorldRestored` (`loader.ts:1070`) calls one `RuntimeCore.resetAfterRestore(turn)` that sets `lastTickTurn` to the restored turn and `eventSeq` to zero; no save key is added and the save format is untouched. The invariant becomes an assertion (DevArch rule 6), not a comment: a guard left set between turns throws, naming the field. **As built (2026-09-09, session 4e5843)**: the five guards (`actDepth`, `actChain`, `moveArrivalDepth`, `moveArrivalChain`, `inStartBlock`) are asserted by `assertBetweenTurns` at the top of the three entry points that run between turns — `runStartBlock`, the scheduler tick (`stepTimers`), and the act flush (`drainActEvents`); the two buffers (`pendingActEvents`, `pendingChannelEvents`) are named in the header but drained, not asserted, because they legitimately hold events between an action and its flush, and `fireEventClauses`/`fireMoveClauses` cannot assert because an act nests them. `Story.onWorldRestored` gained a second parameter, `restoredTurn` (the save's `turnCount`, the turn its last tick ran on), passed by the engine's save-restore service at its one call site — the one edit outside this ADR's scope, because the engine sets its own `currentTurn` only after the hook returns, so no in-scope source of the restored turn existed.
- **D3 — IR-shaped extension construction moves into the registry entry.** `ExtensionRegistration` gains one slot, `installFromIR(ir, world, engine, core)`, and each of the four extensions with config-dependent construction (hunger, chapters, state machines, combat/NPC adjectives) implements it *in its own registry entry*, next to the `registerWorld`/`registerPlugin` it already has. The five loader methods and the two inline blocks move there; `loader.ts` imports no `@sharpee/ext-*` or `@sharpee/plugin-state-machine` package afterward. The loader's engine-ready path becomes one loop over `ir.uses` calling the slot. Adding an extension then edits the registry and the extension, never the loader, which is what ADR-215's "MAPPINGS half" already claimed. **As built (2026-09-09, session 4e5843)**: the slot is `installFromIR(ir, engine, context)` — `context` (`ExtensionInstallContext`: `worldId`, `requireWorldId`, `evalCondition`, `execMachineBody`) stands in for the `RuntimeCore` that D1 has not yet built, and the world is not a parameter because engine-ready construction reads it per turn. Two companions the inventory above did not list: `seedWorldFromIR(ir, world)`, a world-build slot for the chapter opener seed (`loader.ts:813` at `6ad2faeba`) so its timing is unchanged, and `gatedConstruct(ir)`, which names the `define …` construct a `use` unlocks so the two rogue-IR backstops became one generic loop with the same messages. Each entry lives in its own module under `src/extensions/` and the registry map composes them. The loop runs in the registry's order, not `ir.uses` order: scoring's and hunger's narrators (and watchers) share a priority, and the registry order is the tie-break today's inline blocks had. Of the five loader methods named in the Context, three moved (`buildPromotionNarrator`, `buildHungerDaemon`, `buildMachineDefinition`); `applyNpcAdjective` and `applyCombatAdjective` stayed — they run per entity at composition time, lower onto world-model traits through the registry's own route tables, import no extension package, and NPC adjectives are core vocabulary with no `use` entry to move into. The loader lost 270 lines and its four extension-package imports.
- **D4 — One hand-maintained table; the other is derived from it (folded from `adr-review` 2026-09-07, David: "yes" — the first draft generated both tables from `lang-en-us`, which reversed ADR-255 D2 as David ruled it: "a hand-maintained catalog — a curator owns it … it is never silently auto-generated").** The loader's `message-alias-map.ts` (alias → dotted id) is the single curated table, as ADR-255 D2 intends: a curator adds one row per new message id and may polish a spelling. `@sharpee/chord`'s `message-alias-catalog.ts` (names only) is derived from that table's keys by `./repokit aliases` (beside `grammar`, `tools/repokit/src/commands/`), and `./repokit aliases --check` joins `verify` beside the grammar freshness gate (`verify.ts:30-35`). Nothing is generated from the language pack; ADR-255 D2 is unchanged in substance and Interface Contract 3 still holds (dotted ids on the loader side only, names only on the Chord side). The existing bijection test (`message-alias-map.test.ts:29-55`) stays as the drift gate against the live message-id set. ADR-255 gains a one-line amendment note under D2 recording that the Chord-side set is derived from the loader-side table, written by the plan phase that lands the generator, so the flip has an owner and a trigger. The trap recorded in session 0e7d6f is retired because the second hand edit no longer exists. **As built (2026-09-09, session 4e5843)**: `tools/repokit/src/commands/aliases.ts` reads the map's rows from its SOURCE text (the `readStdlibActionIds` precedent — no dist needed, the table and its derivation ship in one commit) and emits the catalog in table order with one `// if.action.<action>` comment per run of rows; the catalog's curator notes on those comment lines do not survive derivation (the map keeps them). The old catalog header's "752 aliases across 56 actions" was a stale hand count; both files held 742 rows, and the generated header carries the counted figure.
- **D5 — The facade does not move.** `createStory`, `ChordStory`'s `Story` implementation (`initializeWorld`, `createPlayer`, `extendLanguage`, `extendParser`, `isComplete`, `onEngineReady`, `onWorldRestored`), `ChordRuntime`'s public surface, and `index.ts`'s exports keep their names and signatures. `bootstrap`, `devkit`, `branch-tester`, and `transcript-tester` compile without edit.
- **D6 — Every phase lands byte-identical.** As ADR-334 D6: each phase ends with the three Chord test trees (`branch-stories/secret-letter`, `branch-stories/fernhill`, `branch-stories/ides-of-march` — the stories this package loads; Dungeo is TypeScript-only and never enters `story-loader`, so its chain is not a net here) byte-identical to the run before it (one run each) and the story-loader suite at 1118 passing or higher. Order: D4 first (a derivation plus a check, no runtime code moves), then D3 (deletes loader code into the registry), then D2 (the assertion, before any section moves so a move that leaks a guard is caught), then D1 section by section, largest self-contained first (`buildTopicArm`, `buildDispatchAction`, then the dialogue and thread sections, then the rest).
- **D7 — Not on this branch, not now.** Discuss-first `packages/` work with its own plan on `main`, sequenced after ADR-334's plan or interleaved with it at David's call; the Secret Letter port's plan closes first.

## Consequences

- A Chord feature that adds a clause kind adds one module under `runtime/` and one line in `bind`; it does not grow a 4900-line class. The section rulers, which were the only map of the runtime, become the file listing.
- The loader loses about 330 lines of extension-specific code and two direct extension imports; the ADR-215 registry becomes the whole boundary rather than half of one.
- `./repokit aliases --check` joins `verify`; a new stdlib message id is one row in the loader's curated table plus a regeneration of the Chord-side set, and the bijection test keeps failing loudly against the live message-id set.
- The runtime's header stops lying, and the two cross-turn counters get an owner. `ChordStory.onWorldRestored` (`1070`) gains one call; the save format is untouched.
- Nothing in this ADR touches the IR, the language, the wire, or any test story.

## Acceptance

- **AC-1 (sections are modules)**: `packages/story-loader/src/runtime/` contains thirteen modules, one per D1 section, each with a rule-9 header; `runtime.ts` contains the facade and `RuntimeCore` only; no section module imports another section module (a `grep` of `from './` across `runtime/` shows only `core` and the package's existing helpers).
- **AC-2 (guards asserted)**: a test that leaves a re-entrancy guard set and enters the next turn gets a thrown error naming the field; after a restore to an earlier save, the next runtime-raised event id and the fallback turn are what a fresh session at that turn would produce (through `resetAfterRestore`, D2).
- **AC-3 (registry owns construction)**: `loader.ts` has no import from `@sharpee/ext-hunger`, `@sharpee/ext-chapters`, `@sharpee/ext-scoring`, `@sharpee/ext-basic-combat`, or `@sharpee/plugin-state-machine`; a story with `use hunger` and a story with `use state-machines` boot and behave as before (the existing story-loader tests for each extension pass unchanged).
- **AC-4 (byte-identical)**: after each phase, `./sharpee test branch-stories/<story> --tree` for `secret-letter`, `fernhill`, and `ides-of-march` reports the same counts and byte-identical captured output as the run before the phase (evidence inline in the plan: command, count, date).
- **AC-5 (one curated table)**: `./repokit aliases` regenerates `message-alias-catalog.ts` from `message-alias-map.ts` with no diff at HEAD; adding a row to the map and not regenerating makes `./repokit aliases --check` fail naming the catalog; `./repokit verify` includes the check; ADR-255 D2 carries the amendment note.
- **AC-6 (facade unchanged)**: `bootstrap`, `devkit`, `branch-tester`, `transcript-tester` build with no source change; `packages/sharpee/docs/genai-api/` shows no removed public member of `@sharpee/story-loader`.
