## Parent

ADR-307 (the testing tree model v2 — the document is the model, and its replay driver and determinism contract "survive intact"; this decision changes *when* the driver runs, never what the document means). **Related**: ADR-293 D7 (per-point seed streams, and their persistence in the save — the invariant that makes a restored branch point possible at all), ADR-305/ADR-306 (the play feed's ordinals, lineages and restart fences — Q-1 below is theirs), ADR-347 (the Ending as queryable state — the seam a branch that dies mid-prefix runs into, tracked separately as the plan's Phase 16), ADR-348 (the world is authoritative on restore).

## Context — measured, not assumed

**The pane replays the whole tree on every load, and it is the most expensive way to get the answer.** `replayTree` (`src/main.ts`) walks in three phases: the main line's own commands; then *every other line*, each one a `localStorage.clear()`, a typed `restart`, a wait for the restart fence, and a replay of that line's **entire prefix from the root** before its own commands; then the active line's full path once more. Every command in all three phases goes through `typeCommand` — a synthetic keydown on the client's real `command-input` — and waits for its turn record to come back through the host.

The cost is the sum of every line's prefix, not the story's size. Measured against `secret-letter` (2026-09-19): **566 cards, 60 branches, depth 3, 61 lines**, whose **565 authored commands become 3,854 executed** ones. The same 3,854 commands take **6 seconds** through `sharpee test --tree --capture-output --capture-world --json`, because that path runs engine-direct with no DOM and no host round trip.

**What a full replay costs is bounded below by observation and estimated above by arithmetic, and this section now separates the two** (amended 2026-09-20, session 1bd093, after `adr-review` raised the original wording as a BLOCKER — a section titled *measured, not assumed* stating a derived number as an observation). **Observed**: the main line's 75 records in **1.8 seconds**; a record arrival rate of roughly **42/s**; and one eager replay **cut off, unfinished, at 240 seconds**. **Derived**: `3,854 ÷ 42 ≈ 90 seconds`, which is what an earlier draft of this paragraph reported as though someone had watched it finish. **No complete eager replay has ever been observed to completion in either head.** The 240-second run puts the true figure above the estimate rather than below it, but that run was also hitting the ending defect described in the Consequences, so it is not a healthy replay: it fixes a floor, not a rate.

A clean observed figure is no longer obtainable, and deliberately so — D1 has shipped and the eager walk is deleted, so producing one would mean reverting live code to time the behavior this decision exists to remove. **Nothing here rests on it.** D1 and D3 are decided by two numbers that are both observed and far apart in what they buy: **1.8 seconds** for the one line an author is looking at, against **6 seconds** for the entire tree through the CLI.

**The main line alone is 75 records and 1.8 seconds.** Everything beyond it is the pane pre-visiting branches nobody asked to see.

**In the Avalonia head it does not even finish.** Left running 240 seconds against `secret-letter`, the pane replays the main line, posts `forkBoot: true`, and stops: 75 records, then nothing. `driveFreshBoot` types `restart` and waits 15 s for a fence that never arrives, and the `break` ends the whole branch loop. Fernhill's 11-line tree replayed intact in an earlier session (270 records), so this is scale- or story-specific. **Measured, not diagnosed** — Q-2. **Read this paragraph with the correction of record in the Consequences**: the "then nothing" was the host logging one record in twenty-five, and records did continue. What survives it is the timing — four minutes, no completion.

**The answer the eager replay produces already exists, faster and elsewhere.** The run column folds `test --tree --json` **per line** (`src/run.ts`), so a line's verdict does not require the pane to have visited it. The replay's unique contribution is the *live* material — a turn's captures, its bound cards, the ability to branch from it — which is only meaningful for a line someone is looking at.

**Branch testing has a user, and he is on the fast path.** John uses branch testing in his own works through devkit — the CLI. The document he authors, the assertions he writes, the seed that pins his runs and the per-line results he reads are therefore a contract this decision must not touch, and does not: everything below is a change to how one IDE pane chooses to visit a tree it does not own.

**Getting to a branch point without retyping its prefix is already possible.** `ISaveData` carries a gzipped, verbatim `WorldModel.toJSON()` (traits, containment, score ledger, capabilities, relationships, ID counters, scope rules), the event source, the turn history, and plugin states including the scheduler's daemons and fuses. Critically it carries `streamStates` (ADR-293 D7, save format 3.0.0): per-point LCG stream state keyed by point name, where the seed *is* the state, so on restore "named points continue exactly where they left off." Randomness is what would otherwise make a branch reached by restore diverge silently from the same branch reached by replay, and it is the part already solved.

**Versioned save state across a changed story is a problem no IF platform has solved, and this decision does not attempt it** (David, 2026-09-19). Changing a game changes its world model, and every save with it. That is a fact about player saves, and the reason save-format versioning in this repository is dormant by decision.

## Decision

**D1 — The pane replays the active line, and only the active line.** On load it replays one path: the line the session was left on. On a click into another line it replays that one. The three-phase eager walk in `replayTree` is deleted rather than reorganized.

*Correction of record, 2026-09-20, session 1bd093*: this decision as first written also said the `intact`/`break` bookkeeping goes. It did not, and reading the shipped code is what says so — `replayTree` still tracks `intact` across the main line's own commands and still guards the hand-off to the active line with it (`tools/ide/web/testing-surface/src/main.ts:890-912`). That is correct as it stands, and for a reason the original sentence had not reached: with the walk gone, `intact` no longer half-aborts a tree traversal — it answers whether the main line's state is sound enough to branch from, which is exactly the question `visitLine` needs settled before it boots. The ADR is corrected to what shipped rather than the code changed to match the ADR.

**D2 — An unvisited branch reads as unvisited. Taking its verdict from the run column is BLOCKED on a line identity that exists** (amended 2026-09-19, same session, before implementation).

As first written this decision said an unvisited line takes its pass/fail from the run column, since `run.ts` folds `test --tree --json` per line. Measurement says it cannot, and the reason is upstream of this ADR.

A line's identity on the wire is its **derived label** (ADR-307 D2/Q-8), and a derived label is not unique. Measured against `secret-letter`, 2026-09-19, from the CLI's own `transcript-start` events under the exact arguments the run column uses: **61 lines, 37 distinct labels, and 31 of the 61 sharing a label with another line** — `top-of-the-post · d` names ten different lines, `alley · se` nine. The column therefore folds **385 of 566** card results, later ones overwriting earlier under the same key, and shows "not run yet" against labels it derived that match nothing emitted.

The tree itself is healthy: the same run reports `totalPassed: 566, totalFailed: 0, totalUnreached: 0` across all 61 lines. **Nothing is failing to run; results are failing to land.** Nor is this the pane's defect — the CLI emits the colliding labels, so both consumers inherit it.

So what stands and what does not. **An unvisited line reads as unvisited — that part stands**, and it is what D1 requires. **Its verdict does not come from the run column until a line carries a stable identity distinct from its display label**, which is a change to what the run emits (`packages/branch-tester`) and therefore a platform change needing its own discussion under CLAUDE.md, not a decision this ADR may take. Until then an unvisited line is honestly unknown, and saying so is better than showing a verdict belonging to a different line that happens to share a name.

**This does not gate D1.** Visiting one line at a time is right whether or not the column can speak for the rest; it only means the pane says less about what it has not visited than this ADR first claimed.

**D3 — The whole-tree answer stays the CLI's job.** The pane does not own "is this tree green"; `test --tree --json` does, and the Run button already carries it into the run column. **The speed gap is two observed rates, not a projection**: the CLI puts 3,854 commands through in 6 seconds (≈640/s) where records reach the pane at ≈42/s — roughly fifteen times, and both numbers were watched rather than computed from each other.

**D4 — A branch image is build-scoped derived state, with no version, no reader, and no shim.** Entering a branch may restore a saved image of its parent's state and run only that branch's own commands, instead of retyping the prefix. An image is keyed to the IR the build emitted and does not outlive it: a rebuild orphans every image, and the cache is reconstructed on demand. There is no migration path because there is nothing to migrate — a stale image cannot be read, so the failure mode where a test passes against a world that no longer matches its source is structurally absent rather than guarded against.

**D4a — A restore is a fork boot, and says so in the shape the wire already has** (David, 2026-09-19, session 04d4dd, Q-1: "a"). Entering a branch by restoring an image stamps a new lineage carrying `parentLineage` — the line the image was taken from — and `forkOrdinal`, the card it was taken at. That is the existing boot-lineage shape (ADR-306 **Phase 2** — the phase of the plan that ADR-306 heads, `docs/work/testing/plan-20260809-testing-surface-revamp.md`, not a section of the ADR, which has none; the shorthand is inherited from `turn-events.ts`'s own header and is kept here so the two read alike), the one the embedder injects through `__SHARPEE_PLAY_LINEAGE__` and whose own source calls it "the IDE's branch-replay boot." **Nothing is added to the wire and no reader learns a new field.**

What the mechanism does not cover today is timing, not shape: `ensureLineage()` reads that global once per page and caches it, because a fork has always begun with a navigation. A restore happens inside a live page, so the stamp must become something the client can apply mid-page rather than a global read at document-start. That is the whole of D4a's implementation.

**The signature** (proposed 2026-09-20, session 1bd093; `adr-review` found that D4a named no shape, so this is the shape to rule on, not one already agreed). `turn-events.ts` keeps its lineage in three module variables — `playLineage`, `bootLineage`, `bootLineageId` — initialized once by `ensureLineage()` from the boot global (`packages/platform-browser/src/turn-events.ts:135-143`) and advanced at each fence by `emitRestartEvent()`, which does `playLineage = ensureLineage() + 1` (same file, 211-218). A restore rides an in-page reboot, so it passes through that fence. The stamp therefore **arms the fence** rather than adding a second increment:

```ts
/** Arm the NEXT restart fence to open a fork lineage rather than a plain one:
 *  its records carry `parentLineage`/`forkOrdinal`, exactly as a boot global's
 *  would. Consumed and cleared by the fence it arms. */
export function armForkLineage(parentLineage: number, forkOrdinal: number): void;
```

`emitRestartEvent()` consumes the armed value as it increments, setting `bootLineageId` to the new id and `bootLineage` to `{ id, parent, fork }`, so `emitTurnEvent`'s existing boot-lineage branch (same file, 196-201) stamps both fields with no edit of its own. **Rejected: having `ensureLineage()` re-read the global on each call**, which makes every caller's lineage depend on when the embedder last wrote a global and turns a once-per-page read into ambient state.

**Rejected: treating a restore as a fence** (a restart — new lineage, no parent). It is the smaller change and the wire already does it, but a fence deliberately carries no ancestry, and ancestry is the one thing the tree is about; the surface folds by ordinal and would have nothing to bind a restored branch's records to. **Also rejected: a new `restoredFrom` field** — it states the fact most explicitly and costs every reader a field, both native heads' generated protocol types moving with it under rule 8b, to say what `parentLineage`/`forkOrdinal` already say.

**D4b — Images live in the head's own cache container, keyed by the IR, and never beside the story** (David, 2026-09-19, session 04d4dd):

```
~/Library/Caches/<bundle-id>/branch-images/<storyId>-<projectRootHash8>/<irHash8>/…
```

Caches rather than Application Support is the semantic, not the convenience: macOS may purge Caches at any time, and D4 already makes an image disposable, so an OS purge is indistinguishable from a rebuild. The existing split in the shipping app is the precedent and it cuts the other way for the other artifact — the testing *session* (active line, dialog outcomes, collapsed state) is in Application Support at `net.sharpee.chord-writer/testing-sessions/<storyId>-<hash8>.json`, because losing an author's place in the tree is not acceptable, while losing a reconstructible image is.

`<projectRootHash8>` is a SHA256 prefix of the project root path, the same keying `TestingSessionStore` already uses, so two checkouts of one story do not collide. `<irHash8>` is what makes D4's invalidation trivial: a rebuild writes a new hash and dropping the old directory is the whole implementation, because nothing has to reason about staleness when nothing can read a stale image.

Each head uses its own container; images are not shared between the Swift and Avalonia heads, since per-build scratch shared across two apps couples their lifecycles to buy nothing. And they are **never** written beside the story, where `<story-id>.tests.json` lives: that folder is authored content an author commits, and a cache landing in it would appear in their `git status`.

**Image size needs no eviction rule** (measured 2026-09-19). Two real `secret-letter` saves taken from the shipping IDE's Play window — at turn 2 and turn 6 — are **34,466 and 37,360 bytes** as stored (`lz-string` `compressToUTF16`, read out of the Play pane's WebKit localStorage). At roughly 35 KB each, sixty branch points is about 2 MB, so D4 caches every branch point it is asked for and evicts nothing. Should a story ever make that false, the `<irHash8>` directory is already the unit an eviction rule would operate on.

**D4c — The restore door already exists: the client's own boot-time autosave restore** (named 2026-09-20, session 1bd093; `adr-review` found the pane→client door unnamed).

`driveFreshBoot` reboots the client in-page by clearing storage and typing `restart` (`tools/ide/web/testing-surface/src/main.ts:753-760`). On the way back up, `BrowserClient.start()` reads the autosave slot and, when one is there, applies it to the engine before the first turn — `loadAutosaveEnvelope()` → `engineApplySave()` → turn count, score and transcript HTML (`packages/platform-browser/src/BrowserClient.ts:606-628`; `autoSave` defaults to `true`, same file, 146-150). So the door is: **write the image into the autosave slot between the clear and the restart, and the client restores it unprompted.**

An image is the bytes already sitting in `localStorage` under `<storagePrefix>save-autosave` — an `lz-string`-compressed `BrowserSaveEnvelope` the client wrote itself on the prefix's last turn (`packages/platform-browser/src/managers/SaveManager.ts:294-307`), and what D4b's 35 KB measured. The pane copies that string out after a prefix lands, posts it to the host over the existing `testingSurface` handler for D4b's cache, and copies it back in when entering the branch. **No serializer runs in the pane, no format is parsed, and no platform code changes** — which is what keeps D5's "same bytes, opposite obligations" literal at the door as well as in the cache.

**Rejected: typing `restore` and driving the restore dialog** (`runRestoreDialog`, `BrowserClient.ts:855`). It is the player's door, it makes the pane drive a dialog's DOM, and it writes a `[Game restored from …]` line into the transcript that belongs to no test.

**D5 — A player save and a branch image share a serializer and nothing else.** A player save is a durable artifact that must survive the story changing under it — the unsolved problem, deliberately parked. A branch image is a cache with the lifetime of a build, like the world index. They are the same bytes with opposite obligations, and the distinction is load-bearing: it is what lets D4 consume an interim save format without making that format durable.

**D6 — Images and laziness compose; laziness lands first.** D1–D3 are subtraction and need no new concept. D4 is addition and needs Q-1 answered. Shipping D1 first means the pane is fast before anything is built, and means D4 is measured against a working baseline rather than against a stall.

**D7 — The tree document, the CLI, the assertion core and the pinned seed do not change.** This decision is confined to one pane's replay strategy. An author on devkit sees nothing.

**D8 — This supersedes the premise of the plan's Phase 17** (parallel branch replay, with dead-player and failed-card handling under concurrency). Phase 17 existed to make an eager whole-tree replay affordable by running branches concurrently; D1 removes the replay instead, and there is nothing left to parallelize, no per-branch seed isolation to preserve under concurrency, and no cross-branch failure coordination to design. Phase 17 is marked superseded rather than re-scoped. **Phase 16's subject is not superseded, but its deliverable was overtaken later in this same session**: the surface became a `story-ending` consumer (`tools/ide/web/testing-surface/src/ending.ts`), because the seam turned out to be the cause of the defect in the Consequences below rather than a design question waiting on a ruling. What Phase 16 still owns is the presentation call — whether cards after an ending read as *ended* or as *failed*, which are different claims about a story — and the ADR that decision may deserve. A branch entered by click can still reach an ending mid-prefix; it now stops there instead of typing into a stopped engine.

**Who flips what** (named 2026-09-20, session 1bd093, answering an `adr-review` finding). Phase 17's SUPERSEDED mark in `plan.md` is this ADR's own consequence and was written in session 04d4dd — it needs no further owner and no further action. **Phase 16's remaining deliverable is a ruling only David gives**: whether a card reached after an ending reads as *ended* or as *failed*, which are different claims about a story. Until he gives it, Phase 16 stays open with its implementation already shipped, and **no session may close it by inferring the ruling from what was built** — which is the specific way this phase nearly closed itself.

## Acceptance Criteria

Added 2026-09-20, session 1bd093: `adr-review` found the ADR carried neither acceptance criteria nor test requirements. Each criterion names what decides it, and is graded per DevArch's self-verifying test — does the criterion's own mechanism detect the failure of its premises, or does a premise need establishing first?

**The end-to-end scenario all of these serve**: an author opens a `secret-letter` tree of 61 lines in the packaged head; the pane comes up on the line they left, live and typeable, in about two seconds, having visited nothing else; the other sixty read as unvisited rather than borrowing a namesake's verdict; clicking one enters it — by replaying its prefix today, by restoring its parent's image once D4 lands — and its cards bind to turns as if it had been typed; and a line whose prefix reaches an ending stops there, with what landed, instead of typing into a stopped engine.

**D1–D3 are shipped and AC-1 through AC-4 grade what landed. AC-5 through AC-7 gate work that may not begin**: D4a needs David's ruling on the platform change the Scope line now names, and D4/D4c wait behind it.

**One shipped criterion is not met today, and saying which is the point of writing them down.** AC-3 still needs a unit test that does not exist and cannot be written where the code currently lives: `main.ts` exports nothing — it is the DOM entry module, and the surface's own `vitest.config.ts` says so in as many words ("the DOM layer and the Swift bridges are covered by the IDE's real-path XCTest suite instead"). **AC-4 was in the same position and was discharged in session 1bd093** by extracting the rule it asserts on into `src/visit.ts`, the same move `Shell/ProjectPaneLayout.cs` made in session 04d4dd when mutation-verification found a probe that logged state without asserting on it. AC-3's own rule lives in the run column's fold and would need the same treatment.

1. **AC-1 (D1) — the pane visits one line per load.** Against `secret-letter` in the packaged head, the driver trace (`trace()` → `testingConsole`) carries **at most one** `boot line …` entry for a load — one when the session was left on a branch, **none** when it was left on the main line, which `replayTree` types directly without a fresh boot — and `grep -n "for (const lineId of model.lineIds())" tools/ide/web/testing-surface/src/main.ts` returns nothing. The grep names the deleted loop exactly, because `model.lineIds()` itself survives as a membership check on the same path and a looser pattern would match it. **SELF-VERIFYING** — a surviving walk shows up as a second trace line, in the mechanism the criterion reads.

2. **AC-2 (D1) — load cost is one path, not the sum of prefixes.** The same load releases the input and settles the main line's **75 records** in under five seconds, against a baseline that ran past 240 seconds without finishing. **PREMISE-DEPENDENT on AC-1** — a fast load proves nothing on its own, since a load that visits one line and a load that silently gave up look the same from a stopwatch; AC-1's trace is what distinguishes them.

3. **AC-3 (D2) — an unvisited line reads as unvisited, never as its namesake.** A test builds a model with two lines sharing one derived label — the measured condition, 31 of 61 in `secret-letter` — and asserts the unvisited one renders as unvisited rather than carrying the other's verdict. **SELF-VERIFYING**, and **not met today** — no such test exists. The collision is the premise and the assertion at once. Must fail if a later session reinstates "take the verdict from the run column."

4. **AC-4 (D1's branch-click path) — a clicked branch replays its prefix suppressed and types its own cards live.** `visitLine()` is asserted to hand `driveFreshBoot` the prefix as `replay` and the line's own cards as `live`, and a click against a real tree produces bound cards on the clicked line. **SELF-VERIFYING**, and **met 2026-09-20, session 1bd093.** The split rule moved out of `main.ts` into `src/visit.ts` as the pure `visitPlanOf(path, prefixLength)`, and all four replay paths — visit, branch, delete-realign, tail-cut — now share it. The extraction closed a seam as well as enabling the test: `prefixSteps` had derived its keys from `pathStepsOf` while `visitLine` re-derived the live steps from `ownCommandsOf` with a hand-built key, two derivations of one rule. Evidence: `tests/visit.test.ts`, 12 tests including the regression itself (a branch with its own cards can never return an empty `live` list) and four driving the real `TreeSessionModel`; `npx vitest run` in `tools/ide/web/testing-surface` → **11 test files, 113 tests passing**, `npx tsc --noEmit -p tsconfig.json` → clean, no output. This is the regression D1 introduced and closed in the same session, so the criterion exists because the failure did.

5. **AC-5 (D4, D4c) — a branch reached by restore is the same world as one reached by replay.** One branch point is entered twice, once by prefix replay and once by image restore, and the world digest at that point is asserted identical — including a story whose prefix draws from a seeded point, since per-point stream state (ADR-293 D7) is the part that would diverge silently. **SELF-VERIFYING** — divergence is exactly what it asserts against, and the seeded case is what makes the assertion able to fail.

6. **AC-6 (D4a) — the armed fence carries ancestry, and the arming does not leak.** In `packages/platform-browser`'s own tests: arm a fork, emit a fence, assert the following records carry `parentLineage` and `forkOrdinal`; then emit a **second** fence and assert its records carry neither. **SELF-VERIFYING** — the second half is the criterion. A stamp that outlives the fence it armed would mark every later lineage a fork of the same parent, which no reader could detect downstream.

7. **AC-7 (D4b) — a rebuild orphans every image, and nothing reads a stale one.** After a rebuild writes a new `<irHash8>`, the pane reconstructs on demand, and `grep` over the head's cache reader shows no path that resolves an image outside the current `<irHash8>` directory. **SELF-VERIFYING on the grep** — D4's whole claim is that a stale image *cannot* be read, so a reader that could reach one falsifies the decision rather than failing a test.

8. **AC-8 (the ending seam, shipped 2026-09-18) — a prefix that ends stops there.** `driveFreshBoot` returns `'ended'` rather than `'ok'` or `'failed'` when the story ends mid-prefix, and no command is typed after it. Evidence, re-run 2026-09-20 in session 1bd093 after this ADR's amendments and the `visit.ts` extraction: `npx vitest run` in `tools/ide/web/testing-surface` → **11 test files, 113 tests passing**; `npx tsc --noEmit -p tsconfig.json` → clean, no output. **SELF-VERIFYING** — `'ended'` and `'failed'` being distinct return values is what the assertion rests on; collapsing them to a boolean would make the criterion unstateable, which is why they are not.

**Not an acceptance criterion, deliberately**: "the pane is fast now." D1 removes visits, the ending fix removes thousands of refused turns, and D4 would remove replays — three different causes with one visible symptom. A single timing that covers all three is how a regression in two of them hides behind an improvement in the third, which is what the 9× batching result already demonstrated once.

## Consequences

- **`replayTree` gets smaller, not rearranged.** Its second and third phases go, and `driveFreshBoot` — which already replays one line from a fresh boot — becomes the only path, called on demand rather than in a loop. The simplification is the point as much as the speed is.
- **Load time stops scaling with the tree.** It becomes the cost of one path rather than the sum of every prefix, so tree size stops entering the figure at all — the gap the old behavior opened between fernhill's 11 lines (270 records, replayed intact in an earlier session) and `secret-letter`'s 61 (3,854 executed commands) simply has nowhere to land. For `secret-letter`: from a replay never observed to finish — past 240 seconds when last left running, estimated at ~90 by arithmetic the Context labels as such — to the main line's **observed 1.8 seconds**.
- **The pane and the CLI take on distinct jobs, stated.** Live and interactive for one line; complete and fast for the tree. Neither is a degraded version of the other, and "the pane is slow on big trees" stops being a defect to fix and becomes a job it does not have.
- **The save format stays interim without that becoming a liability.** D4 consumes it within a single build and never across one, so the dormant versioning decision is unaffected. This is the consequence D5 exists to protect; if a later session finds itself wanting an image to survive a rebuild, that is this ADR being violated, not extended.
- **A restored branch is indistinguishable on the wire from a replayed one.** D4a makes an image's records carry the same ancestry a fork boot's do, so the surface's fold-by-ordinal binding, the run column and any future reader all treat "arrived by restore" and "arrived by retyping the prefix" identically. That is the property that lets D4 be a pure optimization rather than a second semantics.
- **`ensureLineage()`'s once-per-page caching becomes a constraint to change, not a bug.** It is correct for every case that exists today; D4a is what first needs a lineage stamped without a navigation.
- **This decision does not fix the defect that makes a big tree unusable, and that defect is the ending seam.** Observed by David 2026-09-19 in **both heads identically**, which is what rules out either host and places it in the shared surface: partway through the replay a branch's prefix reaches an ending, the engine enters the `stopped` phase, and every command after it is refused with *"the engine is in the 'stopped' phase … The game has ended; only meta commands (RESTART, RESTORE, QUIT, UNDO) are accepted."* Each refusal still returns a completed turn record, so `awaitNextTurn` resolves, the driver counts the step as landed, and it walks on — turn 1929, 1930, … 2470, every one the same error, every assertion failing, every one rendered as a card. The engine states the fact in prose on every turn and nothing consumes it, because the surface is not a `story-ending` consumer (ADR-347 D3a). **This is not a performance problem that D1 fixes; D1 reduces how many branches are visited, and one branch that ends is enough.** Its resolution is the plan's Phase 16, which this ADR deliberately leaves standing.
  - *Correction of record*: an earlier reading in this session held that the Avalonia head's replay stalled silently after the main line. That was an artifact of the host logging one record in twenty-five; unsampled, records continue. One environment difference remains unexplained — an unsampled run here stopped at 78 records where David's reaches turn 2470 — and is deliberately not folded into the explanation above.
- **A branch image is about the size of a player save, because it is one.** The measured 35 KB is the same `ISaveData` a player's save slot holds, which is what makes D5's "same bytes, opposite obligations" literal rather than figurative.
- **One fewer Large phase.** D8 removes Phase 17 (400 tool calls, provisional) from the plan, and the concurrency, seed-isolation and failure-coordination design it carried.
