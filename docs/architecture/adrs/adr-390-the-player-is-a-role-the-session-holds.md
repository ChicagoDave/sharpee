## Context — verified, not assumed

Every line read 2026-10-31 at `5d0ebab3e` on `feat/adr-389-chord-loader`.

**Two serialized facts, three writers, one cache.** `WorldModel` stores `private playerId` (`WorldModel.ts:596`), returns it through `getPlayer()` (1517), writes it through `setPlayer()` (1521), and carries it in the snapshot (1640, 1723) and the restore (1631). `ActorTrait.isPlayer` is a separate boolean on the actor (`actorTrait.ts:190`, `makePlayer()` at 235). The writers: `GameEngine.switchPlayer` clears the old flag, sets the new, then calls `world.setPlayer` (`game-engine.ts:1119–1132`); the install step `createPlayerStep` calls `world.setPlayer` after the story's `createPlayer` has set the flag alone (`install/create-player.ts:21–23`, `loader.ts:818–820`); `ActorTrait.makePlayer` sets the flag with no world write. `GameContext.player: IFEntity` (`types.ts:231`) is refreshed by `syncPlayerState` (1180) and is not serialized. `ActorBehavior.findPlayer` already derives the holder from the flag by scanning (`actorBehavior.ts:219`), so the derivation this record makes canonical exists and is unused for that purpose.

**The role already has a module.** `world-model/src/traits/actor/playerRole.ts` owns the role's vocabulary — `addPlayerRoleVocabulary`, `movePlayerRoleVocabulary` — with a header that says the self words "belong to the ROLE and travel with it when the role moves." The role is a concept the code half-names.

**"Is this the player" is written by hand.** `world.getPlayer()?.id === …` appears ten times in story-loader (`evaluator.ts:471, 985`; `loader.ts:1476, 2859`; `runtime/timers.ts:100, 282`; `runtime/statements.ts:614, 757`; `runtime/move-clauses.ts:67, 85`), 21 times in stdlib, 10 in the engine. Across `packages/`, `tools/`, and `stories/` (archives excluded), `getPlayer()` has 137 non-test call sites — 59 of them in `stories/dungeo/src`, across 45 files with its tests — and 127 in tests; `setPlayer(` has two production callers (`game-engine.ts:1132`, `install/create-player.ts:23`) and 247 test-fixture calls, the `world.setPlayer(player.id)` line nearly every stdlib golden test and Dungeo unit test opens with. Each non-test read decides something only the role decides: whether a move narrates as travel, whether a timer is the player's, whether a clause's actor is the player. The viewpoint is read from the cache: `turn/enrich-events.ts:55, 59, 75` and `turn/sound-dispatch.ts:52` pass `engine.context.player` to perception, presence, and sound witnessing.

**Meta commands are gated on typed input only.** `turn/parse.ts:64` routes a parsed command to `meta` when `MetaCommandRegistry.isMeta(actionId)`. The execution entry `executeAsActor` (`game-engine.ts:1224`), which NPC behaviors and Chord acting statements use, does not consult the registry, so nothing today stops a non-player actor from performing `save` or `quit` if a story asked it to.

**The loader resolves the role in three places.** `playerWorldId()` (`loader.ts:651`) returns `this.playerId ?? this.runtime.assignedPlayerId`; `assignedPlayerId` is set by the start block's `change the player to` (`runtime/statements.ts:201`) and stamped as the flag later, by `finalizeRoleHolder` (838) and again by `createPlayer` (820); `this.worldIds.set('player', assigned)` (850) is the alias every load-time `player` reference resolves through, because the compiler's `resolveEntityId` returns the id `player` for "the player" in any entity-reference position (`analyzer.ts:8444–8448`, 28 call sites) and only value positions are lowered to `{kind: 'player'}` (8040). `EntityIdResolver` (`evaluator.ts:86–90`) exists to hand `playerWorldId` to the evaluator.

**Several sessions over one world.** David's standing direction is multi-user, not multiplayer. A `playerId` on the world says one player per world; that is the single-player case written into the model.

## Decision

- **D1 — One world fact: the role flag on the actor. The world derives the holder and never stores it.** `WorldModel.playerId`, `getPlayer()`, `setPlayer()`, and the snapshot's `playerId` field are deleted, from the concrete class and from `IWorldModel` alike (one-shot cutover, no shim). In their place, three members: `playerCharacter: IFEntity`, a getter that scans the actors for the one whose `ActorTrait.isPlayer` is set and **throws** when none is (resolved: David, 2026-10-31, "I'm reading that we'd throw" — yes; a read before the start block has assigned the role is a bug, and `undefined` would let it flow on as a missing id) and throws when more than one is, naming both, so the invariant "exactly one actor holds the role, or none yet" is asserted, not hoped (DevArch rule 6); `hasPlayerCharacter: boolean`, for the few load-time readers that legitimately run before assignment (the removal observer at `loader.ts:2859` is one); and two entry points over one private writer (amended 2026-10-31, David: "changePlayer has different housekeeping than setPlayer" — "can't we restrict setPlayer to that start game period?"): `setPlayer(entityId): IFEntity`, the first assignment, which throws when an actor already holds the role, and `changePlayer(entityId): IFEntity`, the move, which throws when none does. The world knows no turns, but it knows whether the role is held, and that is the start-game boundary. Both require an `ActorTrait` with `isPlayable`, clear every other actor's flag, set this one's, move the role vocabulary through `movePlayerRoleVocabulary` with the world's own self words, and return the holder — so "exactly one actor holds the role" is kept in the one private writer behind them. **As landed (2026-10-31)**: `setPlayer` on the actor who already holds the role is a no-op, not a refusal — a fixture that constructs its actor trait with `isPlayer: true` and then sets the player is naming the same holder twice, and the one writer's invariant is untouched; only a *different* existing holder makes it a change. `ActorTrait.makePlayer()` is deleted: a trait cannot clear its siblings, so it was the writer that broke the invariant. `ActorBehavior.findPlayer` becomes the getter's implementation. The restore path needs nothing: the flags ride in the entities, and the snapshot's `playerId` was a copy of what they said.

- **D2 — The `Player` is the session's role, and it lives in the engine.** `packages/engine/src/player.ts` declares `Player` with: `readonly character: IFEntity` (a getter over `world.playerCharacter`; throws the same way); `is(actorId: string): boolean`; `permits(actorId: string, actionId: string): boolean` — true for every action when `actorId` is the player, false for a meta action (`MetaCommandRegistry.isMeta`) when it is not; and `viewpointId: string` (the character's id, the one value perception and presence tagging take). `GameEngine` exposes `readonly player: Player`, constructed once with the world and the registry. `GameContext.player` keeps its type, `IFEntity`, because every action reads the character there, but it becomes a getter that reads `engine.player.character` — computed, never assigned — so `syncPlayerState` stops writing it and #394's "third copy" is gone. The Player holds no state of its own in this record; what it holds is identity, permission, and viewpoint. Role-level *state* — command history, the undo stack, what else should travel when the PC rotates — stays in the turn stages where it is (`turn/command-history.ts`, `turn/undo-snapshot.ts`) and is Reflections' decision (ADR-319), not this one. The Player is one per engine today; being session-scoped rather than world-scoped is what leaves room for several over one world later, and nothing here assumes one.

- **D3 — The role moves through one path, and Chord's `player` is resolved against it at use time.** `engine.switchPlayer(id)` becomes `world.changePlayer(id)` followed by the session resync (parser world context, pronoun reset, narrative settings — the body of `syncPlayerState` minus the `context.player` write); the flag juggling at `game-engine.ts:1119–1132` goes. The install step keeps `world.setPlayer(player.id)` — now the first assignment through the one writer — and `createPlayerStep` adopts `world.playerCharacter`. **As landed (2026-10-31)**: the role write is its own install step, `assign-player-role`, placed after `validate-role-holder` and before `stamp-player-self-words`, because the world's writer refuses a non-playable holder too and ADR-344's typed `RoleHolderValidationError` must come first; `create-player` only adopts the entity. In the loader, the start block's `change the player to X` calls `world.setPlayer(X)` at the moment it runs (a later conditional line, with a holder already assigned, calls `changePlayer`) (`runtime/statements.ts:201`), so the role is a world fact from the assignment onward and the start block's later lines (`start the player's bell`) read it from the world; `assignedPlayerId`, `playerWorldId()`, `finalizeRoleHolder`'s stamping, `createPlayer`'s re-stamping, `EntityIdResolver`, and the `'player'` alias write are deleted. `createPlayer` keeps its ADR-344 refusal wording when the start block assigned nothing, now triggered by `hasPlayerCharacter` being false. The compiler's `player` sentinel is resolved in one loader function, `worldIdOfRef(ref, world)`: `ref === PLAYER_SENTINEL ? world.playerCharacter.id : ref`, with `PLAYER_SENTINEL = 'player'` exported from `state-keys.ts` beside the key vocabulary; every site that turns an IR-sourced entity reference into a world id goes through it, and the ten hand-written `world.getPlayer()?.id` comparisons become `engine.player.is(actorId)` where the engine is in reach and `world.playerCharacter.id` where only the world is. Before the role is assigned the sentinel throws through `playerCharacter`, which is the same moment the alias used to yield `undefined` and `requireWorldId` threw "referenced before it exists" — the behavior is unchanged, the message is the getter's.

- **D4 — The execution entry refuses what the role does not permit.** `executeAsActor(actorId, actionId, …)` asks `engine.player.permits(actorId, actionId)` and refuses a meta action for a non-player actor with an `ActResult` that names the action and the actor; the typed-input route in `parse.ts` is unchanged (typed input is always the player's). Today nothing refuses; this is the one behavior this record adds, and it is the activity-only-the-PC-can-do case made a rule.

- **D5 — The viewpoint is read from the Player.** Where the engine today passes `engine.context.player` to perception filtering and presence tagging (`turn/enrich-events.ts:55, 59, 75`, ADR-328 D3), sound witnessing (`turn/sound-dispatch.ts:52`), and narrative configuration (`syncPlayerState`), it passes `this.player.viewpointId` or `this.player.character`. No signature in `if-services` or `stdlib` changes; the parameter's *source* changes, so a later record that gives a session a viewpoint other than its character's has one line to move.

- **D6 — Every reader moves in one cut.** **As landed (2026-10-31)**: the sweep also had to reach three places no `.ts` grep saw — the devkit story template (`templates/story/index.ts.template`), the explorer probe (`tools/explorer-probe/*.js`), and `@sharpee/ext-testing` (a path the word "test" had filtered out) — and the branch-tester claims walk, which keyed each state's identity on the snapshot's `playerId` and now takes the holder from the live world at capture (`claims-game.ts` `readWorldSnapshot`). The 137 non-test `getPlayer()` call sites, the 127 in tests, the two production `setPlayer` callers (one becomes `changePlayer`), and the 247 test-fixture `setPlayer` calls are checked in the same phase; there is no deprecation period and no alias (David: no backward compatibility). A fixture's `world.setPlayer(player.id)` keeps its spelling but now goes through the one writer, which requires the fixture's actor to be `isPlayable` — a fixture whose player is not is a fixture that was lying, and is corrected. A reader that may run before assignment checks `hasPlayerCharacter` first; one that cannot run before assignment reads `playerCharacter` and lets it throw. The stdlib's 21 reads are inside actions and scope, which never run without a player, so they read `playerCharacter` directly; Dungeo's 59 are story code and tests over a built world and read it the same way. `tools/_archive` and `stories/_archive` are not touched.

- **D7 — Byte-identical, with Dungeo in the net.** The phase ends with the Dungeo walkthrough chain (`node dist/cli/sharpee.js --test --chain stories/dungeo/walkthroughs/wt-*.transcript`) at its count before the phase, the three Chord test trees byte-identical to their last capture (ADR-389 Phase 0 baseline), and the world-model, engine, stdlib, and story-loader suites at their counts or higher. Dungeo enters this net because `setPlayer`/`getPlayer` are platform members every TypeScript story's install path uses; it never enters ADR-389's.

- **D8 — One phase, ahead of ADR-389 Phase 2, discuss-first.** This record is implemented as its own phase in `docs/work/adr-389-chord-loader/plan.md`, inserted before "One identity (D1)" so that D1 there is the pure deletion it was written to be; the phase touches `packages/` and needs David's go. GitHub #394 closes with the phase's commit.

## Consequences

- The player's identity has one serialized source — the flag on the actor — one derivation, and one writer. A story or test that flips `isPlayer` by hand cannot produce a world that disagrees with itself, because there is no second place to disagree with.
- "The player" means the role, and the role is the session's. The world knows which actor holds it; the engine knows what the role may do and from where it looks. A second session over the same world is a second `Player`, not a second `playerId`.
- Chord's `player` sentinel has one resolver, and ADR-389 D1 can delete the loader's id maps without losing it.
- A non-player actor can no longer be made to save, restore, or quit through an acting statement or an NPC behavior.
- The world snapshot loses `playerId`. No released story has a save, the format's version and reader are dormant, and nothing is written to read the old field.
- ADR-327 D10's "the `player` sentinel every load-time reference resolves through" and ADR-344's "the install seam refuses an unplaced holder" both still hold; their mechanism changes from a map entry to a world getter. GitHub #394 closes.
- Not decided: what role-level state travels with the PC when it rotates (ADR-319), and whether a session's viewpoint can differ from its character. Both now have one place to be decided from.
