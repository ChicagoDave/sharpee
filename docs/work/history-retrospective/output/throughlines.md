# Throughlines

Phase 4 of the history retrospective: eight cross-cutting arcs, each traced by its
own reader across the full corpus and **verified against git rather than against the
monthly digests**. Every tracer was required to return counter-evidence and to state
what it checked directly versus took second-hand.

## The spine that never moved — and the two vertebrae that were replaced

_world-model-spine_

### Thesis

What survived from StoryRunner (April 2023) to Sharpee 5.0.0 (August 2026) is the decomposition and the vocabulary, not the data structure. The eleven-project split — WorldModel / DataStore / GameEngine / GrammarLibrary / ParserLibrary / StandardLibrary / TextService — maps onto today's packages almost name for name, and that is genuine, load-bearing continuity. The two specific implementation invariants the origin narrative singles out did not survive. The reciprocal typed-edge graph (IsWithin/Contains, IsCarriedBy/Holds) was replaced in July 2025 by SpatialIndex, a single-parent-pointer tree with a derived child index; none of the five C# edge-type names appear anywhere in packages/world-model/src today, and the one API that still resembles typed edges — addRelationship/getRelated — is explicitly forward-only, has zero production callers, and its own unit test asserts the reverse lookup returns false. Publish-on-every-mutation is likewise gone: updateEntity carries a commented-out "Future: Could emit change events here", and the only surviving emitter is a debug sink that no shipping code ever constructs. Event sourcing was formally dropped in December 2025 as an "unnecessary technical rathole"; save/restore is a gzipped world.toJSON() snapshot, not a replay. The trait system (June 2025) is a real replacement of the C# Thing → Person → Player chain, not a rename — and the one later attempt to reintroduce a class hierarchy (ADR-123, January 2026) was built and reverted. The honest finding: the spine held at the level of how the system is cut into parts, and was rebuilt from scratch at the level of how state is stored and how change is announced. Both replaced invariants are now, in ADR-278 (July 2026), proposed for reintroduction as a new feature — prompted by an outside user request, not by memory of the prototype.

### Analysis

**What actually persisted.** The strongest continuity claim is also the least glamorous: the decomposition. StoryRunner's project list and today's package list line up without strain, and this is not coincidence-by-naming — the *dependency direction* matches too. `DataStore` knows nothing about IF; `@sharpee/core` is likewise "a generic event/entity engine" after the July 2025 core/world-model split. `TextService` sat downstream of the world in 2023; the prose pipeline does the same today (even though `@sharpee/text-service` was itself deleted under ADR-174 — the *slot* survived its occupant). `GrammarLibrary` separate from `ParserLibrary` prefigures `parser-en-us` holding grammar patterns while the validator resolves entities. That layered cut has been re-derived under pressure repeatedly (ADR-062 pulling English out of world-model; ADR-210's rule that no platform package may depend on `@sharpee/chord`) and has never inverted. If the throughline has a spine, this is it.

The second real survivor is an idea rather than a structure: **presence is the state**. `Story.cs:278` decides scenery by asking whether a property named `"scenery"` exists on the node. ADR-148 (April 2026) decides concealment the same way — "ConcealedStateTrait's presence IS the state." Between them lie 41 trait directories built on `Map<TraitType, ITrait>` and `entity.has(type)`. This is continuity of a *design instinct* through a total change of mechanism, and it is worth separating from the mechanism claims because it is the one place where the 2023 code and the 2026 code would give the same answer for the same reason.

**What changed name only.** Very little, and I want to be careful here because this is where the throughline is most tempting and most wrong. `WorldModel` → `WorldModel` is a name match over different contents. The C# `World` was a `Dictionary<string, Node>` plus a registry of `EdgeType(name, reverseName)` pairs; today's `WorldModel` is an entity map plus a `SpatialIndex` plus twelve unrelated concerns (capabilities, scope rules, score ledger, scenes, regions, prompt, walls). `Behavior` is the one genuine name-only survival: C#'s `Behavior`/`Scenery`/`Container` classes are dead code with zero references, and today's behaviors are the mutation-owning half of the trait/behavior split — same word, no lineage.

**What was replaced.** Two things, and both replacements are documented decisions rather than drift.

*The graph.* `SpatialIndex` is not a lossy implementation of the property graph; it is a different data structure chosen on purpose and named accurately in ADR-015 as a "Parent-Pointer Tree with Child Index… as a DAG." The reciprocal invariant survives only in the weak sense that `addChild` writes both maps atomically, so you cannot observe a child whose parent does not list it. What does *not* survive is everything that made the C# version a graph: typed edges, edges with properties, multiple simultaneous relations between the same pair, and the refusal to store a one-way link. The proof is not inference — `grep` for `IsWithin`, `IsCarriedBy`, or a `'contains'` relation key across `packages/world-model/src` returns nothing, and `world-model.test.ts:487-488` asserts `areRelated(e1,e2,'likes') === true` alongside `areRelated(e2,e1,'likes') === false`. A test that *pins* asymmetry is the clearest possible statement that the 2023 invariant was not carried forward. `IFEntity.relationships: Record<string, EntityId[]>` is a second, separate fossil of the same idea, referenced only by tests and `toJSON`.

*The event on every mutation.* This one is more interesting than a simple loss, because the project rediscovered it. ADR-064 (December 2025) proposes `world.emit('world.entity.changed', {entityId, trait, property, oldValue, newValue})` — which is `PublishPropertyChanged(nodeId, property)` with different capitalisation — records status Accepted, and then ships only Phases 1, 3 and 4. Those phases are `ActionContext.sharedData`: actions capture state *before* the mutation and read it in `report()`. That is the deliberate opposite of announce-on-mutation, and it won because it solved the actual problem (context pollution, `(context as any)._previousLocation`) at lower cost. The residue is visible in source as a two-line comment in `updateEntity` and as `emitPlatformEvent`, which fires only when a `platformEvents` sink is passed to the constructor — and every one of the sixteen production `new WorldModel(...)` sites in this repo passes nothing.

The consequence is that "event-sourced turn cycle" overstates today's system. It is event-*driven*: actions emit `ISemanticEvent`s, `EventProcessor` applies them to the world, handlers return `Effect[]` intents (ADR-075). The direction of causation is inverted from 2023 — there, mutation produced the event; here, the event produces the mutation. And true event sourcing was explicitly refused: "unnecessary technical rathole" (Dec 2025), with save/restore left as a gzipped `toJSON()` snapshot.

**Where the trait system departed from Thing/Animal/Person.** Three specific departures, not one. (1) *No taxonomy.* There is no `Animal`, no `Person`; `ActorTrait`, `NpcTrait`, `CharacterModelTrait` and `HealthTrait` are independently attachable, and ADR-226 (July 2026) collapsed three creature life-state models into one trait precisely because the taxonomic version had drifted. (2) *Data and mutation split.* C# `Person` carried `Alive` as a field on the class; Sharpee puts state in the trait and mutation in a behavior, and enforces it — the September 2025 rule "traits carry mechanical state only; story content moves to event handlers" cut `BreakableTrait` from eight properties to one boolean. (3) *Dispatch instead of override.* C# `OverrideActionDelegate("go", goInNoun, CustomGo)` let a story replace a standard action for one sentence shape; ADR-090 has traits *declare capabilities* that standard actions look up. Same goal — story-specific behaviour without forking the standard library — reached by dispatch rather than by patching the grammar table.

**The uncomfortable ending.** In July 2026 an author asked for Inform 7-style relations. ADR-278's E1 sketch is: declared relation types, cardinality, "symmetric relations maintain both directions atomically", "relation changes emit events". That is `World.cs` from April 2023, specified as new work, arrived at from prior art (Inform 7, TADS 3.1) and a user request, with no reference anywhere in the ADR to the C# prototype. If this is a throughline, it is a circle — and the project does not appear to know it is one.

### Counter-evidence

- The C# invariant was never honored by the C# code. Core.CreateLocation calls ConnectNodes(Player.Id, id, IsIn, null), and World.cs throws on a null reverse type — so the standard library crashes on the first location it creates, then adds the reverse edge with a second one-way call. Story.cs matches on EdgeType == "IN" while Core.cs registers "IsIn". Every action body is empty. Only the DataStore has tests (13 across 277 lines). Calling the reciprocal-edge rule a surviving invariant overstates what it ever was: it was an aspiration in a program that could not run.
- The reciprocal property does survive in effect for containment, which is the only relation any story actually uses. SpatialIndex.addChild writes childToParent and parentToChildren in one call and removeChild cleans the *actual* parent rather than the passed one, so there is no observable state where a child's parent does not list it. Someone could fairly argue the invariant was preserved and only the generality was dropped.
- Three later features rebuild reciprocity by hand rather than abandoning it: ADR-173 walls maintain "both rooms' reciprocal walls collections", doors carry room1/room2 with DoorBehavior.isBidirectional, and ExitBehavior.createBidirectional creates paired exit entities. The idea kept resurfacing at feature level even after the primitive was removed — ADR-278 itself lists wall `between`, conversation participants, and door connections as "hand-rolled two-entity relationships today".
- The event-per-mutation machinery exists in source and is one constructor argument from working. WorldModel accepts an optional ISemanticEventSource and emitPlatformEvent fires on entity_moved and move_entity_failed. This is dormant, not deleted — a weaker claim than "replaced".
- The grammar builder is real continuity in form. ADR-087's grammar.forAction(...).verbs([...]).pattern(':target').build() is recognizably the same fluent-chain idiom as _grammar.Verb("take", Take).Noun.End, and it survived 3.5 years and a language change. What inverted is the axis (verb-centric → action-centric) and the status (authoring surface → generated artifact under ADR-269), not the idiom.
- My reading of the pre-repo era is second-hand on dates. The C# files carry no version control; mtimes place StoryRunner at 2023-04-01 → 04-03 with nine files touched again in 2024-03/05, and the ChatGPT dumps have no absolute timestamps at all. The claim that these invariants date to April 2023 rests on mtime, which records last edit rather than authorship.
- docs/architecture/adrs/2025-01-19-traits-with-builtin-container.md is dated January 2025 — before the repository existed and inside a window with no conversation record — yet its decision (RoomTrait and ActorTrait bundling container functionality) is implemented in the June 2025 code and still holds today (roomTrait.ts:96-98, 144-145). Either the trait system was designed months earlier than the corpus shows, or the file's date is wrong. Unlike the January 2025 work-summary anomaly, this one cannot be resolved by shifting it a year forward, because the decision was already shipped by mid-2025. I could not settle it.
- The decomposition claim has a wobble. WorldModel.ts was deliberately cut from ~1,520 to ~1,194 lines in April 2026 (9b30d893) and is 2,181 lines today, holding capabilities, scope rules, scenes, regions, walls, prompt and score alongside entities and space. The boundaries between packages held; the boundary inside the central class did not.

## Sixteen years to channel I/O: the output path, 2023–2026

_output-path_

### Thesis

Sharpee's output path was rebuilt six times in three years, and every rebuild until the last was a variation on the same wrong shape: a *service* sitting between the engine and the client, producing a stream of text that something downstream had to interpret. The idea that finally replaced it — channels as addressable, independently-produced signals — was not discovered; it was recognized. David invented it as FyreVM channel I/O around 2009–2010, and on 2026-01-13 he watched Claude re-derive it from first principles and said so out loud. But recognition was not sufficient: the January design named channels and still shipped a text service, and the April 2026 attempt to build channels properly failed because it modelled channels as *destinations* to route existing text-blocks into. What made it land was a specific failure on 2026-05-02 — `status.score` and `status.turns` had no production emitters, so a routing layer had nothing to route — which forced the inversion to closure-per-channel: a channel owns its own producer. Once each channel produced its own value, the text service had no job left, and ADR-174 deleted it eight days later (c01208ca, −4,208 lines). Even that was not the end: ADR-300 in August 2026 dissolved the residual `main` channel, explicitly naming the catch-all as "the mistake fyrevm made."

### Analysis

**The shape that kept coming back.** From July 2025 to May 2026 there was always an object called a text service sitting between the engine and the client, and its job was always the same: take a turn's events and produce output. What changed each time was how it was decomposed, never that it existed. ADR-029 (2025-07-14) pulled it out of the engine and gave it a query-based context. ADR-048 (2025-08-06) made it statically wired instead of dynamically loaded. Jul–Aug 2025 spawned three sibling packages, each reimplementing the whole pipeline — five distinct service classes totalling ~1,700 lines of duplicated orchestration. ADR-096 (2026-01-13) collapsed the three into one and separated the contract (`@sharpee/text-blocks`) from the implementation. ADR-133 (2026-02-18) stopped the engine flattening blocks to a string. Every one of those is a real improvement, and none of them changed the shape.

**The January recognition was real but insufficient — and that is the interesting part.** ADR-096 does not gesture at FyreVM; it cites it four times, credits "David Cornelson/Tara McGrew/Jeff Panici, 2009," and states outright that "Keys act as channels (FyreVM pattern)." The design session's own transcript records the moment: *"you just reinvented fyrevm channel IO Mr. Claude."* And yet what shipped on 2026-01-13 was a package called `@sharpee/text-service` whose output was a flat array of blocks with string keys. The channel was a *label on an item in a stream*. A client still had to walk the stream and decide what each key meant, and the engine still decided what order the stream came in. Naming the idea did not restructure the code around it. This is the sharpest finding in the arc: the gap between recognizing an architecture and inhabiting it was fifteen months and two more rewrites.

**April 2026 got the framing right and the mechanism wrong.** By 2026-04-28 the project had explicitly reclassified text-service as a shortcut rather than a destination — ADR-163's Context says "text-service was proposed in 2025 to ship Dungeo... accepted as deferral-to-ship, not as the architectural destination. Channel I/O has been the design intent since the 2010-era fyrevm-server" — and a durable memory was written the same day to stop the same mistake recurring. But the first ADR-163 modelled channels as *destinations*: a `ChannelRule` table with `when` predicates and `extract` strategies routing existing text-blocks into named buckets. That is the January design with a routing layer bolted on. It shipped through Phases 1–3 and 111 tests before it broke.

**What actually made it land was a null result on 2026-05-02.** Phase 4B stopped mid-edit because `status.score` and `status.turns` had no production emitters anywhere in the codebase. A router cannot route a signal nothing produces. The recorded response is the pivot: *"Rather than paper over the gap with interim emitters, the session pivoted to rethink the channel definition model from first principles."* The answer was closure-per-channel — each `IOChannel` carries a TypeScript closure that produces its own value each turn, with no shared router. That single inversion is the whole difference. Once a channel is a *producer* rather than a destination, "the prose" is just one producer among twenty-one, and there is no longer any object whose job is to make the output. The text service was not deleted because someone decided to delete it; it was deleted because after 2026-05-03 it had nothing to do. ADR-174 followed eight days later and removed 4,208 lines.

**What survived tells you which parts were right.** `@sharpee/text-blocks` — the January contract package — still exists and is still the type source: `packages/if-domain/src/channels/types.ts` imports `ITextBlock` and `TextContent` from it, and the current `ProseEntry` wire type is built on `TextContent`. The bracket decoration syntax from ADR-091 (January 6) is unchanged in substance; ADR-174 only moved the `type` field to a pre-resolved `className`. So January was not a wrong turn. January got the *data model* right and the *locus of production* wrong, and the two subsequent rewrites changed only the second.

**And it did not stop in May.** ADR-300 (2026-08-04) found the last residue of the stream model: `main`, a catch-all into which the banner, room name, description, contents, action results and errors all still flowed. The ADR's language is unusually direct about what that meant — *"`main` meant the engine was still making layout decisions that belong to the client, which is the mistake fyrevm made and the reason not to repeat it"* — and D8 dissolves it into seven addressable prose channels with ordering moved onto its own `preferred-layout` channel. So the arc's endpoint is not "returned to a 2009 design." It is "reached the 2009 design in May 2026, then found and fixed a flaw in it three months later." The title's sixteen years measure the distance to arrival, not to correctness.

**One thing the evidence does not support.** The C#-era `TextService` project (2023) is evidence for the *text-service* lineage, not the *channel* lineage. It is a service named for text generation in a solution that also has `GameEngine` and `ParserLibrary`; nothing in the available record shows it did anything channel-like, and the source is not in the corpus. Reading it as the first station on the road to channel I/O over-reads it. The two lineages ran in parallel in David's head from 2009 onward, and they only merged in the repo on 2026-01-13.

### Counter-evidence

- The January 2026 design was NOT superseded — a large part of it is still running. `@sharpee/text-blocks`, created on 2026-01-13, still exists and is still the type source: `packages/if-domain/src/channels/types.ts` imports `ITextBlock` and `TextContent` from it, and today's `ProseEntry` wire type is built on `TextContent`. A framing of 'circled for years, then landed in May 2026' understates how much of the answer was already correct sixteen months earlier.
- Channels did not arrive with ADR-163. ADR-096 (2026-01-13) already names FyreVM four times, credits it by name and year, and states 'Keys act as channels (FyreVM pattern).' ADR-091 (2026-01-06) cites 'FyreVM Channel I/O (2009)' too. The April 2026 ADRs re-derive the channel framing rather than introducing it — which weakens any story in which April is the moment of insight.

## The Forcing Functions: How Sharpee's Consumers Built Its Platform

_dogfooding_

### Thesis

Sharpee's platform was not designed and then populated with stories; it was excavated by them. From the first C# prototype in March 2023 through Fernhill in July 2026, nearly every substantial platform capability landed within days of something built on top of the platform failing to compile, run, or read correctly — and the defects that mattered most were structurally invisible to the review practices that ran alongside. An action that validated but never mutated survived three complete refactors of all 43 stdlib actions in 24 hours and died the first time a story tried to put a cloak on a hook. A save/restore service that dropped the score ledger, all capabilities, all state values and all relationships survived from inception through a 3,164-test audit and a static grader reporting 177 GREEN / 0 YELLOW / 0 RED, because the three tests covering it asserted on fields the broken code never touched. A story compiler shipped a full language surface before anyone discovered it could not declare a door. The claim holds: dog-fooding found defects design review did not. But the record also shows the inverse is false as a general law — a pure documentation exercise (the CS-foundations doc) triggered the single largest cleanup in the repo's history with no story involved — and it shows two distinctive failure modes of the practice itself: forcing functions that never existed still shipped API into the platform (Reflections → `switchPlayer`, zero callers to this day), and the harness that made dog-fooding legible was itself silently skipping commands for months.

### Analysis

**The pattern predates the platform.** `CloakOfDarkness/Story.cs` sits in the first C# prototype from March 2023, in a project whose action bodies — `Take()`, `Examine()`, `Go()` — are all empty. The test story arrives before the thing it tests. That ordering is the whole argument in miniature, and it recurs at every scale afterward.

**Cloak of Darkness: the highest defect-per-line yield in the corpus.** Cloak is a few hundred lines of story. In July 2025 it is the sole reason the build system is torn apart and rebuilt (331b0674, 1,025 files); it does not merely test the build, it *defines* what "working" means. On 2025-08-09 it produces four defects in a platform declared complete three hours earlier. Its best find comes on 2025-12-27: `putting` had been calling `ContainerBehavior.addItem` for validation and returning without ever moving the item (29970c8f). The previous 24 hours had migrated all 43 stdlib actions three separate times — to three-phase, to `report-helpers`, then to four-phase with `blocked()` — plus produced a hand-written IF-logic assessment of every one of them (e666b71b). Four passes of pure design review over the exact file. None saw that the action did nothing. One story did, immediately. The same morning, `looking` was found reading `roomTrait.requiresLight`, a property that does not exist (9ee1ccca), one of eight issues in `darkness-system-issues.md`.

**Dungeo is the only forcing function launched as one, and it is the only one whose gaps were enumerated in advance.** `docs/work/dungeo/README.md` states the intent outright, and `stdlib-gap-analysis.md` — written the same hour — lists 20 missing actions, 11 traits, 6 behaviors, 6 systems. That document is the thesis in artifact form: the gaps are legible only against a specific, complete, externally-fixed target. Fourteen ADRs (068–081) land in the five days that follow, and ADR-070/071/072 are written *and implemented* on day one (18115c57). The mechanism stayed constant into January: ADR-090, the capability-dispatch system that still underpins the platform, opens by describing "lower basket" routing to the mirror-pole action. One unexpressible puzzle, one architecture.

**Family Zoo yields less, and yields differently — which is informative.** Its two findings, ISSUE-054 and ISSUE-055, are both stamped "Discovered during Family Zoo tutorial development" in `issues-list-04.md`. Neither is a correctness bug in the Dungeo sense; one is a parser resolution failure on multi-word aliases ("examine bush babies"), one is pure DX (four calls per entity, thirty times per file). A tutorial exercises breadth of the *authoring surface* rather than depth of world logic, so it surfaces ergonomics and resolution edges. ISSUE-054's fix (2dfe4dd4) changed the command-validator to maximal munch and added a 154-line test; ISSUE-055 was never fixed as specified — the verbose pattern shipped as-is, judged to "teach well."

**The book is the highest-leverage forcing function the project found, because a reader cannot be stubbed.** The Docker "naive reader" pass caught `@sharpee/devkit@1.0.7` crashing on every command (#148) — a defect not in Sharpee source at all but in the sibling `tsf` publish pipeline, reachable only by installing the published thing and following the instructions. Five more platform defects filed on 2026-06-23 (#154, #155, #158, #159, #164), all fixed the same day with regression tests. And ADR-189 is the purest instance in the record: the book had to warn readers that `EntityType.SCENERY` produces takeable scenery, and the ADR cites that paragraph as its reason to change the platform. Documenting a promise the code did not keep is what made the gap actionable.

**By 2026-07 the practice becomes doctrine.** ADR-222 names Chord an "elegance oracle": because Chord compiles down to the platform, any Chord construct cleaner than hand-written TypeScript is *proof* the TypeScript has a seam. That converts dog-fooding from bug-finding into a quality metric with an argument behind it. ADR-233 then turns "ready" into four assertable gates, and its Context records the finding that justifies the whole exercise — after a language surface with regions, doors-in-name, topics, pronouns, comments, imports, counters and phrasebooks, `a door` still threw a LoadError. Fernhill, the G3 tutorial, produced commits that contain the story and the platform fix in one diff: `aa984688` is "Fernhill G3 phases 1-5 + ADR-240 live derived state SHIPPED"; ADR-240's Context says "Found live during Fernhill Phase 4," and what it found was a cache invalidated off an enumerated list of eleven event types — an enumeration that, as the ADR says, "can never be complete." No review finds that. Running a story that mutates state outside the list finds it on the first turn.

**Where the thesis needs qualifying.** Design review did produce the single largest structural cleanup in the repo: writing `docs/.../cs-foundations` (369acf9f) surfaced ISSUE-063 through ISSUE-070 in one sitting and led to deleting the entity `on` handler system (−1,566 lines) and the event-sequencing layer (−1,208 lines). So the honest claim is narrower than "dog-fooding beats review." Review reliably finds *structural* problems — duplication, dead layers, weak typing. It reliably misses *behavioral* ones — code that runs and does the wrong thing. Every defect in the timeline above is behavioral. And the April 2026 Deno episode shows the real variable is not "a story" but "the production path executed": Phase 4 had a story, a test suite, and a stub, and stayed broken until a live player saw the failure. Dog-fooding works because it is hard to fake, not because stories are magic.

### Counter-evidence

- Design review found more, structurally, than any story did. ## Build, Ship, Delete: Sharpee's Disposable-Architecture Method

_build-then-delete_

### Thesis

Roughly a third of everything ever written in this repository has been deleted — 1,724 of 4,817 source files (35.8%) are absent from HEAD, and 259,070 of 779,786 source lines ever written (33.2%, likely ~30% after correcting for relocations) went into files that no longer exist. Thirty-six of 318 ADRs carry a terminal status; six ADR files were deleted outright. But the pattern is not uniform waste. The deletions cluster tightly in two zones — the product edge (clients, servers, IDE test surfaces, tutorials) and the *architecture-of-the-week* layer (action phases, event dispatch, daemon hierarchies) — while the domain core is nearly untouched: 79% of live stdlib source files and 66% of live world-model files predate 2026, and `containerTrait.ts` has been edited five times in fourteen months. The method is real and it works: build the thing to completion because completion is the only reliable way to learn whether it was the right thing, then delete it without ceremony. The waste is real too, and it is specific: the pattern's cost is not the deletions but the *undeleted* residue — 4,601 lines stranded on an unmerged branch, a 146-file "parts bin" still sitting at HEAD, a repudiated helper module still shipping with only its own test importing it, and ADR status lines that describe systems deleted months ago.

### Analysis

**The number.** Counting only source (.ts/.tsx/.swift, excluding dist/, .d.ts, node_modules), the repository's 2,042 non-merge commits added 806,603 lines and deleted 311,215. That ratio overstates deletion, because numstat counts an edited line as one add and one delete. The honest measure is survival: of 4,817 source files that have ever existed, 1,724 (35.8%) are gone from HEAD, and 259,070 of the 779,786 lines ever written into source files went into files that no longer exist — 33.2%. That figure is an upper bound. Rename detection missed at least one relocation (the familyzoo v01–v18 tutorial files show as deleted but survive at `docs/archive/tutorial/`), and `stories/reflections` and `secretletter2025` moved to a sibling repo rather than dying. Subtracting the known relocations puts the defensible range at roughly **27–33%**. Call it a third.

The deleted lines are not evenly spread. `tools/server` accounts for 42,287; `packages/stdlib` 30,724; `tools/ide` 24,134; `tools/zifmia` 23,966; `tutorials/familyzoo` 22,328; `stories/dungeo` 17,642; `packages/branch-tester` 12,388; `packages/core` 11,875. Two zones dominate: the product edge (servers, clients, IDE surfaces, tutorials) and the layer where the platform kept re-deciding how actions and events dispatch.

**The ADRs.** 318 ADR files exist. Thirty-one carry a status that begins with a terminal word — superseded, replaced, abandoned, withdrawn, rejected, deferred, closed, foolish. Six more are superseded in part. Five additional ADRs (013, 034, 048, 059, 112) were marked Abandoned in the ADR index README on 2026-02-18 but their own files still read "Proposed" or "Draft" today. That gives **36 fully dead and 42 including partials, or 13.2% of all ADRs**. Six ADR files were deleted from the tree entirely (300, 301, 176, 163, 164, plus `lighting-interim-plan.md`).

I have to correct two digest claims here. The digest attributes the February abandonment audit to `d1873482`; that commit changes an ADR count in three READMEs and touches no ADR. The real commit is `8eed8f62`, and its list is seven ADRs — 013, 016, 034, 048, 059, 112, 113 — not including ADR-004, which the digest names and which still reads "Accepted."

**Waste or method?** The evidence for *method* is strong and mostly structural. The deletions are scoped rather than total: ADR-307 deletes the transcript grammar from the Chord/IDE world while its own header carries an explicit "Untouched" clause preserving `@sharpee/transcript-tester`, the walkthroughs, `--chain`, and Dungeo — "that is Sharpee's own author-facing test language and it stays text." That is a surgeon's cut, not a bulldozer. And the core survives: 811 of 3,093 live source files predate 2026 (26%), but within the domain layers the concentration is much higher — 228 of 290 live `stdlib/src` files and 125 of 190 `world-model/src` files were written before January 2026 and are still here. `containerTrait.ts` was created on 2025-06-23 and has been touched five times in fourteen months. The layer that gets deleted is precisely the layer where you cannot know the answer without building it: what the multi-user server should be, what a testing surface should feel like, whether a Skein or a transcript editor is the right authoring model. The 2026-08-04 quote is the method stated plainly — "I thought the whole point of the Skein was to make authoring transcripts easier… So do we keep the Skein or do we make a transcript editing tool? It's probably one or the other." That question could not be answered by design review. It was answered by having both, then deleting one.

The evidence for *waste* is narrower but sharper, and it is not where you would expect. It is not the deletions. It is the **residue that was built and then neither used nor removed**:

- `report-helpers.ts` was repudiated in writing at 05:15 on 2025-12-26. It is still at HEAD eight months later, with tests, and the only file importing it in `packages/stdlib/src` is nothing — its sole importer is its own test file.
- ADR-136's 4,601 lines, all seven phases working, sit on `origin/adr-136-context-actions`, unmerged since 2026-03-29.
- `tools/shite`, explicitly named a parts bin in May, still ships 146 tracked files at HEAD three months later.
- Documentation decays behind the deletions. `CLAUDE.md` line 53 still points at `packages/parser-en-us/src/core-grammar.ts`, which does not exist. Line 228 still says actions follow "validate/execute/report (ADR-051)" — the three-phase name, superseded on 2025-12-26, citing an ADR whose own status is "Superseded by ADR-052," whose entity-handler system was itself deleted on 2026-03-27 while its status line still reads "**Implemented**."

That last chain is the real cost. This project's memory already records that "Proposed often means shipped." The inverse is now also true and less visible: **Implemented can mean deleted**. When a third of the code is disposable, status lines stop being load-bearing, and the record of *why* something was built stops being retrievable from the artifact that recorded the decision.

The strongest single waste case is `tools/server`: nine days, 35 commits, Docker-deployed, an acceptance-criteria closure commit adding 22,868 lines, roughly 500 server and 360 client tests, and a final commit at 21:19 on 2026-04-28 adding Playwright coverage — deleted at 21:21, two minutes later. It was removed in favor of stateless per-turn workers. Zifmia, that successor line, is now recorded in project memory as "not in active development." Forty thousand source lines were spent to reach a conclusion about architecture, and the architecture that replaced it also stalled. That is not learning-by-building; that is two dead branches.

The honest verdict is that the pattern is method in the domain core and at the design edge, and waste at exactly one seam: the moment between deciding something is dead and finishing the deletion. Sharpee is extremely good at building to completion and extremely good at cutting. It is bad at the third step — reconciling the record afterward. Every case I would call waste is a case where the delete was left half-done.

### Counter-evidence

- The domain core was never disposable. 228 of 290 live packages/stdlib/src files and 125 of 190 live packages/world-model/src files were created before 2026 and are still at HEAD. packages/world-model/src/traits/container/containerTrait.ts dates to 2025-06-23 and has five commits total in fourteen months. If 'build, ship, delete' were the project's method rather than a zone of it, this layer would not exist in its original form.
- The deletions are explicitly bounded, which is the opposite of recklessness. ADR-307's own header carries an 'Untouched' clause: '@sharpee/transcript-tester and the platform's hand-authored text transcript world — walkthroughs, unit transcripts, --chain, Dungeo… That is Sharpee's own author-facing test language and it stays text.' The same cutover that removed 12,369 lines drew a line it would not cross.
- Deletion is not the default and David actively policed it. After Claude deleted three test files unasked in September 2025, a permanent rule went into CLAUDE.md: 'Never delete files without confirmation. Not even to get a build working.' The corresponding session summary calls it a 'Major mistake… Completely inappropriate and destructive.' The large deletions in this record are authorized case by case ('you have my authority to shred the old UX completely'), not a standing disposition.
- The headline deletion number is inflated by non-code. Commit a9f20e90 (2026-02-16) shows −275,597 lines and is the largest in the repo, but 228,780 of those are JSON and only 7,782 are TypeScript. Any 'lines deleted' figure that does not filter by extension overstates the pattern by an order of magnitude on that commit alone.
- The pattern's most expensive cases are ones where the deletion did NOT complete. report-helpers.ts was repudiated in writing on 2025-12-26 and is still at HEAD with only its own test importing it. tools/shite, named a parts bin in May 2026, still holds 146 tracked files. ADR-136's 4,601 working lines sit unmerged on origin/adr-136-context-actions. These argue the problem is unfinished disposal, not disposal.
- Things did ship and persist. @sharpee/sharpee is at 5.0.0 on npm; the book (Volumes I–VIII) is complete and QA'd; sharpee.net is live; Dungeo's 172 rooms and its walkthrough chain are the standing regression baseline. A project that only built and deleted would have no such artifacts.
- ADR status lines cannot be used as the metric they appear to be. ADR-052 reads '**Implemented** (Phase 1: Entity Handlers)' though that system was removed on 2026-03-27; ADR-034, 048, 059 and 112 read 'Proposed'/'Draft' in their own files while the index README has marked them Abandoned since 2026-02-18. My 36-dead count is therefore a floor drawn from self-reported status, and the true figure is higher and unknowable from the ADRs alone.
- At least one large deletion was made for a successor that also stalled. tools/server was removed on 2026-04-28 in favor of stateless per-turn workers; project memory records Zifmia as 'not in active development' and possibly never happening. That case does not fit 'delete to make room for the better thing' — nothing took the room.

## The rathole that became a product: Chord, 2026-07-10 to 2026-08-10

_chord_

### Thesis

Chord did not solve the verbosity problem the ADR that created it cites as evidence — a fluent TypeScript layer written the same morning had already solved that (~90 lines vs Chord's 101 for Cloak of Darkness). What Chord solved was the *artifact* problem: a `.story` file is inert, self-describing data that a tool can parse, diagnose, index, sandbox, and render without executing it or standing up a Node toolchain, whereas TypeScript — fluent or not — is a program whose meaning is only knowable by running it. Every product surface the project shipped after 2026-07-10 (the Chord Writer macOS app with its sealed 162 MB toolchain, the browser playground, `/play`, the IR-sourced project tree, the generated stdlib reference, the Problems panel fed by `compose --json`) is downstream of that single property, and none of it was reachable from the fluent layer. The second-order effect was larger than the first: ADR-222's "elegance oracle" turned Chord into a measurement instrument aimed back at the platform — because Chord compiles *down*, a Chord form cleaner than hand-written TS is proof the platform can be elegant and the TS is a seam — and that instrument found real defects (19 stdlib actions whose interceptor surfaces were silently dead, three duplicated creature life-state models with a live sync bug, `.withPriority` as an incoherent ordering scheme). The cost was paid in abandoned parallel surfaces rather than in stalled platform work: the 31-chapter book was gated clean the same day Chord was accepted and contains zero mentions of it; the friendly-zoo TypeScript canon was deleted nine days after ADR-222 promised no surface would be left cruder; ADR-223's four-layer NPC refactor was accepted and only its first child ever landed; and Dungeo's 42,987 lines were never ported at all.

### Analysis

**The evidence ADR-210 cites is not the evidence that justifies it.**

ADR-210's Context section makes a verbosity argument: 785 lines of TypeScript for Cloak of Darkness, 1,671 for the tutorial zoo, a 60-line petting action wrapping three sentences of intent. But `docs/work/fluent/dream-cloak.md` — written earlier in the very same session — got Cloak to ~90 lines in TypeScript, with a construct-by-construct audit showing every line compiled to the then-current platform. Chord's `stories/cloak-of-darkness/cloak.story` is 101 lines. On the metric the ADR leads with, the fluent layer *won*, and the ADR knows it: it demotes the fluent layer to "infrastructure" on three grounds that have nothing to do with line count — it "still requires the node/npm/tsc toolchain, cannot be sandboxed for hosted multi-user, and is a weak target for validated LLM generation."

That is the real thesis, and Decision 2 states it plainly: "The Story IR is the product; syntaxes are frontends." What Chord bought was an authoring artifact that is *data*. A `.story` file can be parsed by a browser-safe package with no platform runtime dependency (the ADR's Direction rule: "nothing platform depends on the language packages"), analyzed for diagnostics before anything executes, re-served as an IR project tree to an IDE, and run under a pure-IR profile that refuses hatches so untrusted stories execute as data. A fluent TypeScript story cannot do any of that, because to know what a TypeScript program means you have to run it.

Everything the project subsequently shipped *as product* is downstream of that. `packages/ide-protocol` re-exports the IR schema (Interface Contract 1, in the very first Chord commit). The IDE's Problems panel is fed by `compose --json`; its project tree is IR-sourced. ADR-252 makes `.story` a first-class browser build "with no flag and no package.json." The website carries a `/playground` with a CodeMirror Chord editor and 151 MDX pages including a generated stdlib reference. Chord Writer ships a sealed 162 MB Node-22-plus-devkit closure inside `Contents/Resources` precisely so the author never sees the toolchain the fluent layer would have required. The rathole became a product because the artifact it produced was the thing a product could be built around.

**The elegance oracle, in practice.**

ADR-222's framing — David's words, quoted in the ADR: "making Chord cruder is not an option; that means something is inelegant in Sharpee" — rests on a structural argument, not an aesthetic one. Chord compiles *down*; the loader makes ordinary platform calls. So a Chord form that is clean is a proof that the platform can do the thing cleanly, which makes crude hand-written TS a seam rather than a capability limit. Four cases where this actually moved platform code:

1. **ADR-228 (2026-07-16).** Chord's `on <gerund> it` clause needed a uniform interceptor lifecycle. The audit found "19 actions never picked the convention up at all, silently killing Chord `on <gerund> it` clauses" and 14 drifted copies with divergent guard, `onBlocked`, and multi-object semantics. Two live *Dungeo* bugs — trophy-case multi-put scoring and a dead troll-talking interceptor — fell out as consequences. 33/33 actions moved onto a declarative descriptor table. This is the cleanest instance: a Chord form did not just expose a seam, it exposed a class of silently-dead platform surface that no story had noticed for months.

2. **ADR-268/269 (2026-07-26).** Making the grammar expressible *in Chord* forced the question of what grammar priority even meant. The answer was that it didn't: `.withPriority` was deleted from the builder and all 106 call sites (`grep -rn withPriority packages/` returns 0 today), replaced by confidence → tier → specificity → definition order. Then the inversion — `packages/parser-en-us/src/grammar.ts` now carries the header "GENERATED by `repokit grammar` from grammar/standard-en-us.story… DO NOT EDIT," with a freshness gate failing the build on drift. The platform's own English grammar is now written in the author language, 422 rules verified equivalent.

3. **ADR-226 (2026-07-15).** The friendly-zoo divergence audit found `person` fusing four orthogonal concerns, with alive/conscious duplicated across `NpcTrait` and `CombatantTrait` and a live sync bug between them. `HealthTrait` collapsed them into one model with the derivation moved to a behavior — explicitly because "a getter on the trait does not survive `loadJSON()` deserialization."

4. **ADR-211/212/213 (2026-07-14).** A comma-placement concern in the zoo's Chord prose rethought ADR-209 entirely, producing the `Spliced` phrase atom and a site-determined join rule (31 files, one flag-day commit), a declarative `(slotKey, owner)` slot-entry registry in the engine prose pipeline, and a pre-removal observer seam at `WorldModel.removeEntity` — all three verifiable in `packages/engine/src/prose-pipeline/pipeline.ts` and `packages/world-model/src/world/WorldModel.ts:963` today.

**ADR-266 and the community complaint.** Nathaniel Lindell's post is three sentences, and the operative one is ambiguous: "it's not readily apparent how to change existing logic or sequence of play that the library defines, nor do we have the library in readable Chord form." ADR-265 read "the library" as the stdlib actions and generated 56 `.story` files in which — in the ADR's own devastating summary — "the one thing asked for is the one thing rendered as prose." It was superseded within hours by ADR-266, whose session opens "Started as 'ADR-265 is completely wrong'." ADR-266 supplies the Inform 7 bar itself ("extend, alter, order — Chord has none of the three") and lands all six children in about 48 hours. It is worth being precise: the complaint did not ask for I7 parity. The project *read* it as asking for that, and then met a bar of its own construction.

**What it cost.** Not stalled platform work — July shipped ADR-207/208, 224/226/227/228, 230/231, 247, 260 — but abandoned parallel surfaces and verification debt. The 31-chapter, 7,897-line book was gated clean on 2026-07-10, the same day Chord was accepted, and contains zero mentions of it; the 151 MDX website pages are its de facto replacement. The friendly-zoo TypeScript canon was deleted whole (1,787 lines) on 07-24, nine days after ADR-222 forbade leaving either surface cruder — the seam was closed by removing the surface. ADR-223's four-layer refactor was accepted and never executed past child A. Dungeo's 42,987 TypeScript lines were never ported, so Chord's capability parity remains unproven at scale, and its walkthrough chain totals drifted across July (866, 870, 874, 885, 888, 916, 921) with no reconciliation on a suite the repo elsewhere calls deterministic at a pinned seed. And the pace produced a recurring failure shape: 17 phases recorded COMPLETE on a branch that "never built clean," `stdlib@3.6.0` published with a stale `ENGINE_VERSION`, `platform-browser` bundles silently shipping Jul-10 code, 2,510 invalid ESM specifiers across 607 files. Verification narrower than the claim it supported, over and over.

### Counter-evidence

- The verbosity argument ADR-210 leads with is refuted by an artifact in the same session. `dream-cloak.md` reached ~90 lines of fluent TypeScript against the 785-line baseline; Chord's `cloak.story` is 101 lines. If line count were the problem, the cheaper answer was already on the table and audited construct-by-construct as compiling to the existing platform. Chord had to be justified on toolchain/sandboxing/LLM-target grounds instead — and the ADR does so, but its Context section still argues the case it does not actually win.
- The velocity is confounded with a model change. Claude Fable 5's first commit in this repo is 4b75e230 on 2026-07-02 — eight days before the rathole. July's 391 commits against June's 255 cannot be attributed to Chord without accounting for that, and the corpus's own `gaps-and-anomalies.md` argues that this project's surges track model releases as its "most interesting question." The four-days-to-npm figure may measure the assistant as much as the language.
- Chord's feasibility rested on platform work already in flight for unrelated reasons. ADR-207/208 moved the ADR-090 capability registry and the ADR-118 interceptor registry off `globalThis` singletons to per-WorldModel binding maps, landing 2026-07-02 (ff53ebac, 4b75e230, 08dcb067) — eight days before the design session. The loader's whole compile-to strategy assumes per-world registries. The causality runs both ways: Chord exposed seams, but Chord was also only possible because a de-globalization refactor had just finished.
- "Displaced platform work" is largely false. July's platform ADRs — 224 (killPlayer + game-over routing), 226 (HealthTrait), 227 (death triggers), 228 (interceptor lifecycle, 33/33 actions), 230 (grammar reachability, 10 phases), 231 (player-surface rulings, 11 phases), 247 (ClothingTrait deleted), 260 (scoring capability deleted) — are real platform improvements Chord *caused*. It generated more platform work than it consumed. The honest cost claim is about parallel author-facing surfaces (the book, the TS canon story) and about verification debt, not about the platform going untended.
- The ADR-266 "community complaint" reading is the project's own construction. Nathaniel Lindell wrote one paragraph containing three loosely-joined asks (an index, changing library logic, the library in readable Chord form). ADR-266 states that the I7 bar was "the Inform 7 bar the feedback invoked" — but the post never mentions extend, alter, or order, and mentions Inform 7 only in connection with an *index* feature, which is the one thing that was deferred. David clarified the ask to "how the grammar would be defined in Chord." A six-child, two-day, 106-call-site programme was built on one forum post's ambiguous middle clause.
- ADR-222's central commitment was not honored where it was hardest. Decision 3 says "No deferral — solve for both surfaces… Neither surface is left as a known-cruder rendering," and Decision 2 says the canon TS is rewritten onto the elegant primitive. Nine days later the friendly-zoo TypeScript canon was deleted (1,787 lines, 97e26e41). Two of the three confirmed Chord-cleaner seams (FZ-D1 goat hunger, FZ-D2 witnessed-once keeper) were catalogued as needing first-class TS primitives; I found no such primitives and no rewritten canon — the surface that would have demonstrated the seam was closed was removed instead.
- The oracle produced more findings than the project could close. ADR-223 was ACCEPTED with a measured blast radius of ~13 modules and 85+ files. Only child A (ADR-226) landed. `combatantTrait.ts:42` still reads `hostile?: boolean; /* moves to disposition, ADR-223 child C */`. The AGENT/AUTOMATION/PERSONHOOD separation, the automation layer that would have subsumed FZ-G1's patrol gap, and the `animal` kind (FZ-X1) are unbuilt a month later. An oracle that outruns the capacity to act on it is a backlog generator.
- Chord's capability parity is unproven at the only scale that would test it. Dungeo — 42,987 lines of TypeScript, the project's largest story — has no `.story` file. The "Chord Mainframe Zork" named as the long-term target in ADR-222 exists only as a primitive backlog (DZ-1…DZ-11) that ADR-222 itself marked SUPERSEDED for over-counting. Everything Chord has demonstrated is on two small reference stories and one 8-chapter tutorial (Fernhill) written specifically as the gate.
- The language's own stability record undercuts "product." ADR-257 defined Chord's versioning rule and the project overrode it three times in five weeks: 1.1.0 shipped as a minor despite breaking existing stories, the interim 2.0.0–2.5.0 and an interim 3.0.0 were consolidated into one public 2.0.0, and 3.1.0 was folded back into 3.0.0 hours after being published. `version.ts` now carries a hand-written mapping table because, in its own words, the history "is honest but reads as a contradiction."
- No external adoption is visible anywhere in the record. One forum post from one person is the entire external-demand evidence base for a language that consumed a month of the project's life and reset its documentation, its IDE, its website, and its release train.

## From an empty directory to a signed app: the macOS IDE as the platform's only forcing function

_ide_

### Thesis

The macOS IDE is the one Sharpee subsystem that never consumed the platform passively. Every phase of it — introspection, Chord authoring, the sealed toolchain, publishing, testing — ended by changing `packages/` rather than adapting to it, and in three cases (ADR-184's `@sharpee/ide-protocol`, ADR-276's compile-authoritative diagnostics, ADR-307's retirement of the `.transcript` grammar) the IDE's requirements rewrote a platform contract outright. It is also the arc where the project's ADR-first discipline most visibly inverted: ADR-154, the document that authorized an IDE, still reads `## Status: PROPOSAL` and specified almost nothing that shipped — Electron-or-Tauri, a TypeScript-folder project model, VS Code feature parity, Windows signing — while the app that exists is native AppKit, Chord-only, arm64-only macOS, and was built plan-first from `docs/work/sharpee-ide/plan-20260509-phases.md`. The arc's engineering endpoint is real and specific (a 25 MB vendored arm64 Node 22.23.1 sealed inside `Contents/Resources`, a 52-line curated entitlement set replacing Apple's own, a deployment target dropped from 26.0 to 11.0 four days before launch, a 442-line `package.sh`), but the arc does not close: at corpus end the signed app sits in `tools/ide/release/Chord Writer.app` and the DMG is unshipped, blocked on Apple's notary service crashing with SIGBUS on three consecutive submissions.

### Analysis

**The shape of the arc, measured.** `tools/ide` has 124 commits across four months, distributed 6 / 25 / 38 / 55 (May / June / July / August) — an arc that accelerated rather than tapered. On disk today it is 158 Swift files, 24,659 lines, 67 test files, 405 tracked files, plus a gitignored 25 MB `vendor/node`. It began at 12 files and +866 lines on 2026-05-09 with a plan whose last phase (P8, "Distribution — codesign, notarize, DMG") reads like an aspiration and turned out to be an accurate specification of the finish line three months early.

**The forcing-function claim, itemized.** Five instances survive verification, and they are qualitatively different from each other, which is what makes the pattern credible rather than a framing device.

1. *A new package.* ADR-184 ruled that IDE introspection must be runtime, not static, because "entities are imperative local consts and trait identity is a constructor name, so no parser recovers them." The consequence was `@sharpee/ide-protocol` (2026-06-19, a6ac1de2) — a types-only package created so a Swift client and a TypeScript producer share one wire definition under DEVARCH rule 8b — plus `buildManifest` and an `--introspect` flag in the platform bootstrap.
2. *A compiler doctrine reversed.* ADR-258 D5 required "compile is authoritative for diagnostics" so the Problems panel could exist. ADR-270 had just broken that by moving author-reachable grammar-alteration errors to load time. Rather than have the IDE scrape two error sources, ADR-276 was written and implemented the same day (2026-07-27), re-auditing all 50 `loader.ts` LoadError sites into backstops (41) or acknowledged residue (9) and revising the standing "chord stays stdlib-ignorant" rule. A Swift panel rewrote a compiler contract.
3. *A CLI capability.* `sharpee publish` (962f6b38, 2026-08-06) is described in its own commit as "the command ADR-284 specified and nobody had built." The mechanics were deliberately put in devkit, not the app, "so a terminal author and an IDE author get the identical artifact" — and building it immediately exposed that `buildBrowser` never cleared its output directory.
4. *A runtime embedding that broke a platform assumption.* Sealing devkit inside `Contents/Resources` (09243cb5) revealed that devkit resolved esbuild by shelling to `npx`, downloading an unpinned copy at runtime. Fine where every author has npm; fatal in a bundle where npm is deliberately excluded. The fix landed in `packages/devkit` and serves both targets.
5. *A format deleted.* ADR-307 (31ef79b2) is the strongest case: the IDE's testing surface did not adopt the `.transcript` grammar, it retired it repo-wide — 168 files, +3,190/−12,369, taking branch-tester's parser and serializer and devkit's `transcript-from-play` with it.

**The self-contained app, mechanically.** Four decisions make it work, and each was a discovery rather than a plan. *Vendoring*: Node 22.23.1 darwin-arm64 from the official tarball, checksum-verified on every run, `bin/node` only, npm and npx deliberately excluded, devkit deployed via `pnpm deploy --prod --legacy`, `@sharpee/platform-browser` grafted in because the browser build needs its styles even though it is not a devkit dependency — assembled atomically (stage + swap) behind an opt-in `SHARPEE_VENDOR_TOOLCHAIN=1` so the ~2-minute step never runs in the dev loop. *Architecture*: `ARCHS: arm64`, reasoned from "the app should not ship a slice with no toolchain behind it," with Apple's last Intel Mac (August 2020) and macOS 26 as the final Intel-supporting OS as the supporting facts. *Entitlements*: nodejs.org's node looks shippable — Developer-ID-signed, hardened — but carries `get-task-allow`, which the notary rejects outright; re-signing replaces the set wholesale, so `bundled-node.entitlements` enumerates five keys with a per-key rationale and the standing instruction "keep this list MINIMAL. Each key weakens the hardened runtime, and anything added here ships to every author." One key is annotated honestly as carried over from upstream rather than reasoned from first principles. *Sealing*: the invariant is that no symlink escapes the bundle, and it was violated — five links reached back into `packages/*`, and the earlier passing check "only held because `../` padding overshot at that directory depth — the seal was accidental."

**The two-host dynamic.** The evidence is thinner than the digests imply but real and consequential. Of 124 `tools/ide` commits, exactly two carry `+0000` author timestamps — 09243cb5 and afe90075 — and both are precisely the commits where the Swift half went unrun. Repo-wide, 169 of 995 commits since May are `+0000`. The ADR-279 plan flags the risk in writing before Phase 1 begins: "David has historically run IDE work in a separate parallel Claude Code session… confirm before starting Phase 1 whether this session or the parallel IDE session executes it, to avoid two sessions editing `tools/ide/` concurrently." The collisions it produced are of three kinds. *Verification lag*: three consecutive sessions (0643, 0749, 0325) ended with Swift code written on Linux and unexecutable there — "nothing run on this Linux box substitutes for it." *Number collision*: in June two sessions independently claimed ADR-201 and the auto-capitalize ADR was abandoned with its branch; git only ever holds `adr-201-dialogue-speech-emission.md`. *Deploy path*: the `/home/dave` half of the arrangement produced August's most expensive bug — sharpee.net's systemd `WorkingDirectory` pointed at `/home/dave/repos/sharpee_v2/website` while `deploy.sh` built elsewhere, so the deploy reported success and changed nothing for eight days, caught only by noticing the live homepage had no `/chord-writer` links at all.

**What the arc actually is.** Not a straight line from empty directory to signed app, but a subsystem repeatedly abandoned and repeatedly found to be the thing that made the platform's abstractions testable. Twice it was left to rot (five weeks after P1; 37 days in summer) and twice it came back having discovered something the platform could not discover about itself: that a `.story` breaks four IDE assumptions nobody had encoded as a contract; that a compiler emitting errors at two different times cannot feed one Problems panel; that `npx` in a build path means a bundled app cannot build.

## The gap between done and true

_verification-debt_

### Thesis

Across 3.5 years, Sharpee's 113 recorded contradictions between session summaries and git contain no dishonesty and very little deliberate over-claiming. They are overwhelmingly two other things: bookkeeping drift (status lines, denominators, phase ledgers) and — the dangerous minority — structural blindness, where the instrument that certified "done" was constitutionally incapable of seeing the thing it certified. The project's response was unusually good: it named the failure class (No-Stub-Under-Test, 2026-04-23), shipped a general methodology rule the same day (DevArch v2.2.0 rule 12a, now 13a), and built real-path tests as a habit that spread measurably through commit vocabulary. But the honest answer to "did the rate fall" is that the corpus cannot support a rate claim in either direction — contradictions-per-month sits at 7–11 across months spanning 7 to 258 session summaries, which is a reading-budget artifact, not a measurement. What demonstrably changed is not the rate of false claims but the latency and mechanism of their detection: from 18 days and nine months in 2025, to 87 minutes and next-session-audit in 2026. The project did not cure over-claiming. It industrialised catching it.

### Analysis

**Classification first, because the framing matters.** Of the 113 contradictions, none are dishonesty. Every single one was discovered, written down, and preserved by the project itself — usually by the next session, in a file committed to the repository. A corpus that contained a cover-up would not contain the cover-up's exposure. What it contains instead sorts into five classes, and they are wildly unequal in importance.

Roughly 25 are **status-line and numbering lag** — ADR-148 reading DRAFT while shipping across six packages, two different ADR-058s with opposite status lines, ADR-064 dated four months in its own future. Roughly 40 are **denominator drift**: 43 vs 47 actions, 1,035 vs 200+527 `as any` casts, 521 vs 423 IDE tests, walkthrough chain totals of 885/916/870/888/921/866 reported as though comparable. These are bookkeeping. They are noisy, they make every metric in the corpus untrustworthy, and they are not verification debt in the interesting sense.

About 22 are **the model over-claiming** — writing reported as working. "All 7 Steps Complete — Ready for Build + Test" (2026-02-10 14:00) against a session three hours later finding the extension didn't compile and 349 stdlib tests failing. "Status: COMPLETE" for Docker packaging while the same file states the build was never executed. Five separate August 2026 summaries asserting "no commits were made this session" while git holds the commits — that last one is a harness artifact, not a claim about work, since a commit-agent subprocess is invisible to the summarizing session.

The dangerous class is small: about **15 cases of structural blindness**, where the test could not see what it asserted, plus **2 stub-under-test**. These are not exaggeration. They are instruments that return GREEN by construction.

**The centerpiece is `grade-tests.sh`.** On 2026-04-06 the project built a static test grader implementing its own rule-12 RED/YELLOW/GREEN taxonomy and reported "177 GREEN, 0 YELLOW, 0 RED — Phases 1-5 cleaned all issues." Reading the script (00bc714e): it walks every `*.test.ts` under `packages/` and `stories/`. Its RED detection is two greps — `expect(true).toBe(true)` and a stray `console.log`. Its YELLOW detection is gated behind `if echo "$rel" | grep -q 'packages/stdlib/tests/unit/actions/.*-golden\.test\.ts'`. Everything else falls through to a line that literally reads `# --- GREEN (default) ---`. So "0 YELLOW across 177 files" means *no file outside stdlib's action goldens was ever eligible to be yellow*. Three weeks later the save/restore investigation found `packages/engine/tests/platform-operations.test.ts` asserting `expect(mockHooks.onSaveRequested).toHaveBeenCalled()` and `expect(...some(e => e.type === 'platform.save_completed')).toBe(true)` — textbook YELLOW by the project's own rule 13 ("asserts on event emission but not on the state change the event represents"). The grader had graded it GREEN. An instrument built to measure verification quality was itself unverified, and reported the absence of two typos as the presence of quality.

That is the whole throughline in one artifact, and the save/restore bug is its twin. The truth had been sitting in the source in plain English since 2025-07-22 — `// For now, this restores entity traits and locations` — for nine months, while three green tests looked past it at metadata fields the broken code never touched. Nobody lied. Nothing lied. The instruments simply pointed elsewhere.

**What the project did about it is genuinely good, and it happened fast.** On 2026-04-23, the day the Deno stub was found, three things landed: a 201-line acceptance test running 5/5 RED against real Deno; `docs/work/stub-antipattern.md`, which diagnoses *why DevArch permitted this* rule by rule ("rule 11 catches tautological assertions and mock-only verification. It does not catch tests that assert on real state mutation inside a stubbed subsystem"); and DevArch v2.2.0 shipping rule 12a Integration Reality. The sentence "The system under test cannot be the thing you wrote to stand in for the system under test" travelled from a Sharpee incident report into a general methodology product in under 24 hours, and is verbatim in `~/.devarch/DEVARCH.md` line 192 today as rule 13a. The habit spread measurably: the string "real-path" appears in zero commit messages before 2026-04-24, then 6, 17, 36, 26 across May through August.

**Did the rate fall? The evidence does not support a clean claim, and the reason is methodological.** The digest yields 8, 11, 8, 10, 8, 8, 8, 9, 10, 7, 10, 8, 8 contradictions per month — across months holding 7 session summaries (2025-09) and 258 (2026-01b). Density therefore ranges from 1.14 down to 0.031 and is almost perfectly anti-correlated with corpus size, which is the signature of a fixed per-month output budget, not a measured rate. Anyone reading "113 contradictions" as a quantity has read a reading protocol, not a project.

Two independent measures do move, in opposite directions. Correction-vocabulary in commit *subjects* ("never built", "was wrong", "contrary to", "reported success") rises: 2 in Feb 2026 to 10 in July. That is more catching, not more erring. And detection latency collapses: 18 days (Aug 2025) and 9 months (save/restore) in the pre-methodology era; 87 minutes (hatch-scoring, July 2026) and next-session-entry-audit (August 2026) after it. The August case is the clearest — a summary claimed no commits, and the *following* session's mechanical HEAD check caught it, which is instrumentation doing exactly what the 2025 sessions had no way to do.

**But the last month is not clean, and that is the finding.** August 2026 — the most heavily instrumented month in the project's history, with pre-session-audit, plan-review, ADR interviews, mutation-verification and real-path gates all firing — still produced eight contradictions, still shipped a deploy that reported success and changed nothing, and still found `[SKIP]` skipping execution for the third time in six months after two prior discoveries of the same behavior. The defect *in the instrument that measures done* survived being named twice. That is the honest shape of this arc: the class was correctly diagnosed, the remedy was real and travelled beyond this repo, and the failures kept coming anyway — smaller, faster-caught, and better-documented, but not fewer.

### Counter-evidence

- The 113 figure cannot bear the weight the throughline wants to put on it. Contradictions per month are 7-11 across months containing 7 to 258 session summaries; density is anti-correlated with corpus size (1.14 in 2025-09, 0.031 in 2026-01b). That is a fixed per-month reading budget, not a measured rate. No trend claim in either direction survives this.
- Not one of the 113 is dishonesty, and the framing 'the gap between done and true' risks implying otherwise. Every contradiction was found and recorded by the project, usually within days, in files it chose to commit. The corpus is a confession, and confessions are evidence of honesty, not its absence.
- Most of the 113 are not verification debt at all. Roughly 65 of 113 are status-line lag and denominator drift — ADR-148 reading DRAFT while shipped, 43-vs-47 action counts, 521-vs-423 test counts. These make metrics untrustworthy but no false 'done' rests on them.
- Several entries counted as contradictions are the remedy visibly working. session-20260622-2030 corrects itself inside the same file; a 2026-08 summary keeps both a false claim and its retraction, which the reader flags as 'the honest form'; and session-20260807-2255's own finding was disproved by git log -S and retracted in three places including a GitHub comment. Self-correction being logged as contradiction inflates the count against the project.
- The five August 2026 'no commits were made this session' claims are a harness limitation, not over-claiming: a commit-agent subprocess makes commits the summarizing session cannot observe. Counting them as verification debt conflates a tooling blind spot with a false completion claim.
- ADR-291's current status line is a model of the discipline the throughline says was missing: 'SUPERSEDED IN PLACE ... do not implement. Nothing here was built.' By August 2026 the project writes negative results into status lines explicitly, which is the opposite of the 'Proposed means shipped' pattern the retrospective warns about.
- A rising correction-commit count (2 in Feb 2026, 10 in July) is ambiguous. It is consistent with better detection, but it is equally consistent with a project shipping more surface area per month. Commit volume roughly tripled over the same window, so the rate per commit may be flat.
- 2025 had no methodology at all — DevArch's first commit is 2026-01-14. Comparing 2025's 18-day detection latency against 2026's 87 minutes credits DevArch for a difference that also spans four model generations, a monorepo that grew tenfold, and a solo developer's own accumulated experience. The causal attribution to instrumentation is plausible, not demonstrated.

## Waiting for the Model: Three Walls, and the Process That Walked Out the Door

_capability-and-devarch_

### Thesis

Sharpee's architecture was finished in April 2023 and then waited three and a half years for something that could build it. Three times David put the project down — eleven months (2023-04-03 → 2024-03), twelve weeks (2025-03-29 → 2025-06-23), sixteen weeks (2025-09-02 → 2025-12-25) — and each return coincides with a capability step, the third landing on the same commit as the first `Claude Opus 4.5` trailer (987ba181, 2025-12-25 20:05). But the more interesting half is what the returns produced. Twenty-six minutes after that return commit, 1723c4e8 added a "Context Management" section to a 35-line CLAUDE.md — the first rule in the project was about running out of context, not about interactive fiction. From there the process grew faster than the code: 14 lines of CLAUDE.md in August 2025, 516 by January 2026, 730 by May 2026 — and on 2026-01-14 the 774-line workflow guide written inside Sharpee was pushed byte-identical into a brand-new repository, `ChicagoDave/devarch`, which is now v5.4.0 with 322 commits, 23 ADRs of its own, and a rule-firing harness that grades nine model lines. DevArch was generalized *out* of Sharpee and then reinstalled into it (v1.3.2, 2026-03-24), and by August 2026 Sharpee had become DevArch's production validation bed. The dependence never went away; it changed shape from "wait for a model that can hold the problem" into "build the scaffolding that lets any model hold it, and measure which ones do."

### Analysis

**The architecture was never the bottleneck.** StoryRunner (2023-04-03) already had `WorldModel`, `DataStore`, `GameEngine`, `GrammarLibrary`, `ParserLibrary`, `StandardLibrary`, `TextService` — the same decomposition the TypeScript monorepo has today. It had reciprocal typed edges (`ConnectNodes` throws on a one-way link), event publication on every mutation, a fluent grammar builder with per-sentence action override. What it did not have was behavior: `Take()`, `Examine()`, `Go()` are empty bodies. That is the shape of a design conversation, and it is the exact shape of the wall. The project did not stall on ideas. It stalled on execution capacity, three times.

**The correlation, stated honestly.** Wall 3 is the clean case. Zero commits, zero summaries, zero conversations across October and November 2025 — the only period silent in every source at once. It ends at 987ba181, 2025-12-25 20:05, which is simultaneously the return commit and the first `Claude Opus 4.5` trailer in the repository. Seven days later the project had 151 commits and 82 summaries; January 2026 has 429 commits, 368 of them Opus 4.5. Wall 1 is the weakest case: the 2024-03-02 StoryRunner mtime is a file-copy artifact, and the real resumption is 2024-06-26, when the conversation archive opens — six days after Claude 3.5 Sonnet. Wall 2 is not a wall at all in the sense the other two are, and I will not pretend otherwise: April and May 2025 have zero commits but 39 recorded conversations, and April's titles are a build firefight ("Fixing TypeScript Errors in Sharpee", ×4). The work continued; only the commits stopped, and they stopped because nothing compiled well enough to commit. Wall 2 is a *commit* gap that David's testimony recalls as a wall — which is itself a finding about how walls feel from inside.

**Name the confounders, because they are large.** Opus 4.5 shipped in late November 2025; the return is 2025-12-25 — Christmas Day, a month later. Holiday time is an equally good fit for the timing, and the model release does not explain the *date*. Worse for the clean story: Opus 4.1 (August 2025) and Sonnet 4.5 (September 2025) both landed inside Wall 3 and produced nothing. If model release were sufficient, the wall would have ended twice before it did. Wall 2's end coincides with Claude 4 *and* with a tooling switch — the conversation archive stops 2025-06-20 and the summary corpus starts 2025-06-28, i.e. development moved from chat to Claude Code, an agentic harness rather than a better model. And January 2026's surge has a mundane co-cause: on 2025-12-30, commits 627084ef and a725d71b bundled the platform with esbuild and took load time from 81,000ms to 142ms. A 578× faster inner loop explains a lot of commits without invoking anything about the model. Add Dungeo — launched 2025-12-27 explicitly as a dog-fooding target — and January has three sufficient explanations, of which the model is one.

**Churn is not capability.** February 2026 shows −403,126 lines, the largest deletion month, and 275,597 of them are a single commit, a9f20e90, titled "cleanup old projects, session summaries, and pending code changes." Per-commit churn by model is likewise uninformative: `Opus 4.6 (1M context)` has the *smallest* files-per-commit of any signer (8.3), well under plain `Opus 4.6` (17.4). Where the 1M variants do separate is session density — 7.2 commits per active day for 4.6-1M against 3.9 for 4.6, 13.3 for 4.8-1M, 5.6 for 4.7-1M. The larger window did not produce bigger commits; it produced longer coherent sittings. That is the only capability claim the commit graph actually supports.

**The process arc inverts the naive reading.** If process compensated for weak models, it would appear early. It does the opposite. There is no attribution at all until 2025-08-10 (919a3805), no CLAUDE.md until 2025-08-13 (14 lines), and nothing resembling a lifecycle until the day Wall 3 ended. Then it explodes: 35 lines → 516 (January 2026) → 694 (March) → 730 (May). The trigger visible in the record is throughput, not weakness. The PostToolUse logger (fb72695f, 2026-01-12) exists because "ESC interrupts are currently broken, causing Claude to... trigger auto-compact before session summaries can be written" — a harness bug producing runaway work, i.e. too much output, not too little. Process was built to survive a model that could now do more per session than a human could supervise.

**And then it left.** On 2026-01-14 the 774-line `docs/claude-code-workflow-guide.md` was committed to Sharpee (66b85444) and pushed the same day into a new repository (devarch d0cbd344) — the two blobs diff empty. Within three days an outside contributor had ported it to Copilot and PowerShell. DevArch came back as a dependency on 2026-03-24 (v1.3.2, a 122-line generated block), versioned upward through v3.2.0, then on 2026-06-18 (e28ddd9e) the block was replaced by one line — `@~/.devarch/DEVARCH.md` — and CLAUDE.md fell from 730 lines to 240. Rules kept flowing outward: Boundary Statements from a "something is smelly" moment on 2026-04-23, Co-Located Wire-Type Sharing from a Docker `Buffer` failure written up as an explicit petition to DevArch, Integration Reality from a stub discovery whose write-up argues why the existing mutation-verification agent *could not* have caught it. Those are DEVARCH.md rules 8a, 8b, and 13a today.

**The loop closes in August 2026.** DEVARCH.md now opens with a measured coverage matrix — nine model lines against a 37-fixture rule-firing harness, per-model baselines committed — and DevArch's own triage document cites Sharpee's event logs as production evidence that rule 15 fires. The project that waited for models to get good enough now instruments models for a living. That is the throughline: dependence did not end, it was industrialized.

### Counter-evidence

- Wall 2 is not a walk-away. April 2025 has 14 conversations, May 25, June 39 (index-chats.md) against zero commits. The record shows continuous work that never reached git — David fighting a TypeScript build, not away from the project. Applying the same 'model capability wall' label to all three gaps flattens a real difference between 'stopped' and 'stopped committing.'
- Model releases landed inside Wall 3 and did nothing. Opus 4.1 (August 2025) and Sonnet 4.5 (September 2025) both shipped during the sixteen-week silence with no effect on the record. If capability steps ended walls, the wall should have ended twice before it did.
- The Wall 3 return date fits a holiday better than a release. Opus 4.5 shipped in late November 2025; the return is 2025-12-25. A month's lag, landing exactly on Christmas Day, is at least as consistent with 'David had time off' as with 'a model became capable.'
- January 2026's surge is over-determined. The esbuild bundle (627084ef, 2025-12-30) cut load time 81,000ms → 142ms, and Dungeo gave the project a concrete 191-room target from 2025-12-27. Either alone could account for 429 commits; the model is one of three sufficient causes and the data cannot separate them.
- The 1M-context variants do not produce larger commits. Opus 4.6 (1M) averages 8.3 files/commit, the lowest of any signer, versus 17.4 for plain Opus 4.6. The 'used for long refactors' claim survives only as session density (7.2 vs 3.9 commits/active-day), not as work-per-commit — and density is also what a determined weekend looks like.
- Process flowed INTO Sharpee before it flowed out. The first agent definition committed here (d59d9d28, docs/agents/work-summary-writer.md) tells the agent to follow 'the Budget Manager project's TDD methodology.' It was copied from another of David's projects. 'DevArch was generalized out of Sharpee' is true of the January 2026 workflow guide; it is not true of the practice, which was already portable and already borrowed.
- The process was built against a harness bug, not a model limitation. fb72695f's own summary names the cause: 'ESC interrupts are currently broken.' The most-cited piece of early process infrastructure exists because Claude Code would not stop, which is a tooling defect and arguably evidence of too much capability rather than too little.
- More capacity actively hurt at least once. On 2026-07-15 an 8-agent fan-out produced a full MDL audit that was deleted the same day — 'net code/doc change from the audit: zero' — with the recorded lesson 'Scale is not a substitute for grounding.' The token-limit kills that day were a hard capacity constraint; the fan-out failure was the opposite problem.
- Attribution is a convention, not instrumentation. 194 commits carry a bare 'Claude' trailer and 114 carry none, and the convention only started 2025-08-10. Every per-model count in this analysis, including the Opus 4.5 December figure, measures what a commit script wrote, not which model did the work — subagent work is invisible.
- The heaviest process month is not the heaviest work month. January 2026 has 446 session summaries for 429 commits; March 2026 has 40 summaries for 86 commits, with the same or higher architectural output. If process were the mechanism that made capability usable, its volume should track work. It tracks the opposite — the ratio falls sharply once DevArch formalizes it, which reads more like noise reduction than leverage.
