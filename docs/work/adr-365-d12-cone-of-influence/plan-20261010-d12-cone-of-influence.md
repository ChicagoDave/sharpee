## Design notes the checkpoints settle (read once, referenced by the phases)
1. **Where the finding is produced.** The story analyzer (`packages/chord/src/analyzer.ts`) never sees a claim: `compile()` strips and rejects any `claims` block (`analysis.claims-in-story`), and claims are lowered only in `compileClaims`. So the "analysis.* finding" is emitted from `compileClaims` (as `analysis.claim-inert-needs`, a warning, so `ok` stays true and D9's never-gate holds), not from `analyzer/`. The ADR's "packages/chord/src/analyzer" wording is read as "the chord compiler's analysis tier". David confirms or redirects at the Phase 1 checkpoint.
2. **One implementation, two consumers.** The closure is a pure function over `StoryIR` + a lowered `IRClaim` (+ its effective set), exported from `@sharpee/chord`. `compileClaims` uses it for the finding; the branch-tester runner (which already imports `StoryIR` from `@sharpee/chord`) calls the same export for the count. The JSON sidecar path has no compile step, so the runner count is the only surface for it.
3. **Conservative closure.** Roots: the claim's predicate reads (room, placement, state, flag, fired counter, event, ending). Grow by: rooms the set reaches plus each exit's `IRBlockedExit.condition` reads; every rule/clause/timer/machine/trigger (`IROnClause`, `IRTimerClause`, `IRMoveClause`, `IRMachineTransition`, sequence/counter/chapter effects) whose statements move the player, change or move something already in the closure, or fire the claim's event; each such rule's `stmtWhen`, `condition`, and trigger reads; named conditions expanded. Computed over the WHOLE story's rules, not the set's rooms. Any IR construct the closure cannot model (e.g. `any-of`/`none-of`/`satisfies` open conditions, `change-player`, channels) widens the closure to "keep everything it could name", never narrows it: an unmodelled construct can only produce fewer inert findings, never a wrong one.
4. **What is reported.** Only things (D12 is about things; rooms and verbs are not reported inert). Each kept thing carries its reason (the guard or rule line that reads it); each inert thing is listed under the finding with the trimmed `needs things:` line proposed.
