## What is already closed (do not re-litigate)

Phase 5 of `avalonia-ide-evaluation` tried four signing routes against the *unmodified* `vpk` output and hit the same wall each time: `Contents/MacOS/` holds all 225 entries (data files, satellite cultures, the 175 MB toolchain), Apple's rule says only the executable and code belong there, and `codesign` refuses to seal a bundle shaped that way. **No flag fixes this** — in `vpk` **1.2.0**, which is the only version that record tried (its §7 says so explicitly). This plan does not repeat those four routes. It starts one step further: given that the fix must be post-processing (moving files after `vpk pack`, before signing), is that post-processing actually possible end to end, or does it break somewhere along the way?

**One thing is *not* closed, and it is checked first.** `phase-5-velopack-packaging.md` §6.1 states the fix as a disjunction — *"**Either Velopack grows a layout option, or** the build post-processes the bundle"* — and §7 records *"Whether the layout problem is Velopack-version-specific. Only 1.2.0 was tried."* An earlier draft of this plan took only the second half of that disjunction and pinned 1.2.0 throughout, which would have spent three phases on a problem a newer `vpk` may already solve. Phase 1 therefore opens with a version check (step 0 below) before any relocation work.

Three concrete places it could break, matching the goal's own numbered list:

1. **The AppHost might not be able to find its managed assemblies, `deps.json`/`runtimeconfig.json`, or the vendored toolchain once they are moved to `Contents/Resources`.** This is the load-bearing unknown — if the executable structurally cannot be pointed at a relocated payload, the rest is moot and Q-5 is answered NO without needing to touch signing at all.
2. **Velopack owns its own update-apply path**, and it rewrites the bundle when a delta is applied. A layout fixed by a one-time post-processing script is not a fix if `UpdateManager.ApplyUpdatesAndExit` (or whatever install-time mechanism `vpk` uses on macOS) reconstitutes the flat, unsigned `Contents/MacOS/` layout on every update.
3. **The relocated, per-binary-signed bundle has to actually notarize.** `package.sh` already proves the target layout is signable and notarizable for the Swift app; this plan needs the same proof for a `vpk`-produced payload, which has a different file manifest (225 entries from a `dotnet publish`, not an Xcode archive).

### Phase 2: Does Velopack's update-apply path survive the relocated layout
- **Tier**: Medium
- **Budget**: 250 tool calls

- **Entry state — the signing dependency, which is real and was wrong in an earlier draft**: `phase-5-velopack-packaging.md` §7 records that update *application* was never exercised *"because that path wants a release feed **and a signed app**"*, and `parity-table.md:109` says the same. - **Deliverable**: A real update round trip against the *relocated* layout, not the flat one Phase 5 already measured: pack `v1.0.0` with the Phase 1 recipe applied, install it, generate a `v1.0.1` delta with `vpk pack -v 1.0.1`, point the installed app at a local release feed, and drive the actual apply path (`UpdateManager`/`VelopackApp` apply-and-restart, or whatever `vpk`'s macOS updater mechanism is — determined as part of this phase, not assumed) so the installed `1.0.0` becomes `1.0.1` on disk.
