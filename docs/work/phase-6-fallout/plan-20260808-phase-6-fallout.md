### Phase 1: Web-client Reset menu item + ThemeManager owns its own theme menu
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: `packages/platform-browser` (`ThemeManager`, `BrowserClient`/`SaveManager` storage-prefix knowledge) + the shared devkit build core (`packages/devkit/src/standalone/browser-core.ts`, used by both devkit's author build and `tools/repokit/src/commands/browser.ts` per ADR-252 D5) + devkit's `templates/browser` menu markup.
- **Entry state**: Fernhill's theme list is restored (Fix A, already landed); `injectThemes` in `browser-core.ts` still does the build-time `#theme-menu` regex rewrite; the published client's menu has no Reset entry.
- **Deliverable**: Implements P-3 and P-4 together (same code area per the proposal — "do alongside P-3"). P-3: a Reset menu item that, on confirmation, deletes every storage key under the story's storage prefix (saves, autosave, theme preference) and restarts the story. P-4: the build-time `#theme-menu` regex rewrite is deleted from `injectThemes` (link injection stays); `ThemeManager` renders the menu at runtime from the wired theme list instead, and ADR-253 custom pages that keep a `#theme-menu` element still get it populated the same runtime way.
- **Exit state**: A real build (fixture or fernhill) shows a working Reset item that clears exactly the story's prefixed keys and restarts; the menu renders correctly with zero, one, and several wired themes with no build-time regex involved. Evidence: `platform-browser` vitest (`ThemeManager`, `SaveManager`/storage-prefix tests) + `devkit` vitest (`browser-core.test.ts`, `browser-build.test.ts`) green; a real CLI build (`node packages/devkit/dist/cli.js build <fixture>.story` or the repokit path) inspected for menu HTML and Reset wiring in `dist/web/`; `platform-browser` and `devkit` both rebuilt `dist` + `dist-esm`; `tsc --noEmit` clean.

### Phase 5: Auto-assertion policy for new commands
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: A settings surface (home TBD by this phase's own design step — per-story in the `.story`/project config, or per-user in `UserDefaults`/IDE settings) plus the testing-tab runner path that decides what a **new command's first run** auto-writes as its assertion.
- **Entry state**: Today's behavior is the `[SKIP]` placeholder ("let me decide") on every new command; the proposal's review flagged the setting's home (per-story vs per-user) as unresolved and required it be settled before implementation.
- **Deliverable**: Implements P-6. **Design step first** (this phase's own entry work, not a separate phase): resolve where the setting lives — per-story (travels with the project, shared by every author) or per-user (an individual's authoring preference) — and record the choice plus rationale in a short note or ADR amendment before writing code. **Implementation**: a Testing setting offering room description / room name + room description / all emitted text / let me decide (current `[SKIP]` behavior unchanged as the default); on a new command's first RUN, the chosen policy auto-writes the assertion — `contains(room name)`/location from the world capture (ADR-293's `RandomService`-adjacent world-state read, not a new mechanism). **"All emitted text" is defined in EMISSION terms (David, 2026-08-08): the ordered sequence of emissions the command produced — before text, room name, description, list contents, NPC activity — asserted in order, all of them.** The policy menu is really "which emissions get asserted": description only / room name + description / every emission in order / none. The written form for the full sequence is a per-command `[OK]` + literal text block — ADR-287's exact-match form, retained as the assertion tier's strongest form per ADR-294 D2 (note: this is *not* a golden-tier recording; ADR-294 D1 is explicit that the golden tier has no per-command assertions) — and the design step must confirm the literal block captures the emissions in their emitted ORDER, since order is part of David's definition (a block that flattened or reordered emissions would assert less than the policy promises). The policy is honored identically whether the command was run from the runner (CLI) or from the editor.
- **Exit state**: Setting the policy to each of the four choices and running a fresh command produces the documented assertion form every time, at both the runner and editor call sites; only retained grammar (never `[WHILE:]`/`[ENSURES:]`/`[OK: any]`) is ever written. Evidence: a design note/ADR-amendment artifact recording the setting-home decision; unit/vitest coverage at the runner level; a tab real-path or vitest test confirming the editor writes the same form; `tsc --noEmit` clean; testing-tab bundle rebuilt into `tools/ide/SharpeeIDE/Resources/testing-tab`.
- **Status**: PENDING

### Phase 6: Create Transcript from played commands
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: `tools/ide/SharpeeIDE/Play` (a left-margin turn-selection affordance over the play transcript) + the testing-tab's existing `createTranscript` wire (already used by Phase-6-exercise root/branch creation this session) + provenance/seed handling (ADR-294 D3).
- **Entry state**: Phase 5 (P-6) is DONE — this phase's auto-assertion step at creation time is P-6's policy, not a separate mechanism, so P-6 must exist first (hard dependency per the proposal: "Depends on P-6"). Phase 4 (P-5, the testing workspace) is strongly recommended done first — the proposal notes this composes with the workspace layout ("select on the left, transcript appears on the right," ADR-304 Consequences) — but is not a hard blocker if sequencing forces it earlier.
- **Deliverable**: Implements P-7, the largest item. **Design step first** (not a separate phase, per the proposal's own framing — front-load before implementation): resolve the three open design points named in the proposal and the phase-6 log (F9) — (a) seed pinning for the created transcript (the play session's seed, carried as provenance per ADR-294 D3), (b) mid-session selections' ancestry prefix (what a selection starting mid-play implies about `continues:`/parentage), (c) meta commands in the selection (save/restore/undo — included, dropped, or rejected). Record the resolution in a short design note before writing code. **Implementation**: the Play pane offers a left-margin selection over played turns and a Create Transcript action; the created file holds exactly the selected commands with the play session's seed pinned; P-6's auto-assertion policy applies at creation exactly as it does on a manually-added command's first run.
- **Exit state**: Playing, selecting a run of turns, and choosing Create Transcript produces a `.transcript` file that (1) contains exactly the selected commands, (2) pins the correct seed, (3) carries assertions per P-6's policy, and (4) passes a real run through the runner unmodified. Evidence: a real-path test that plays, selects, creates, and runs the resulting transcript to a pass (rule 13a — no stubbed runner); the design note covering (a)/(b)/(c); `xcodebuild test` and tab vitest green; bundle rebuilt.
- **Status**: PENDING
