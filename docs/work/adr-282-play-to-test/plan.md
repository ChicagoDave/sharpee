## Open question this plan surfaces rather than decides: does selection capture need a NEW platform-browser change?

ADR-282's Consequences state plainly: **"Nothing else platform-side (ADR-283 rejected)"** beyond the one authorized `actualOutput` field. But D2 requires capturing what text the author *selected* in a rendered response, and the existing turn-events bridge (`packages/platform-browser`) only ever carried command/response pairs — it has no selection concept.

The likely resolution, **not yet verified against the real WKWebView setup**: Swift can read `window.getSelection().toString()` via `WKWebView.evaluateJavaScript(_:)` **on demand**, entirely from `tools/ide/` — no change to `packages/platform-browser`'s shipped bundle needed, since selection state is standard DOM, not app-specific bridging. If that holds, selection capture is IDE-side work only, consistent with the ADR's "nothing else platform-side" ceiling. **If it turns out `evaluateJavaScript` can't cleanly get selection boundaries relative to the specific response paragraph** (e.g., because the selection needs to be scoped to "which turn's response" when multiple turns are visible at once), a small JS-side helper shipped as part of platform-browser's bundle might be needed after all — which would be a second platform-side change ADR-282's own Consequences text does not authorize, and would need a discussion/amendment before Phase 1 proceeds past its spike. **Phase 1 below opens with a short spike to resolve this before committing to an approach**, rather than assuming either answer.
