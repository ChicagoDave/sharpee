# Session Plan: OpenSilver IDE evaluation — WPF/native vs OpenSilver (.NET-native desktop host) for Chord Writer

**Created**: 2026-09-13
**Plan Status**: ACTIVE
**Overall scope**: An evaluation, not a build. Determine, on evidence, whether OpenSilver (XAML + C# compiled to WebAssembly for the browser, with a **.NET-native desktop host** — not Tauri, not Electron; David's correction, 2026-09-13, see Phase 0) can replace ADR-341's WPF ruling for Chord Writer on Windows — and, since an OpenSilver app is cross-platform, whether it eventually replaces the Swift macOS app too. Output is a filled parity-table column, a decision record with inline evidence, and (only on David's ADR-worthy confirmation) a draft new ADR that supersedes or confirms ADR-341. ADR-341 itself is not edited by this plan.
**Bounded contexts touched**: N/A — infrastructure/tooling evaluation, no domain behavior change. Product surface judged is the existing macOS `tools/ide/SharpeeIDE` parity table; no Chord change, no `packages/` change.
**Key domain language**: N/A (see above) — the evaluation's own vocabulary is "capability parity" (native host capability: subprocess, filesystem, toolchain) versus "control parity" (editor feel, custom drawing), and this plan orders work capability-first.

**Desktop host correction (David, 2026-09-13, mid-session — supersedes the goal framing this plan was first drafted from): the desktop host is .NET-native, not Tauri.** No Rust, no JS-interop IPC bridge, no Tauri commands, no `SecretLetter.Desktop/src-tauri`. `cargo-tauri` being installed on this machine is irrelevant to this evaluation. In a .NET-native host, `System.Diagnostics.Process` (streamed stdout), filesystem calls against `~/Documents/<Story Title>/`, and locating a vendored Node binary are plain .NET calls — the same primitives WPF would use, not a bridge crossing a sandbox boundary. ### Phase 1: Native host capability check — the kill phase (Integration Reality, rule 13a)
- **Tier**: Small
- **Budget**: 150
- **Domain focus**: Proves or disproves the one capability gap that OpenSilver's browser target cannot close by itself — everything ADR-341's Context calls out as native-only (subprocess spawn, real filesystem, vendored Node) is a plain .NET call under the Phase 0-identified desktop host, the same as WPF would use. Renamed and shrunk from an earlier "host bridge" framing that assumed a Tauri/JS-interop crossing; David corrected this 2026-09-13 (see the plan-level note above) — there is no bridge to build, only a capability to confirm, so the expected cost is small.
- **Entry state**: Phase 0's scaffold builds and runs under the identified .NET-native desktop host. No subprocess, filesystem, or Node-location code exists yet in the OpenSilver spike.
- **Deliverable**: OpenSilver XAML code running under the .NET-native desktop host that (a) calls `Process.Start`/`System.Diagnostics.Process` to run the real `sharpee compose --json` against a real story folder (e.g. a copy of a Dungeo-sized story) and streams stdout back to the UI incrementally, not just a final blob; (b) reads and writes files inside a real `~/Documents/<Story Title>/` folder (ADR-280 D6, ADR-341 D6) with no synthetic stand-in path; (c) locates and executes a vendored Node binary reachable from the desktop-host app bundle, the same shape `vendor-toolchain.sh` produces for the macOS app. Each of (a)-(c) is a REAL-PATH test per rule 13a — no stub of `sharpee`, no mocked filesystem, no placeholder Node. The same app's browser (WASM) target is also checked: does it still compile with these calls behind a host-abstraction seam (compiled out or interface-swapped for the browser target), or does the codebase fork? Command, output, and date recorded inline in this plan's phase record or a linked `docs/work/opensilver-ide-evaluation/host-bridge.md`.
- **Exit state**: Pass/fail is the gate for every phase after this one. If any of (a)-(c) fails outright (not "harder than expected" — actually fails) under the .NET-native host, record the failure with its exact error inline and stop; Phases 2-4 do not proceed on an unproven capability, and Phase 5's decision record states the kill plainly rather than continuing to judge editor feel on a foundation that cannot ship.
- **Status**: DONE — PASS (2026-09-13, session 30faa2) — record: `phase-1-host-capability.md`; evidence: `evidence/phase-1-capability-log.txt`, `evidence/phase-1-photino-capability-check.png`. Under `OpenSilver.Photino`, XAML code-behind spawns the real `sharpee compose --json` with streamed stdout (exit 0, 89 ms), writes and reads the real `~/Documents/OpenSilver Capability Check/` folder, and runs the vendored Node (v22.23.1); the same source builds for the browser target with a runtime-selected refusing host. 9 real-path xunit tests passing. Side finding filed as GH #457 (vendored toolchain cannot `build`: `files` omits `dist-esm` in seven packages) — a platform packaging gap, not an OpenSilver limit.

### Phase 2: Web-pane hosting — the third host for D3's contract
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: ADR-341 D3's host contract (serve pane files, serve the story's own `dist/web/<id>/` bundle, answer subprocess-result requests) seen from a third host shape after `WKWebView` (macOS) and `WebView2` (WPF spike, already PASS per `decision.md` Assumption 2).
- **Entry state**: Phase 1's native host capability check passes (filesystem + subprocess proven). No pane-hosting code exists yet for OpenSilver.
- **Deliverable**: The Play pane (a real story's `dist/web/<id>/` bundle, unmodified) and at minimum one of the two IDE-owned panes (`docs-tab` or `testing-surface`) served inside the OpenSilver app — via OpenSilver's `HtmlPresenter` (the browser target's own mechanism for embedding HTML/iframes) for the WASM build, and via whatever web-view control the Phase 0-identified .NET-native desktop host offers (a `BlazorWebView`/WebView2-backed control on Windows, a WKWebView-backed one under Mac Catalyst if MAUI Hybrid is the chosen host) for the desktop build — with two-way messaging proven for the Testing pane's tree-of-cards round trip (turn-feed in, serialized document out) and script injection working, since that is what D3's contract actually demands of a host, not just static serving. Serving from a custom origin (as `WKWebView`/`WebView2`'s scheme handlers do today) versus a plain served localhost origin is an open question this phase answers by trying, not by assumption.
- **Exit state**: At least one pane loads a real bundle, accepts input, and round-trips a message both directions, with the command/steps and result recorded inline. Any capability D3 requires that this host genuinely cannot provide (not merely awkward) is named explicitly as an owned gap, not glossed over.
- **Status**: DONE — PASS (2026-09-13, session 30faa2) — record: `phase-2-pane-hosting.md`; evidence: `evidence/phase-2-*`. Test story: fernhill (David, 2026-09-13). All three panes load real bundles inside the OpenSilver Photino app over custom-scheme origins (61 requests, all 200); the Testing pane completes the ADR-307 round trip (31-card tree replayed through the real client, a typed turn, the 32-card document posted back and written beside the spike, fernhill untouched); Play accepts typed input; Docs boots (106 nav links, Chord 3.6.0). Host-shape finding for D3: panes detect the host by the WebKit-specific `window.webkit.messageHandlers` shape, which a non-WebKit host must counterfeit (the read-only native object has to be replaced wholesale). Owned gap: the browser (WASM) target has no custom-scheme origin — panes there need an HTTP origin.

### Phase 3: Editor
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: What a code editor is, concretely, on OpenSilver — the parity table's first-spiked, highest-weight row (D2's own ordering: "the editor first").
- **Entry state**: Phase 1 passed (the native host capability for programmatic file read/write the editor needs for save/reload is proven). A plain XAML `TextBox` is assumed inadequate going in (no per-token highlighting, no gutter) and this phase either confirms or overturns that assumption with evidence rather than assertion.
- **Deliverable**: A working editor surface — most likely Monaco or CodeMirror hosted in an `HtmlPresenter` (an OpenSilver-native control is a fallback only if the hosted-editor route fails outright) — judged against the same feature list the WPF/WinUI3 spikes used: typing speed, per-token syntax highlighting (a hand-rolled or reused Chord tokenizer, not the full ADR-182 tree-sitter grammar unless it's already reachable), a gutter/line-number ruler, span selection and scroll-to-span from outside the editor, and programmatic undoable text replacement (needed by the World tab's fixes and the Problems panel's IFID fix per the parity table).
- **Exit state**: A felt judgment, backed by a timed measurement comparable in kind to the WPF/WinUI3 spike's 14.8-15.9ms / 13.5-15.4ms style-pass numbers on a same-sized real file, plus an explicit call on whether editing feels native or feels like "a web page in a box." No claim about tree-sitter reachability without having actually tried loading a `.NET`-consumable tree-sitter binding (or the same `TreeSitter.DotNet` package the WPF spike used) into this host.
- **Status**: DONE — measured PASS; felt judgment OPEN (2026-09-13, session 30faa2) — record: `phase-3-editor.md`; evidence: `evidence/phase-3-editor-log.txt`, `evidence/phase-3-editor-pane.png`. CodeMirror 6 + the real Chord lexer (bundled from `packages/chord/src/lexer.ts`) inside the OpenSilver Photino app: on a 1755-line real-Chord file (fernhill + ides-of-march head, 8,545 tokens) the whole-document style pass costs 0.92 ms per pass (WPF spike, different highlighter: 14.8–15.9 ms); 200 typed characters at 1.09 ms each; select/scroll-to-span, undoable replace (hash restored after undo), line numbers, wrap all proven from C#. Tree-sitter not tried: no Chord grammar exists (ADR-182 unimplemented) and the applicable binding here would be web-tree-sitter in the page, not TreeSitter.DotNet. The "native or a web page in a box" call is David's, via `dotnet run -- --pane editor` — this phase does not make it.
