### Phase 1: Source-side narration semantics — chain slot declaration (D3) and reaction override partition (D4)
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: N/A (platform-internal). Packages: `packages/world-model`, `packages/event-processor`.
- **Entry state**: ADR-296 ACCEPTED at v3.1 (verified above). No prior ADR-296 code changes in the tree.
- **Deliverable**:
  - `world-model`: `ChainEventOptions` gains `slot?: 'beforeRoomDescription' | 'afterRoomDescription' | 'afterEverything'`. Dispatch (wherever `executeChains` produces events today) stamps the registration's slot as `data._narrativeSlot` onto each produced **phrase event only** (`game.message` / `chord.phrase`) — typed non-phrase events a chain produces (`if.event.revealed`, `zoo.event.*`) are explicitly excluded from stamping and keep stream position, per D3's round-four finding. Default slot is `afterRoomDescription` when the option is omitted.
  - `event-processor` (`src/processor.ts:269-329`, the ADR-106 override path): implement the D4 partition —
    - a `game.message` targeting a trigger with NO `messageId` is a phrase emission: promote it to a standalone event; if it did not already receive a `_narrativeSlot` stamp via chain dispatch (i.e., it came from a plain `eventProcessor.registerHandler`, not a chain), default-stamp `_narrativeSlot: 'afterRoomDescription'` here.
    - a `game.message` targeting a trigger that HAS a `messageId` remains an ADR-106 override (unchanged behavior) — dungeo's mirror-room rumble is the living example and must keep overriding.
    - any `game.message` carrying `_chainedFrom` is always a phrase emission (never an override), regardless of trigger messageId.
    - the multiple-`game.message` error branch counts only the override partition — phrase emissions leave the consumption set before the count (round-four SMALL finding).
  - Dated pointer note: a short addendum to `docs/architecture/adrs/adr-106-domain-events-and-event-sourcing.md` recording the D4 narrowing (override now requires an existing trigger `messageId`; chain-produced and messageless-trigger messages are phrase emissions handled by ADR-296).
- **Exit state**: both packages compile clean; new unit tests below are green; no dungeo code touched yet.
- **Tests** (derived from D7):
  - `world-model`: chain registration with an explicit `slot` option stamps `_narrativeSlot` on produced phrase events; omitted option defaults to `afterRoomDescription`; a chain producing a typed non-phrase event (`if.event.revealed`-shaped fixture) is asserted to carry NO `_narrativeSlot` stamp and unchanged stream position.
  - `event-processor`: (1) messageless-trigger `game.message` becomes a standalone event, default-slotted; (2) messageId-bearing trigger still overrides (asserts the trigger's `data.messageId` is replaced, not appended); (3) chain-stamped `game.message` (`_chainedFrom` present) is always standalone even when its trigger has a `messageId`; (4) the multiple-message error branch fires only when two or more messages remain in the override partition, not when phrase emissions are present.
  - All tests assert on emitted event `data` fields (messageId, `_narrativeSlot`, `_chainedFrom`) per the project's "verify" bar — never on "didn't throw" or return-value-only.
- **Verification**:
  - `pnpm --filter '@sharpee/world-model' test` — report and stop on failure, no auto-retry.
  - `pnpm --filter '@sharpee/event-processor' test` — report and stop on failure, no auto-retry.

### Phase 3: Engine — sort restructure to slot insertion (D2/D3/D5, the core GH #208 fix)
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: N/A (platform-internal). Package: `packages/engine`, file: `packages/engine/src/prose-pipeline/stages/sort.ts` (tests at `packages/engine/tests/prose-pipeline/stages/sort.test.ts` — not colocated with the source).
- **Entry state**: Phases 1-2 complete — `_narrativeSlot` stamps exist on phrase events (Phase 1), `_transactionId` stamps are real per-source values (Phase 2).
- **Deliverable**: this is the riskiest phase (ADR-296 Risks: "slot insertion is new sort behavior, not just deletion") — go carefully, one change at a time, run `sort.test.ts` after each step.
  - **Delete**: room-description hoist (`sort.ts:71-78`), `action.*` hoist (`sort.ts:80-84`), chain-depth comparator (`sort.ts:86-89`) — comparator's terminal statement becomes an explicit `return 0`.
  - **Missing-id never-groups**: the sort treats an absent `_transactionId` as equal to nothing, including another absent id (closes #208's defect class structurally).
  - **Anchor cluster detection**: within a transaction, the anchor is the `if.event.room.description` event plus the following `if.event.list.contents` events, skipping non-rendering interleaved types — skip list is exactly `if.event.illustrated` today, extended only by named addition (comment the skip list as an explicit, named array — not an inline literal — so a future addition is a one-line diff).
  - **Anchor-less collapse**: a transaction with no room-description event collapses the frame around its primary report event — the transaction's first event with `data.messageId` set. Declared `afterRoomDescription` phrases insert after it; `afterEverything` stays transaction-final.
  - **Slot insertion pass**: `_narrativeSlot`-stamped events insert at their transaction's frame boundary — `beforeRoomDescription` before the anchor cluster (or before the primary event in the collapsed case), `afterRoomDescription` immediately after the anchor cluster (or after the primary event), `afterEverything` at the transaction's end. Unstamped events keep stream position (this is what realizes D0 rule 1 — "phrases you emit in your own report render in the order you emit them").
  - **Second-anchor defect guard**: a second room-description event within one transaction is a defect — warn, first one anchors (ADR-295 D1 already guarantees the known dungeo case cannot recur; this is a guard for the general case).
  - **Fixtures kept, unchanged**: lifecycle-first (banner), implicit-take-first (both the emission-side prepend convention and the sort rule stay — v1 review lesson: required feature, doubly guaranteed).
  - **Stability**: the insertion pass must be stable (does not reorder events that don't need to move) and cheap — turn event counts are small, no algorithmic complexity concern, but it gets its own unit tests.
  - **Header restatement**: `sort.ts`'s header comment is rewritten to state the D0 contract directly (module purpose per project doc-header convention).
  - Dated pointer note: append the further paragraph to `docs/architecture/adrs/adr-094-event-chaining.md` Amendment A1 — "the promise is delivered via slots; the depth-sort mechanism is retired, the provenance stamps remain" (D5).
- **Exit state**: `sort.ts` contains only fixtures, never-group, slot insertion, and stability logic (per ADR-296 Consequences: "the sort shrinks to: fixtures, never-group, slot insertion, stability"). All non-dungeo unit suites green. Dungeo output WILL diverge from baseline starting at this phase — that divergence is expected and is Phase 5's job to characterize and gate, not this phase's.
- **Tests** (derived from D7 `sort.test.ts` list):
  - Replace the defect-enshrining test at `sort.test.ts:134` with its inverse: absent ids never group.
  - Emission order within a transaction survives untouched (rule 1).
  - A slot-stamped phrase inserts after the anchor cluster (rule 2), including the "cluster" case (description + one or more `if.event.list.contents`, with an `if.event.illustrated` interleaved and correctly skipped).
  - Anchor-less collapse: a TAKE-shaped transaction with no description event places an `afterRoomDescription`-slotted phrase after the primary report event.
  - Two transactions keep occurrence order (rule 3): player action transaction, then plugin batches in plugin-priority order.
  - Fixtures (rule 4): banner first in the turn; implicit-take first in its action — both still pass.
  - Second-room-description-in-one-transaction: warns, first one anchors (does not throw, does not silently pick the second).
  - Stability: an unrelated pair of unstamped events in the same transaction never swaps order across a sort call.
- **Verification**:
  - `pnpm --filter '@sharpee/engine' test` (esp. `sort.test.ts`) — report and stop on failure, no auto-retry.
  - Full non-dungeo regression: `pnpm --filter '@sharpee/world-model' test`, `pnpm --filter '@sharpee/stdlib' test`, `pnpm --filter '@sharpee/event-processor' test` — confirm nothing outside `engine` regressed.
  - `tsc --noEmit` clean for `packages/engine`.
  - Do NOT run dungeo goldens/walkthroughs as a pass/fail gate in this phase — expected to diverge. A quick manual `node dist/cli/sharpee.js --test stories/dungeo/walkthroughs/wt-02-bank-puzzle.transcript` sanity peek is fine to eyeball the diff shape, but do not re-bless or treat its result as this phase's exit criterion.

## Risks and open questions surfaced while reading the ADR

- **The D4 seam is explicitly flagged in the ADR as "the rug seam"** (ISSUE-074/ADR-157 precedent: override-vs-append regressed silently once before). Phase 1's tests are the mitigation the ADR calls for — they must lock the partition semantics, not just the happy path.
- **`death-penalty-handler`'s message effect is classified at implementation time**, not predetermined by the ADR (D4: "its turns have no description anchor; the collapse rule applies"). Phase 1 or Phase 5 may surface a fifth affected transcript if this classification produces a visible diff — if so, that diff is NOT in the D8 predicted set and trips Phase 5's abort criterion; the fix is to update the design doc's scenario table and get it re-accepted before blessing, not to quietly add it to the predicted list.
- **The unused duplicate `TurnEventProcessor` class** (Phase 2, v2 finding 12) has an explicit "or" in the ADR text (stamp it too, or deprecate it) — this plan defers the choice to implementation time with an instruction to record whichever is chosen, since the ADR itself doesn't resolve it.
- **Plugin invocation-counting assumption** (Phase 2, D1: "one batch per plugin per turn today; an invocation counter is added only if that changes") — if implementation finds a plugin that runs multiple batches per turn, the `txn:{turn}:plugin:{plugin.id}` id shape under-specifies and Phase 2 should stop and report rather than inventing a counter scheme unreviewed.
- **Pre-existing, out-of-scope flake**: unpinned clock-seeded unit transcripts intermittently die to thief combat (session-20260801-2346 addendum). Do not let Phase 5's transcript run block on this — it is a known, separately-tracked issue, not a regression from this work.
- **Save-format changelog location**: the ADR requires a changelog entry (D1, D4) but this repo's plan sources don't pin an exact file path for it; Phase 4 should locate the existing save-format changelog convention (referenced in project memory as "save-format versioning") before writing the entry, and stop to ask if no such file exists yet.
