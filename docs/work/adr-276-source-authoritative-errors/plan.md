# Session Plan: ADR-276 — Chord source-authoritative errors (the stdlib manifest)

**Created**: 2026-07-27
**Overall scope**: Migrate all 16 census entries of author-reachable, load-only
`LoadError`s in `story-loader/src/loader.ts` into Chord compile diagnostics
(`analysis.*` codes, collected, with spans), converting each loader site to a
defensive backstop in the same commit. Ships a locale-keyed, freshness-gated
stdlib manifest in `@sharpee/chord` (generated by a new `repokit` build step,
mechanism copied from ADR-269 D7), a declarative per-trait setting-schema table
owned by `story-loader` (prerequisite for the manifest's setting-schema slice),
and re-emits `compose`'s hatch lint as structured diagnostic records (D4). One
arc, one end-of-arc census re-audit — no deferred remainder (Q-1).
**Bounded contexts touched**: N/A — this is compiler-frontend/build-tooling
work (no `docs/ddd/notation.yaml` in this project; not domain modeling). The
packages involved, in the ADR's own vocabulary: `@sharpee/chord` (compiler —
lexer/parser/analyzer/catalog/diagnostics), `@sharpee/story-loader` (load-time
IR lowering — the census's current home and the D5 residue owner),
`parser-en-us` (the standard grammar source the manifest's grammar-shape slice
reads), `tools/repokit` (build orchestration — the new manifest generator and
freshness gate), `packages/devkit` (the `compose` command — D4's hatch lint).
**Key domain language**: census entry, `LoadError` backstop ("the compiler's
gate refuses this"), stdlib manifest, freshness gate, locale-keyed, grammar-file
mode, `parse.*`/`analysis.*` diagnostic code, `DiagnosticBag` (collected, never
first-throw), declarative setting-schema table (`boolean` \| `number` \|
`entity-ref`), hatch lint / structured diagnostic record.

## Hard constraints carried from the ADR (not re-litigated by this plan)
1. **One arc** (Q-1): all 16 census entries are phases in this plan; the final
   phase's census re-audit covers all of them — no accepted-but-unscheduled
   remainder.
2. **D3 ordering**: entries 9, 11, 12, 14, 15, and 13 (its map is the 2-entry
   closed `toolGatedGerunds` table — confirmed small and closed) migrate before
   the manifest generator exists (Phase 1).
3. **Locale-keyed from day one** (Q-2): the generator is parameterized by
   locale; `en-US` is the sole entry; locale-owned facts (grammar shapes,
   direction words) are structurally distinguished from locale-neutral ones
   (action ids, setting schemas).
4. **Setting-schema refactor first** (Q-3): entries 4–6 wait on one exported
   declarative schema module in `story-loader` that both the loader's own
   validation and the manifest generator consume — Phase 2, before Phase 5.
5. **Same-commit backstop conversion**: every migrated `LoadError` site gets
   its defensive-backstop rewrite (loader comment convention: "the compiler's
   gate refuses this") in the same commit as its analyzer diagnostic — never
   split across phases or left as dead code pending cleanup.
6. **Corpus stays green after every phase**: dungeo units + wt chain, cloak,
   fernhill, friendly-zoo, nautical, acceptance stories. A migrated gate may
   not be stricter than the load check it replaces except by explicit ruling
   recorded in the ADR (none recorded — so no phase may tighten behavior).
7. **D4 record shape only, no new transport**: the hatch lint's
   `{severity, code, message, file, line}` record joins the one diagnostics
   stream; `compose`'s text output stays behaviorally unchanged until
   ADR-258's `--json` lands (out of this plan's scope).
8. **Import direction unchanged**: chord imports nothing new; no platform
   package imports chord (`scripts/bundle-entry.js` direction check stays
   green every phase).
9. **Browser boot-compile parity**: every migrated check must be provable via
   the browser client's actual boot-compile path, not just a Node-side
   `compile()` call — a REAL-PATH test per DEVARCH rule 13a's Integration
   Reality discipline (this "browser" claim needs the production browser
   bridge path exercised, not a stand-in).

  v1 adjective, `:1772`).

  already carries `TRAIT_ADJECTIVES` (the set entry 15 needs) and the trait

- **Deliverable**: six new `analysis.*` diagnostic codes in
  `packages/chord/src/analyzer.ts` (one per entry, each with a full span,
  collected in the `DiagnosticBag` — never first-throw), each named for its
  check (e.g. `analysis.patrol-needs-route`, `analysis.dark-rooms-only`,
  `analysis.worn-not-wearable`, `analysis.ambiguous-gerund-surface`,
  `analysis.conditional-composition-unsupported`,
  `analysis.trait-not-declared`). Each of the six `loader.ts` sites rewritten

  diagnostic (positive: rogue IR still trips the backstop; negative: the
  analyzer catches it first for any story that reaches the loader).
- **Exit state**: Six `LoadError` sites are unreachable for gate-clean IR;
  each has an analyzer test proving the compile diagnostic fires with the
  right code, span, and message, plus a loader-level test proving the backstop
  still fires against hand-built rogue IR (constraint 5/hard constraint 5 —

- **Test scenarios**:

    named diagnostic code + span from `analyze()`.
  - Six loader-level backstop tests constructing rogue `StoryIR` objects

### Phase 2: Declarative setting-schema table (story-loader prerequisite for entries 4–6)
- **Tier**: Medium
- **Budget**: ~250 tool calls
- **Focus**: Q-3's ruling — one exported schema module the loader consumes
  directly and the Phase 5 generator bakes into the manifest, so the compile
  gate and the load backstop are provably one source. No new diagnostics in
  this phase; pure prerequisite refactor.
- **Census entries prepared (not yet migrated)**: 4 (`:1808`, `:2000`), 5
  (`:1995`), 6 (`:226`, `:2041`).
- **Entry state**: Phase 1 landed. Setting-schema data is currently scattered:
  `COMBAT_FIELD_ROUTES` and `NPC_FIELD_ROUTES` in
  `packages/story-loader/src/extension-registry.ts` (typed `trait`/`field`/
  `convert: 'number' | 'boolean'` — no `entity-ref` variant yet), plus two
  separate ad-hoc, keyless entity-name resolution sites
  (`entityRefFor` at `loader.ts:220-228`, `traitFieldValues` at
  `loader.ts:2030-2049`) that treat **any** config value of `valueKind ===
  'name'` as an entity reference regardless of which key it's on — i.e. today
  there is no declared set of "which keys are entity-typed," only a runtime
  duck-type on the parsed value shape.
- **Deliverable**: one new exported module (e.g.
  `packages/story-loader/src/setting-schema.ts`) with a single schema shape
  — trait name → setting key → `'boolean' | 'number' | 'entity-ref'` — folding
  in `COMBAT_FIELD_ROUTES`, `NPC_FIELD_ROUTES`'s boolean fields, and an
  explicit enumeration of every entity-typed `with`-key the two ad-hoc sites
  currently accept by duck-typing (walk every `define trait`/`with` call site
  in the corpus stories to enumerate them — the schema must be exhaustive, not
  best-effort, since the Phase 5 diagnostic is authoritative going forward).
  `extension-registry.ts` and the two ad-hoc resolution sites refactored to
  consume the new module directly (table lookup replacing hand-written
  branches); behavior preserved exactly (no diagnostic changes yet — this
  phase must not alter what any story accepts or rejects).
- **Exit state**: One schema module is the sole source for setting-value-type
  facts in `story-loader`; `COMBAT_FIELD_ROUTES`/`NPC_FIELD_ROUTES` either
  become thin views over it or are retired in favor of it (implementer's call,
  recorded in the phase's work summary); full corpus green with zero behavior
  change (this is a refactor phase — a corpus diff here is a regression, not a
  finding).
- **Test scenarios**:
  - Existing story-loader unit tests for combat/NPC field routing and
    entity-ref config resolution re-run unchanged (they must still pass
    verbatim — proves the refactor is behavior-preserving).
  - New schema-module unit test asserting every `FieldRoute`/`NpcFieldRoute`
    consumer resolves through the one table (a structural drift gate, in the
    spirit of the existing `EXTENSION_REGISTRY`/chord-manifest conformance
    test noted in `extension-registry.ts`'s header).
  - Full corpus re-run, byte-for-byte same pass/fail set as Phase 1's baseline.
- **Status**: PENDING

### Phase 3: Locale-keyed stdlib manifest generator + freshness gate + action-id entries
- **Tier**: Large
- **Budget**: ~400 tool calls
- **Focus**: D2/Q-2 — stand up the generator mechanism itself (the highest-risk,
  most novel piece of the arc) against the simplest data slice (the stdlib
  action-id set), and establish the browser boot-compile parity test harness
  every later phase extends.
- **Census entries migrated**: 1 (`extend action` target names no story/standard
  action, `:1123`), 2 (`remove from action` target names no standard action,
  `:1141`).
- **Entry state**: Phase 1 landed (pattern established: diagnostic + same-commit
  backstop + rogue-IR test). Phase 2 not required for this phase (action ids
  are locale-neutral, no schema dependency) but should be done first per this
  plan's ordering for review continuity — not a hard dependency.
- **Deliverable**:
  - A new `repokit` command (sibling to `tools/repokit/src/commands/grammar.ts`,
    which is the mechanism precedent) that generates a **locale-keyed** manifest
    module into `@sharpee/chord` (e.g. `packages/chord/src/stdlib-manifest.ts`,
    committed, marked generated — never hand-edited). Shape: `{ locales: {
    'en-US': { actionIds: ReadonlySet<string>, ... } } }` — structurally ready
    for future manifest slices (grammar shapes, setting schema, vocab sets) even
    though only `actionIds` is populated this phase.
  - The action-id slice is read from `packages/stdlib/src/actions/constants.ts`
    **source** (not dist — mirrors `readStdlibActionIds()` in
    `grammar.ts`, since stdlib builds after chord in the platform build order).
  - `--check` freshness gate wired into `repokit verify` (alongside
    `checkGrammarModule`/`checkDocsBlocksModule` in `verify.ts`) and the main
    build loop before any package that imports the manifest compiles: stale
    manifest fails the build, never a silent diff.
  - Two new `analysis.*` diagnostics in `analyzer.ts` consuming
    `stdlib-manifest.ts`'s `actionIds` set for `extend action`/`remove from
    action` target resolution, preserving ADR-270 D2's **story-first**
    resolution order (a story-defined action of the same name still wins —
    the analyzer must see the story's own action table before falling back to
    the manifest, exactly mirroring `loader.ts:1112-1130`'s current order).
    Both `loader.ts:1123` and `:1141` sites convert to backstops in this
    commit.
  - Browser boot-compile parity test harness: a new test (pattern from
    `packages/devkit/src/standalone/chord-import-browser.test.ts`, the existing
    real-path browser-bridge precedent) driving `packages/runtime/src/
    bridge.ts`'s actual `handleStart()` boot-compile path against a `.story`
    fixture with a bad `extend action`/`remove from action` target, asserting
    the diagnostic surfaces there — not a bare `compile()` call in isolation
    (rule 13a: this is the REAL-PATH test for the "browser" acceptance claim).
- **Exit state**: The generator mechanism, the freshness gate, and the browser
  parity harness all exist and are proven end-to-end on the smallest data
  slice; entries 1 and 2 are analyzer-gated with `loader.ts` backstops;
  `scripts/bundle-entry.js`'s direction check stays green (generator lives in
  `tools/repokit`, outside the runtime graph, per ADR-210).
- **Test scenarios**:
  - `.story` fixtures: unknown `extend action` target with a typo (asserts
    did-you-mean suggestion, mirroring `suggestGerund`'s existing UX), unknown
    `remove from action` target, and a story-first case (a story defines an
    action of the same name an `extend action` also names — story wins, no
    diagnostic).
  - Freshness-gate demonstration test: hand-edit `constants.ts` to add a bogus
    action id, run `repokit verify --check` (or the direct `--check` entry
    point), assert non-zero exit / failure output — then revert (ADR
    acceptance: "demonstrated by a deliberate stale edit during review").
  - Browser boot-compile test asserting the same two diagnostics from the
    bridge's `handleStart()` path.
  - Rogue-IR backstop tests for both sites (hand-built `StoryIR` bypassing the
    analyzer).
  - Full corpus green.
- **Status**: PENDING

### Phase 7: Hatch lint as structured diagnostic records (D4)
- **Tier**: Small
- **Budget**: ~100 tool calls
- **Focus**: D4 — independent of the census/manifest track (no dependency on
  Phases 2–6; may be scheduled at any point after Phase 1 lands the
  diagnostic-code-and-backstop convention this phase's records format mirrors).
- **Entry state**: `compose`'s hatch lint
  (`packages/devkit/src/commands/compose.ts`, `hatch.chord-namespace`,
  currently formatted text at the file's existing `console.error`/`f.file:f.line

- **Deliverable**: hatch lint findings re-emitted as
  `{ severity, code, message, file, line }` records — same shape as compile
  diagnostics minus the end-span (hatch findings have no end-span; D4 is

  collection inside `compose`'s in-memory result, so a future `--json` mode
  (ADR-258, out of scope here) has one stream to serialize. `compose`'s
  current text output is preserved byte-for-byte (D4: "text output unchanged
  in behavior... D4 defines the shape, not a new transport") — this phase adds
  a record alongside the existing text write, it does not replace the text
  write.
- **Exit state**: Hatch findings are structured records collected with compile
  diagnostics; `compose --check`'s text output is unchanged for any existing
  hatch-lint fixture (regression: byte-identical stdout on the fixtures
  ADR-259 introduced).
- **Test scenarios**:
  - Existing hatch-lint fixture/test re-run, asserting identical text output.
  - New test asserting the structured record's shape and that it appears in
    the same collection as a compile diagnostic from a story with both an
