# Session Plan: Restructure the Chord Writer Documentation tab to mirror sharpee.net's real nav (GH #238)

**Created**: 2026-08-07 (amended same day — scope change folded in, David approved)
**Overall scope**: The Documentation tab's bundler (`tools/ide/web/docs-tab/build.mjs`) currently derives page order, section labels, and breadcrumbs by walking `content.mdx` files alphabetically. The site's real, hand-authored navigation (`website/src/lib/nav.ts`) is never read. This plan makes the bundler read `nav.ts` as the source of truth and makes the tab's UI (`main.ts`) render a nested nav tree, correct breadcrumbs, and a prev/next pager from that data — matching the website's structure (David's D1, amended below), with no reading-position persistence (D2).

**Naming note**: the product is **Chord Writer**, not "the Sharpee IDE." `AppIdentity.productName`, `CFBundleDisplayName`, and the website's landing page all say so; `SharpeeIDE` is only the internal Xcode target name and never reaches the UI. This plan uses "Chord Writer" in prose; file/target paths under `tools/ide/SharpeeIDE*` are unaffected (that is a filesystem/target name, not the product name shown to authors).

**Bounded contexts touched**: N/A — this is IDE/tooling work (a build pipeline + a bundled web UI), not domain-behavior work. Framed in plain technical terms per the DDD-does-not-apply carve-out.
**Key domain language**: N/A

## Phases

### Phase 1: Navigation-as-data in the bundler
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: N/A (tooling) — `tools/ide/web/docs-tab/build.mjs`, a new pure helper module, and `docs-index.json`'s emitted shape.
- **Entry state**: `build.mjs` derives page order/section/crumb from `readdirSync(...).sort()` over `content.mdx` files; `website/src/lib/nav.ts` exports `NAV`, `pagerFor`, `crumbsFor` but nothing in `tools/ide` reads it; esbuild (already a `build.mjs` dependency) transpiling `nav.ts` to a temp ESM module for import was proven working this session (scratchpad probe, not committed). The four new `/chord-writer/*` pages and the new `Chord Writer` NAV section are already committed (see Scope amendment above) — `nav.ts` now names 147 hrefs across 4 sections, and the filesystem under `website/src/app/chord-writer/**` now holds the matching `content.mdx` files.
  - `SECTIONS` (the filesystem walk) becomes `['chord-writer', 'chord', 'learn']` — `chord-writer` added, `sharpee` still excluded.
  - The nav-bridge's shipped-section-title list becomes `['Chord Writer', 'Chord', 'Tutorial']`, Chord Writer first — matching `nav.ts`'s section order.
  - `/play` and `/playground` (Tutorial section's ungrouped top-level `items`, not inside any `group`) remain app routes with no `content.mdx` and must not be treated as documentation pages — the rule stands: only hrefs reachable through a section's `groups` (items and their `children`) are documentation pages; a section's own top-level `items` field is never walked for this purpose.
- **Deliverable**:
  - `build.mjs` transpiles `website/src/lib/nav.ts` via esbuild into a temp ESM module at build time and imports `NAV` from it (no change to `nav.ts` itself — it is website-owned).
  - New pure module (e.g. `tools/ide/web/docs-tab/src/nav-bridge.mjs`) exposing a function that, given `NAV`, a set of section titles to ship (`['Chord Writer', 'Chord', 'Tutorial']`), and a set of **explicitly excluded groups**, walks only `section.groups[].items[]` (and their `.children[]`) — skipping any group named in the exclusion set — and returns an ordered list of `{ href, title, section, crumb }` records. `crumb` built the same way `nav.ts`'s `crumbsFor` builds it (`section.title › group.title › item.title[ › child.title]`, with a group-titled "Overview" the same way `pagerFor` relabels it); `section` set to the nav section's `title` (so `/learn/*` pages get section `'Tutorial'`, not `'learn'`; `/chord-writer/*` pages get section `'Chord Writer'`).
  - **Group-level exclusion (new — the main code delta over the original design)**: `Chord › Getting Started` is dropped from the shipped bundle. Its three pages (`/chord/getting-started/install`, `/chord/getting-started/first-story`, `/chord/getting-started/compose-and-run`) are CLI install/scaffold/run instructions superseded by the Chord Writer section. Declare this as an explicit, named constant in `nav-bridge.mjs` — e.g. `const EXCLUDED_GROUPS = [{ section: 'Chord', group: 'Getting Started' }]` — with a comment stating *why* (superseded by Chord Writer's getting-started, not a bug) so a future reader sees a decision, not an oversight.
  - `build.mjs` replaces its file-path-derived `title`/`section`/`crumb`/order with this NAV-derived data for every page whose `href` has a matching nav-bridge record, and replaces the file-walk's alphabetical iteration order with NAV traversal order when writing `pages[]`.
  - `docs-index.json` gains a new `nav` field: the filtered NAV tree (sections → groups → items → children, hrefs and titles only, with `EXCLUDED_GROUPS` already removed — no page text) emitted **as data**, so the tab (Phase 2) can render the site's real hierarchy and compute prev/next without re-deriving it.
  - **Hard invariant, restated for the exclusion (enforced by the build, not just true today)**: after filtering `NAV` to `['Chord Writer', 'Chord', 'Tutorial']`, walking only `groups`, and removing `EXCLUDED_GROUPS`, the resulting href set must equal **exactly** the walked `content.mdx` set **minus** the excluded group's hrefs. A page that is neither shipped nor named in `EXCLUDED_GROUPS` but is missing from one side of the comparison still throws — excluded-by-configuration is not the same as orphaned, and both directions of mismatch (a `content.mdx` with no NAV entry and no exclusion; a filtered, non-excluded NAV leaf with no `content.mdx`) must fail the build loudly (extends the existing "unhandled MDX component" throw pattern — same reasoning: silent loss with no signal is the failure mode being prevented).
- **Exit state**: `docs-index.json`'s `pages[]` is ordered, titled, sectioned, and crumbed by `nav.ts`, with the `Chord › Getting Started` group excluded by name; it carries a new `nav` tree field; the invariant (shipped = walked − excluded) is enforced by code, not just verified by hand.
