# Session Plan: Implement ADR-345 — the engine's lifecycle phase becomes an explicit concept

**Created**: 2026-09-10
**Plan Status**: DONE
**Overall scope**: Implement ADR-345 D1–D14. `GameEngine`'s lifecycle — today five proxies (`running`, `story`, `_context`, `channelService`, `commandExecutor`) answering the same question in three different sentences — becomes one discriminated field, `EnginePhase`, with four states (`empty`, `ready`, `playing`, `stopped`) and one guard per lifecycle method instead of a hand-picked proxy per method. D1–D11 are a pure refactor (no behavior change). D12 is the one behavior change: `resume()` starts emitting `game.resumed`, which nothing does today. D13 obliges the phase that lands D2 to amend ADR-344 D6a's now-stale quoted refusal string in the same commit. D7's outward half removes dead `?.`/`?? 0` optionality-hedging in `TurnEngine`, `ISaveRestoreStateProvider`, and both bridge packages, which exists only because those callers wanted the phase and couldn't get it. D5 is explicitly NOT proposed (no type-level lifecycle) — not planned.
**Platform change**: every phase below touches `packages/engine`; Phase 2 additionally touches `packages/bridge` and `packages/runtime`; Phase 3 additionally touches `packages/core` and possibly `packages/lang-en-us` (D14's "no template registered" condition, verified not assumed). Per CLAUDE.md, all `packages/` changes require discussion with David before implementation — **this plan's existence is not that approval.** Ask before starting each phase's edits, not just once at the top.
**Bounded contexts touched**: N/A — this is *Making Implicit Concepts Explicit* (DDD Ch. 9 tactical pattern) applied to one class's internal state machine, not strategic domain modeling. The ADR says so directly (Context, "The framing, stated honestly"): no bounded context is touched, and the discriminant is deliberately not exported past `GameEngine` (D7) — so there is no new ubiquitous-language term for a consumer-facing glossary. Framed in plain technical terms, consistent with the sibling ADR-344 plan.
**Key domain language**: `EnginePhase` (`empty` / `ready` / `playing` / `stopped`), the phase discriminant field on `GameEngine` — not exported, not a `TurnEngine` field (D7). No other domain terms are introduced.

## Sequencing rationale

ADR-345 is explicit that D1–D11 (no behavior change) and D12 (one behavior change) "must not be verified as one thing" (Consequences; also stated directly under D12 and reiterated after AC-8). That constraint, not file-count balancing, is what drives the three-phase split below:

1. **Phase 1 (D1, D2, D3, D4, D8, D9, D11, D13)** — the internal refactor: the `EnginePhase` type, one guard per method (including the D8 exception — `stop()` stays tolerant while its siblings go strict), the `context` getter's narrowing, the naming (`empty`/`ready`/`playing`/`stopped`), and the D13 amendment to ADR-344 D6a in the same commit as D2. Confined to `packages/engine`. Everything here is behavior-preserving by the ADR's own claim, and AC-1, AC-2, AC-4, AC-7, AC-8 are exactly the tests that would catch a claim that turned out false.
2. **Phase 2 (D7)** — the outward-facing half: `TurnEngine.story`/`.channelService` and `ISaveRestoreStateProvider.getStory()` stop being optional, and the two bridge packages lose the dead `?.`/`?? 0` hedge that exists only because they wanted the phase and had no way to ask for it. Sequenced after Phase 1 because D7's whole premise — "the optionality the phase disproves is gone" — is meaningless until the phase exists to disprove it. Touches `packages/bridge` and `packages/runtime` in addition to `packages/engine`, so it is its own platform-approval ask. Gated by AC-3 alone.
3. **Phase 3 (D12, D14)** — the one behavior change, isolated per the ADR's own instruction: `resume()` emits `game.resumed`; the prose pipeline is verified (not assumed) to render nothing for it; the Dungeo walkthrough chain confirms no rendered-output drift. Sequenced last and kept separate from Phases 1–2's green suites so a false "no behavior change" claim in Phase 1/2 cannot hide inside this phase's evidence, and this phase's genuine behavior change cannot hide inside Phase 1/2's. Gated by AC-5 and AC-6 alone, in the order AC-6 itself specifies (pipeline test first, as the premise check; chain run second).

**I-52e228-1 (the systemic dist-vs-source audit) is judged out of scope for this plan.** AC-3 already carries the narrow instance that matters here — per-package `tsc --noEmit` plus `./repokit build dungeo`, not root `tsc` — and that is stated as this plan's evidence standard in every phase below. The open item asks a repo-wide question (which suites across the whole workspace read `dist/` vs source, which gates trust artifact presence over freshness) that is not bounded by ADR-345's scope and was already deliberately deferred as its own decision in the session that raised it. Folding it in here would widen this plan past the ADR it implements. It stays a standing Long Term item.
