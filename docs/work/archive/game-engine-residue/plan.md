## Considered from `docs/work/engine-refactor/ddd-assessment.md` and deferred, with reasons

- **`Session` as a modeled concept** (one playthrough of one story on one client; `start`/`stop`/`resume` as its lifecycle). The diagnosis is right: the class speaks an assembly dialect (constructor, `setStory`) and a playthrough dialect (`start` onward), and "session" is already in three field names. But every payoff the assessment lists is either already true or lands in this plan: `bootstrap` already builds one engine per playthrough and reboots a fresh one on restart (ADR-248, `packages/bootstrap/src/index.ts` ~410), so an engine *is* a session in practice; save already serializes exactly the session (`IEngineState` = event source + world snapshot + turn history + plugin states, `SaveRestoreService.createSaveData(engine)`); the four dead `start()` guards go in Phase 5(a); `setStory`-twice is Phase 4's guard; the shared channel registry is #393. What a `Session` type would add is a typed handoff between assembly and playthrough in place of an ordering convention, at the cost of a public-surface cutover across the five `new GameEngine` sites (`bootstrap`, `bridge`, `runtime`, two browser entries), `BrowserClient`, and the runtime protocol's load-then-start sequence. Phase 4's install steps are the assembly half of that split, so this plan builds toward it without committing to it. Revisit as its own ADR once this plan closes, judged by whether the IDE's Play surface or the bridge protocol gets simpler.
- **`PlayerRole` as a single representation** (today three: `ActorTrait.isPlayer`, `WorldModel.playerId`, `GameContext.player`, kept aligned by `syncPlayerState`). Real finding, and the trait flag is the odd one: it is serialized with the entity while `playerId` is also serialized with the world, so a save carries two sources of truth. Deriving the flag from `world.getPlayer()` is a world-model change: `ActorBehavior.isPlayer(entity)` takes no world, `story-loader` sets the flag directly (`loader.ts` ~744), and `transcript-tester` displays it. That is a discuss-first change to `packages/world-model` with its own consumers, not a `game-engine.ts` extraction. File as an issue; not this plan.
- **World invariants audited by free functions** (`validateRoomSnippets`, `validateCombatantHealth`). Evans's general point holds, but these two are end-of-build, cross-entity checks (a snippet binding is not known until the phrase registry is complete; combatant health is checked across every actor the story built). They cannot be enforced at the mutation, so they are correctly load steps, and Phase 4 names them as such in `STORY_INSTALL_STEPS`.
- **Renaming `setStory`** (it installs, it does not set). Agreed on the name; it is a public-surface rename across the five construction sites plus `bootstrap`. Cheap under the no-backward-compatibility rule, but it amends ADR-334 AC-5, so it is David's call at Phase 4, not a default.
- **`turnEngine()` versus `platformOperationHost()`, "what was different about the thinking".** The host was designed fresh under D3 as a contract. `turnEngine()` was the extraction seam under D5's "private stays private", built one byte-identical step at a time, and its width is the seventeen helper bodies that never moved. Phase 1 is the answer.
- **Running Phase 2 before Phase 1 for risk discovery** (`ddd-assessment-3.md` point 3). The argument was that Phase 2 holds the plan's only stop-and-escalate branch and should not sit behind 400 units of unrelated work. The risk it was meant to discover has been retired by inspection instead (see Phase 2's gate-exposure note: no Chord tree and no Dungeo path can expose the precedence change), so the order David approved stands: 0, 1, 2, 3, 4, 5, 6. Phases 2 and 3 remain independent of Phase 1's seventeen bodies, so the order can still change at no cost if Phase 1 stalls.
