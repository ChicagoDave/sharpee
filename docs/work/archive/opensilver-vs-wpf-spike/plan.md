# Session Plan: OpenSilver vs WPF — capability-first spike for Chord Writer on Windows

**Created**: 2026-09-12
**Plan Status**: ABANDONED (2026-09-14, session 6c19b3 — David's rule-18b disposition when `docs/context/.current-plan` was repointed to `docs/work/web-ide-evaluation/plan.md` by a pull from `origin/main`. No phase of this plan was ever started. Its question — whether OpenSilver beats WPF for Chord Writer on Windows — was answered on the Mac by three evidence-first evaluations (`docs/work/opensilver-ide-evaluation/`, `docs/work/avalonia-ide-evaluation/`, `docs/work/web-ide-evaluation/`) and recorded in ADR-351, so this plan is superseded rather than resumable.)
**Overall scope**: David (2026-09-12): "Consider building the OpenSilver version instead, so we need a spike comparison for WPF vs OpenSilver and trying for full parity." This plan re-opens ADR-341 D2's SHAPE ruling ("Not Electron, not Tauri, not a web application in a window") on new evidence David supplied this session (his own shipped Secret Letter restoration: OpenSilver in the browser, Tauri for desktop). It is evidence-first, the same way D2's WPF-vs-WinUI-3 tie was resolved: build, measure, record, then decide — never argue from marketing. Unlike that spike, both candidates here are **not** like-for-like: WPF is native, OpenSilver compiles XAML+C# to **WebAssembly**, so this plan screens on **capability** (can the shell even run `sharpee build`, touch the real filesystem, host the panes) before it screens on **control parity** (editor, drawing, appearance) the way the WPF/WinUI 3 spike did. If OpenSilver wins, the reach is **all three platforms** (Windows, browser, Linux via Tauri) and eventually the macOS Swift app too — so this plan also measures against that reach, not only against WPF.
**Bounded contexts touched**: N/A — infrastructure/technology spike under `tools/spikes/opensilver-vs-wpf/` (never `packages/`), same posture as the ADR-341 D2 spike. No domain modeling; no production code path changes on any platform.
**Key domain language**: N/A — infrastructure/tooling spike. Phase names use ADR-341's own terms (D1–D8, AC-1) plus this plan's own capability/control split.

### Phase 2: KILL gate — subprocess spawn and real-filesystem capability
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: N/A — capability spike, not domain modeling.
- **Entry state**: Phase 0's Tauri shell builds and launches; Phase 1's CAPABILITY rows name what to test.
- **Deliverable**: In the trivial Tauri shell (OpenSilver content not required yet — this phase isolates the IPC/OS-integration question from the OpenSilver-specific rendering question Phase 3 covers), a Rust-side Tauri command that (a) spawns `sharpee <verb> --json` as a real child process and returns its stdout to the JS/WASM side through `invoke`, mirroring what the seven Swift subprocess sites do today; (b) reads and writes a file under `Documents\<Story Title>\` through Tauri's filesystem API, then confirms an **ordinary non-Tauri process** (a second shell, `git`, a text editor) can read what the app wrote and vice versa — the same test `msix-packaging-check.md` ran for MSIX, applied here to Tauri's fs-scope/capability model instead of MSIX's virtualization. Record whether Tauri's fs-scope allowlist (`tauri.conf.json` capabilities) supports an arbitrary, user-chosen story folder without either a blanket `fs:allow-all` (a security regression from the sandboxed default) or per-story dynamic re-scoping that would need its own plumbing.
- **Kill criterion, stated before building**: If subprocess spawn cannot reach the seven sites' pattern (return code, stdout, stderr, JSON parse) through the Tauri IPC bridge without prohibitive latency or brittle plumbing, **or** if the filesystem capability cannot be satisfied for arbitrary user-chosen folders without a security regression — record **FAIL**, stop building, and go directly to Phase 6 (Decision) with WPF recommended to stand. If both pass, continue to Phase 3.
- **Exit state**: `docs/work/opensilver-vs-wpf-spike/capability-checks.md` records both checks pass/fail with command, output, and date (same evidentiary standard as `assumption-checks.md`); the parity table's subprocess and filesystem CAPABILITY rows are filled in for OpenSilver.

### Phase 3: KILL gate — pane hosting and the IPC bridge shape
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: N/A — capability spike.
- **Entry state**: Phase 2 passed (both subprocess and filesystem checks). Phase 0's OpenSilver template builds.
- **Deliverable**: An OpenSilver app (not just a trivial Tauri shell — this phase needs OpenSilver's WASM content actually running inside the Tauri-hosted `WebView2`) that hosts the docs tab and testing surface builds (`tools/ide/web/docs-tab`, `tools/ide/web/testing-surface`) and a sample Play bundle (`dist/web/<id>/`) as **nested browsing contexts** (the shape the plan's goal names: iframes or an OpenSilver equivalent, since the panes stay unchanged web builds inside a browser app rather than native `WebView2` children per ADR-341 D3). For each pane, verify: (i) it loads and renders its own JS bundle unmodified; (ii) it can round-trip a request through the D3 host contract's shape — file/subprocess-result requests — now proxied through OpenSilver's JS interop into Tauri's `invoke` rather than a native resource-request hook (name the concrete seam: pane → `postMessage` → OpenSilver interop layer → Tauri `invoke` → Rust → OS, or record the actual shape found if different); (iii) `localStorage` persists across a shell restart — the same property the WebView2 assumption check (`assumption-checks.md`, Assumption 2) verified for the native shells.
- **Kill criterion, stated before building**: If OpenSilver cannot host a nested browsing context that loads an unmodified existing pane build — i.e., the panes would have to be reimplemented as OpenSilver-native controls rather than reused as-is — record this as a **major finding** (not necessarily an outright kill, but a real cost the WPF/WinUI 3 spikes never had to pay: D1's "designed once, lands twice" now means "designed once, lands three ways," with the third way rewriting the pane layer). If the IPC round-trip (ii) cannot be made to work at all — no pane can ever learn a subprocess result — record **FAIL** and go to Phase 6 with WPF recommended to stand. If nested hosting and the IPC round-trip both work, continue to Phase 4.
- **Exit state**: `docs/work/opensilver-vs-wpf-spike/pane-hosting-check.md` records each of the three properties per pane, with evidence, and states the concrete IPC-bridge shape found; the parity table's pane-hosting CAPABILITY row is filled in for OpenSilver.

### Phase 4: Control-parity spike — editor, custom drawing, and the appearance flip
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: N/A — technology spike, same posture as the ADR-341 D2 WPF/WinUI 3 spikes.
- **Entry state**: Phases 2 and 3 both passed (capability screen cleared). Phase 1's parity table names the AC-1 rows already flagged "possibly problematic" from the prior spike (editor, project tree, window chrome/appearance, custom drawing — the tab strip and World map).
- **Deliverable**: In the OpenSilver app built out in Phase 3, spike the three items `decision.md`'s OpenSilver caveats name as the real open questions, in this order:
  1. **The editor and D4's one-grammar rule.** Does any .NET tree-sitter binding (`TreeSitter.DotNet` or an alternative — health-check current maintenance per project convention) run under OpenSilver's WASM/Mono-AOT execution model at all, given its native `win-x64` binaries were built for a native .NET host, not WASM? If no binding survives, record whether a WASM-compiled tree-sitter (e.g. via a JS/WASM tree-sitter port callable from OpenSilver's JS interop, bypassing .NET entirely) is a viable fallback, and what that costs against D4's rule. Drive whatever editor surface OpenSilver offers (a XAML `TextBox`, or a JS-interop bridge to a web editor component) from whichever binding survives.
  2. **Custom drawing — decision.md's caveat 2, the one that matters most.** WPF won D2 on immediate-mode `OnRender`/`DrawingContext` mapping cleanly onto AppKit's `drawRect:`. Build the same representative custom-drawn surface the WPF spike built (the tab strip, or the World map) in OpenSilver and record what drawing model is actually available — Silverlight-lineage retained-mode shapes, a `Canvas`, a WASM canvas/WebGL escape hatch via interop, or something else — and whether it is closer to WPF's immediate mode or to WinUI 3's retained composition (which WPF beat on this exact ground).
  3. **The appearance flip — ADR-297 D2's "immediately" requirement.** WPF gets this free via `{DynamicResource}`. Test whether OpenSilver's theming route (its own resource-dictionary system, or a fallback to DOM/CSS custom properties via interop, since the app ultimately renders as HTML+WASM in a browser context) can apply a full palette swap without a rebuild-visuals cost, the way WinUI 3 could not.
  Record each inline in `docs/work/opensilver-vs-wpf-spike/opensilver-spike.md`, same shape as `wpf-spike.md`/`winui3-spike.md` (what was built, what failed, how it felt) so Phase 6 can compare all three columns — WPF, WinUI 3 (carried from the prior plan, not re-run), OpenSilver — side by side.
- **Exit state**: `opensilver-spike.md` records pass/partial/fail on the editor/grammar question, the drawing-model question, and the appearance-flip question, each with evidence; if budget does not cover all three, this phase's exit state names which were reached and defers the rest to a follow-on phase this plan appends, rather than silently shrinking scope (the prior plan's own escape hatch).
