### Phase 1: Step 4a resolves the floor in two passes (GH #354)
- **Tier**: Medium
- **Budget**: 180
- **Domain focus**: `packages/character` scene runtime — thread floor-turn ordering (D14) and the D10a interjection challenge, both inside step 4a
- **Entry state**: This plan reviewed and approved; David's explicit go-ahead given (rule 5). No code touched yet.
- **Deliverable**: `packages/character/src/tick-phases.ts` step 4a (currently one loop over id-sorted candidates, per-candidate challenge-then-serve) splits into two passes over the same candidate list: **pass one** runs the D10a challenge (`runtime.resolveIntrusion(foreign.id, npc.id, false)`) for every ready candidate NOT seated with the player, applying its wire events and skipping (`continue`, no throw) any candidate whose outcome is `blocks`; **pass two** re-checks `runtime.threadTurnReady(npc.id, ctx.playerId)` for every candidate that survived pass one (a candidate parked by another candidate's challenge in pass one must read as not-ready in pass two — verified against `threadTurnReady`'s built shape, `story-loader/src/loader.ts:966`, `runtime.buildThreadTurnReady`, not assumed) and serves the floor turn (`ensureScene` + `runtime.threadTurn`) for whoever still holds it. `blocking` (D14) threads keep working exactly as today — a `blocks` outcome in pass one means that candidate's challenge never ran, so the seated owner's own pass-two floor turn proceeds untouched. Behavior Statement (rule 12) produced before tests, covering: DOES (parks the outgoing partner's thread and renders its `on parting`, in pass one, before the incoming partner speaks in pass two — no partner ever serves a floor-turn beat on the same turn a later candidate's challenge parks them), WHEN (two or more candidates are ready in the same tick and at least one is not seated with the player), BECAUSE (GH #354: entity-id order must not decide who speaks on the hand-off turn), REJECTS WHEN (the surviving seated owner holds a `blocking` thread — pass one's challenge never runs against a candidate whose own thread later needs the floor is not the case here; REJECTS WHEN is about the *seated owner's* thread strength stopping other candidates' challenges from succeeding, per D10a's existing thread-aware grip — no new scoring, this phase changes ordering only, not the grip math).
- **Exit state**: Extended/new Vitest coverage on the real path — `packages/story-loader/tests/adr-320-d10-interruption.test.ts`, `packages/character/tests/conversation/interruption-d10a.test.ts`, and `packages/character/tests/tick-phases/thread-interruption.test.ts` (test file names per the goal statement; add a three-candidate fixture reproducing GH #354's exact ordering bug — a seated owner whose id sorts before a later-ready challenger — asserting the challenger's `on parting`/park and the correct floor-holder land on the hand-off turn regardless of id order) all GREEN, graded per rule 12/13 (state asserted via the scene store and thread status, never return-value-only). `pnpm --filter '@sharpee/character' test` and `pnpm --filter '@sharpee/story-loader' test` green at whatever count they land on (no full-suite re-baseline yet — that is Phase 3). ### Phase 2: Chord-spelled state pins (GH #355)
- **Tier**: Medium
- **Budget**: 160
- **Domain focus**: `packages/story-loader` entity construction (IR-id stamping) and `packages/branch-tester` tree-document evaluator (`evaluateStateExpression`) — Testing Intelligence surface, ADR-294 D13–D16
- **Entry state**: Phase 1 done and green (independent of Phase 2's code, but ordered first per the goal's suggested shape; the two could run in either order — no real dependency between them).
- **Deliverable**: Two changes, contracted before either is coded (rule 12's DOES/WHEN/BECAUSE/REJECTS WHEN for each):
  1. `packages/story-loader/src/loader.ts` stamps the IR entity id onto the world entity it creates, in `entity.attributes` (check the field name against what the loader already puts there before choosing `chordIrId` or another name — `attributes` is confirmed as the entity's open metadata bag, `packages/world-model/src/entities/if-entity.ts`; no existing IR-id attribute was found in this plan's research, so this is new). Stamped at entity-creation time (the same site around `loader.ts:1905`, `this.worldIds.set(irEntity.id, entity.id)`, so both directions of the mapping exist — the loader's internal `worldIds` map for its own use, the entity attribute for any consumer holding only the world).
  2. `packages/branch-tester/src/runner.ts` `evaluateStateExpression` gains a reserved head recognized before the existing `story.state =` and `entity.property =` regexes are tried: an (optional leading article) + name + `is` / `is not` + state word, e.g. `the first partner is waiting`, `second partner is not dancing`, `the story is ended`. Resolution: the name resolves through `findEntity`'s existing name/alias lookup (`world.findEntityByName`, etc.) — widened to accept spaces, since the current head regexes are `\w+`-only; the resolved entity's `chord.state.<ir-id>` value (read via `world.getStateValue?.(CHORD_STATE_PREFIX + entity.attributes.chordIrId)`, importing `CHORD_STATE_PREFIX` from `@sharpee/story-loader`'s `state-keys.ts` — already a dependency of `branch-tester`, confirmed) is compared against the trailing state word. `the story is <state>` is a special case reading `CHORD_STORY_STATE_KEY` directly (mirrors the existing `story.state =` head's semantics, spelled the Chord way) — decide during implementation whether it delegates to the existing `story.state =` matcher internally or duplicates the two lines; prefer delegating. Existing `story.state =` and `entity.property =`/`contains` forms are untouched syntax and untouched behavior.
- **Exit state**: New `packages/branch-tester` tests (co-located under its `tests/`) covering: a pin naming an entity's Chord state resolving true/false correctly against `chord.state.<id>`; a multi-word entity name resolving where the old `\w+` head could not; `the story is <state>` matching `CHORD_STORY_STATE_KEY`; the old `story.state =` and `entity.property =` forms still passing their existing assertions (regression, not just "still compiles"). `packages/story-loader` tests confirm the attribute is stamped on every created entity kind (room/container/person/supporter/region/door/null) without changing any existing entity-shape assertion (rule 13a's REAL-PATH TEST for the OWNED loader→runner integration: a test that builds a real story through the loader and reads the stamped attribute off the resulting world entity, not a hand-built fixture entity with the attribute pre-set). Integration Reality Statement (rule 13a) produced in-conversation before this phase is marked done: OWNED = the loader's entity construction and the runner's evaluator (both this repo controls); EXTERNAL = none; REAL-PATH TEST = the loader test above plus a `./sharpee test` run against a small fixture tree using the new pin form (not just the Vitest unit tests) before Phase 2 is called done.
