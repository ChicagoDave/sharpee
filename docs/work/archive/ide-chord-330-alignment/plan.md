**Created**: 2026-08-18

**Overall scope**: Retire the D9 "IDE is behind the installed Chord" warning honestly — extend the lexer-golden corpus to exercise the 3.1.0/3.2.0/3.3.0 conversation-grammar surface (manner, greetings, exchange, initiative, conversation/threads), confirm the Swift lexer needs no change, add the seven new keywords to the highlighter, and move the `supportedLanguageVersion` pin with a dated history entry — closing the gap between `ChordVersionCheck.swift` (pinned 3.0.0) and `CHORD_LANGUAGE_VERSION` (3.3.0, already shipped on this branch).

### Phase 4: Clear the pre-existing `authors:` header drift blocking the suite
- **Tier**: Small
- **Budget**: ~80 tool calls
- **Domain focus**: IDE test fixtures + the story-header writer (`tools/ide`). Added 2026-08-18 on David's instruction ("fix the fixtures and check the scaffold") after Phase 3 surfaced the drift; not part of the original three-phase scope.
- **Entry state**: Phase 3 green on its own goal (pin/bundle/compiler agree at 3.3.0, D9 warning retired) but the full suite is red — 9 tests failing, all on `parse.header-inline-list` / `parse.header-list-empty` from the `authors:` header form. Drift dates to `ea65f2a3`, present at the branch point.
- **Deliverable**:
  1. **Scaffold check first** (it could have changed the fix's shape): the shipped template `packages/devkit/templates/story-chord/story.story.template` already uses the correct indented list form. **The scaffold is fine — Chord Writer scaffolds compilable stories.** The earlier concern came from `StoryScaffoldTests`, which writes its *own* fake template inline in `setUp` and asserts on it; that fake had drifted from the real one. Fixture updated to mirror what ships, assertion updated with it.
  2. **Fixture sweep**: inline `authors: X` → indented list in the sources that feed the real toolchain — `TestToolchain.cleanStory` and `.hatchStory` (the shared helpers behind most failures; their "verified against the live CLI" comment had gone stale), `TestRunnerTests`, `TestingSurfaceRealPathTests`.
  3. **A real product bug, not a fixture** — `testToggledThemesReachTheHeaderAndARealBuildShipsExactlyThatSet` copies the *correct* frozen fixture and fails anyway, because toggling themes rewrites the header. `StoryHeaderThemes.edit(setting:in:)` scans for its insertion point with `StoryHeaderLines.field(in:)`, which reads a list item (no colon) as a non-field, so the scan stopped on the first author and the insert landed **between `authors:` and its authors** — emptying the list and leaving a header the compiler rejects. **Toggling a theme in Chord Writer corrupted the author's story.** Fixed by stepping the scan over a list-valued field's indented items so the insert lands after the whole list. Behavior Statement produced (rule 12); two regression tests derived from it (`testInsertingLandsAfterAListValuedFieldNotInsideIt`, `testInsertingAfterATrailingListKeepsTheListIntact`).
  4. **The bug is systemic, not the themes writer's alone.** Fixing the writer exposed the matching read-side blindness, and a grep for `StoryHeaderLines.field(in:)` found the identical scan in **8 sites across 4 modules** — `StoryHeaderThemes`, `StoryHeaderIFID`, `StoryHeaderPublishSource`, `StoryHeaderAutoAssertion`, each with one insert scan and one `locate`. All eight stop at the first line `field(in:)` returns nil for, and a list item (no colon) is exactly that. On any real story — fernhill, and every story the scaffold creates, all of which use `authors:` lists — the readers return nil for fields written after the list and the writers insert inside it. `StoryHeaderIFID.read` returning nil on a real story is how this surfaced in `testCreateWritesTheConfigSidecarAndRendersItInTheHeader` once the scaffold fixture was corrected. All 8 sites made list-aware via one documented helper, `StoryHeaderLines.isListItem(_:under:)`.
  5. One test expectation moved as a direct consequence of the fixture fix, and is called out rather than quietly retuned: `ComposeRunnerTests.testAnalyzerErrorArrivesWithFullSpan` asserted `span.line == 14`; the indented `authors:` adds a line above the error site, so it is now 15.
- **Exit state**: full `SharpeeIDETests` green, making the suite usable as a regression gate again.
- **Follow-up worth David's call**: the duplication is the reason one defect lived in four modules. The durable fix is to extract the header walk itself into `StoryHeaderLines` (one list-aware iterator the four modules share) rather than four copies of a skip loop guarded by a shared predicate. Deliberately not done here — it is a refactor of working product code, wider than the failure being cleared.
- **Status**: DONE (2026-08-18, session ade288) — full `SharpeeIDETests` **493 of 493 passing, 0 failures** (`xcodebuild test -scheme SharpeeIDE -derivedDataPath ./DerivedData`), up from 482/491 with 9 failing. Count rose by 2: the regression tests for the list-valued-field insert. The suite is a usable regression gate again.
