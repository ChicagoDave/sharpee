## Phases

### Phase 1: #295 — repaint the active tab on external reload (data-loss fix)
- **Tier**: Small
- **Budget**: ~60 tool calls
- **Domain focus**: IDE editor view/model sync (`tools/ide/SharpeeIDE/Editor/EditorViewController.swift`)
- **Entry state**: Confirmed current at HEAD — `reloadPreservingCaret` (:330) calls `switchTo(index:)` when the reloaded tab was active; `switchTo` (:554-562) early-returns via `if activeIndex == index { refreshUI(); return }`, so `loadActiveDocumentIntoTextView()` never runs; `refreshUI` (:640) never touches `textView.string`; `handleExternalChange` (:310) calls `persistTextViewToActiveDocument()` first, which is what silently undoes the reload on the next external write, save, or tab switch. `currentText(at:)` (:195) reads the model; `currentText(of:)` (:228) reads the view for the active document — the test gap the fix must close.
- **Deliverable**: `reloadPreservingCaret` puts the reloaded content on screen for the already-active tab without going through `switchTo`'s same-index short-circuit (either give `switchTo` a force-reload path, or call `loadActiveDocumentIntoTextView()` directly when `wasActive` before restoring caret/scroll). A new XCTest in `EditorExternalChangeTests.swift` that asserts on `currentText(of:)` (the view), not `currentText(at:)` (the model), for the active-tab external-reload case — this is the named test gap, and it must fail against the old code and pass against the fix.
- **Exit state**: `xcodebuild test -project tools/ide/SharpeeIDE.xcodeproj -scheme SharpeeIDE -derivedDataPath ./DerivedData` (or the equivalent existing test invocation) is green including the new view-asserting test; the existing `testCleanBufferReloadsSilentlyOnExternalWrite` (model-asserting) still passes unchanged.
- **Status**: DONE (2026-08-22, session 95a8f5) — `reloadPreservingCaret` loads the active tab directly (`EditorViewController.swift:336`); new view-asserting test failed on old code at lines 101/108 and passes on the fix. The fix exposed a pre-existing 50 ms watcher re-arm drop-window (`testWatcherSurvivesAtomicReplaceChains` timed out); resolved by re-arming synchronously before handling (`startWatching`). Full IDE suite: 562 tests passing, 0 failures (15:53 CDT).

### Phase 3: #290 — fix the frame/container guard mismatch behind the gutter-overlap bug
- **Tier**: Small
- **Budget**: ~50 tool calls
- **Domain focus**: IDE editor layout geometry (`tools/ide/SharpeeIDE/Editor/EditorViewController.swift`)
- **Entry state**: Confirmed current at HEAD — `syncWrapWidth` (:898-916) guards on the **container** width (`force || abs(container.containerSize.width - wrapWidth) > 0.5`) but the body also sets the **frame** width via `textView.setFrameSize`. `loadActiveDocumentIntoTextView` (:696) calls `applyWordWrap()` → `syncWrapWidth(force: true)` pre-layout on document load (via `viewDidLayout` at :141 calling the unforced form afterward). Per the issue, this is a hypothesis read from source, not yet confirmed under the debugger — intermittent symptom.
- **Deliverable**: Confirm the mechanism under the debugger (or with a deterministic repro harness) before changing the guard. Fix: make the guard also cover the frame width (so a stale frame with a matching container still re-syncs), or stop deriving `rulerAlreadyExcluded` from a pre-layout `scrollView.contentSize` measurement. A new XCTest exercising `loadActiveDocumentIntoTextView` → simulated `viewDidLayout` sequence that asserts `textView.frame.width` matches the expected post-layout value (not just the container), reproducing the reopen ordering.
- **Exit state**: New XCTest fails against old code, passes against the fix; existing wrap/layout tests in `SharpeeIDETests` remain green under `xcodebuild test -derivedDataPath ./DerivedData` (Manual-signed target).
- **Status**: DONE (2026-08-22, session 95a8f5) — mechanism confirmed with a deterministic harness rather than the debugger: pre-layout `clipWidth` counts the ruler and post-layout excludes it, so `wrapWidth` is identical both times and the container-only guard never fires while the frame stays 46pt too wide (test showed 669 vs 623). Fix: `syncWrapWidth` guards on frame width as well as container width (`EditorViewController.swift:918-925`). New `EditorWrapWidthTests.swift` (registered in project.pbxproj) fails on old code, passes on fix. Full IDE suite: 563 tests passing, 0 failures (16:09 CDT).
