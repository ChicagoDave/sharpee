## Phases

### Phase 1: `IChannelRegistry.add` position parameter + `story.chapter` registers before the prose flush
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: Channel registry contract (`if-domain`) and its `stdlib` implementation, plus the one call site that registers the chapters extension's channel (`packages/story-loader`'s `extension-registry.ts` → `packages/extensions/chapters/src/chapter-channel.ts`). No platform-browser renderer change — the renderer already appends the chapter card directly to `layout.main`; only the dispatch order that decides when `onValue('story.chapter', …)` fires relative to the prose buffer's flush changes.
- **Entry state**: Current behavior confirmed by reading the source (this session): `StdlibChannelRegistry.add` is a plain `Map.set`, so a new id is appended at the end of insertion order; `registerChaptersChannels` is called from `Story.registerChannels?.(channelRegistry)` in `packages/engine/src/game-engine.ts` *after* `STANDARD_CHANNELS` (which ends with `preferredLayoutChannel`) is already populated, so `story.chapter` lands after `preferred-layout` in `registry.all()` order; both `ChannelService.buildManifest()` and its per-turn dispatch loop (`packages/channel-service/src/channel-service.ts:103,133`) walk `registry.all()` in that order, and `platform-browser`'s prose renderer (`packages/platform-browser/src/channels/prose.ts`) buffers prose entries and flushes them on `preferred-layout`'s `onValue` — so today the chapter card's direct append to `layout.main` happens strictly after the flush, i.e. after the room.
- **Deliverable**:
  1. `IChannelRegistry.add(channel: IOChannel, position?: { before: string }): void` in `packages/if-domain/src/channels/types.ts`. Doc comment states: last-write-wins on id is unchanged; `position` only affects where a *new* id lands; re-adding an existing id with a `position` still replaces in place (position is not consulted on an update — same last-write-wins contract, documented explicitly so the two rules don't read as contradictory).
  2. `StdlibChannelRegistry.add` in `packages/stdlib/src/channels/registry.ts` honors `position`: when given, rebuild the internal `Map` so the channel is inserted immediately before the named id, preserving the relative order of every other entry. An unknown `before` id throws (loud on a typo, per the agreed design) with a message naming both the missing id and the channel attempting to register before it.
  3. `registerChaptersChannels` in `packages/extensions/chapters/src/chapter-channel.ts` calls `registry.add(chapterChannel, { before: 'room-name' })` (`'room-name'` is `PROSE_CHANNEL_IDS.ROOM_NAME` / `PROSE_CHANNELS[0].id` — import the constant, don't hand-string it).
- **Exit state**: `story.chapter` sits in `registry.all()` order immediately after `banner` and before `room-name` (and therefore before every prose channel and `preferred-layout`). No change to `packages/platform-browser`. `pnpm --filter '@sharpee/if-domain' test` and `pnpm --filter '@sharpee/stdlib' test` green, including the new registry-position tests (before an existing id; unknown-id throws; re-adding an existing id preserves its original position and does not require `position` to be re-specified).
- **Status**: DONE (2026-09-05 ~23:58 CDT). Evidence: `pnpm --filter '@sharpee/stdlib' test tests/channels/registry.test.ts tests/channels/standard.test.ts` → 68 passing (registry 14, four new: before-an-existing-id order, unknown id throws naming both ids and registers nothing, re-add keeps position, canonical STANDARD_CHANNELS + story.chapter = banner+1 = room-name-1); `pnpm --filter '@sharpee/ext-chapters' test` → 8 passing; `pnpm --filter '@sharpee/if-domain' test` green; if-domain dist rebuilt; stdlib and ext-chapters `tsc --noEmit` exit 0.
