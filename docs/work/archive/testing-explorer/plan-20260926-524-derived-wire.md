**Overall scope**: `packages/devkit/src/commands/test-derived.ts` runs ADR-356's derived rule-test suite by default under `sharpee test` and, under `--json`, writes D5's coverage report (branches exercised/declared, endings reached/declared, rooms entered/declared, and the gap list by span) to **stderr** — the run-event wire (`packages/ide-protocol/src/run-events.ts`) has no event type for a derived branch outcome. The IDE's Testing tab (`tools/ide/web/testing-surface`) therefore sees only the process exit code plus stderr text; it cannot render a derived branch as it runs, distinguish a SKIPPED branch from a failure, or show the three ratios anywhere but a raw text dump. This plan gives the derived tier the same live, structured wire the tree tier already has (the run-event spine, `docs/work/ide-testing-wire/plan-20260806-run-event-spine.md`), renders it in the Testing tab, and verifies both native heads still relay the stream unaffected. **No implementation is authorized by this plan** — every phase reaches `packages/` (ide-protocol, transcript-tester, branch-tester, devkit) or is gated the same way by rule 8b, and CLAUDE.md requires David's discussion and go-ahead before Phase 1 starts and before each later phase resumes.
**Bounded contexts touched**: `@sharpee/ide-protocol` (the wire vocabulary), `@sharpee/transcript-tester` (`RunEventStream`, the one place that writes the wire), `@sharpee/branch-tester` (the derived runner's existing per-branch observer hook, the coverage module), `@sharpee/devkit` (`test-derived.ts`/`test-tree-document.ts`, the command surface), `tools/ide/web/testing-surface` (the Testing tab's run column). Native shells (`tools/ide/SharpeeIDE`, `tools/ide/PaneHost`) are consumers verified in Phase 3, not modified — see the correction below.
**Key domain language**: derived branch, exercised/SKIPPED/failed/errored (D2/D5), SKIPPED-by-shape (a named arrange-floor limit, never a failure — D5a), the three ratios (branches, endings, rooms), gap (an unexercised branch, an unreached ending, an unentered room — named by span, not a percentage), END STATE card (D4), one-shot repair vs. shim.

**Correction to this plan's own task framing, found during reference consultation, stated here rather than silently applied**: the task that produced this plan named "generated Swift/C# protocol" as part of Phase 1's likely scope. That is not what the Affected list or the shipped code do. ADR-352's Consequences say outright that the run-event stream "deliberately has no native target" — the Testing tab is a TypeScript surface that imports `@sharpee/ide-protocol` directly, and `TestRunner.swift`'s own header states "It does NOT decode: the tab owns the wire… a Swift decoder in front of it could only be a second opinion that drifts." Reading `tools/ide/PaneHost/Shell/ShellWindow.axaml.cs:1153-1159` shows the Avalonia head does the identical thing: it serializes each raw NDJSON line and calls `window.__sharpeeTestingSurface.runLine(l)` in the webview — no C# decode either. **New wire variants therefore need no `repokit protocol` regeneration and no native decoder change in either head.** Phase 1 below is TypeScript-only; Phase 3 verifies the two native relays still pass the new lines through unexamined, which is what "no native target" predicts rather than something this plan has to build.

## Phases

### Phase 1: The wire vocabulary and its emitter
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: `@sharpee/ide-protocol` (two new `RunEvent` variants), `@sharpee/transcript-tester` (two new `RunEventStream` methods — the wire's one writer), `@sharpee/branch-tester` (no new instrumentation — the existing `onOutcome` hook is the seam), `@sharpee/devkit` (`test-derived.ts`/`test-tree-document.ts` wiring). No native package touched (see the correction above).
- **Entry state**: `run-events.ts` at `RUN_EVENT_SCHEMA_VERSION = 2`, seven variants, no derived-branch shape. `runDerivedSuite` already calls `options.onOutcome?.(outcome)` per branch; `runDerivedTests` computes `branchCoverageOf`/`endingCoverageOf`/`roomCoverageOf` and prints them via `console.error` under `--json`, never through the stream. `runTreeDocumentCommand` already holds a live `RunEventStream` instance (`stream`) in scope at the point it calls `runDerivedTests`.
- **Deliverable**:
  1. Two new `RunEvent` variants in `packages/ide-protocol/src/run-events.ts`, each with its own guard function per the file's existing pattern, added to the `RunEvent` union and `isRunEvent`. Names deliberately avoid "coverage" as a type-name segment (only ADR-293's `CoverageEvent` owns that word on this wire): something in the register of `DerivedBranchEvent` (`type: 'derived-branch'`) and `DerivedRunSummaryEvent` (`type: 'derived-summary'`) — the exact spelling is this phase's call, not an open question, since it is a naming convention with no content stakes.
     - `DerivedBranchEvent`: one per branch, emitted as `onOutcome` fires — `label`, `span` (nullable, per `Span | null`'s existing type), `status: 'passed' | 'failed' | 'skipped' | 'error'` (four distinct values, never a boolean — this is the field that keeps D5a's rule literal on the wire: a consumer must not be able to construct "SKIPPED counts as failed" from this shape), `shape?` (the named arrange-floor limit, present only when `status === 'skipped'`), `detail?`, and `claim?` (the first failing claim's rendered message, present only when `status === 'failed'`, mirroring `firstFailureOf` in `coverage.ts` — this is what closes GH #522's complaint that a failure needs its claim, not just a boolean, to be actionable from the wire alone).
     - `DerivedRunSummaryEvent`: one per run, emitted once after the derived suite and the tree's ending/room contributions are both known — the three ratios (`branches: {declared, exercised, passed, failed}`, `endings: {declared, reached}`, `rooms: {declared, entered}`) plus three gap lists (unexercised branches by span, unreached named endings by span, unentered rooms by id, and unnamed endings listed apart per `EndingCoverage.unnamed` — never folded into the ratio, matching `coverage.ts`'s own distinction). Each gap list entry carries enough to render `formatDerivedRun`/`formatCoverageSummary`'s existing text without re-deriving it — this event is `coverage.ts`'s output shape carried onto the wire, not a redesign of it.
  2. Two new methods on `packages/transcript-tester/src/run-event-stream.ts`'s `RunEventStream` class (`derivedBranch(...)`, `derivedSummary(...)`), following the file's own `envelope()`/one-method-per-event-kind idiom exactly as `coverage(report)` does today.
  3. `packages/devkit/src/commands/test-derived.ts`'s `DerivedTestOptions` gains an optional `stream?: RunEventStream` (or the narrower callback shape the implementation prefers, decided against the existing `tree` option's own shape for consistency); `runDerivedTests` passes an `onOutcome` into `runDerivedSuite` that calls `stream.derivedBranch(...)` per branch as it completes (live, not batched — the seam already fires per branch, so this is wiring, not new concurrency), and calls `stream.derivedSummary(...)` once after `formatCoverageSummary`'s inputs are computed. **Under `--json`, the human-readable report continues to print to stderr as today** — this is additive, not a replacement: `--json` consumers that only read stdout gain a structured stream; a consumer reading stderr (a human watching a CI-less local run) loses nothing.
  4. `packages/devkit/src/commands/test-tree-document.ts` passes its existing `stream` into the `runDerivedTests` call at the point it already sits (after the tree run, before `stream?.runEnd(...)`) — no reordering of any other event on the wire.
  5. Behavior Statement (rule 12) for the new stream-writing code before its tests are written; tests derived from it and graded per rule 13.

## Open decisions for David

- **Where the derived rows and the three ratios sit in the Testing tab.** Phase 2's deliverable names two shapes (a new panel vs. folded into the existing per-line list) and defers the choice. The tree's per-line rows are keyed by derived label (a tree concept); a derived branch is keyed by clause/span (an IR concept) — they are two different identities on the same document, and which one the author sees first when they hit "Run" is a UX call, not a technical one.
- **Whether SKIPPED branches show by default or behind a toggle.** On secret-letter 363 of 721 branches are SKIPPED by shape (the first-cut measurement) — showing all of them inline by default could dominate the tab for a story at the arrange floor's edge, while hiding them by default risks re-creating the "authors ignore what they can't see" failure mode D5a was written to avoid for the derived tier as a whole (ADR-356 D5a's own rejected alternatives: "report only" was rejected for exactly this reason at the CLI level).
- **Re-blessing a failed prose card** (added 2026-09-26, session e9f1df, from the author narrative `narrative-20260926-author-testing.md`). The default policy pins room name and description on every move, so one rewritten room description fails every card that enters that room, and the surface has no bless/accept gesture (grep for `bless` in `tools/ide/web/testing-surface/src` finds nothing): today the author deletes each claim and re-adds it, or tail-cuts and replays. This is the prose half of the 93%-rewrite problem ADR-356 left with the tree. Not in this plan's scope — the run column would need to offer "accept this card's new prose" per failed card and in bulk per line — but it is the first thing an author hits after the derived tier works, so it is named here for the plan that follows.
- **Related issues filed from the same narrative** (2026-09-26): #529 (room entry/leave clauses SKIPPED as command-lifecycle though a direction is a typed command — an enumerator command-synthesis gap, not in #525's ranking), #530 (a derived failure caused by a platform defect, here #242, fails the author's build with no acknowledgement path — a D5a decision for David), #531 (ADR-321 D6a contradicted by its own D22 with no note). None changes this plan's phases; #530 may change what Phase 2 renders beside a failed row if David decides an acknowledgement exists.
- **Event granularity for a long derived run.** The derived suite runs sequentially and can be large (721 branches on secret-letter) — Phase 1 emits one `derived-branch` event per branch, matching the existing per-command granularity elsewhere on this wire, but if that proves too chatty for a very large story, `ProgressEvent`'s existing `scope: 'nodes' | 'states'` shape is available to add `'branches'` as a coarser default with per-branch detail behind `--verbose`-equivalent, the way `command-result`'s `actualOutput` is failures-only by default. Not designed in this plan; named here so a future session doesn't have to rediscover the tension.
