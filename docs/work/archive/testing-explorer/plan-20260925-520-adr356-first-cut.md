- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: `@sharpee/story-loader` — a new public function beside the loader's existing exports (`packages/story-loader/src/index.ts`) that performs the floor-only arrange grammar as writes against a live world, never a play-to-precondition.

- **Deliverable**: `arrange(world: WorldModel, expression: string): { arranged: true } | { arranged: false; shape: string }` in a new `packages/story-loader/src/arrange.ts`, exported from `index.ts`. Handles exactly the Q-2 floor forms, each mapped to one loader write, never more: `story.state = <phase>` → `world.setStateValue(CHORD_STORY_STATE_KEY, phase)`; `<entity>.location = <place>` → `world.moveEntity(entityId, placeId)` (resolving both names to world ids the same way the loader's own placement pass does); `<entity>.inventory contains <item>` → `world.moveEntity(itemId, entityId)` (holding is arranging containment, per the ADR's own gloss: "`player.inventory contains garden shears` is how holding is arranged"); `[the] <name> is <state>` → `world.setStateValue(CHORD_STATE_PREFIX + irId, state)` (entity declared state, resolved through `CHORD_IR_ID_ATTRIBUTE` the same way `evaluateChordStateClaim` reads it); `<entity>.<property> = <value>` for the `openable`/`lockable`/`switchable` trait flags → a trait-property write (`entity.get(TraitType.OPENABLE).isOpen = ...` and the lockable/switchable equivalents) reusing whatever trait accessors the loader already has (`packages/story-loader/src/loader.ts:1717,1906-1965` shows where these traits are constructed at load time; the arrange write goes through the same trait instances at runtime, not through re-construction). Occurrence ordinals, topic history, timer phases and timer-driven positions are the four SKIPPED shapes (Q-2's list) — `arrange` recognizes their expression shapes (they are not in scope to write, but they must be *named*, not fall through to "cannot parse") and returns `{ arranged: false, shape: '<one of four fixed names>' }`; any other unparseable expression is also `{ arranged: false, shape: 'unrecognized' }`, never a throw. **One grammar, one parser, two directions** (amendment, David, 2026-09-25, "add amendment"). The ADR says the arrange grammar is "the `states:` pin grammar the assertion core already evaluates"; this plan reads that as pinning the *code* as well as the forms, because a second hand-written parser of the same grammar is exactly the pattern open recurrence issue #425 names (hand-duplicated facts instead of one canonical source). That edge runs the permitted way — test tooling depending on the runtime, the direction `bootstrap` already takes (`packages/bootstrap/package.json:33`) and `branch-tester` already takes (`packages/branch-tester/package.json:23`) — and the reverse edge, story-loader importing transcript-tester, stays absent because it would be a cycle (transcript-tester → bootstrap → story-loader). The assertion core keeps every claim it has today (the plain `entity.property` and `contains`/`not-contains` forms included); only the recognition of the pin forms moves, the evaluation stays where ADR-340 D1 put it. A behavior test in transcript-tester pins that `evaluateStateExpression` still answers every form it answered before the move (the existing `state-pins` and story-state/chord-state claim suites in `packages/branch-tester/tests/` are the regression net, run unchanged). AC-5's grep-shaped test (`no file outside packages/story-loader/src writes chord.state./chord.story.state/chord.occurrence./chord.gone.`) is added here, as a real assertion over the repo, not a promise in a header comment.

### Phase 3: The derived rule-test runner (D3) — new assertion-core claim kinds + `branch-tester`'s second entry
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: `@sharpee/transcript-tester` (two new claim kinds) and `@sharpee/branch-tester` (a new runner entry beside `tree-walker.ts` that arranges, runs one real command, and asserts via the assertion core) — the only phase where a derived test actually executes against the real parser and engine.
- **Entry state**: Phase 1's `collectClauseBranches` and Phase 2's `arrange` and `parsePin` all exported and building clean, with `evaluateStateExpression` already consuming `parsePin` (Phase 2 amendment) so the new claim kinds here extend one grammar, not two.
- **Deliverable**: Two new claim kinds land in `packages/transcript-tester/src/assertion-core.ts` (D3, ADR-340 D3 — imported by branch-tester, never copied): `is gone` (reads the `CHORD_GONE_PREFIX` flag through `world.getStateValue`, the same way `evaluateChordStateClaim` reads declared state) and `emitted <message-id>` (reads the turn's captured events/phrase-fired records — the exact read surface `checkEventAssertion` already has for `event-assert`, extended to recognize a phrase/refuse/emit message id rather than a raw event type). A new `packages/branch-tester/src/derived-runner.ts` (name open at implementation) exports a function that, per `ClauseBranch` record: boots a fresh world at the pinned seed (reusing whatever `loadAuthorGame`/`TreeGameLoader` boot path `tree-walker.ts` already uses — no second boot mechanism); calls `arrange` once per precondition term (a branch's precondition may name several floor facts, e.g. the worked example's "player in the vine's room; holds shears; vine flowering" — three `arrange` calls); on any `{ arranged: false }` result, short-circuits to a SKIPPED outcome carrying the shape, without running the command (this branch counts in D5's denominator, per D2's "counts against D5's coverage," but is not a pass/fail); runs the branch's `command` through the real parser/engine exactly once (ADR-293 D12, real path only — AC-7: a command the parser cannot resolve is reported as a parse failure, not swallowed); asserts every mapped claim from D3's effect-catalog table (`change`→`<entity> is <state>`, `move`→`<entity>.location = <place>`, `remove`→`is gone`, `change-player`→`player.location = <place>`, `win`/`lose`/`kill`→the ending fired with that id, `phrase`/`refuse`/`emit`→`emitted <message-id>`, `award`/`raise`/`lower`→the score/counter decision below); for a `refuse-when`/`must` branch, additionally asserts the refusal message **and** the negative space — every effect statement inside the guarded body did not fire (AC-3: a planted defect that fires the refusal and then runs the body anyway must fail on the state assertion, not the message alone). **Score/counter decision, made in this plan** (D3 explicitly leaves it open): score and counter deltas stay **runner-side reads**, not new assertion-core claim kinds.
