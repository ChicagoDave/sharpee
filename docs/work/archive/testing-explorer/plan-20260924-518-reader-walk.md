## Open questions for David

1. **Reader row shape — owner as object or string?** `collectStateWriters` returns `owner: WriterOwner` (a tagged object: `{kind:'entity',id}` / `{kind:'machine',name,roles}` / `{kind:'story'}`). The lens's local `collectStateReads` returns `owner` as a flat string (`'entity:'+id`, etc.) — already the shape the writer rows get flattened *to* by the lens's own `ownerLabel()` before reporting. Moving the walk into world-index means choosing one: **(a)** match `collectStateWriters` and return `WriterOwner` objects (consistent with the existing derivation's contract; ADR-322 D8's "consume, don't rebuild" argues for one shape across both), or **(b)** keep the flat string the lens already uses (less churn at the call site). **Recommendation: (a)**, reusing `WriterOwner` unchanged (no new type) as both rows' owner field — it is already a general "what must be reachable" tag, not writer-specific. This means the lens's `byTargetAndValue`/`ownerLabel` path (which already normalizes both shapes) needs no change, but the **fixture-level fragment tests** in `lens-declared-state.test.js` (lines 76-84, asserting raw tuples like `['lamp','dim','entity:lamp','is']`) need their `owner` assertions rewritten from strings to `{kind:'entity',id:'lamp'}` objects. The fixture/corpus report-JSON pins (layers 2-3) are unaffected either way, since `ownerLabel()` already flattens before those assertions run — those stay byte-for-byte regardless of which option is chosen.
2. **Field name for the read-form discriminator.** The lens's local rows carry `via: 'is' | 'select-on' | 'story-state'`. **Recommendation: keep `via` unchanged** — no functional reason to rename it to something like `form`, and keeping the name avoids churning every test line that reads `r.via`.
3. **One shared traversal pass, or two independent calls over `forEachStatementRoot`?** `collectStateWriters` and the proposed `collectStateReaders` would each call `forEachStatementRoot(ir, ...)` separately (matching the file's existing independent-walk convention — `collectStateWriters` and `entitiesMovedIntoPlay` already do this), meaning every statement-bearing root's subtree is walked twice when both derivations run in the same pass (as the lens's `classify()` does). A combined single-pass visitor (one walk collecting both writes and reads) would halve node visits but couples the two collectors' internals together and complicates testing each in isolation. **Recommendation: two independent calls**, matching the file's existing pattern; these are small per-story IRs (the largest corpus story — secret-letter — has 41 dimensions) already comfortably inside ADR-321 D6's performance budget, so the 2x node-visit cost is not worth the coupling. Flag for revisit only if a future corpus story makes this measurably slow.
4. **Should `conditions.ts` or `dimensions.js` consume `collectStateReaders` now?** The issue's own "Acceptance if built" bullet names only the lens's `collectStateReads` deletion. **Recommendation: out of scope for this plan.** `conditions.ts` evaluates gate truth and has no current need to enumerate reads; `dimensions.js`'s `harvest` is a different, narrower walk serving a different purpose (vocabulary reference tracking, not this issue's concern). Wiring a second consumer is future work the issue names only as *why this belongs in world-index*, not as this issue's own deliverable.
5. **Test derivation (rule 12/13) and stash-toggle proof.** Settled, not open: follow the #517 convention exactly — a Behavior Statement for `collectStateReaders` before writing tests; one `compileSource`-based test per read form (`is` predicate, `select-on` with one arm per value, `story-state`) plus the trait-per-composer expansion case and at least one regression case (entity's own `states` list contributes no phantom reader); every new test verified to fail against the pre-change `statements.ts` via the same `git stash push -- packages/world-index/src/statements.ts` toggle #517 used, and to pass after.
