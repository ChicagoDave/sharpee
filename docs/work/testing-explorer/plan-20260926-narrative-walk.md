# Session Plan: a CLI-spawning test suite that walks the author-perspective narrative

**Created**: 2026-09-26
**Plan Status**: DONE (all four phases DONE, 2026-09-26, session e9f1df; the plan directory stays in place — archiving is a human decision)
**Overall scope**: `docs/work/testing-explorer/narrative-20260926-author-testing.md` tells one author's afternoon writing and testing `branch-stories/fernhill` — the World tab's Incomplete list, the Testing tab's default-policy claims, the derived rule tier testing itself, playing through and forking, endings, the coverage ratios, an unexpected failure, and the exit-code rule. ## Runtime and Spawn Budget

The task's framing ("fernhill's full test run takes on the order of a minute") does not match the measured wall-clock (0.537s for a full `sharpee test branch-stories/fernhill --json` run, cold, no warm cache). This may describe a different story (secret-letter, 721 branches vs. fernhill's 63) or a cold-start `pnpm`/registration path this measurement didn't hit. Recorded here rather than silently designed around: **this suite's own runtime is small under either number**, but the plan is written to control spawn count regardless, since spawn count (not wall-clock per spawn) is what the task's "cache one `--json` run per file" instruction is really about.

**Design rule for every phase below**: each `*.test.ts` file spawns the CLI **at most twice** — once in a `beforeAll` for its primary run (cached in module scope, asserted against by every `it()` in the file), and a second spawn only when the beat itself requires two runs to compare (determinism, or a before/after-mutation diff). No test re-spawns the CLI per assertion. Counting every phase: Phase 1 makes 5 spawns (one `build` + one `world-index` for beat 1; one `--json` run each for beats 2, 6, 7 — beats 2/6/7 share ONE cached run per the note below, so really 1 `test --json` spawn shared across three files via a small shared fixture module, not three separate spawns); Phase 2 makes 4 (one baseline `test --json`, one on the locket-deleted scratch copy, one SKIPPED-only fixture run, one for AC-style exit-code confirmation); Phase 3 makes 4 (one baseline for the transcript/fork beat, one repeat run for the determinism diff, one baseline for the endings beat, one on the ending-card-removed scratch copy). Total across the suite: **13 CLI spawns**, each well under a second by the measurement above — the whole suite's own added CI-less local runtime is on the order of several seconds, not minutes.

**Shared fixture module** (`scripts/__tests__/support/fernhill-run.ts`, new, Phase 1): a single exported `runFernhillTest(): CliResult` that spawns `sharpee test branch-stories/fernhill --json` once per `vitest` process (module-level memoized `beforeAll`-safe cache — vitest runs each test FILE in its own worker/module scope by default, so "once per file" is the real unit; the memoization exists so Phase 1's three files that each need the same baseline run do not each pay their own spawn if collocated, and so a later phase reusing the same baseline doesn't need to know the caching detail). Parses the NDJSON stdout into typed events using `@sharpee/ide-protocol`'s own `isRunEvent`/`isDerivedBranchEvent`/`isDerivedRunSummaryEvent` guards — never a hand-rolled parse of the wire.
