### Phase 2: `arrange(world, expression)` (D2, Q-1) in `@sharpee/story-loader`
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: `@sharpee/story-loader` — a new public function beside the loader's existing exports (`packages/story-loader/src/index.ts`) that performs the floor-only arrange grammar as writes against a live world, never a play-to-precondition.
- **Entry state**: Phase 1 done (not a hard dependency — Phase 2 can run independently, since `arrange` does not consume enumerator output directly; sequenced second only because Phase 3's runner needs both). `packages/story-loader/src/state-keys.ts` and `loader.ts`'s `world.setStateValue`/`author.moveEntity` calls (`packages/story-loader/src/loader.ts:616,645` for entity/story state; `:489,498,502` for placement/holdings) are the write primitives `arrange` wraps.
- **Deliverable**: `arrange(world: WorldModel, expression: string): { arranged: true } | { arranged: false; shape: string }` in a new `packages/story-loader/src/arrange.ts`, exported from `index.ts`. Handles exactly the Q-2 floor forms, each mapped to one loader write, never more: `story.state = <phase>` → `world.setStateValue(CHORD_STORY_STATE_KEY, phase)`; `<entity>.location = <place>` → `world.moveEntity(entityId, placeId)` (resolving both names to world ids the same way the loader's own placement pass does); `<entity>.inventory contains <item>` → `world.moveEntity(itemId, entityId)` (holding is arranging containment, per the ADR's own gloss: "`player.inventory contains garden shears` is how holding is arranged"); `[the] <name> is <state>` → `world.setStateValue(CHORD_STATE_PREFIX + irId, state)` (entity declared state, resolved through `CHORD_IR_ID_ATTRIBUTE` the same way `evaluateChordStateClaim` reads it); `<entity>.<property> = <value>` for the `openable`/`lockable`/`switchable` trait flags → a trait-property write (`entity.get(TraitType.OPENABLE).isOpen = ...` and the lockable/switchable equivalents) reusing whatever trait accessors the loader already has (`packages/story-loader/src/loader.ts:1717,1906-1965` shows where these traits are constructed at load time; the arrange write goes through the same trait instances at runtime, not through re-construction). Occurrence ordinals, topic history, timer phases and timer-driven positions are the four SKIPPED shapes (Q-2's list) — `arrange` recognizes their expression shapes (they are not in scope to write, but they must be *named*, not fall through to "cannot parse") and returns `{ arranged: false, shape: '<one of four fixed names>' }`; any other unparseable expression is also `{ arranged: false, shape: 'unrecognized' }`, never a throw. **One grammar, one parser, two directions** (amendment, David, 2026-09-25, "add amendment"). The ADR says the arrange grammar is "the `states:` pin grammar the assertion core already evaluates"; this plan reads that as pinning the *code* as well as the forms, because a second hand-written parser of the same grammar is exactly the pattern open recurrence issue #425 names (hand-duplicated facts instead of one canonical source). The parse step is split from the evaluate step: a new `packages/story-loader/src/pin-grammar.ts` exports `parsePin(expression: string): ParsedPin | { unrecognized: true }`, a pure function from an expression to a structured form (`{ kind: 'story-state' | 'location' | 'contains' | 'declared-state' | 'property', ... }` plus the four named non-floor shapes), exported from `index.ts`. `arrange()` consumes `ParsedPin` in the write direction. `evaluateStateExpression` in `packages/transcript-tester/src/assertion-core.ts:317` consumes the same `ParsedPin` in the read direction, replacing its inline regexes for those forms; `packages/transcript-tester/package.json` gains `@sharpee/story-loader` as a dependency. That edge runs the permitted way — test tooling depending on the runtime, the direction `bootstrap` already takes (`packages/bootstrap/package.json:33`) and `branch-tester` already takes (`packages/branch-tester/package.json:23`) — and the reverse edge, story-loader importing transcript-tester, stays absent because it would be a cycle (transcript-tester → bootstrap → story-loader). The assertion core keeps every claim it has today (the plain `entity.property` and `contains`/`not-contains` forms included); only the recognition of the pin forms moves, the evaluation stays where ADR-340 D1 put it. A behavior test in transcript-tester pins that `evaluateStateExpression` still answers every form it answered before the move (the existing `state-pins` and story-state/chord-state claim suites in `packages/branch-tester/tests/` are the regression net, run unchanged). AC-5's grep-shaped test (`no file outside packages/story-loader/src writes chord.state./chord.story.state/chord.occurrence./chord.gone.`) is added here, as a real assertion over the repo, not a promise in a header comment.
- **Exit state**: `packages/story-loader` suite green including new `arrange` tests: one per floor form (five), one per SKIPPED shape (four, each asserting the named shape string), one for an expression naming an entity the story does not declare (asserted as `{ arranged: false, shape: 'unrecognized' }` per D2's own text — "An expression that names an entity the story does not declare is a failure of the derived test, not a SKIP" is Phase 3's runner-level distinction, not `arrange`'s; `arrange` itself has no notion of "the enumerator produced this," so this plan states here that `arrange` reports `unrecognized` uniformly and Phase 3's runner is what turns an *enumerator-sourced* unrecognized result into a failure rather than a SKIPPED result — AC-4's SKIPPED status is therefore assigned by the runner, not by `arrange`). AC-5's grep test passing. `parsePin` has one test per form it recognizes (five floor, four named non-floor, one unrecognized) asserting the structured result, and `evaluateStateExpression`'s existing suites pass unchanged after it consumes `parsePin`. `tsc --noEmit` clean across story-loader, transcript-tester and branch-tester; `dist`/`dist-esm` rebuilt for all three (branch-tester and `./sharpee` read `dist/`).
- **Status**: CURRENT (since 2026-09-25, Phase 1 DONE)

### Phase 3: The derived rule-test runner (D3) — new assertion-core claim kinds + `branch-tester`'s second entry
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: `@sharpee/transcript-tester` (two new claim kinds) and `@sharpee/branch-tester` (a new runner entry beside `tree-walker.ts` that arranges, runs one real command, and asserts via the assertion core) — the only phase where a derived test actually executes against the real parser and engine.
- **Entry state**: Phase 1's `collectClauseBranches` and Phase 2's `arrange` and `parsePin` all exported and building clean, with `evaluateStateExpression` already consuming `parsePin` (Phase 2 amendment) so the new claim kinds here extend one grammar, not two.
- **Deliverable**: Two new claim kinds land in `packages/transcript-tester/src/assertion-core.ts` (D3, ADR-340 D3 — imported by branch-tester, never copied): `is gone` (reads the `CHORD_GONE_PREFIX` flag through `world.getStateValue`, the same way `evaluateChordStateClaim` reads declared state) and `emitted <message-id>` (reads the turn's captured events/phrase-fired records — the exact read surface `checkEventAssertion` already has for `event-assert`, extended to recognize a phrase/refuse/emit message id rather than a raw event type). A new `packages/branch-tester/src/derived-runner.ts` (name open at implementation) exports a function that, per `ClauseBranch` record: boots a fresh world at the pinned seed (reusing whatever `loadAuthorGame`/`TreeGameLoader` boot path `tree-walker.ts` already uses — no second boot mechanism); calls `arrange` once per precondition term (a branch's precondition may name several floor facts, e.g. the worked example's "player in the vine's room; holds shears; vine flowering" — three `arrange` calls); on any `{ arranged: false }` result, short-circuits to a SKIPPED outcome carrying the shape, without running the command (this branch counts in D5's denominator, per D2's "counts against D5's coverage," but is not a pass/fail); runs the branch's `command` through the real parser/engine exactly once (ADR-293 D12, real path only — AC-7: a command the parser cannot resolve is reported as a parse failure, not swallowed); asserts every mapped claim from D3's effect-catalog table (`change`→`<entity> is <state>`, `move`→`<entity>.location = <place>`, `remove`→`is gone`, `change-player`→`player.location = <place>`, `win`/`lose`/`kill`→the ending fired with that id, `phrase`/`refuse`/`emit`→`emitted <message-id>`, `award`/`raise`/`lower`→the score/counter decision below); for a `refuse-when`/`must` branch, additionally asserts the refusal message **and** the negative space — every effect statement inside the guarded body did not fire (AC-3: a planted defect that fires the refusal and then runs the body anyway must fail on the state assertion, not the message alone). **Score/counter decision, made in this plan** (D3 explicitly leaves it open): score and counter deltas stay **runner-side reads**, not new assertion-core claim kinds. Rationale: every other claim kind asserts an absolute post-turn value; a delta claim would need to smuggle in a "before" baseline that is meaningless outside this one runner's arrange-then-run-once shape (an ordinary transcript or tree card has no equivalent "before" to diff against, since play is cumulative). The derived runner reads the score/counter world-state key (`counterKey`, `packages/story-loader/src/state-keys.ts:54`) immediately after `arrange` and again after the command, and asserts the arithmetic itself — no new public surface on the assertion core, no claim type either transcript-tester or branch-tester's existing test writers ever need. Fixture branches (dedicated fixture story/stories under `packages/branch-tester/tests/fixtures/`, following the existing `state-pins` fixture's shape — `packages/branch-tester/tests/fixtures/state-pins/state-pins.story`) cover AC-2 (the fernhill `when flowering` branch from a fixture copy of the worked example, passing as written, then failing by name with the `move` line deleted), AC-3 (a planted refusal-then-body-anyway defect), AC-4 (a branch guarded by a non-floor precondition, asserted SKIPPED with the exact shape name, and its inclusion in the total count), and AC-7 (a branch whose command has no vocabulary, asserted as a parse failure). **Fernhill and secret-letter are read-only measurement targets in this phase, never edited** — AC-2's "deleted move line" happens on the fixture copy only, per the constraints.
- **Exit state**: `packages/transcript-tester` and `packages/branch-tester` suites green including the new claim kinds and the derived-runner fixture tests (AC-2, AC-3, AC-4, AC-7 each a literal, named test — SELF-VERIFYING per the ADR's own framing). `tsc --noEmit` clean on both packages; `dist`/`dist-esm` rebuilt where consumed via `require()`. Behavior Statements produced for the new claim-kind functions and the derived-runner's per-branch execution before their tests were written (rule 12); tests graded GREEN (rule 13). No change to `tree-walker.ts:368`'s revive-after-ending behavior (that is D4's, a later plan) and no new optional field on `TreeCard`/`tree-document.ts` (also D4's).
