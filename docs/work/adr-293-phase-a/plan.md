## Scope assessment — is Phase A too large for one session, and where does it cut

**Yes.** ADR-293 itself admits this: Amendment A1 ruling 5 moved `resolve()` and D10's full melee class taxonomy into Phase A specifically "at the cost of a meaningfully bigger Phase A," and the measured blast radius is ~45 call sites plus ~30 declaration lines across core, engine, stdlib, plugins, character, extensions/basic-combat, stories/dungeo, devkit, family-zoo-tutorial, and docs/book — plus a save-format version bump, four new CLI/transcript directives, and a split verify gate. This is a Large-tier cross-cutting change stretched well past one session's budget. It decomposes into **7 phases**, described below.

**The real cut points are dependency-respecting, not arbitrary slicing.** Two phases (1, 2) are purely additive and keep the full platform build green throughout. Phase 3 flips one injection surface (`GameEngine.random` → turn-plugin/scheduler/NPC context) that no other package's *type* depends on, so it also stays green. Phases 4–6 are a **single ordering-hazard arc**: TypeScript's composite project references mean the moment `EnhancedActionContext.random`'s type flips from `SeededRandom` to `RandomService` in stdlib, every package and story that statically references that type (or a parameter typed from it, including the action-interceptor hook signatures) fails to compile until *it* is updated too — stdlib, `stories/dungeo`, `packages/extensions/basic-combat`, `stories/family-zoo-tutorial`, and `packages/devkit`'s fixture all break simultaneously. That arc cannot be given a false green boundary between its phases; see "Ordering hazards" below for how to work it safely. Phase 7 is the integration/acceptance pass that restores the full green regression baseline and formally checks every gated AC.

## Ordering hazards

1. **The `ActionContext.random` retype is a big-bang across five packages/stories at once**, not a gradual rollout — this is the hazard the task explicitly asked to be flagged. `EnhancedActionContext.random` (`packages/stdlib/src/actions/enhanced-types.ts:145`) is the shared type; `action-context-factory.ts:82` (engine) constructs it; `stories/dungeo`'s interceptor hooks and `melee-npc-attack.ts:109` receive a parameter typed off the same surface; `packages/extensions/basic-combat`, `stories/family-zoo-tutorial`, and `packages/devkit/fixtures/basic-story` all call `context.random.chance(...)`/`.pick(...)` in the old bare-probability shape. Because engine depends on stdlib (never the reverse) and stories/extensions depend on stdlib's published types, **the type change and every consumer's call-site conversion must land as one coherent change-set** for `./repokit build dungeo` to pass again. Recommendation: do Phases 4–6 on a single branch/worktree in immediate succession (back-to-back sessions with no other work interleaved), verify each phase with **package-scoped** `pnpm --filter <pkg> build` / `test` rather than the full platform build, and only require the full `./repokit build dungeo` + walkthrough-chain gate to go green again at the end of Phase 6. Do not merge to `main` mid-arc.
2. **`melee-npc-attack.ts:116` currently overrides the RNG it receives at `:109`.** Deleting the module singleton without also fixing `:116` reintroduces the same bug in a new shape (a correctly-typed `RandomService` parameter, silently discarded). Phase 5 must fix both lines in the same commit.
3. **`resolve()`'s `materialize` parameter ships unused in Phase A** (per A1 ruling 5) — it exists only so the four multi-draw call sites (`weaponBehavior.ts:45,48`; `melee.ts:213,232,449,450`) have a real route to a stream. Do not attempt to wire forcing against it in Phase A; that is Phase C's job and pulling it forward re-opens scope A1 deliberately deferred.
4. **`SAVE_FORMAT_VERSION` bump is a one-shot cutover, not a dual-write.** Per the project's standing ruling after the v3→v4 hard-break (auto-delete rejected in favor of a version reader), Phase A must ship the `2.0.0`→`3.0.0` reader as a real branch on day one — there is no intermediate state where both formats are silently accepted without a reader.
5. **World-model needs zero Phase A source changes.** `deadlyRoomBehavior.ts` and `weaponBehavior.ts` keep accepting bare `SeededRandom` parameters per D6 — only their *callers* (stdlib, dungeo) change shape to wrap them in `resolve()`. No new trait or export lands in `packages/world-model/src/index.ts` or `src/traits/index.ts`, so the root-barrel discipline does not apply to this plan.
