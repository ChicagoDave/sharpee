## Phases

### Phase 1: Canonical transcript model + serializer (D11, D17)
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: `packages/transcript-tester` — the parser (`parser.ts`) already produces the model this phase edits nothing about; this phase adds the matched-pair serializer (`golden.ts`'s `serializeGolden`/`parseGolden` is the working precedent) that emits D17's canonical form.
- **Entry state**: ADR-300 ACCEPTED. `parseTranscript` already parses all 185 `.transcript` files under `stories/` clean (measured 2026-08-04, cited in D11). No serializer exists yet — today nothing writes a `.transcript` back out from the model.
- **Deliverable**: A `serializeTranscript` (naming TBD at implementation, matched-pair with the parser) implementing every D17 rule: trailing newline; `> ` command prefix; double-quoted `contains` values; column-0 assertions/directives; blank line after `[GOAL: …]` and after the `---` separator; `# ` comment spacing; 2-space header continuation indent; blank line before each stanza (leading comments + command + assertions, blank above the comments); header fields emitted in D3's enumeration order with long values re-folded at 78 columns / 2-space continuation; assertions emitted in model order, never reordered; a block's `text`/`end text` at column 0, verbatim content, no blank line between an assertion and its block (D11's one semantic rule).
- **Exit state**: AC-3 holds — round-trip fidelity test (parse → serialize → parse, assert model equality) passes over every `.transcript` under `stories/` (185 files). AC-4 holds — idempotency test (serializing an already-canonical file is a byte no-op) passes. Both tests are part of `packages/transcript-tester`'s own suite and green.
- **Status**: COMPLETE (2026-08-04, session 088e3e)
- **Outcome**: `src/serializer.ts` (`serializeTranscript`, exported from the root barrel) plus `tests/serializer-roundtrip.test.ts` (13 tests: AC-3 and AC-4 over all 185 files, and the D17 form rules individually). Package suite 245 passing; Dungeo walkthrough chain 952 passing across 17 transcripts, verified against a fresh `./repokit build dungeo`.
- **Two parser defects had to be fixed first — neither was known when this plan was written, and both would have caused silent data loss in Phase 2:**
  1. **Folded header values were discarded.** D17 asserts the parser joins them; it did not. An indented continuation line matched no branch and fell out of the loop — 176 lines across 41 files, every one a wrapped `description:` — or, when it contained a colon, became a header key parsed out of prose (four in `article-rendering.transcript` alone). Neither raised a parse error, so AC-3 could never have caught it: both parses agree on the truncated value, and the loss happens upstream of the gate. Fixed by holding a header field open until the next field, the separator, or EOF; covered by `tests/header-folding.test.ts` (10 tests, including a whole-corpus sweep asserting no header key falls outside the grammar).
  2. **Comment order did not survive a save.** A command was recorded in `items[]` only when it was finalized — at the *next* command — while comments were recorded immediately, so any comment written under a command was filed ahead of it. Serializing then moved it there for real, and re-parsing moved it again: the transformation had no fixed point, which is why AC-3 *and* AC-4 both failed on 172 of 185 files. Fixed by recording a command where it is read; `finalizeCommand` still completes the same object in place.
- **Still open, and it lands in Phase 2 if left**: five files write `description: |` (a YAML block-scalar marker) with the text on continuation lines. Now that continuations join, the marker leads the value (`"| AA SCORE sets…"`). Before this session those files' descriptions were the literal string `"|"`, so this is not a regression — but normalization would bake the `|` into 5 descriptions permanently. Ruling needed on whether a lone `|` is stripped as the marker it plainly is.

### Phase 2: Normalization commit (D11, D17 — isolated, requires go-ahead)
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: One reviewable commit applying Phase 1's serializer to every committed transcript, and nothing else.
- **Entry state**: Phase 1's serializer ships with AC-3/AC-4 green. **Explicit go-ahead confirmed** (see Platform-change checkpoint) before running.
- **Deliverable**: A single commit running the serializer over all 183 transcripts in `stories/*/tests/transcripts/` and `stories/*/walkthroughs/`, and nothing else in that commit (no editor code, no unrelated changes). Diff shape should match D17's tally (~1689 blank-line insertions before stanzas, 72 before separators, 40 header re-folds, 34 comment respacings, 11 header reorders, 4 indent corrections, 2 blank lines after a separator) — a materially different diff shape is a signal to stop and investigate before committing, not to proceed.
- **Exit state**: AC-5 holds — one walkthrough-chain run before the commit and one after are byte-identical (sound per ADR-293 Phase D's verified pinned-seed determinism; per CLAUDE.md, a single run each side is sufficient, do not re-run to "check for flakiness"). Every touched transcript still parses clean and round-trips (re-run Phase 1's AC-3/AC-4 tests over the post-commit corpus as a second confirmation).
- **Status**: COMPLETE (2026-08-04, session 088e3e)
- **Outcome**: 152 of 185 transcripts rewritten; 33 were already canonical. `+629 / -533` lines. AC-5 verified: chain output byte-identical across the change with timings normalized, 952 passing on both sides. The corpus is now a fixed point of the serializer — a second pass reports `byte-changed: 0`, which is AC-4 against real files rather than against a second serialization.
- **Diff shape differed materially from D17's forecast, and the forecast was the thing that was wrong.** D17 predicted ~1689 blank-line insertions and no removals; the real diff is `+222 / -235` blank lines and `+407 / -296` content lines. Two reasons: the corpus was already far closer to canonical than the survey implied, and the model carries no blank-line item, so 235 blank lines used for vertical spacing were dropped (111 between a banner comment and its `[GOAL:]`, 53 between a comment and its command, 54 inside comment runs). Ruled not to matter — these transcripts are generated, not hand-authored, so there is no author spacing to preserve and no `blankBefore` model change is warranted. D17's tally should be treated as superseded by these measurements.
- **Note for later phases**: AC-3 and AC-4 were green throughout the blank-line loss, exactly as they were green through the header-fold truncation in Phase 1. Both are round-trip gates, so neither can see anything the first parse already discarded. Any future claim that "the round trip proves nothing is lost" is false in that specific way.

### Phase 3: Standalone tool scaffold — `sharpee test --ui` (D0, D6)
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: The CLI-served, framework-free web tool itself: where it lives, how it's launched, and its in-process verification path. This is the phase that makes D0 real — everything after it is a surface built inside this shell.
- **Entry state**: Phase 1 done (a model + serializer exist to build an editor over). No standalone tool surface exists yet — `TestRunner.swift` still only spawns `sharpee test --json` as a child process; there is no `--ui` flag anywhere in `packages/devkit`'s `test.ts` command or `packages/sharpee`'s CLI wrapper. **Confirm the platform-change scope with David before starting** (new tool package/command surface — see checkpoint above).
- **Open decision — which CLI hosts `--ui`, and where the tool's code lives. Decide with David at phase start; do not improvise.** ADR-187 R1 split the `test` command across two independent implementations and this phase is the first thing that has to pick one:
  - `sharpee test` — `packages/devkit/src/commands/test.ts`, the author tool. It is the surface AC-1's wording names verbatim, it already carries `--json`, `--coverage` and `--capture-output`, and it is what `TestRunner.swift:96` spawns. But devkit is the **outside-repo** author tool; in-repo platform and story builds are deliberately a separate process (ADR-180's devkit rework), so hosting the in-repo corpus's editor here works against that split.
  - `dist/cli/sharpee.js --test` — the platform bundle (esbuild output). CLAUDE.md mandates it for *all* in-repo transcript testing including Dungeo, and `tools/vscode-ext/src/test-runner.ts:198` and `packages/channel-service/tests/ac-13-cli-real-path.test.ts:51` both drive it. D0's entire justification is corpus reach — Dungeo's 134 of 183 files — which is this bundle's territory, not devkit's.
  - **Recommended**: build the server and web UI inside `packages/transcript-tester`, which already owns the model, parser, runner and (after Phase 1) the serializer, and have **both** CLIs expose a thin `--ui` flag over it. That honors ADR-187 R1's "each its own implementation" at the command surface without a second copy of the tool, and it keeps AC-1's `sharpee test --ui` spelling true while giving the in-repo corpus a bundle-hosted route. Getting this wrong means re-plumbing the flag and possibly the server's package home later, which is why it is a decision and not an implementation detail.
- **Deliverable**: `sharpee test --ui` (or the equivalent flag on the existing `test` command) starts a local server and opens a framework-free web UI built on `packages/platform-browser`'s substrate (reusing what `--browser` already builds, per D0), listing the target story's transcripts (reusing `findTranscripts`) with a run action per file. The run path calls `runTranscript` in-process — no `sharpee test` subprocess is spawned by the tool itself. No editor UI yet; this phase is infrastructure plus a minimal list-and-run surface.
- **Exit state**: AC-1 holds — the tool runs with the macOS IDE neither installed nor running, on both macOS and Linux (verify on Linux explicitly, not just "should work"); a story opens and its transcripts list and run. AC-2 holds — assert on the absence of a spawned child process in the tool's own run path (the ADR-277 wire still exists and the IDE still uses it — this phase does not touch `TestRunner.swift`).
- **Status**: PENDING

- **Budget**: 400
- **Domain focus**: The carried-over ADR-299 interaction design (D2), rebuilt fresh in the tool's own runtime — one column per transcript file, card-per-turn, and the D4 default gesture.
- **Entry state**: Phase 3's shell exists (list-and-run works, in-process verification works). Phase 1's model/serializer exist to edit and save through.

Card-per-turn reading surface: command, expected, actual, verdict-as-tint (plain unblessed, green blessed — session dd4189's rulings, D2). ### Phase 5: Editor — remaining assertion forms, GOAL sections, grammar containment (D3 completion, D5, D15, D16's editor half)
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: The forms nobody reaches by hand today (D3's stated reason the tool exists), `[GOAL:]`'s structural rendering, and construction-level enforcement that illegal/removed grammar cannot be produced.
- **Entry state**: Phase 4's core editor exists (cards, columns, save/run round-trip).
- **Deliverable**: `[EVENT: true|false, N?, type="…" key="value"]` and `[STATE: true|false, expression]` gain authoring gestures (0 hand-written uses today per the research doc — this is the experiment that tests whether they were unwanted or merely undiscoverable). `[TODO: note]` gets a one-click "mark pending" gesture on a turn card (D16). `[GOAL: name]`/`[END GOAL]` renders as a collapsible band grouping the cards between them; in the model a goal is a section object created and deleted as a unit, so no gesture can produce an orphaned marker (D15). - **Exit state**: AC-10 holds — no gesture produces an orphaned `[GOAL:]`/`[END GOAL]`; deleting a section removes both markers together. AC-11 holds — an audit (ideally an automated one: enumerate every editor affordance and assert its possible outputs against the legal-grammar set) confirms no removed form is reachable, and `[TODO: note]` has its one-click gesture.

### Phase 6: Play + Promote workflow (D12)
- **Tier**: Large
- **Budget**: 400
- **Domain focus**: D12's replacement for ADR-299's record mode and ADR-290 D1–D4's atomic mode — play accumulates a session log, and a transcript is promoted from a chosen turn range afterward.
- **Entry state**: Phase 3's in-process runner exists. Phase 4/5's editor exists (promoted transcripts are authored through it). No record/promote mechanism exists yet anywhere in the new tool.
- **Deliverable**: Playing a story in the tool accumulates a session log — for each turn, command, output, events, and an engine save (per-turn saves are an authoring cache only, keyed on story build + prefix commands + seed; nothing is committed or referenced by any transcript, per D12's "never a citation"). The author selects a contiguous turn range afterward and promotes it into a transcript: turns before the selection are included, assertion-free, and collapsed in the editor (D12's "a promoted transcript carries its prefix"); `[STATE: true, …]` is available on the last setup turn for stating preconditions (no new grammar — D12 gives `[STATE:]` a job). Verification of a promoted (or any committed) transcript always runs from turn 1, never from a restored save (`search.ts`'s occurrence-counter divergence is the reason — a save-jumped run must never reach the repository).

  **Where the promoted file lands is inferred, never asked (ADR-290 D8 — surviving, not superseded).** D8 is one of the ADR-290 decisions ADR-300 D12 leaves standing, and it governs exactly this flow: the destination comes from the existing folder classifier, the author is never prompted for a path, and an **unresolved destination fails loudly before promotion begins** rather than defaulting silently at save time. Tracked live as GitHub issue #198 ("Save should not ask for a location"). D5 applies alongside it — the blessed mark is rendered by the client, not baked into the artifact.
- **Exit state**: AC-6 holds end-to-end — the ADR's worked scenario: open a story, play 40 turns with no prior recording decision, promote turns 28–40, get a file with turns 1–40 (1–27 collapsed and assertion-free), select "the tarnished key" in turn 31's actual output to add `[OK: contains "the tarnished key"]`, sign off, and the file runs clean from turn 1. AC-7 holds — a transcript promoted from a save-jumped session and one promoted from a played-from-the-top session are byte-identical and both run clean from turn 1.
- **Status**: PENDING

### Phase 7: Re-bless / drift lifecycle (D7, D13)
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: `Rebless.swift`'s rules (D2: rules carry, Swift does not) — locate the block a failing command owns, replace only its content, refuse to widen a `contains` claim — plus D13's eager stale-marking and sign-off-is-the-only-re-record rule.
- **Entry state**: Phase 6's play/promote/sign-off flow exists (sign-off is where a re-record happens). Phase 4/5's editor exists (the refusal is surfaced as an editor choice).
- **Deliverable**: Editing a transcript's command list eagerly marks its paired `.golden` stale in the UI the moment the edit happens, before anything runs (the editor already has the information — no run required to know this). The runner's own detection (`runner.ts:262` command-list drift, `runner.ts:480` `staleProvenanceFields`) remains the backstop and is not duplicated. On a failed run where the prose changed, re-bless offers the author a choice: keep the narrow `contains` claim (never silently widened to the whole new response) or replace it deliberately — the affordance ADR-282 D2 always implied. Nothing auto-re-records on save; sign-off (Phase 6, a clean run from turn 1 followed by an explicit author-initiated bless) is the only re-record path.
- **Exit state**: AC-8 holds — editing a command in a transcript with a paired `.golden` reports the recording stale without running anything, the `.golden` on disk is unchanged after the save, and only sign-off re-records it.
- **Status**: PENDING
