**The questions, with options plainly**

- **Q1 (F1). May a compass vehicle take a computed way?** A compass vehicle's step stops at any way that is not a plain `exit` (`vehicleBehavior.ts:686-691`). Option A: yes — a compass vehicle crosses a computed way when its candidates admit it, same as a streets vehicle (one mover rule). Option B: no — a computed way is only for steered-by-streets and pushed things; the compass vehicle keeps its stop and the compiler refuses a computed way in a compass vehicle's rooms. Option C: no, and the stop stays silent as today but is documented in the guide. Fix for F1 in all cases: `wayFor` answers admittance for a computed way.
- **Q2 (F9). What does `exit` aboard a vehicle do when the room has several outside directions?** Option A: refuse with a message that names the directions ("go port or go starboard"). Option B: ask which one (a disambiguation question, as the parser does for nouns). Option C: the compiler refuses a room aboard with more than one outside direction unless it names one as `exit`'s way. Option D: keep first-declared and document it (the shortcut we are removing; listed only so it is declined plainly).
- **Q3 (F12). Which key does a counter use for "the player's"?** Today the player's timer keys on the role (`'player'`, ADR-325 D3d) while the player's counter keys on the character holding it. Option A: both key on the character (a timer survives a role change only if the same character holds the role). Option B: both key on the role (a counter follows the role, as Reflections' rotating player would need). Option C: leave the two different and say so in the guide (a design asymmetry, not a shortcut).
- **Q4 (D1). Which `passage` gets a new word?** `passage: 3 turns` is a flight vehicle's time between destinations; `passage climb the rope to …` is an exit reached by its own words. Option A: rename the flight vehicle's line (`flight time: 3 turns`, `journey: 3 turns`, or `takes: 3 turns`; David picks the word). Option B: rename the exit form (`way climb the rope to …`; but `way` is already the traversal system's word for the result). Option C: leave both and document the two meanings (not recommended: one word, two concepts is the defect). Whichever is chosen is a language change, with the corpus, the guide and the grammar docs following; no backward compatibility.
- **Q5 (D8). Who hears a vehicle move?** Today the machine reports an arrival when the player is aboard or in the room reached, and every other step only when aboard. Option A: route the report through `PerceptionService` like every other event (a player in a dark room does not see a tram arrive, hears it only if it has a sound). Option B: keep containment as the rule, because arrival is announced by the machine as a stage direction, and document it. Option C: split — arrival goes through perception, steps stay containment.
- **Q6 (D12). Does a passenger arrive in a room?** The machine carries the player by moving the vehicle and emits `vehicle_arrived`; no `actor_moved` follows. Option A: a passenger arrives — the machine also chains `actor_moved` for the player, so `when the player enters <room>` clauses fire. Option B: a passenger does not arrive; clauses for entering fire only for walking, and `vehicle_arrived` is the author's hook. Option C: both events, with `actor_moved` carrying a `by vehicle` mark so a clause can tell them apart.
- **Q7 (D19). Where does the expanse extension's data live?** `seenFromAfar` is on `IdentityTrait` and a landmark's outlook is `RoomTrait.sight`, so every entity and room in every story carries `use expanses` fields. Option A: a `LandmarkTrait` (the outlook and seen-from-afar text), attached only by `use expanses`; core traits lose the fields. Option B: leave the fields on the core traits, add a header note, and accept the cost (a two-field cost across every story). Option C: only `RoomTrait.sight` moves (a landmark is a room); `seenFromAfar` stays on identity because any thing may be seen from afar.
- **Q8 (D20). One event or two for "now gives light"?** Lighting a flame records `if.event.lit`; lighting a switchable lamp delegates to switching on and records `if.event.switched_on` only. Option A: lighting always records `lit` as well (the lamp records both: `switched_on` for the device and `lit` for the light). Option B: a lamp records only `lit` and switching on a lamp records `lit` through the light behavior (the light is what changed). Option C: leave two events and document that a reaction to "lit" must also catch `switched_on` for a lamp.
- **Q9 (Older-3). Should `play sound … when client has sound` gate the world sound?** A consequence of one sound with two sides (ADR-374 D6). Option A: the world side ignores a client-capability condition (the heard event always fires; only the client playback is gated). Option B: keep it gated and document it (what the guide says now). Option C: refuse the condition on a `play sound` that has a world side, at compile time.
- **Q10 (F5). Confirm the shape for removing English from stdlib.** The grammar gives the `steering` action the gesture (hard to port, make sail, furl, board and so on) as data, and `setting-course` its destination as a resolved entity (so a room's alias matches); articles are dropped by the English parser, not the language-neutral loader. Option A: one `steering` action with a `gesture` argument from the grammar's own slot (a grammar-engine change, no new action ids). Option B: ten actions, one per gesture (more ids, less data, more lang entries). Confirm A, B, or a variant.
- **Q11 (D2, D3, D4, D6, D13). The renames, for David to name.** (D2/D3) Which word for each of: the room a vehicle is boarded through (`boarded through` / `boardedThrough` / `boardingRoom`) and the movement type (`movement` / `model`)? Default offered: `movement` and `boarded through` win everywhere because they are Chord's authored words, and the trait fields follow (`VehicleTrait.movement`, `VehicleTrait.boardedThrough`). (D4) *Lock* wins in the Testing tab and ADR-367; branch-tester's *pin* and the wire's `ClaimLockPin` follow, or *pin* wins everywhere and the Testing tab follows? Default offered: *lock* everywhere, because *pin* already means a held value in the state-pins feature. (D6) `ContainerBehavior.addItem` becomes what? Default offered: `ContainerBehavior.canAdd` (or the call goes and `canAccept` is the check). (D13) `if.event.expanse_edge` / `vehicle_in_irons` / `vehicle_at_end` become past-tense facts: default offered `expanse_edge_reached`, `vehicle_put_in_irons`, `vehicle_reached_end`.
- **Q12 (Older-1). The tool-requirement trio.** Five traits carry the same `requiresTool` / `requiredTools` / `canXWith` and `toolId` / `toolIds` shape. Option A: one shared tool-requirement shape (a `ToolRequirement` value object each trait holds; `tool-shared.ts` reads it) — a refactor across five traits and their loader and Chord bindings. Option B: leave the five and say so in the ADR (not a shortcut fix; listed so it is declined plainly). Option C: do A now but in its own phase after the rest, because it touches five traits and their tests (this is how Phase 10 below is written).
- **Q13 (D17, D18). Confirm the shapes.** (D17) `admits` becomes `{ vehicles: string[], pushing: boolean }` (no reserved word in an id list, and `admitsPushed` folds into it). (D18) The IR names outside with a value of its own: `to: { kind: 'outside' }` replacing `to: ''` plus `toOutside: true`, and the analyzer's error results stop using `id: ''` (a distinct error kind). Confirm, or name another shape.
