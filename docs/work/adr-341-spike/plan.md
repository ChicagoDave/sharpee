### Phase 0: Decide and provision the spike environment
- **Tier**: Small
- **Budget**: 100
- **Domain focus**: N/A — infrastructure decision, not domain modeling.
- **Entry state**: ADR-341 ACCEPTED (GH #386). No Windows environment provisioned for this work yet. David develops on macOS; every subsequent phase needs Windows to run C#/.NET, WPF, WinUI 3, and WebView2.
- **Deliverable**: A written decision, recorded in this plan's progress notes (not a separate ADR — this is an execution-environment choice, not a constraint on future sessions), naming which of the three options David picked and why, plus the provisioned environment itself:
  1. **A local Windows VM** (e.g., Parallels/UTM/VMware on the Mac, or a cloud Windows VM) — can verify interactive editor feel, WebView2 resource-request behavior, and MSIX install/run; cannot cheaply verify Windows-on-ARM emulation unless the VM host is itself Apple-silicon-hosted x64-on-ARM (which is a different emulation layer than Windows-on-ARM's own x64 emulation and does not substitute for it).
  2. **A physical Windows machine** — can verify everything a VM can, plus is the only option that can verify Windows-on-ARM emulation for real if the physical machine is a Windows-on-ARM device (e.g., a Snapdragon-based laptop); without one, the ARM assumption stays unverified by this plan and is flagged as such in Phase 6, not silently passed.
  3. **A GitHub Actions Windows runner** — build-only: can verify the tree-sitter binding compiles and loads headlessly, can run the MSIX packaging check's filesystem behavior, can run WebView2 in headless/offscreen mode if the check can be scripted that way; **cannot** judge interactive editor feel (auto-indent responsiveness, bracket-match highlighting under real keystrokes, scroll performance) — the ADR's own language ("how it felt") names a judgment this option cannot deliver.
  This phase does not decide for David; it presents the three options with what each can and cannot verify, gets David's pick (and, if he picks more than one — e.g., a runner for build-only checks plus a VM for the editor-feel judgment — records the split), and provisions the chosen environment(s): .NET SDK (matching D2's ".NET" — verify current LTS at provisioning time), a WebView2 runtime install, and `git` access to this repository (or a worktree) on the Windows side.
- **Exit state**: Environment decision recorded; chosen environment(s) provisioned and confirmed reachable (a trivial `dotnet --version` or equivalent run, evidence inline: command, output, date); `tools/spikes/adr-341/` scaffold directory created (empty save for a header `README.md` stating it is spike code, exempt from the repository's documentation standard beyond that header, never shipped, and not under `packages/`).
- **Progress (2026-09-08, session 4a2d5f)** — Decision: **option 2, a physical x64 Windows machine** (David: "I guess I need a Windows machine"). Reasoning recorded from the conversation: AWS ships no license-included Windows 11 AMI and a retail key carries no right to shared-tenancy cloud (Dedicated Host plus Software Assurance or VDA required); Azure's Marketplace Windows 11 works for dev/test but bills by the hour with the license folded in, and a one-vCPU size is too slow for an interactive spike; a local arm64 VM on the Mac (Parallels or UTM with a retail Windows 11 key) would judge editor feel and verify the ARM assumption but cannot run Phase 2's x64 Node check or Phase 5's x64 MSIX check, which are about what ships. A physical x64 machine covers every phase except the Windows-on-ARM emulation check, which stays unverified and is flagged in Phase 6 per this phase's option text. Sizing: four cores and sixteen gigabytes is comfortable; Windows 11 Home suffices (developer mode and MSIX sideloading are available on Home). The exit state's `dotnet --version` evidence is not yet recorded. **Claude Code runs on the Windows machine itself** (native install with Git Bash, not WSL — the spike's toolchain, WinUI 3 deployment, and MSIX packaging are Windows-side), and David judges the editor feel at that machine's keyboard, on a monitor or over RDP from the Mac. **DevArch on Windows** (David, 2026-09-08: "this goes back to my need to get DevArch installing cleanly on Windows"): this plan is the first Sharpee work to run a DevArch session on Windows. ### Phase 2: Verify the three named assumptions and select spike candidates
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: N/A — dependency verification, not domain modeling.
- **Entry state**: Phase 0's environment provisioned and reachable. Independent of Phase 1's exact row contents — none of the three assumptions below depend on which controls end up flagged, though Phase 2 also selects the editor-control candidates Phases 3/4 will build against, which is easier once Phase 1's editor row is confirmed.
- **Deliverable**: Three assumption checks, each recorded with command, result, and date (evidence inline per the repository's evidence rule):
  1. **A .NET tree-sitter binding exists and loads a grammar.** Identify the candidate binding(s) (ADR-341's Context calls this "an assumption here" without naming a specific package), verify current maintenance status per the project's "check dependency health before recommending" rule, install it in the spike scaffold, and load any grammar (a TypeScript grammar is sufficient for this check — the Chord grammar itself is ADR-182's unimplemented artifact and is out of scope here) to confirm the binding actually parses. Record pass/fail; a fail does not block the spike, it changes what the editor spike can test (a custom hand-written lexer becomes the fallback the record notes, mirroring D4's own contingency language).
  2. **WebView2's resource-request hook can satisfy the D3 host contract.** Build the smallest possible WebView2 host (in whichever toolkit is fastest to scaffold — this check is toolkit-agnostic since both WPF and WinUI 3 host the same `WebView2` control) that intercepts a resource request and serves a small directory of files over a custom origin, the way `PlayURLSchemeHandler.swift` and `DocsTabSchemeHandler.swift` do on macOS (both confirmed `WKURLSchemeHandler` conformers by read this session). Confirm `localStorage` persists and relative URLs resolve against the custom origin — the two properties D3's Context names as what the WKURLSchemeHandlers currently guarantee.
  3. **The vendored x64 Node runs acceptably under Windows-on-ARM emulation.** Checked once, not a gate (D6's own wording). If Phase 0's environment includes a Windows-on-ARM device, run the vendored x64 Node build under it and record whether it launches and executes a trivial script; if no ARM environment was provisioned, record that explicitly as unverified rather than silently passing it — Phase 6 must not report this assumption as checked if it was not.
  Also select and health-check (per project memory, dependency health verified before recommending) the editor-control candidates Phases 3/4 will build against: for WPF, the mature third-party code-editor ecosystem ADR-341's Context names generally (name specific candidates at spike time — AvalonEdit is the most commonly cited mature option, verify its current maintenance status rather than assuming it); for WinUI 3, the three options ADR-341's Context names (the Scintilla port, which the ADR already characterizes as "early work in progress" — verify that characterization still holds; the Win2D control; Monaco hosted in WebView2 — check each for current maintenance).
- **Exit state**: All three assumptions checked (pass, fail, or explicitly unverified-with-reason) and recorded with evidence; editor-control candidates for both toolkits named and health-checked, ready for Phases 3/4 to build against.
