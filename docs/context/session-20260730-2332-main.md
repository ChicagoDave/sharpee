## Completed — Part 1: ADR-041 Amendment 1 (the blocker)

P-3's recorded blocker instructed: "Mark ADR-041 superseded — almost certainly by ADR-051's
four-phase context." Reading the ADRs before acting found **two errors in that instruction**:

1. **ADR-051 is not the successor.** It is *Action Behaviors for Complex Action Handling*,
   is itself marked `Superseded by ADR-052`, and never touched the context interface. The
   four-phase pattern actually comes from **ADR-058** (`report()`) plus **ADR-228**
   (lifecycle engine). Superseding ADR-041 "by ADR-051" would have pointed at an ADR that
   does not say what the pointer claims.
2. **ADR-041's decision is still live.** It decides exactly one thing: one method creates
   events — `event(type, data)`, with no `emit`/`emitSuccess`/`emitError`/`emitMany`/
   `createEvent`. That is true of `ActionContext` today. Only the interface *name* went
   stale: `ActionContext` and `EnhancedActionContext` were consolidated in code with no ADR
   recording it, leaving an empty `@deprecated` alias behind.

So it was **amended, not superseded**. `docs/architecture/adrs/adr-041-simplified-action-context.md`
gains **Amendment 1 (2026-07-30, session deae34)**, placed directly under the Status line so
no reader hits the stale Decision block first. The amendment:

- Retargets the ADR from `EnhancedActionContext` to `ActionContext`.
- Records the previously-undocumented consolidation of the two interfaces.
- Explains why a many-membered `ActionContext` does not contradict "simplified" — the ban is
  on a *parallel event-creation path*, not on member count.
- Flags the stale `execute(): SemanticEvent[]` example against ADR-058/ADR-228.
- Records explicitly that ADR-051 is **not** the successor.

Original Context / Decision / Consequences left intact — an amendment must not rewrite
history. Related ADRs extended with 058, 228, 172, and 231 D6.

world-level registry. `EventHandler` is the signature of `WorldModel.registerEventHandler()`
(ADR-052) and types **nine live handlers** in `handlers/state-change.ts` — `handleOpened`,
`handleClosed`, `handleLocked`, `handleUnlocked`, `handleSwitchedOn`, `handleSwitchedOff`,
`handleWorn`, `handleEaten`, `handleDrunk`. Removing it would untype all nine.

The retained-reason comment also distinguishes it from `StoryEventHandler` (ADR-075,
effects-returning) — that conflation is the likely origin of the original tracker finding.

## Key Decisions

### 1. Amend ADR-041 rather than supersede it
The ADR's decision (one event-creation method) is still enforced by the current code; only
the interface name changed. Superseding wholesale would have discarded a binding decision and
cited a successor (ADR-051) that neither addresses the context interface nor is itself live.

### 2. Do not flip ADR-058's status
An inconsistent repo-wide convention is a sweep, not a drive-by edit. Recorded for David's
planned DevArch status sweep instead.

### 3. Remove `MetaAction.canExecute` alongside `Action.canExecute`
P-3 named one; both are the same dead member on sibling abstract classes. Removing one would
have left the finding standing.

### 4. Retain `EventHandler` with a comment instead of removing it
The item's premise conflated two different handler concepts. The Done-when's escape hatch
(comment explaining retention) is the correct outcome, not a partial delivery.
