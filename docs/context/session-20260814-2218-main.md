### Work item 1 — `/play` served an empty iframe (root cause found and fixed)
- `/play` itself always returned 200; the 404 was the game *inside* it. `website/src/app/play/page.tsx:20` embeds `/web/fernhill/index.html`, served from `website/public/web/fernhill/`, which did not exist on this host (plover). Confirmed live: `sharpee.net/play` → 200, `/web/fernhill/index.html` → 404, `/play/dungeo/` → 404.
- That tree is gitignored (`.gitignore:152`) and generated only by repokit's `--browser` mirror (`mirrorToWebsite`, `tools/repokit/src/commands/browser.ts:132`).
- **Root cause**: commit `18d65ab3` (2026-08-05, ADR-302 D16) moved Fernhill from `stories/fernhill` to `branch-stories/fernhill`. `resolveStoryDir()` (`tools/repokit/src/repo.ts:159-171`, pre-fix) searched only `stories/` and `tutorials/`, so the story became invisible to repokit — the only tool whose path runs the website mirror. The artifact stopped regenerating; `/play` served an empty iframe for nine days (2026-08-05 → 2026-08-14). Nothing failed loudly: the artifact is untracked, so no test, `git status`, or deploy step ever mentioned it. `deploy.sh` already had a "rebuild the playground bundle" step (`e1128470`) for exactly this class of gitignored-artifact problem, but never got an equivalent for browser clients. The `/play` page itself was added 2026-07-19 (`d0cc4807`), while Fernhill was still under `stories/` — it worked at the time.
- A first build attempt using the `.story` file path failed (`repokit: story not found`, `build.ts:192`, exit 2). Per CLAUDE.md's no-auto-retry rule this was reported and diagnosed, not retried — reading the resolver established the correct invocation form before any second attempt.
- **Fixes** (user chose both options via AskUserQuestion):
  - `tools/repokit/src/repo.ts:164` — `resolveStoryDir()` now searches a third base, `branch-stories`, with a header comment recording the ADR-302 D16 move, the silent mirror failure, and that a story is a location (ADR-180 Decision 4).
  - `tools/repokit/src/commands/build.ts:192` — the "story not found" error hint now names all three bases (`stories/|tutorials/|branch-stories/`).

### Work item 2 — `npm audit fix` made durable
- User ran `npm audit fix` in `website/`, resolving 3 high vulnerabilities: `brace-expansion` 1.1.16→1.1.18 and 5.0.8→5.0.9, `js-yaml` 4.3.0→4.3.1, `nanoid` 3.3.16→3.3.18. - Added to `website/deploy.sh` after `npm ci`: an `npm audit --audit-level=high` step that reports and never repairs, warning rather than aborting (matching the playground/examples precedent). The added comment explicitly documents why `npm audit fix` must not run in the deploy — it would mutate dependencies mid-deploy, ship an untested tree, and undo the determinism `npm ci` and the pnpm `--frozen-lockfile` exist to provide.

## Key Decisions

### 1. Extend the existing resolver rather than special-case Chord stories
Adding `branch-stories` as a third search base in `resolveStoryDir()` keeps "a story is a location" (ADR-180 Decision 4) intact — repokit doesn't need to know or care which harness a story belongs to to find it. This is the minimal fix; no change to `buildStory`'s Chord-skip logic was needed.

### 2. Assert the artifact, not the exit code, in deploy.sh
A build step that reports success while silently mirroring nothing is indistinguishable from one that worked — that's precisely how this outage went undetected for nine days. The new deploy step checks for `public/web/fernhill/index.html` directly rather than trusting `./repokit build`'s exit status alone.

### 3. `npm audit fix` belongs in a human's hands, never in deploy.sh
The new audit step reports and warns but never runs `npm audit fix` automatically — doing so mid-deploy would ship an untested, non-lockfile-committed tree and defeat the determinism `npm ci` / `--frozen-lockfile` are there to guarantee.
