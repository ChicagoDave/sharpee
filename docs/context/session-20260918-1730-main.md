## Completed
- **(1) Rail glyphs follow the palette.** `ProjectToggle`/`BottomToggle` are plain
  `Button`s and never had a `Foreground`, so they kept FluentTheme's own ink — which
  tracks the *system* variant — while the shell forces its palette dark at startup.
  `PaintChrome` now assigns `ThemeTokens.Foreground` to both, so they flip with the rail.
- **(2) The project pane collapses.** The toggle set `ProjectPane.IsVisible` while the
  pane's grid column stayed a fixed 220 px, so the pane blanked and the hole remained.
  New `SetProjectPaneVisible` drives the column (and its splitter) to 0 and restores the
  remembered width on reopen — the same move the shipping app makes
  (`SharpeeIDE/MainWindow.swift`, `applyProjectPaneVisible`).
- **(4) The relay delivers a batch, not a record.** `PaneRelay.DrainAsync` awaited one
  `EvaluateAsync` per record; the shipping Swift app posts each without awaiting and
  WebKit coalesces them. It now drains the whole queue into one script.

- **(5) The splitter grips reach past the gap they sit in.** A `GridSplitter` is
  hit-testable only across its own bounds, so a 4 px column gave a 4 px target. A window
  style gives the vertical ones `Margin="-4,0"` and the horizontal one `Margin="0,-4"`,
  with `ZIndex` above their neighbours. **That was wrong and is backed out**: a negative
  margin moves where the Grid *arranges* the splitter, so every drag started from an offset
  position and the pane jumped, and the reach only won hit-testing on one side — which is
  what "the grabber shows moving right but not left" was. The track itself is 10 px now,
  the grip is the track, and `ResizeDirection` is stated rather than inferred from bounds
  that change whenever the track does. The bottom splitter is now shown and hidden with the panel it
  resizes, so it no longer overhangs the editor's edge with nothing below it to drag.

- **(6) The run bridge was never implemented in this head.** The testing surface's Run
  button posts `{run:true}` on the `testingSurface` handler; `OnPaneMessage` filed that
  under "last post" and did nothing, and there was no `runLine`/`runExit` relay back — so
  the button could only ever hang. It now runs the shipping app's own arguments
  (`test <story> --tree --capture-output --capture-world --json`, from
  `SharpeeIDE/Test/TestRunner.swift`), streams the NDJSON into the run column through a
  second `PaneRelay`, and always closes with `runExit` — including for the three refusals
  (no story, no toolchain, already running), because silence was the defect.
- **(7) Word wrap on by default**, since story prose lines run long. View ▸ Word Wrap
  still turns it off.
- **Two probe defects found by (6)'s real-path test.** `--app-exit-state`'s save step wrote
  its marker as `// …`, which Chord rejects as an unknown declaration, and it restored the
  file afterwards but not the editor buffer — so anything that saved later wrote the bad
  line back. Both fixed; the marker is now a `##` comment with the blank lines Chord
  requires either side of it.

- **(8) The build report.** The CLI's `build` output stops at `npx serve`; `✓ Build
  succeeded.` and the closing banner are the app's own (`SharpeeIDE/Build/BuildController`
  → `StoryIndex.buildReport`). `Shell/StoryBuildReport.cs` derives the same from the IR the
  build emits, with the same counting rules: an entity counts once in the first bucket it
  matches, a dotted phrase key is a platform id and is not counted, a zero count is
  omitted. Against secret-letter it reproduces David's pasted banner exactly —
  `21 rooms · 2 regions · 121 things` / `14 people · 9 actions · 223 phrases`.
  The build also now drains the output queue before appending, since the CLI's last lines
  are still in flight at process exit and the report was landing mid-tail.

## Key Decisions
- **The stutter was not one paint per record — it was a replay storm.** Per-record
  delivery gave each record its own dispatcher turn, so the surface kept tripping its own
  ordinal-mismatch guard and forking a fresh boot, replaying the whole tree each time.
  720 cards against a settled 169 is the tree replayed about four times over. Batching
  removes the storm, which is why it is nine times faster rather than marginally smoother.

## Open Items
- **(3) The Testing pane at an ending — reported, not fixed; David's call.**
  ADR-347 shipped the ending as state and `platform-browser` consumes it: its
  `story-ending` renderer disables `command-input` and stamps `data-story-ended`. The
  testing surface is the client that was never made a consumer — zero references to
  `story-ending` in `tools/ide/web/testing-surface/src`. Its driver's only door is
  `typeCommand`, which writes into that very element without checking `disabled`, so
  every replay step past an ending lands nowhere and burns a 15 s `awaitNextTurn` /
  `awaitFence` timeout before degrading. `setInputHeld(false)` then re-enables the box the
  platform deliberately disabled. The only live route past an ending is the client's menu,
  which the driver cannot reach — so `driveFreshBoot`'s `typeCommand('restart')` is a dead
  letter. Fixing it is a design question (what a test line means past an ending) against an
  asset that ships in the Swift app too.

  against secret-letter, not fernhill, in every run above. Worth pinning for a probe.
