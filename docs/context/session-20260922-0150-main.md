## Completed

### GH #481 re-diagnosed — the x86_64 slice does not fail in the runtime
The issue recorded a silent `exit 132` as a translation-level SIGILL in JIT or ReadyToRun code, and named "disable R2R" as the probe that would distinguish Rosetta from a real Intel failure. That probe was run along with five others; the diagnosis does not hold.

- Six conditions on the same binary, `timeout 15`, `</dev/null`, 2026-09-22, all exit 132: baseline; `DOTNET_ReadyToRun=0` (bundled and unbundled); `DOTNET_TieredCompilation=0`; R2R + tiered + `DOTNET_EnableAVX=0` + `DOTNET_EnableAVX2=0`; `DOTNET_EnableHWIntrinsic=0` (bundled and unbundled); and the **unbundled `dotnet publish` output**, which `relocate.sh`, `patch-apphost.py` and `presign-payload.sh` have never touched.
- The unbundled row exonerates the whole packaging recipe. The R2R and intrinsics rows close the original hypothesis directly.
- `lldb` names the site: `EXC_BAD_INSTRUCTION` at a deliberate `ud2` in `AppKit`_NSViewValidateGeometry`, reached via `NSViewValidateRect` ← `-[NSView initWithFrame:]` ← `WebKit`-[WKWebView initWithFrame:configuration:]` ← managed frames. AppKit's abort path for a non-finite frame rect — which is also why no `.ips` is written.
- So the slice clears dyld, hostfxr, coreclr, the JIT, Avalonia startup and window creation, and dies constructing the **first `NativeWebView`**. `ShellWindow.axaml` declares three (`PlayWeb`, `TestingWeb`, `DocsWeb`), all `IsVisible="False"`.

### The controlled comparison that bounds it
- x86_64, every run: `CurrentVBLDelta returned 200000 for display 1 -- ignoring unreasonable value`, then `Bad CurrentVBLDelta for display 1 is zero. defaulting to 60Hz.`
- arm64 (`release-avalonia/arm64`, the notarized build), same machine, same display, 12 s: **stderr completely empty**, no VBLDelta lines, exit 124 at the timer (it held), `panes: loaded — play=True, docs=True, testing=True`.
- Stated as a correlation, not a causal chain: `CurrentVBLDelta` is a refresh-rate figure, not geometry. It shows the display subsystem reports nonsense to the translated process and not to the native one; it does not show that is what produces the bad rect.

### What was NOT established, deliberately
Whether real Intel hardware fails the same way. No run on an Apple Silicon machine can decide it. Two routes recorded in the issue and the plan: an Intel Mac, or a one-shot `macos-13` GitHub Actions runner (x86_64 native) — cheap and definitive, but this repository runs no macOS CI today (both workflows are `ubuntu-latest`) and standing policy is no CI gates for Sharpee. A diagnostic run is not a gate, but it is a new CI surface and David's call.
