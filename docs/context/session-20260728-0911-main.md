Four findings, three contradicting ADR-286: (1) D2's claim that the transform emits "`sharpee-*` ids for standard slots" is wrong — the default page uses unprefixed semantic ids (`menu-title`, `status-line`, `location-name`, `score-turns`, `main-window`, `text-content`, `input-area`, `command-input`); `sharpee-*` is the CLASS vocabulary plus synthesized hidden-fallback ids in `BrowserClient.adaptHostLayout` (`BrowserClient.ts:423-452`). Following D2 literally would break every existing `browser/<id>.css`. (2) `score` and `turn` are fused today into one `<span id="score-turns">`, propped up by a "score+turn composite override" with local caches at `BrowserClient.ts:344-370` — the DSL's separate boxes let that override be deleted, a simplification the DSL unlocks. (3) ADR-286 self-contradicts on `game-title`: D2 says chrome is always emitted and "not the template's business," but `game-title` is the sketch's first slot and its mount `#menu-title` lives in the title bar (chrome) per `BrowserClient.ts:131` — ADR-286's Consequences wrongly claims `game-title` has no mount. (4) The one real ambiguity in David's sketch — whether `>` in `< room-name > score | turn` binds to `score` alone or to `score | turn` — frozen provisionally as "a marker applies to every item until the next marker." Also surfaced: ADR-286's Q-5 (slot label delivery) and the score/turn split are the same change — `channels/status.ts` hardcodes the literals `Score: N` and `Turns: N`, exactly what Q-5 moves into the lang layer. Output: `docs/design/template-dsl/grammar-freeze-draft.md`, a candidate freeze written as a SEPARATE file so David's `design.md` sketch stays untouched for him to fold in or override; provisional rulings marked `##` (comments, tabs are an error, `scrolling`/`fixed` required, widths need not sum to 100, containers may nest, `time` not in v1). Two questions remain open for David: Q1 (`game-title` slot or chrome) and Q2 (unprefixed mount ids, requiring a correction to ADR-286 D2).
- **Web Extensions concept**: David clarified that `compass` in the sketch is a Compass Rose with clickable directions highlighting open exits — not a layout concern. Chasing what that needs surfaced a general capability; the concept moved through several models (standard slot → story-declared channel → html asset → Web Extension) on David's successive corrections. Settled model: a Web Extension is a governed bundle specific to the web browser client — explicitly NOT the existing engine-side platform-extension system (ADR-022/111/215/120) — consisting of (1) a channel definition with a data-element contract, (2) assets including an html component, and (3) a defined path for that component to send commands to the engine. The author creates the channel and supplies the assets; the platform ships the mechanism, not any given extension. Rulings recorded: shareable at the author's discretion; live in the workspace at `~/Documents/Chord/web-extensions/` (the ADR-280 Phase 1 `StoryHome` root) where every story sees them but inclusion stays explicit; Chord Writer gets a dedicated surface plus Add Web Extension and story Export/Import; packaged as a single distributable file, explicitly NOT npm (ADR-279 just sealed a Node toolchain so writers never meet one); a hosted "blessed" repository with security-reviewed extensions is a plausible future, since HTML assets are not meaningfully sandboxable inside a published story and curation is the available lever. Output: `docs/work/web-extensions/concept.md`, marked "captured, not designed — not to be implemented from"; six open questions recorded rather than answered, the two highest-leverage being (a) whether html components are literally W3C custom elements — which decides whether a binding contract exists at all, and collides with ADR-170's framework-free commitment — and (b) that stories created outside the project home would see no extensions, since ADR-280 Phase 1 deliberately kept "Choose Location…" and David's own story lives in `~/repos/ifstories/`.

## Key Decisions

### 1. ADR-286 does not go first
David asked whether ADR-286 (Web Template layout DSL) should be implemented before ADR-280. Answer: no — ADR-286's spec (`docs/design/template-dsl/design.md`) is a 36-line sketch, not a frozen grammar, and its Q-5 (slot label delivery) is unresolved and blocks part of D1/D2. Recorded as a prerequisite: ADR-286 needs a grammar-freeze design session with David before any implementation.

### 2. Plan carved into 4 phases to unblock Phase 1 immediately
plan-review surfaced a real CONTRADICTION: `sharpee init`'s Chord path writes `package.json` (`packages/devkit/src/standalone/init.ts:178-181`), the exact divergence ADR-258 D2 names as something that must not happen. Rather than block all work on resolving this in devkit, David asked to carve out the default-folder work (D2) as its own phase — it touches no `packages/` code and doesn't depend on D3/D4 or ADR-286. The planner's original 3-phase plan was amended to 4, inserting the new Phase 1 and renumbering the rest.

### 3. No-group-if-empty vs. always-show-six-groups
Ruled (mine, flagged to David and accepted): a project with nothing on disk for an artifact type shows no row for that type, rather than an empty placeholder row. Phase 3's seed will make new projects show all six regardless; this only affects pre-existing projects like fernhill.

### 4. Collapsed-by-default sidebar groups (David's ruling)
The first draft opened every group. David's review of the fernhill screenshot showed 17 transcript tests pushing Assets/Web Template/Other off-screen, so the sidebar now opens with every group collapsed except Story. Pinned by test, plus a second test proving a collapsed group still holds its members and reveals them on expand.

### 5. ADR-286 grammar freeze written as a separate draft, not merged into `design.md`
Kept `grammar-freeze-draft.md` distinct from David's own sketch so he can fold in or override each ruling individually, rather than handing him back a rewritten source file with edits buried inside it.

### 6. Web Extensions are web-client-specific, and explicitly not the engine-side platform-extension system
Disambiguated from ADR-022/111/215/120's platform extensions on first mention, to avoid the name collision propagating into a future ADR. Distribution is a single file, never npm — consistent with ADR-279's just-sealed no-toolchain-for-writers stance.

### 7. ADR-288 superseded in place rather than deleted or rewritten
David's Web Extensions rulings (author-supplied channel/assets) directly contradict ADR-288's D1/D5 (platform-shipped `exits` channel and default rose). Rather than delete the file or silently rewrite it, it stays on disk marked SUPERSEDED IN PLACE — do not implement, preserving the verified Context-section groundwork (direction constants, `InputManager.onCommand`'s single caller) and the D3 ruling likely to carry forward, for whatever ADR replaces it.
