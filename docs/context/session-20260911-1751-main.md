### The blocker: **`repokit` does not run on Windows**

`repokit` shells out with `execFileSync('pnpm', …)` — `tools/repokit/src/commands/build.ts:218`, the same pattern at `clean.ts:74`, and `execFileSync('npx', …)` at `bundle.ts:46`. On macOS `pnpm` is a plain executable and resolves. **On Windows it is `pnpm.CMD`, and `execFileSync` without `shell: true` does not try `.CMD`/`.EXE`** — so it fails `ENOENT` although pnpm is installed and on PATH. Same root cause as the bin-shim warnings `pnpm install` emitted for `sharpee` and `repokit`.

The platform itself is fine: `tsf build` proves every package compiles on this machine. **It is repokit's own subprocess layer that is macOS-shaped.**

**Not fixed, deliberately** — CLAUDE.md says report a build failure and wait, and `tools/repokit` is platform tooling, where a change wants discussing rather than improvising to unblock a docs commit.

**This is bigger than today's commit and belongs to ADR-341.** D8's order has real Windows work ahead — ADR-182, the D5 generator, the D3 host contract, then the shell — and the in-repo build CLI cannot run on the Windows box. It warrants an issue and probably a parity-table row.

**Three ways to clear it, for tomorrow**: commit from the Mac (its tree is built and the gate passes) and file the defect; fix repokit's spawn calls (`shell: true`, or resolve `pnpm.CMD` on Windows — small and well-understood, but a platform-tooling change needing David's go-ahead); or bypass the gate with a commit-message line recording that no TypeScript was touched and the tree is a cold clone.
