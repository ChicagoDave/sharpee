## Key Decisions

### 1. Bundle the toolchain in the DMG (ADR-279 D4, amended)
Requiring a global `@sharpee/devkit` npm install before Cmd-B works loses first-time authors at minute one; a ~50-80MB heavier DMG loses no one. Directly motivated by David's own reproduction of the failure.

### 2. Chord Writer stays in-repo at `tools/ide/` (ADR-279 D5, new)
The IDE's contract surface with the platform (compose JSON, build/test CLI, version pairing) is still actively evolving; co-location keeps contract and consumer changes in one commit. Extraction is cheap later if the license or contributor base diverges.

### 3. Full Sparkle 2 auto-update from v1, not a stopgap (ADR-279 D7, new)
David's explicit ruling overriding Claude's more conservative default — bundling (D4) means an author on an old app is also on an old toolchain, so silent-update reach matters from the first release.

### 4. Distribution: GitHub Releases + sharpee.net front door (ADR-279 D6, new)
Zero-VPS-cost versioned artifact hosting via tagged Releases (`chord-writer-v*`), with sharpee.net presenting a product download page rather than a raw GitHub UI.

See `docs/architecture/adrs/adr-279-chord-writer-packaging.md` for full text of D1-D7, the corrected Context, and the reworked Acceptance/Implementation-touchpoints sections.

### Post-acceptance: basic-features discussion → seven new DRAFT ADRs
- After ADR-279 landed, David raised the "basic features to think through before implementing ADR-279" list: onboarding (a new story appears in the project list but isn't auto-opened), embedded searchable help, replacing the raw file-list sidebar with a typed artifact view, a default project folder (`~/Documents/Chord`), and the artifact set a project scaffold should contain — story + seeded walkthrough/transcript-test folders + assets + a customizable "Web Template" (`index.html`).
- **Rulings surfaced in conversation** (not yet formal ADR decisions until each ADR's interview runs, but directional): scaffolds are seeded with real starter content, not empty folders; the artifact view stays an *open* view — unknown/foreign files remain visible rather than hidden; the help corpus is the existing book plus the Chord reference docs, embedded rather than linked out; `sharpee init` (already in devkit) is the correct owner of scaffolding, not new IDE-side logic.
- **Play-to-test design** (ADR-282): modeled on Inform 7's Skein/testing workflow but deliberately simplified per David's steer. While playing, each turn gets a per-command verdict — correct / incorrect / untagged. A correct verdict becomes an `[OK]` assertion on the transcript line; untagged stays a bare command with no assertion; incorrect becomes a new *negative* assertion (David's "option 1" ruling) — the transcript line is authored to fail as long as the bad response persists, and flips to passing automatically once the story's behavior changes to match.
- **Fact-finding that grounded the seven ADRs**:
  - `sharpee init` already exists in devkit and is Chord-first in its templates — confirmed before writing ADR-280/284, so those ADRs assign scaffolding ownership to the existing command rather than proposing new machinery.
  - Transcript grammar surveyed directly in `packages/transcript-tester/src/parser.ts` — existing assertion vocabulary (`[OK: contains]`, `[ENSURES]`, `[WHILE]`, etc.) mapped before designing ADR-282/283's new tag forms.
  - Media pipeline verified end-to-end already complete: ADR-216 (ACCEPTED) defines `sound|image|music` story primitives and `play`/`show` sugar that emit `media.*` events; `platform-browser`'s `channels/image.ts` and `channels/audio.ts` already render them. This means ADR-285 (asset management) needs **no platform work** — it only needs IDE-side asset browsing/import UI.
  - Third-party embeddable web/HTML editor health checked per the standing "verify before recommending" rule (ADR-286): Pinegrow 9.3 (June 2026 release, actively maintained, edits files in place — fits the file-based project model) and GrapesJS (BSD-3, v0.22.16, actively maintained) both came back healthy; Webflow-class SaaS editors were rejected outright because they have no round-trip back to a plain `index.html` file.

### 5. Scaffolding ownership stays with devkit's `sharpee init` (ADR-280/284)
Rather than inventing IDE-side project-creation logic, both the project-model and publishing ADRs anchor on the already-existing, already-Chord-first `sharpee init` command — extending it beats duplicating it.

### 6. Seeded scaffolds, open artifact view (ADR-280)
New projects get real starter content (story + seeded walkthrough/transcript-test folders + assets + Web Template), not empty folders; the artifact-typed sidebar view still shows unknown/foreign files rather than hiding anything the typed view doesn't recognize — avoids the IDE becoming a walled garden around its own conventions.

### 7. Play-to-test negative-assertion semantics, option 1 (ADR-282)
An incorrect verdict during play becomes a new assertion written to fail while the bad behavior persists and pass once the story is fixed — David's explicit choice, keeping the regression signal live rather than requiring a manual second pass to correct the assertion after a fix.

### 8. ADR-285 needs no platform work
Verified the media pipeline (ADR-216, ACCEPTED) already provides `sound|image|music` primitives and channel rendering end-to-end; asset management in the IDE is pure UI atop an already-complete platform capability, not a new platform feature.
