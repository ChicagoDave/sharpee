- **The BLOCKER.** The "~90 seconds" figure sat in a section titled *measured, not
  assumed* and was `3,854 ÷ 42` extrapolated from a rate. Context now separates observed
  from derived: observed are the main line's 75 records in 1.8 s, the ≈42 records/s
  arrival rate, and one eager replay **cut off unfinished at 240 s**; derived is the ~90 s,
  labelled as such. **No complete eager replay has ever been observed to completion in
  either head**, and the 240 s run puts the real figure above the estimate, not below it.
  A clean figure is now unobtainable — D1 shipped and the eager walk is deleted — and
  nothing rests on it: D1/D3 are decided by 1.8 s for one line against 6 s for the whole
  tree through the CLI, both observed.
- **Two further instances of the same defect, found while sweeping.** D3's "roughly
  fifteen times the speed" now rests on two observed rates (≈640/s CLI against ≈42/s pane)
  rather than on the corrected estimate, and an unsourced "8× slower" in the Consequences
  is replaced by the two measured tree sizes.
- **Acceptance Criteria section added** — eight criteria, each graded SELF-VERIFYING or
  PREMISE-DEPENDENT, with a stated end-to-end scenario. This also carries the missing test
  requirements.
- **D4a's signature.** `armForkLineage(parentLineage, forkOrdinal)` arms the *next*
  restart fence rather than adding a second increment, since a restore rides an in-page
  reboot and passes through `emitRestartEvent`'s existing `playLineage + 1`. Rejected
  alternative recorded: re-reading the global per call, which turns a once-per-page read
  into ambient state.
- **D4c — the restore door, named.** It already exists and needs no platform change: the
  client restores an autosave at boot (`BrowserClient.ts:606-628`, `autoSave` defaults
  true), so the pane writes the image into `<storagePrefix>save-autosave` between
  `driveFreshBoot`'s `localStorage.clear()` and its `restart`, and the client does the
  rest. An image is the compressed `BrowserSaveEnvelope` the client wrote itself — a
  string copy out and back, no serializer in the pane. Rejected: driving the restore
  dialog, which is the player's door and writes a transcript line belonging to no test.
- **D8 names who flips what.** Phase 17 needs no further action; Phase 16's remaining
  deliverable is a ruling only David gives, and no session may close it by inferring the

### Perf measurement that became a defect report
David authorized perf measurement with no further permission needed. Added
`MeasureBranchVisitAsync` to `ShellWindow.axaml.cs` and ran the Avalonia head from source
(`dotnet run --project PaneHost/PaneHost.csproj -- --app-exit-state <secret-letter.story>`)
against the rebuilt testing-surface bundle. **Finding: a branch visit FAILS.**
`driveFreshBoot` reports "no boot look in 15s" after 15.1s, deterministic across six runs;
the branch's own steps never run. `driveFreshBoot` is shared by visit/branch/
delete-realign/tail-cut, so all four are affected; the main line's boot replay is
unaffected because `replayTree` types it directly. Ruled out by direct test: the reboot
path (an author-typed restart reboots fine, 77 records), `localStorage.clear()` as the
cause, the held input swallowing the typed restart (`InputManager`'s keydown listener and
`handleSubmit` never check `disabled`), a waiting confirmation dialog (`dialogsOpen` 0), a
thrown error (`unhandledrejection` + `console.error` hooks caught nothing), and the host
dropping records after `forkBoot` (the Avalonia host does not implement `forkBoot` at all —
the only occurrence of the string in `PaneHost/` is a comment). **Unresolved anomaly**:
with `SHARPEE_IDE_LOG_EVERY_RECORD=1` there are ZERO `turnEvents` between the click and
the failure, yet `awaitFence` clearly succeeded (the failure is "no boot look", not "no
restart fence", at 15.05s not 30s). Either the surface resolves its fence waiter without a
real fence, or records reach the page by a path that does not pass through
`OnPaneMessage`. Two earlier instrument versions were wrong in instructive ways (100ms
polling of `disabled` missed the window; a `MutationObserver` caught a re-render freeing
the input 25ms in) — only the driver's own trace is trustworthy. Filed as issue #496; see
Open Items.

## Key Decisions

### 1. The honest correction beat manufacturing the measurement
Reproducing a full eager replay would mean reverting shipped code to time a behavior the
ADR exists to remove. Labelling the derived number as derived, and stating the observed
floor beside it, is stronger than the false precision it replaces — and the decision never
rested on it.

### 2. D4a is a platform change and the Scope line said otherwise
Stamping a lineage mid-page means a new export in `packages/platform-browser`, because
`ensureLineage()` caches once per page by design. That correction is the one thing keeping
ADR-353 DRAFT. The restore door, by contrast, needs no platform change at all.

### 3. A test gap that cannot be closed where the code lives is a structural finding
AC-4 had no mechanical backing because `main.ts` exports nothing. The answer was to move
the rule, not to loosen the criterion — the same move `ProjectPaneLayout.cs` made last
session.

### 4. A failing measurement is a defect report, not a discarded run
Six deterministic failures at 15.1s, with five plausible causes ruled out by direct test
and one anomaly (zero recorded turnEvents against a fence that evidently succeeded) left
genuinely unresolved, was written up and filed rather than left as an unexplained gap in
the perf numbers. The honest state is "broken and not yet understood," not a number.

### 5. Probe corruption gets a repair and a defect, not a quiet fix
The polluted `secret-letter.tests.json` was restored with `git checkout` immediately on
discovery, and the fact that `--app-exit-state` mutates a real story's test tree was
written up as its own defect (issue #497) rather than folded silently into "lessons
learned" — the next person to run this probe needs to know before they point it at real
data again.

### 6. Stop implementation pending David's ruling on intent and factoring
The Outline column and its naming rule are both built against the assumption that the
document's current shape (one card per full playthrough) is the shape to work with.
David's own read of the outline shows that assumption is questionable. Continuing to
refine naming or add factoring before he rules on `intent`/prefix-factoring risks
building on a foundation that gets replaced.
