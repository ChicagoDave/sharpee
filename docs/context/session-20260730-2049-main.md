### #201 fix — `tools/repokit/src/consumer-gen.ts`
`generateConsumer` (local mode) gave the story's runtime deps full closure treatment but
packed `@sharpee/transcript-tester` as a bare single tarball. Since a `file:` tarball
resolves none of its own `@sharpee` deps, anything TT needed that the runtime closure
missed fell through to the public registry.

- **Dev closure vendored**: TT now gets the same `computeClosure` walk as the runtime seed.
  Whatever it reaches beyond the runtime closure is written to `devDependencies` — not
  `dependencies`, which would overstate the story's runtime surface in a file meant to model
  a real author project. (`file:` refs dedupe across both sections, so resolution is
  unaffected.) One of the two judgement calls #201 flagged.
- **`pack()` memoized**: a package reachable from both closures is packed once. The other
  flagged judgement call.
- **New guard `assertVendoredClosureComplete()`**: every `@sharpee` dep declared by a
  vendored package must itself be vendored, checked *before* any packing, throwing an error
  naming both the missing package and its requirer. Turns a silent registry fallthrough (an
  `npm install` ETARGET much later) into a named generation-time failure. Verified against
  the real staging graph first — zero gaps today, so this is a guard, not a behavior change.
- **New `declaredSharpeeDeps()`**: declared `@sharpee` deps including unstaged ones;
  `stagingDepsOf()` is now its filtered form.
- **`GenerateConsumerResult.devClosure`** added and logged by `test-npm.ts`, so dev-only
  vendoring is visible in the run output rather than silent.

Tests: `pnpm --filter '@sharpee/repokit' test consumer-gen` → **17 passing** (was 11).
Six added, derived from the Behavior Statement. The local-mode generation test is real-path
(rule 13a): it drives the production `npm pack` subprocess against a fixture staging tree,
no stub, and asserts every `file:` ref resolves to a tarball on disk.

Ruled out as causes (David asked directly):
- **npm upgrade** — this host is npm 11.11.0; the container is 12.0.1 (the source of #199,

- **tsf staleness** — `pnpm exec tsf` resolves to published `@davidcornelson/tsf@1.0.3`,
  which carries its own npm 12 pack fix. The `/Users/david/repos/tsf` working copy's `dist`

- **plover** — hosts sharpee.net behind Apache; never reads this host's `~/.tsf-publish`.

**Reconciles a contradiction in #201.** The issue claimed staging had 4.3.0; this host has
3.6.0. Both are true: the container keeps its **own** `~/.tsf-publish` tree, staged
independently. `test:npm --local` therefore gives different answers per environment — worth
knowing beyond today's fix.

**Publishing is unaffected.** `.github/workflows/publish-npm.yml` checks out clean and runs
`pnpm install` → `./repokit build --no-genai` → `tsf build --npm` from scratch with npm

## Second finding — the published `transcript-test` bin never wired ext-testing

Staging rebuilt to a uniform 4.3.0; `npm install` then succeeded, closing Phase 1's
second exit clause. The consumer ran the full suite for the first time ever:
**111 passing, 5 failures**. The same 5 passed in-repo against a verified-current
bundle, so the divergence was real.

Root cause: two paths run transcripts and only one passed the extension.

| path | call site | wired? |
| --- | --- | --- |
| in-repo bundle (`dist/cli/sharpee.js --test`) | `scripts/bundle-entry.js:726` | yes |
| published bin (`npx transcript-test`) | `packages/transcript-tester/src/cli.ts:353` | **no** |

`runner.ts` handled the missing extension by skipping the `$command` and continuing,
with the warning gated behind `verbose` — which `test:npm` does not pass. So
`$teleport`/`$restore`/`$take`/`$state` were complete no-ops with no error, no output
line, and no non-zero exit, for every author installing from npm. Not a regression:
that call site last changed 2026-07-02 (`4b75e230`). It was simply unreachable until
#201 let `test:npm --local` get past install.

The silence also explains why 3 of dungeo's 8 `$command` transcripts passed anyway —
`save-restore-basic` and `interceptor-save-restore` never assert on the effect, so they
were green over a no-op.

**Fix**: `cli.ts` passes `testingExtension` from the `LoadedGame` that `story-loader.ts:36`
already returns; `runner.ts`'s missing-extension branch returns a named error instead of
skipping. Result: **5 failures → 2**.

**Known incompleteness of that second change**: `runner.ts:289` only records a directive
error as a failure when `stopOnFailure` is set. The new error is therefore still silent in
a default run — the wiring fix is what actually resolved this. Making directive errors
always count is a change to shared error semantics across all directive types and was
deliberately not folded in.

## Third finding — two transcripts depend on gitignored walkthrough output

The 2 remaining consumer failures (`frigid-river-restore`, `rank-survives-ceiling-change`)
restore `wt-06`/`wt-13` from `stories/dungeo/saves/` — gitignored
(`stories/dungeo/.gitignore:1`), 19 files, none tracked. `test:npm` copies `src` and
`transcripts`, not `saves/`. Verified every file is regenerable before deleting: `wt-01`..
`wt-17` are each written by their own walkthrough's `$save`, and `ac9-checkpoint` /
`test-checkpoint-1` are `$save`-then-`$restore` within a single transcript.

Deleted at David's instruction. The walkthrough chain is a **save/restore relay** — each
`wt-NN` opens with `$restore wt-(NN-1)` — and the run immediately after deletion failed 886
of 11168 tests.

**That correlation was not causation, and this summary originally recorded it wrongly.** The
relay self-bootstraps: `wt-02`'s `$restore wt-01` runs *after* `wt-01`'s `$save wt-01` in the
same invocation, so an empty `saves/` costs nothing. Verified by deleting `saves/` a second
time and re-running from empty: **871/871 clean**. David flagged this — the chain has worked
this way for months.

The 886 failures were an RNG excursion in thief combat, matching the project's standing rule
to re-run flakey walkthroughs before blaming a code change. Corroborating detail: passing
runs report *different* test counts (902, then 871) because combat retry blocks expand
differently per run; the bad run's 11168 was that same mechanism running away.

Structural conclusion: those 2 transcripts cannot pass in the npm consumer as it is
built. The consumer would have to run the walkthrough relay first, or exclude them.
114/116 is the honest passing bar for `test:npm --local`.
