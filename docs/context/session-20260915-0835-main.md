## Key Decisions

### 1. `renderStatusLine` is not a reader of this payload
ADR-349's Consequences and Scope line call
`packages/channel-service/src/render-to-string.ts` "the second status-rendering
path". It is not one for the `location` channel: it filters `ITextBlock`s for the
key `status.room` (`render-to-string.ts:269`), and no in-repo producer emits that
key — the only mentions are its own tests and `text-blocks`'s constant table. It
is a published API over a block shape, not a second consumer of the channel, so
the payload cutover does not reach it. No edit was invented for it; the ADR owes
a correction.

### 2. A third writer to the status-location element, found in platform-browser
`BrowserClient.updateStatusLine` pushed `SaveManager.getCurrentLocation()` — the
player's containing-entity name — into the same `statusLocation` element
`createLocationChannelRenderer` owns under ADR-165, on save, restore, and state
change. Left alone it would overwrite the composed heading with a raw entity name
on the next restore. `updateStatusLine` now refreshes score and turns only;
`getCurrentLocation` keeps its other job, naming save slots, where the entity name
is the right answer. `BrowserClient.ts` is outside ADR-349's Scope line — David's
call whether the Scope grows or the change is reverted.

`mutation-verification` found this change untested and it was right: no test
referenced `updateStatusLine`, and reinstating the old call would have gone
unnoticed. Closed with a sixth case in
`packages/platform-browser/tests/shadow-renderer.test.ts` — a real
`channel:packet` writes the composed heading, then a status-line refresh runs
against a world that CAN answer `getCurrentLocation()`, and the element still
reads the heading. Probed: reinstating `statusLine.update(location, …)` fails
that test alone; platform-browser is 159 passing with it.

### 3a. The distinct `TextContent` variant paid for itself immediately
Declaring `IChosen` as a third variant rather than a flag on `IDecoration`
meant the type checker caught `channel-service`'s renderer unaided — it did
not handle the new shape and failed to compile until updated. A boolean field
bolted onto `IDecoration` would have compiled silently wrong; the type-level
separation turned a latent rendering bug into a build failure at the point of
introduction.

### 3b. `extractPlainText` was not a drop-in for the 23 broken projections
Fixing the two-member-union assumption (`typeof c === 'string' ? c : …`)
scattered across 23 lang-en-us test files — 30 tests went red at once when the
third variant appeared — could not reuse the package's existing
`extractPlainText` helper, because that helper drops a decoration's inner text
where those inline projections keep it. A new shared helper,
`tests/test-utils/flatten.ts`, was written instead and centralizes the
projection all 23 files now share.

### 3c. A whitespace-authority discovery Phase 3 must act on
The whitespace authority trims only the *final* non-verbatim run, so a stable
span keeps its trailing space when a chosen run follows it and loses it when
none does — `"A tidy kitchen. "` with the NPC present, `"A tidy kitchen."`
without. Phase 3's stable-span reader must trim before building a `contains`
claim, or AC-8's "the same room with no NPC present pins the same claim" fails
on a single space. Pinned as an assertion in `chosen-provenance.test.ts` so
it's a recorded fact rather than a surprise for Phase 3.

### 4. The channel's D16a fallback resolves through `getDescribableLocation`
Not `getContainingRoom`, which is what the channel used before. D7 says an
un-authored world "renders exactly as it does today", but D4a forbids the
resolver that produced today's answer, and the two only conflict for a player
inside an opaque vehicle — precisely GH #468. The fallback follows D4a; the
divergence it removes is the bug the ADR names.

**What writing ADR-353's Context turned up**, all verified against source: `mode`
is doing three unrelated jobs at once (accumulation, mid-session replay, and the
client obligation it implies), with `emit` a fourth axis crossed over them, and no
channel can set them separately. `replace` already means two different things — a
live varying value (`score`, `location`) and a boot-time constant (`ifid`, `info`,

which have *opposite* answers under ADR-349 D14 and are indistinguishable on the

an Element may have both a current value and an occurrence stream, with the client
choosing — which is what the DOM does, and would make ADR-349's two channels the
intended shape rather than drift.

### ADR-353 interview — D1, D2, D3 settled
`ADR-353` opened as the question, then three decisions landed in the interview.

**D1** — every Element has two readings, state and occurrence, and one mechanical
test decides which are populated: *does the thing exist between turns?* World facts
(exists, in the fiction) carry both; session facts (exists, machinery or packaging)
carry state only; narration (does not exist between turns) carries occurrence only.
Reached by sweeping known IF output — Infocom status lines, Inform room
presentation, the standard meta verbs, and Sharpee's twenty-one channels — rather
than by argument. No case resisted, including the one expected to (time of day in
*Deadline*: state in the header, occurrence when the clock strikes). This resolved
the "one cardinality or two" question and dissolved the override question that made
it seminal.

**D2** — the four missing state readings get built: room contents, exits, inventory,
and the location description, each deriving both readings from one function
(ADR-349 D3 generalized). Three are cheap projections; the description is computed
through the phrase pipeline and its change-detection is the one unsolved piece.

**D3** — a preference command is a viewer's choice about whether an Element's
occurrence reading is rendered, so VERBOSE/BRIEF/SUPERBRIEF/NOTIFY belong to the
client. The pattern was already in the repo under its own heading
(`meta-registry.ts:42-47`, "Preference commands"), and the registry's header says
meta-commands never incremented turns — so the turn-accounting objection raised
against moving them was wrong. The feature turns out to be declared, categorized,
and unimplemented: `game-meta` has `verboseMode`, `looking-data.ts` hardcodes
`verboseMode = true` twice under a TODO (`:100-101`, `:347-348`), and
`room_description_brief` in `lang-en-us/src/actions/looking.ts:24` is unreachable.
D2 supplies what those TODOs were waiting for.

Seven acceptance criteria written. Five open questions remain, none blocking the
others; **ADR-353 Q-4** (which state readings are stable enough to auto-pin) is what
discharges ADR-349 AC-11.

### ADR-353 completed and reviewed — D1 through D10
Seven more decisions landed after D1-D3, all through the interview:

- **D4/D5** — a value is auto-pinnable exactly where its realization made no
  state-dependent choice, tracked **per run** so the stable segments pin and the
  chosen ones skip; identity claims are the complement, not a substitute. Reached
  by sweeping auto-assertion scenarios. **Four of the five unsafe cases predate
  ADR-349** — a spliced snippet, a state-derived detail clause, an occupant
  clause, a `Choice` — so D14 was a special case of a defect already shipping.
- **D6** — viewer preferences are one state Element, a record. One Element rather
  than one per preference, because ADR-352 D4 has clients ignore Elements they do
  not know, so per-preference Elements would make each new one invisible.
- **D7** — the description's state reading detects change by evaluating its
  registered predicates, never by realizing its tree: realization is not
  side-effect-free (`Choice` advances a `textState` counter — the assembler's one
  declared realize-time mutation), so recompute-and-compare would burn a story's
  cycling variants on turns nobody looked.
- **D8** — undo re-runs rather than restoring a snapshot, which ADR-293's
  determinism makes available.
- **D9** — the turn packet splits into `state` and `occurred`, keyed by **Element
  id**. The three one-fact-two-channel pairs collapse.
- **D10** — a story declares presentation by name and a client may honour it,
  extending ADR-174's decoration discipline from appearance to behaviour;
  unrecognized names are ignored **and reported as console warnings** (David's
  amendment, folded into ADR-352 D4 as well).

**`adr-review` in multi-ADR mode over 349/352/353 found one blocker at a seam
neither decision showed alone.** D8's replay re-runs commands from history; meta
commands are deliberately not in history, so a typed VERBOSE would never be
re-applied and an undo would silently revert the display mode — which AC-13 had
*required* in its original wording. D8 now scopes replay to world facts, AC-13 is
scoped with it, and AC-17 tests the seam. Six smaller findings folded: ADR-353's
Scope line, ADR-163's supersession owner and flip trigger, D7's cache lifecycle,
the Open Questions section's format (the contract requires deletion, not "answered"
entries), ADR-349's stale Status line, and a **laundered citation** — ADR-349
described ADR-289 D6 twice as "exits are a room-block line" when D6 gates exits to
rooms at compile time, and ADR-353 inherited it without opening the source.
Checking also turned up that exits and inventory are emitted as no Element at all,
in either reading, which is stronger evidence for D2 than the false version was.
