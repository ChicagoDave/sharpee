Fixed by adding step 4.5: a Node-based lexical path scan (`path.resolve` clamps `..` at `/` exactly as the kernel does, so dangling links are classified rather than silently skipped) run against `.incoming`, pruning escaping links only when a sealed replacement is provably present and hard-failing otherwise, then re-scanning to assert zero escaping and zero dangling links. Two shell-correctness fixes landed in the same edit: a herestring instead of a pipe (a piped `while` runs in a subshell where `die` would exit only the subshell, letting the swap proceed with a leaky seal) and `IFS=$'\t'`. ### 5. Two notarization blockers found by inspecting the actual signing surface
- The vendored node ships Developer-ID-signed by Node.js Foundation *with* `com.apple.security.get-task-allow`, a debug entitlement Apple's notary service rejects outright. Fix: re-sign with David's identity and a curated entitlement set (allow-jit, allow-unsigned-executable-memory, disable-library-validation, allow-dyld-environment-variables, disable-executable-page-protection) minus `get-task-allow` — hence `bundled-node.entitlements`.
- The bundled esbuild ships `adhoc,linker-signed` with no team identifier, which never passes notarization. Fix: re-signed with Developer ID + hardened runtime. Binaries needing this treatment are discovered via a Mach-O scan rather than hardcoded, since the closure's native binaries change with the dependency graph.

### 6. Two real defects caught by the `--no-notarize` rehearsal
- `grep -q` inside a `set -o pipefail` pipeline inverts its own assertion: it exits at the first match, SIGPIPEs the `codesign` feeding it, and the pipeline reports failure exactly when the match succeeds. The hardened-runtime check fired on a correctly-signed app; worse, the `get-task-allow` check would have stayed silent in the one case it exists to catch. Rewritten to capture output first and match against the captured string, with an `assert_hardened` helper and an added positive assertion that `allow-jit` IS present (an empty entitlement set means the signature never took).
- macOS ships bash 3.2, which has no `mapfile`. Because it is a builtin, `bash -n` accepts the script and it fails only at runtime. Replaced with a bash-3.2-compatible `while read` + process substitution.

### 7. Deliberate deviation from the plan's stated Phase 3 deliverable
The plan specified that `project.yml` gain a Release signing config. This was deliberately NOT added — all signing happens in `package.sh` instead. Reason: the toolchain lands in `Contents/Resources` via a post-build script, so its binaries are Resources to Xcode and nothing in the target signs them, and node needs its own entitlement set. Since the app signature seals its resources by hash, every nested binary must be final before the outer signature is applied; one script owning that order is verifiable, splitting it between Xcode and `package.sh` is not. `project.yml` is therefore unchanged and the Swift suite is unaffected.

## Key Decisions

### 1. App Store Connect Team Key over Apple ID + app-specific password
Not tied to the Apple ID password, no 2FA prompt mid-build, independently revocable, and team-scoped so it covers anything shipped under the team, not just Chord Writer.

### 2. Seal enforcement via lexical path scan, not a runtime existence check
`path.resolve`-based clamping at `/` classifies dangling vs. escaping links the same way the kernel would; a scan against `.incoming` (the only tree at true final depth) avoids the false-pass that sandbox directory depth produced in the original AC6 result.

### 3. Node/esbuild re-signed rather than shipped as vendored
The notary service rejects `get-task-allow` outright and never passes an unteamed ad-hoc signature; re-signing with a curated entitlement set (node) and Developer ID + hardened runtime (esbuild) is the only path to a notarizable bundle. Native binaries are discovered via Mach-O scan so the fix survives dependency-graph changes.

### 4. `project.yml` left unchanged — signing centralized in `package.sh`
The vendored toolchain is a post-build Resource, not an Xcode-signed target, and the outer app signature seals nested resources by hash — every nested binary must be final before the outer signature applies. One script owning that ordering is verifiable; splitting the responsibility between Xcode and a script is not. This is arguably a packaging-boundary decision a future session could re-litigate — flagged as an ADR candidate, not written up formally this session (rule 11 judgment call left to the user).
