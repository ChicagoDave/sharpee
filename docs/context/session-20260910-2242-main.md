### GH #410 filed and fixed — engine tests ran on the wall clock (uncommitted, about to be pushed with ADR-346)
- David's correction is what reopened the "flake" from the ADR-346 evidence sweep: *"there shouldn't be rng flake issues anymore - we seed tests so they're deterministic."* That intent was real but enforced nowhere, so the single failure was a genuine determinism hole, not noise — filed and diagnosed as **GH #410**.
- **Diagnosis**: `packages/engine/src/game-engine.ts:485` resolves `this.masterSeed = this.config.seed ?? Date.now()`. That is the right production default and a silent trapdoor in tests — a test injecting no seed runs on the wall clock, nothing fails, and the omission is invisible until the dice land differently. `action-rng-determinism.test.ts` — the test whose entire subject is post-restore roll determinism — booted through `setupTestEngine()` with no config, so every engine in it ran on `Date.now()`.
- **Mechanism**: the restored engine is a fresh engine with its own clock-derived master seed. Points that already drew before the save restore exactly from `streamStates` and match. A point that had NOT drawn reseeds from `deriveStreamSeed(masterSeed, name)` — the new engine's different master seed. Whether the post-restore commands reach such a point depends on earlier rolls, which depend on the clock. Most runs don't; one did.
- **Scale measured**: 108 engine test files, only 2 pinning a seed, 26 calling `setupTestEngine()` with no config, 5 of those touching random/rng/roll/chance (`action-rng-determinism`, `platform-operations`, `engine-master-seed`, `on-world-restored`, `unit/platform-dispatcher`).
- **Changes (3 files, all under `packages/engine/tests`, uncommitted)**:
  - `test-helpers/setup-test-engine.ts` — injects `seed: TEST_MASTER_SEED` (`20260911`, exported) by default; a caller's own `config.seed` still wins; new `unseeded: true` option is the explicit opt-out. Retroactively covers all 26 files.
  - `engine-master-seed.test.ts` — the single opt-out caller: "still resolves a master seed without config.seed (clock, read once)" now passes `unseeded: true`, so the one test whose subject IS the production fallback declares it instead of being indistinguishable from an oversight.
  - `action-rng-determinism.test.ts` — pins its own `THROW_RNG_SEED = 20260911` rather than leaning on the helper default, since every claim in that file is about seeds.

## Key Decisions

### 1. "Tabled" is a third disposition, distinct from rule 18b's "still live"
Rule 18b's "still live" stamp is for interruptions with a returning pointer (another plan takes `.current-plan` temporarily, this one resumes). The secret-letter-port went on hold indefinitely on 2026-09-09 with no returning pointer — there is nothing to point back to it — so the plan-staleness sweep was re-prompting a disposition David had already made. Tabling records the pause inline (a `**Tabled**` header, phases DEFERRED with their entry state preserved) without pretending the plan is either still actively worked or terminal.

### 2. Per-package `tsc -p <pkg> --noEmit` over `tsc -b` for the typecheck gate
`tsc -b` (project references build mode) was the more "correct" TS idiom but the session found `tsc -p <composite-tsconfig> --noEmit` now works cleanly on TS 5.9.3 (the TS6304 failure that used to force `-b` is gone), so the gate could be wired per-package through turbo's own dependency graph (`dependsOn: ["^build"]`) instead of restructuring 42 tsconfigs for a `-b` graph. Falsification probes in `core`, `bridge`, and `stories/dungeo` confirm each package's own compiler surfaces errors independently.

### 3. Ambiguous evidence (bridge/runtime) is filed as a question, not resolved by inference
`packages/bridge` and `packages/runtime` show two contradictory signals — zero consumers anywhere in the repo, yet ongoing mechanical edit activity. Rather than guess at intent (dormant vestige vs. active prep for an unlanded consumer) and either wire them into `PLATFORM_PACKAGES` or flag them for removal, the session filed GH #409 and left the packages exactly as found. This follows the project's standing pattern that content and direction calls on ambiguous repo state are David's, not inferred.

### 4. GH #401 is a ratchet, not a one-shot fix — 1,500 errors stay OPEN by design
With 1,500 real test-file type errors and 589 of them (39%) traceable to one fixable-but-mechanical pattern (`ITrait` excess-property checks on object-literal `add()` calls), fixing all of it in one session either meant a bulk scripted rewrite across stdlib and world-model without review, or stopping short of the stated goal. Neither was right: the session built the enforcement mechanism (per-package `tsconfig.test.json` + `typecheck:tests` turbo task) and the ratchet (a clean package's gating `typecheck` script grows the test leg, so regressions in already-clean packages are caught immediately), fixed the 15 errors that were real drift rather than the cluster pattern, and left the issue open with the corpus measured and characterized. This mirrors the #400/#404 split: build the gate, then burn down what it finds, rather than conflating gate-building with gate-satisfying.

### 5. Harness noise (`import.meta`/CommonJS) is separated from real error count before reporting
The initial audit's 1,574 included 10 `import.meta` failures (TS1343) caused by the test tsconfigs inheriting `module: commonjs` from `tsconfig.base.json`, not by anything wrong in the test files (vitest runs them as ESM). Setting `module: "esnext"` on the test configs (while leaving `moduleResolution` alone, so package resolution stays identical to the src typecheck) removed this noise, dropping the true count to 1,500. Reporting a corpus size that includes harness artifacts would have overstated the burn-down and misdirected effort toward files that were never actually broken.

### 6. A test-fixture conversion surfaced a real invariant question, and the fix went to the invariant, not the fixture
Converting the `ITrait`-literal cluster's fixtures to real constructors (GH #401's burn-down) made `DoorTrait`'s constructor throw on two stdlib tests that had silently been asserting against a one-sided door. The easy fix — invent a destination room id to satisfy the throw — would have made the fixture pass while meaning nothing. Instead the session investigated whether the throw was a real invariant (it wasn't: no ADR required it, the file's own header disputed it, and only 2 of 44 trait classes validated in-constructor) and, on David's ruling, removed the throw from both `DoorTrait` and `ExitTrait` (D7) and moved completeness-checking to the behavior/world-model layer where it already partly lived (`ExitBehavior.createBidirectional`, and now `WorldModel.connectRooms`'s new fill-in). ADR-346 records this as a general rule — traits are data, behaviors and callers police completeness — not a door-specific exception.

Trait constructors do not validate cross-field invariants (e.g. a `DoorTrait` no longer requires both `room1` and `room2` at construction); that responsibility moves to the behavior layer and to callers like `WorldModel.connectRooms`. D7 extends the same rule to `ExitTrait`, resolved via `/devarch:adr-interview`. Related: GH #401 (the test-file typecheck burn-down that surfaced the bug this ADR fixes).
- Pattern applied: capability/behavior separation from ADR-090's family — "traits are data, behaviors and callers police completeness," one level down from "behaviors own mutations, actions coordinate" (`docs/core-concepts/README.md`).
