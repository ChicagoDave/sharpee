## Phase 1 — Dissolve `main`, add `preferred-layout` (ADR-300 D8/D9) — COMPLETE

### The measurement that changed the phase

The plan's entry state predicted migrating 2921 `contains` assertions and
re-blessing 21 goldens. Measured first instead:

```
grep -rn "CHANNEL: *main" --include='*.transcript' stories/ tutorials/ | wc -l   → 0
grep -rn "^channels:" --include='*.transcript' stories/ tutorials/               → 1 file (channels: main, info)
```

**Zero** assertions name `main` explicitly. All 2921 read it *implicitly*,
through the turn text the harness composed from the `main` payload. So the
migration is not a corpus rewrite at all — it is a requirement that the
composed text stay byte-identical.

### Design

- Seven prose channels replace `mainChannel`: `room-name`, `room-description`,
  `room-contents`, `action-result`, `action-blocked`, `error`, `game-message`
  (append / **sparse** — a turn with no error emits no empty `error` array).
- `preferred-layout` (replace / **always**) carries the turn's reading order as
  one entry per prose entry, naming its source channel. A repeated id means
  that channel produced more than one entry, and each occurrence advances that
  channel's cursor — so interleaving (`['game-message','room-name','game-message']`)
  reconstructs exactly. A fixed render order cannot express this, which is why
  D9 rejects one.
- **`composeProse` is the shared rule**, in `@sharpee/channel-service`. Every
  surface composes identically: bootstrap, the CLI bundle, the browser, the IDE
  recording bridge, zifmia's pane.
- **Channel-id vocabulary moved to `@sharpee/if-domain`** (`PROSE_CHANNEL_IDS`,
  `PREFERRED_LAYOUT_CHANNEL`). It is wire protocol shared by producer and every
  consumer; a duplicated list is protocol drift waiting to happen (DEVARCH rule
  8b). stdlib keeps only the engine-side half — which block key routes where —
  typed on `ProseChannelId` so a route to an unknown id fails to compile.

### The one non-obvious client problem

The ADR-165 dispatcher calls `onValue` **per channel**, so seven independent
browser renderers would append in *manifest* order — a fixed order, exactly
what D9 rejects. Resolved by having the prose renderers **buffer** and the
`preferred-layout` renderer **flush** in composed order. That makes
registration order load-bearing: `preferred-layout` must be registered after
every prose channel. Stated as an invariant in `STANDARD_CHANNELS` and pinned
by a test rather than left as a latent trap.

## The stopping point

ADR-302 D8 left one implementation question open, and the plan named it the
plan's only genuine unknown with the instruction to **stop and raise a negative
result rather than engineer around it**. Measured against the real
`EngineRandomService`:

| mechanism | point that **drew** in the parent | point that did **not** draw |
| --- | --- | --- |
| master `seed:` override | **inert** | applies |
| `point-seed:` override | **inert** | applies |
| `forces:` | applies | applies |

Cause: `streamFor` resolves `restoredState ?? pointSeedOverride ??
deriveStreamSeed(masterSeed, name)` — a restored state outranks **both** seed
instruments. Correct for ADR-293 D7, and exactly what makes seed-based
variation from a shared state impossible.

Worse than the anticipated risk: the plan expected `point-seed:`/`forces:` to
survive; the measured answer is **`forces:`-only**.

Recorded in ADR-302 as a measured table under D8 plus an **AMENDMENT PENDING**
note in Consequences with three candidate shapes. Deliberately did **not** open
an Open Questions section — that flips an ACCEPTED ADR to DRAFT (DevArch rule
11a), which is David's call.

## Phase 5's seed question — resolved, not just measured

The stopping point recorded at the last checkpoint turned out not to be a
stopping point. David's call, mid-session: *"I just want the correct
branch→seed process to work properly."* Rather than amend ADR-302 D5/D8's
variation semantics to `forces:`-only, the engine gained a third session
instrument. `restore` keeps its ADR-293 D7 contract untouched (a plain restore
is unchanged, so every linear chain — Dungeo's 17-file, Fernhill's spine —
still reproduces one continuous run). A new operation runs *after* restore:
`EngineRandomService.reseedStreams(points)` drops the named points' stream
continuity so they re-derive through the ordinary `seed:`/`point-seed:` chain
instead of reading the restored state. No save-format change — one artifact,
read two ways. No ADR-293 amendment — reseeding is recorded there as a third
instrument, same species as forces and point-seed (session state, never
serialized). This closed the open question the previous checkpoint raised;
Phases 6–11 all build on it.

## Phases 6–9 — every one complete

- **Phase 6 (tree runner, D10) — COMPLETE.** `src/tree-runner.ts` walks the
  tree depth-first, not a loop over paths — each node's commands run exactly
  once, a divergent tail resumes from a save of its parent's end state. One
  save per parent, restored before *every* child including the first, which is
  what makes sibling order not matter (in theory — Phase 10 found the
  exception). Reseed wired: keys on what a child *declared*, never what it
  inherited. AC-1 and AC-5 pinned on executed command count, not wall-clock —
  a fork over a 2-command spine executes 4 commands, not 6.
- **Phase 7 (reporting, D13) — COMPLETE.** `src/tree-report.ts`: a broken
  interior node reports as one failure with N descendants `unreached`,
  originating node named — not one failure per descendant. AC-7 pinned:
  1 failed, 4 unreached, origin named, healthy sibling still runs.
- **Phase 8 (rename, D14) — COMPLETE.** `src/rename.ts`, validate-then-write.
  Turned out to be **five** things, not the ADR's four: the golden's
  *provenance* (`transcript:`, checked against basename every replay per
  ADR-294 D3) has to move with the file, or the next run reports a stale
  recording. AC-8 pinned by snapshotting every file's bytes before and after a
  rejected rename and asserting byte-equality.
- **Phase 9 (assertion vocabulary, D13/D14) — COMPLETE.** Needed one additive
  platform change first: `@sharpee/bootstrap` gained `lastChannelValues`
  (structured, alongside the existing flattened `lastChannels`) because a
  dotted path can't read a flattened line and a flattened line can't be
  un-flattened. Three load-bearing, non-obvious rules in the new
  `[CHANNEL: id.path, …]` grammar: a path onto a list matches **any** element
  (no index a test could name); a wrong-type comparison fails **by name**
  (`is 5` against text `"5"` says so and suggests `is "5"`, rather than just
  not matching); and `is absent` is distinct from emptiness, so `not contains`
  on a silent channel points the author at the right assertion instead of
  passing for the wrong reason. Capture set is now inferred from
  `channelsReferencedBy(assertions)`, unioned with any declared `channels:`.

**Issue #226 — found by running the real tree, and it was three stacked
defects, not one:**

1. **NPC behaviour state never serialized** — the `getState`/`setState`
   contract on NPC behaviours was dead: nothing captured it into the save,
   nothing restored it out.
2. **The tree runner never revived an engine stopped by a `*-lose` branch** —
   a losing leaf halts the engine, and the walk needed to resume the next
   sibling from a live one.
3. **`captureSave` swallowed its own errors** — which is what made the first
   two defects unreadable and produced two wrong diagnoses before the real
   cause surfaced. Removing the swallow is what made the bug legible.
4. Plus a fourth, found while fixing the others: the **scheduler's
   `setState` merged instead of resetting** — a restore left scheduler residue
   from the previous sibling's subtree instead of a clean reset
   (`0cf8f0fb fix(scheduler): a restore is a reset, not a merge`).

**Lesson recorded in the commits**: reading the two `setState` implementations
would have taken 30 seconds and shown both were pure assignments — doing that
first would have prevented the first wrong attempt at a fix. The error-swallow
removal, not any of the three substantive fixes, is what made the actual
defects visible. Filed, fixed, and closed same-session: `dc652b3f` (find),
`0cf8f0fb` (scheduler fix, partial), `79181f9f` (rebuild after reverted NPC
state attempts), `3b95e260` (restore leaves no residue between siblings —
close).
