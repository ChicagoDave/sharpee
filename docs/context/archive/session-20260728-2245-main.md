## Completed

### Checkpoint affordance (D4)
`PlayHeaderView` gains a Checkpoint button beside Bless, reading back the standing mark
(blue "Checkpoint ✓"), plus Test → **Checkpoint Here (⇧⌘K)**. The key equivalent exists for
the same reason Bless needed one: while playing, focus sits in the story's own input field,
where a menu shortcut fires and a button click does not. `RecordingSession` gained
`canCheckpointLatestTurn` / `toggleCheckpointOnLatestTurn()`, mirroring the bless gesture —
the same press marks and un-marks.

Two rules stated deliberately rather than falling out of the code:
- **A blank response still takes a checkpoint**, unlike a bless. A checkpoint says where the
  author reached, not that the text was right. Pinned by a test so the asymmetry reads as a
  decision.
- **A checkpointed turn is the LAST turn of its segment.** The gesture is pressed after seeing
  the turn that finished a chapter — "this far", not "from here" — so a trailing checkpoint on
  the final turn adds no empty segment.

### Chain naming and placement
New `tools/ide/SharpeeIDE/Test/WalkthroughChain.swift`: pure naming/placement, no file writing
and no AppKit, so the save flow's question ("append after what is here, or replace it?") is
answered by something tests drive directly. `plan(segmentCount:slug:in:mode:)` returns the
destinations plus what a replace clears.

Numbering is strict about the two-digit zero-padded form because **filename sort IS run order**
(ADR-277 D3, no manifest): `wt-9-…` sorts after `wt-10-…`, so it reads as a stray rather than
being silently renumbered around. `wt-100-…` likewise — D4 puts chains past 99 out of scope,
and a stray is the loud failure rather than the silent one.

### Stray warning and replace
`WalkthroughChain.warning(strays:)` names every stray and says why it matters: the directory IS
the chain, so a stray runs in it wherever its filename sorts, and appending numbered segments
beside one interleaves the two. Nil is also the save sheet's signal not to offer replace at all.
Replace clears every `.transcript` present — strays included, since a replace that left one
behind would still interleave — and leaves non-transcripts alone.

### Save flow
`saveRecording()` branches on `hasCheckpoints`: unmarked sessions keep Phase 2's save panel into
`tests/transcripts/` (D3); checkpointed ones get a sheet naming the chain, because the author is
not naming one file — the flow names N of them, and where they land is fixed by the fact that
the directory is the chain. `configureRecording(saveDirectory:)` became
`configureRecording(storyDirectory:)`, with the Play pane deriving both ADR-280 classified
paths, so the two locations are known in one place instead of one being passed in pre-resolved.

### FOUND AND FIXED — a replace could delete the files it had just written
`writeChain` writes the new segments before clearing the superseded ones (so a failure part-way
through a replace leaves the author with both chains rather than neither), and skips removing
anything the new chain just wrote over. It compared URLs to decide that — but `removing` comes
back from a directory listing (`/private/var/…`) while `files` are built from a passed-in path
(`/var/…`), so the same file compared unequal and **every reused segment name was deleted after
being written**. A replace under the same chain name would have destroyed its own output.
Identity is now the filename, which is exactly right for files in a single directory.

Caught because a test asserted on the plan's contents rather than on the save "succeeding".

## Key Decisions

### 1. A checkpoint closes the segment it sits on
"This far", not "from here" — matching when the gesture is actually pressed during play. Makes a
trailing checkpoint a no-op rather than an empty trailing file.

### 2. Checkpointing does not require a blessable response
Bless and checkpoint are different claims. Blessing says the text was right (so a blank response
carries no affordance); a checkpoint says where the author reached, which is true of any turn.

### 3. Strict two-digit numbering, with non-conforming names treated as strays
Filename sort is the chain's run order with no manifest, so a name that does not sort correctly
cannot be trusted as a chain position. Renumbering around it silently would produce a chain that
runs in an order nobody chose.

### 4. Replace clears strays too
A replace that cleared only the numbered files would leave the stray running in the new chain —
the exact interleave the author chose replace to avoid.

### 5. Acceptance 4's state-carry claim is proved by a failure, not a pass
A chain of three independent transcripts would pass a `--chain` run too. The proof is running the
same three files a second time WITHOUT `--chain`, where each is a fresh game, and requiring the
last segment to fail.
