## Work done

- **Root cause** (deeper than stale defaults): AppKit's split-view frame
  autosave restores while the window is at its pre-appearance fitting width
  (the window briefly shrinks when contentViewController is assigned). Play
  gets squashed to its 240 minimum; the regrowth all goes to the editor
  (lowest holding priority). The persisted frames in `net.sharpee.ide` were
  actually near-equal (play 562) — restore itself was the bug, every launch.
- **Fix (MainWindow.swift)**: `splitView.autosaveName` dropped for the main
  split; manual persistence instead — project/play pane widths saved to
  `SharpeeIDEMainSplitProjectWidth`/`...PlayWidth` on
  `NSSplitView.didResizeSubviewsNotification`, gated on
  `didApplyInitialLayout` so pre-appearance constraint churn can't clobber
  them. `viewDidAppear` applies saved-or-default positions via `setPosition`;
  no saved widths → equal editor|play split. Legacy autosave frames key is
  ignored (left in defaults, harmless).
- **Tests (SplitDividerTests)**: `testOpensWithEqualEditorPlaySplitByDefault`
  (legacy frames present + clean width keys → equal, play > 400) and
  `testUserDragPersistsAcrossRelaunchAtCurrentVersion` (drag to 300,
  relaunch, still 300). Both save/restore the defaults keys they touch.
  A first-cut layout-version reset was implemented then discarded — the
  relaunch test correctly failed it (restore re-squashed play next launch).
- **Orphaned tests removed** (David's ruling on last session's open item #2):
  BuildSettingsTests, BuildSettingsStoreTests, StoryDetectorTests,
  PackageDetectorTests, IntrospectionRunnerTests, ProjectManifestTests;
  xcodegen regenerated.
