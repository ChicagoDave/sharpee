- Was demoted from Phase 1 early in the session on evidence that shipped releases go through Xcode's Distribute App, which already signs `Contents/Frameworks` correctly (verified: 1.0.1's `libswift_Concurrency.dylib` carried a correct Developer ID signature timestamped 1s before the outer app). - `package.sh` now enumerates every nested code bundle (`*.xpc`, `*.app`, `*.framework`) and loose Mach-O under `Contents/Frameworks`, sorted deepest-first, and asserts Team ID (not just `codesign --verify --deep --strict`, which passes on *any* valid signature, including one that isn't ours) on each.
- Three bugs found in the fix itself, two silent: (1) bash 3.2 mis-parsed a comment inside `<( )` because "Sparkle's" contains an apostrophe — loud, `bash -n` passed, only running failed; (2) the `.app/` exclusion matched the *absolute* path (which contains `Chord Writer.app/`), excluding every file in the bundle from signing — silent, would have left `libswift_Concurrency.dylib` unsigned again; (3) excluding `.framework` contents dropped Sparkle's `Autoupdate` helper, which a framework's own signature does not cover — silent.

## Key Decisions

### 1. Phase order changed twice on the same evidence question
The Phase 6 demotion answered "is this gap blocking the path releases currently take?" — a narrower question than "is this gap blocking?" — and stayed right for hours until Phase 3's real-path test changed the path. Recorded in-plan as a lesson.

### 2. ADR-279 Amendment A2 — GitHub Releases withdrawn from D6
The GitHub Releases URL had been carried in the ADR without verification; `curl` confirmed sharpee.net serves artifacts directly and no GitHub tag scheme is in use. Corrected at David's explicit direction rather than built against as written.

### 3. ADR-279 Amendment A3 — per-architecture appcasts required
Sparkle has no architecture filter of its own; `generate_appcast` emits `hardwareRequirements arm64` on the Apple silicon side only, so a single combined feed would offer the wrong slice to the wrong Mac.

### 4. `notarize_artifact` recovers submission ids from history
The notarytool crash-after-accept pattern was already a documented recurrence in `package.sh`'s header before tonight; rather than treat each occurrence as a one-off retry, the recovery path is now built into the pipeline itself.
