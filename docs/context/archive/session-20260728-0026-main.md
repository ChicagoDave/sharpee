### 4. Build bootstrap repair (largest unplanned finding)
David had re-cloned into `repos/sharpee` after working in `sharpee_v2`, so the checkout had no `node_modules` and no `dist/` — effectively a fresh clone, deliberately used as a test of whether the documented clone-to-build steps actually work. They did not. Four distinct defects, all fixed in `tools/repokit` and verified by `./repokit clean && ./repokit build dungeo` succeeding twice with no `tsf` step in between:
1. **Load-time devkit dependency** — `cli.ts` → `build.ts` → `browser.ts`/`playground.ts` imported `@sharpee/devkit` at top level, making devkit's `dist/` a prerequisite for running any repokit command, including the one that builds devkit. Converted to lazy `require` behind a function, with erased type-only imports so no signatures are duplicated. `ifid.ts` had the identical problem with `@sharpee/core`.
2. **`clean` deleted repokit itself** — `pnpm -r run clean` swept all workspace packages including `@sharpee/repokit`, removing its own `dist/` mid-run. `clean` now excludes `@sharpee/repokit`.
3. **devkit loaded to stat a directory** — version stamping calls `chordStoryFile` on every build, pulling in all of devkit for eight lines of `readdirSync`. Extracted as `findChordStoryFile` in `tools/repokit/src/repo.ts`, with a comment explaining the deliberate non-import.
4. **Silent no-op breaking every browser build** — found only because the IDE suite regressed 251/0 → 251/4 after a clean. Per-package `clean` scripts remove `tsconfig.tsbuildinfo` but not `tsconfig.esm.tsbuildinfo`; the stale file makes the ESM pass emit nothing and exit 0. `dist-esm/` never returns, and since `@sharpee/*` resolve through the `import` condition, browser builds die with "Could not resolve @sharpee/platform-browser". `clean` now sweeps every `*.tsbuildinfo` under packages/tools/stories/tutorials, skipping `node_modules` and repokit.
- NEW tests: `tools/repokit/src/commands/clean.test.ts` (6, covering sweep scope and the repokit/node_modules exclusions) and `tools/repokit/src/repo.test.ts` (4). repokit suite: **54 passing, 1 skipped.**

## Key Decisions

### 1. ADR-279 chosen as the family's entry point
It is the hard prerequisite (`Parent:`) for ADR-280 D3, ADR-281's help-index step, and ADR-284 D1; ADR-287 is the only sibling independent of it and was explicitly carved out of scope.

### 2. ADR-258 D8 split into "discard stale entry" vs. "migrate on identity change"
Recorded directly on ADR-258 rather than left implicit in ADR-279, so the distinction is available to any future session that touches persisted IDE state — not just this one.

### 3. `PRODUCT_MODULE_NAME` stays `SharpeeIDE` through the rename
Decouples the user-facing product identity (which changes) from the Swift module identity (which ~15 test files depend on via `@testable import`), avoiding a mechanical rename across the whole test suite for a cosmetic change.

### 4. Defaults migration is domain-wide, not key-by-key
AppKit's own autosave keys (split-view divider widths) aren't enumerable by the app, so a key-by-key copy would silently drop state a full-domain copy preserves. The legacy domain is left in place rather than deleted, matching the ADR-258 D8 ruling.

### 5. Build bootstrap fixes centered on breaking devkit's load-time coupling
Rather than reordering the build pipeline, the fix targets the actual defect: repokit's own commands imported devkit eagerly, making devkit's build output a prerequisite for building devkit. Lazy `require` plus the `tsconfig.esm.tsbuildinfo` sweep were both minimal, targeted fixes rather than a broader pipeline redesign.
