## What was done

**1. Deterministic genai-api docs (`2de1c4d1`, `cdb690d4`)**
`scripts/generate-genai-api.js` stamped a wall-clock timestamp into
`packages/sharpee/docs/genai-api/index.md`, so every build rewrote the file with no
content change. That left the tree permanently dirty and blocked a fast-forward
pull. Replaced it with the platform version read from `packages/sharpee/package.json`
via a new `readPlatformVersion()` helper, which falls back to `unknown` so docs
generation never fails on a missing manifest. Verified by running the generator
twice: byte-identical output (md5 match). Later regenerated to `3.6.0`, where only
the stamp line moved, confirming the `.d.ts` surface did not change between releases.

**2. `@sharpee/stdlib@3.6.0` ships a stale ENGINE_VERSION (`7dc2275b`)**
The 3.6.0 release bumped 32 manifests but never ran a stamping build, so stdlib
compiled against the previous value. Confirmed by downloading the published tarball:
`package/actions/standard/version/engine-version.js:8` reads `3.5.0` while the
manifest reads `3.6.0`. Impact is narrow: that constant is the fallback version
banner for Chord `.story` stories, which carry no stamped `src/version.ts` of their
own, so authors on 3.6.0 see `3.5.0` from `version`. TypeScript stories are
unaffected. Stamped the repo to `3.6.0` and committed.

**3. CI publish flow would have automated the bug (`fd784578`)**
`docs/publish/npm-ci.md` (landed mid-session as `6f577685`) specified
`pnpm run build` as the CI build step. That is `turbo run build`, which compiles
without calling repokit's `stampVersions()`, so CI would publish whatever
`engine-version.ts` happened to be committed. Switched the step to `./repokit build`
(which stamps first, `build.ts:214-237`), added a `git diff --exit-code` guard so an
incomplete release commit fails the job instead of publishing, added tarball
verification to Part D, and documented the 3.6.0 evidence as §1.4.

**4. genai-api docs are repo-only (`406a3af1`)**
Traced why `docs/genai-api/` never reached npm despite `files: ["dist", "docs"]`.
Two causes: tsf deletes `files` from the publish manifest outright
(`sync/package-json.js:143`), and staging receives only compiled output, the
generated manifest, README/LICENSE, and the `assets` globs from the package's own
`ts-forge.json` (`orchestrator/index.js:220-250`) — and
`packages/sharpee/ts-forge.json` is `{"assets": []}`. Per the user's decision the
docs stay out (the IDE will carry them), so the claims were corrected rather than
the behavior: dropped the dead `docs` entry from `files`, dropped the `genai`
manifest field (which survived into the published tarball pointing at an unshipped
`./docs/genai-api/` and a `./GENAI.md` that exists nowhere), and fixed the "ships
with the npm package" wording in `CLAUDE.md`, `packages/sharpee/CLAUDE.md`, and the
generator header.

## Key decisions

- **Leave `@sharpee/stdlib@3.6.0` as published; 3.7.0 corrects it.** npm forbids
  overwriting a version, and a stdlib-only 3.6.1 would break lockstep versioning for
  a misreported banner. Recorded as npm-ci.md §10.4.
- **genai-api docs are not published to npm.** The IDE ships the reference, so npm
  need not carry 1.3 MB of generated markdown per install. Recorded as §10.5. If
  this reverses, it is a one-line change to `{"assets": ["docs/**"]}`, the pattern
  `packages/devkit` uses for its templates.

## Diagnosed, not changed (needs user action)

- **esbuild's 26 `"esm"` condition warnings.** Every manifest carries a dead `esm`
  key in `exports`, ordered after `import`/`require` and pointing at the same target
  as `import` (verified across all 38 keys in 32 files: none differ, none ordered
  first). It is generated by tsf from `ts-forge.config.json`'s
  `targets.esm.condition: "esm"` (`sync/package-json.js:306-313`), and that field is
  load-bearing — `repokit build.ts:164,206` invoke `tsf build --condition esm`. So
  it cannot be fixed from Sharpee: hand edits get regenerated, and deleting the field
  breaks ESM target selection. The fix belongs in tsf, either skipping a custom
  condition whose path already matches a standard one, or adding `esm` to the
  internal condition set. Warnings only; resolution is correct today.
- **Website `npm audit` reports 9 high-severity vulnerabilities.** All nine trace to
  one root, `brace-expansion`'s DoS, reached via `minimatch` → eslint and
  `eslint-config-next`. Lint toolchain only, no runtime exposure.
