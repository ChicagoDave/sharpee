## Completed — Part 1: ADR-231 Amendment 1 (the blocker)

P-4's blocker read: *"ADR-231 D2a deleted `.hasTrait()` on the premise that '.where()
function constraints remain the one parse-time gating mechanism' … That mechanism does not
exist — `entity-slot-consumer.ts:480` warns 'FunctionConstraint in slot constraints not yet
supported' and evaluates nothing, so Sharpee currently has **no** working parse-time
gating."*

Reading it against the code and the prior delivery record found **two errors**:

1. **"Function constraints" means the scope-callback form**, `.where(slot, scope => …)`
   (`ScopeConstraintBuilder`), not the type named `FunctionConstraint`
   (`(entity, context) => boolean`). ADR-273 reads D2a that way throughout — "the `.where()`
   mechanism ADR-231 D2a designates" — and its Consequences record that ADR-273 made exactly
   this path work: *"Parse-time scope gating works for the first time."*
2. **Parse-time gating exists and works.** The scope-callback form is evaluated end to end:
   `entity-slot-consumer.ts` builds the `ScopeConstraint`, and
   `grammar-scope-resolver.ts:82-93` applies its base scope, its `filters` (from
   `ScopeBuilder.matching()`), and its `traitFilters` (from `ScopeBuilder.hasTrait()`). D2a
   deleted only *rule-level* `.hasTrait()`; the scope-builder's survives.

That second point had already been settled once. `docs/work/player-surface-contracts/pins.md`
PIN 4 pinned it before delivery as "a same-name/different-type conflation" — two fields both
called `traitFilters`, one dead (rule-level `SlotConstraint`), one live (`ScopeConstraint`
inside `.where()`) — and Phase 4 shipped on that pin (`f56b88fa`, zero parse-behavior change).
**The blocker is the same conflation one level up**, this time between the prose phrase
"function constraints" and the type `FunctionConstraint`.

So the discharge is a **clarifying amendment**, not the "implement function constraints in
the slot consumer" fork the finding offered. `adr-231-player-surface-contract-rulings.md`
gains **Amendment 1 (2026-07-31, session ec1c25)**, placed directly under the Status line so
no reader meets the ambiguous D2a sentence first. It pins what the phrase names, records that
the property and function forms never gated at any point (their branches only ever
`console.warn`ed), confirms the `.hasTrait()` deletion is unaffected, and states that
narrowing `.where()` *discharges* the ruling rather than contradicting it — it removes the
two forms that never gated and leaves the designated mechanism as the only thing `.where()`
accepts. Original Context / Decision / Consequences left intact.

## Key Decisions

### 1. Amend ADR-231 rather than implement function constraints
The blocker offered two paths; both rested on the premise that parse-time gating was dead.
It is not, so the work is to pin what D2a's sentence names, not to build a mechanism to
satisfy a misreading of it.

### 2. Remove the `Constraint` union outright
Narrowing `.where()` left it with no consumer. Leaving an exported union that still advertises
three constraint forms would have re-created P-3's finding on the next tracker pass.

### 3. Convert the two constraint tests instead of deleting them
The forms did not disappear from the platform, only from `.where()`. `matching()` still takes
and evaluates both, so the coverage moves to the surface where it is real.

### 4. Drop the annotation at a production call site, not only in a probe
Source absence is not proof, and a scratch probe proves it once. `loader.ts:1343` is
typechecked by every `tsf build`, so the inference claim cannot silently regress.

### 5. Do not edit the v1.5.0 book edition
It correctly documents its own platform version.
