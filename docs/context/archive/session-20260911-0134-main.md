## What 5.3.2 is — David's framing (2026-09-11)

**What started the effort: the Chord `playable` syntax had never been connected to the platform.**
ADR-327 D9 (2026-08-26) gave Chord `playable` and `change the player to <character>`; the analyzer
refused a non-`playable` target from that day on. The loader step that would write
`ActorTrait.isPlayable` from `irEntity.isPlayable` was never implemented, and the trait's class
default was `true` — so every actor in every story read as playable, and `switchPlayer`'s guard
(`game-engine.ts:793`) could never fire. The language said one thing and the runtime knew nothing
about it: exactly the two-sided alignment failure core-concepts names.

**Which led to several other seams** (David). Pulling on it produced four ADRs in five days:

| ADR | Seam it opened | Landed |
| --- | --- | --- |
| ADR-343 | `StoryEngine` role interface for `onEngineReady` | `eca36867a` |
| ADR-344 | The player role holder belongs at the install seam — D7 connects `playable` to the runtime and flips the default to `false`; D6 removes `EngineOptions.player` (the engine never receives a player at construction); D5 removes the loader's first-declared-room placement fallback | `f63455aaa`…`70096ec9a` |
| ADR-345 | The engine lifecycle phase becomes an explicit concept — found because ADR-344 Phase 2's last failing test was a symptom: D6a had made an `installStory` guard unreachable | `9d63352f9`…`b2981a776` |
| ADR-346 | Traits do not police completeness — `DoorTrait`/`ExitTrait` fields are optional while a story is still composing the passage | `4c1eacebb` |

The gate work that rode along (#400, #401, #404, #402, #410) is the second thread in this release:

### **The finding underneath it: npm 11 does not run `pre<script>` hooks**

All five of the site's derived-artifact scripts — `sync-versions`, `sync-chord-ebnf`, `sync-roadmap`, `sync-releases`, `build-search-index` — were wired **only** into `prebuild`/`predev`. Under npm 11.11.0 those never fire.
