### Phase 2 — update-apply survival (DONE, sub-question 2 = YES, unassisted)
Full record: `docs/work/velopack-macos-bundle-layout/evidence/phase-2-update-apply.md`.
- The plan's entry-state fork resolved empirically: the apply path DOES run against an unsigned bundle, so Phase 2 needed no keychain and stayed before Phase 3.
- Key finding: `vpk pack` accepts a pre-built `.app` as `--packDir` and passes its `Contents/` tree through unchanged (probed with a 3-file throwaway bundle first). The relocation therefore belongs BEFORE the pack step — the `.nupkg` then carries the relocated layout natively and no post-apply hook is required.
- One failed pack, reported to the user before any retry per CLAUDE.md's no-auto-retry rule: feeding `vpk` the already-packed Phase 1 bundle collided on `sq.version` in `OsxPackCommandRunner.PreprocessPackDir` (`overwrite: false`). Fixed by building the `.app` from `out/publish` instead, matching what a real build does.
- Full round trip through the real `UpdateMac apply` path: delta reconstruction in 4.45s (the delta engine is a plain file-tree differ with no layout assumptions); apply recreated 235 symlinks; layout survived; seal scan clean; app and bundled toolchain both run.
- Sizes/timing (`phase2-apply-round-trip.txt`): full 99,908,968 / delta 8,274,247 bytes, pack 28.4s — against Phase 5's flat-layout baseline of full 99,829,165 / delta 8,114,592 bytes, 34.5s. The relocation costs nothing measurable.
- Condition discovered: an apply from a package built out of an **unsigned** app destroys the bundle seal — this reproduces Phase 5's exact prior failure. Packing with `--signAppIdentity` instead puts `_CodeSignature` inside the `.nupkg`; applying that package leaves the installed bundle sealed and `codesign --verify --deep --strict` clean (`Sealed Resources version=2 rules=13 files=9985` both post-apply and on a fresh install from the same signed package — confirms determinism, not a one-off pass).
